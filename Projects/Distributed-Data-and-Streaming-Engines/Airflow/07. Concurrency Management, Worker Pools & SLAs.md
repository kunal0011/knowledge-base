## 1. Canonical Motivation & Theoretical Foundation

In an enterprise Airflow deployment shared by dozens of analytics, engineering, and data science teams, hundreds of DAGs run concurrently. Without strict concurrency controls, resource contention quickly causes operational chaos:
1. **Target System Overload:** An unthrottled DAG launching 200 parallel database extraction queries can inadvertently cause a Denial-of-Service (DoS) on production OLTP databases.
2. **External API Rate Limiting:** Scraping third-party REST APIs without concurrency limits triggers immediate HTTP 429 (Too Many Requests) errors and IP bans.
3. **Noisy Neighbor Starvation:** A massive historical backfill running thousands of non-urgent tasks can occupy every worker slot in the cluster, blocking critical 9:00 AM executive dashboards from running.

Airflow resolves these challenges through a multi-tiered **Concurrency Hierarchy**, **Worker Pools**, and **Priority Weighting**.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Airflow Concurrency Hierarchy

Airflow evaluates task scheduling eligibility through a strict cascade of independent resource gates:

```
                            [ Task Ready to Execute ]
                                        │
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │ Gate 1: Global Parallelism (core.parallelism)       │ (Max tasks running across entire cluster)
             └──────────────────────────┬──────────────────────────┘
                                        │ PASS
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │ Gate 2: DAG Active Runs (max_active_runs)           │ (Max concurrent DagRuns for this DAG)
             └──────────────────────────┬──────────────────────────┘
                                        │ PASS
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │ Gate 3: DAG Task Concurrency (max_active_tasks)     │ (Max tasks running concurrently within this DAG)
             └──────────────────────────┬──────────────────────────┘
                                        │ PASS
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │ Gate 4: Worker Pool Capacity (Pool Slots)           │ (Available slots in the assigned named Pool)
             └──────────────────────────┬──────────────────────────┘
                                        │ PASS
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │ Gate 5: Priority Weight Ordering                    │ (Sorts eligible tasks by priority_weight)
             └──────────────────────────┬──────────────────────────┘
                                        │ HIGHEST PRIORITY
                                        ▼
                             [ Enqueued to Worker ]
```

### Worker Pools Architecture
A **Pool** is a named logical bucket with a fixed integer number of slots (e.g. `postgres_pool: 8 slots`, `salesforce_api_pool: 2 slots`):
- When a task is assigned to a pool, it must claim available slots before entering the `QUEUED` state.
- Tasks can declare **`pool_slots`**: a heavy Spark submission task might consume `pool_slots=4`, claiming half of an 8-slot pool.

### Priority Weight Engine & Weight Rules
When multiple tasks compete for limited pool slots, Airflow breaks ties using **`priority_weight`**. Airflow calculates effective weights dynamically based on the configured **`weight_rule`**:
- **`WeightRule.DOWNSTREAM` (Default):** The effective priority of a task is the sum of its own weight plus the weights of **all tasks downstream of it**. This ensures tasks that unblock large downstream execution trees are prioritized first.
- **`WeightRule.UPSTREAM`:** Sum of weights of all upstream tasks.
- **`WeightRule.ABSOLUTE`:** Uses strictly the integer value assigned to that task alone.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Service Level Agreements (SLAs)

An **SLA** in Airflow represents the maximum allowed duration a task or pipeline may take to complete, measured relative to the start of the data interval:

```python
def sla_alert_webhook(dag, task_list, blocking_task_list, slas, blocking_tis):
    """Sends webhook notification to PagerDuty or Slack on SLA breach."""
    print(f"CRITICAL SLA BREACH in DAG {dag.dag_id}!")

# Configure on DAG or Task:
dag = DAG(..., sla_miss_callback=sla_alert_webhook)
task = BashOperator(..., sla=timedelta(hours=2))
```

## 4. Practical Systems & Production Use Cases

1. **Protecting Production Read Replicas:** Assigning all reporting queries to a dedicated `oltp_read_replica_pool` capped at 5 slots to prevent database CPU saturation.
2. **Third-Party API Rate Limiting:** Restricting Stripe or Salesforce ingestion tasks to a 2-slot pool to comply with enterprise API tier quotas.
3. **Critical Path Fast-Tracking:** Assigning `priority_weight=100` to revenue attribution pipelines while assigning `priority_weight=1` to internal telemetry DAGs.

## 5. Annotated Code Implementations & Execution Traces

### Production DAG with Custom Pools, Multi-Slot Weights & SLA Miss Handling

The following production Python DAG demonstrates the use of custom pools, weighted scheduling, heavy multi-slot consumption, and SLA miss alerts:

```python
"""
Production Concurrency Management DAG.
Demonstrates:
  - Custom pool assignment and multi-slot consumption (pool_slots=4)
  - Priority weight calculation with downstream propagation
  - SLA configuration and breach callback integration
"""

from datetime import datetime, timedelta
import logging

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.empty import EmptyOperator
from airflow.utils.weight_rule import WeightRule

logger = logging.getLogger(__name__)


def handle_sla_miss(dag, task_list, blocking_task_list, slas, blocking_tis):
    """Callback invoked when task breaches configured SLA."""
    logger.error(
        f"SLA MISS TRIGGERED for DAG [{dag.dag_id}]! "
        f"Tasks missing SLA: {[t.task_id for t in task_list]}. "
        f"Blocking tasks: {[t.task_id for t in blocking_task_list]}"
    )


with DAG(
    dag_id="concurrency_managed_pipeline_v1",
    schedule_interval="0 4 * * *",  # Daily at 04:00 UTC
    start_date=datetime(2026, 1, 1),
    catchup=False,
    max_active_runs=1,     # Only 1 concurrent run of this DAG allowed
    max_active_tasks=8,    # Max 8 concurrent tasks within this DAG
    sla_miss_callback=handle_sla_miss,
    default_args={
        "owner": "core-platform",
        "retries": 1,
        "retry_delay": timedelta(minutes=5),
        "sla": timedelta(hours=3),  # Entire pipeline should finish within 3h of interval start
    },
    tags=["concurrency", "pools", "sla"],
) as dag:

    start = EmptyOperator(task_id="start_pipeline")

    # Task 1: API Scraper throttled by dedicated external API pool
    # Uses priority_weight=50 to jump ahead of non-critical tasks
    api_extraction = BashOperator(
        task_id="extract_external_api_data",
        bash_command="echo 'Querying third-party API under strict rate-limit...' && sleep 3",
        pool="third_party_api_pool", # Pool capped at 2 slots in cluster config
        pool_slots=1,
        priority_weight=50,
        weight_rule=WeightRule.DOWNSTREAM,
    )

    # Task 2: Heavy database extraction claiming 4 pool slots simultaneously
    # Consumes half of an 8-slot DB pool to protect database CPU
    heavy_database_dump = BashOperator(
        task_id="extract_large_db_table",
        bash_command="echo 'Executing high-volume bulk extraction...' && sleep 5",
        pool="production_postgres_pool", # Pool capped at 8 slots
        pool_slots=4,                    # Consumes 4 slots!
        priority_weight=20,
    )

    # Task 3: Transformation on compute cluster
    transform_data = BashOperator(
        task_id="transform_lakehouse_data",
        bash_command="echo 'Running transformation...' && sleep 2",
        priority_weight=10,
    )

    end = EmptyOperator(task_id="end_pipeline")

    start >> [api_extraction, heavy_database_dump] >> transform_data >> end
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Global Parallelism DB Starvation Trap
- **Antipattern:** Setting `core.parallelism = 512` in `airflow.cfg` while keeping PostgreSQL's `max_connections = 100`.
- **System Consequence:** Under heavy load, 512 worker processes spin up concurrently. Each worker attempts to open multiple connections to the metadata database. The database connection pool is immediately exhausted, throwing `OperationalError: FATAL: remaining connection slots are reserved for non-replication superuser connections`. The entire cluster crashes.
- **Fix:** Size `core.parallelism` proportionally to your database connection pool and use connection pooling proxies (e.g. PgBouncer).

### 2. Assuming Pools Limit Physical CPU / Memory
- **Antipattern:** Believing that assigning a task to a 2-slot pool restricts its memory usage to 2GB.
- **System Consequence:** Pools are **purely logical scheduling counters** inside the scheduler. Airflow pools enforce zero OS-level or container-level cgroup constraints. If a task assigned to a 1-slot pool consumes 64GB of RAM, it will still crash the worker.
- **Fix:** Enforce physical hardware limits via Kubernetes resource requests and limits (`KubernetesPodOperator`).

### 3. Retroactive SLA Miss Storms on Historical Backfills
- **Antipattern:** Running `airflow dags backfill` on a DAG with an active `sla` configured.
- **System Consequence:** Historical backfills process dates months or years in the past. Because the current time is far past the historical SLA deadline, Airflow fires hundreds of retroactive SLA miss emails and Slack webhooks, spamming on-call channels.
- **Fix:** Disable SLA notifications during historical backfills or ensure alerting scripts verify that `context['dag_run'].run_type != DagRunType.BACKFILL_JOB`.
