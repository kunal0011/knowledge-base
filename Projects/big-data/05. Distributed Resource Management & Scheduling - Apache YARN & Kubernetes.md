## 🏛️ 1. The Death of MapReduce 1.0 & The Birth of YARN

In original Hadoop 1.0, the **JobTracker** daemon was responsible for two fundamentally distinct tasks simultaneously:
1. **Cluster Resource Management:** Tracking CPU and memory slots across all worker nodes.
2. **Job Lifecycle Monitoring:** Supervising every individual map and reduce task, tracking retries, and handling task failures.

### The 4,000-Node Scalability Bottleneck
At $\approx 4,000\text{ nodes}$ and $40,000\text{ concurrent tasks}$, the JobTracker's single JVM collapsed under lock contention, memory exhaustion, and heartbeat processing overhead.

**Apache YARN (Yet Another Resource Negotiator)** introduced in Hadoop 2.0 solved this by strictly separating cluster resource allocation from individual application supervision:

```text
===================================================================================================
                                     APACHE YARN ARCHITECTURE
===================================================================================================

  Client Submits Spark Job
             │
             ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │                           YARN RESOURCE MANAGER (Cluster Master)                            │
  │                                                                                             │
  │  ┌─────────────────────────────────────────┐  ┌──────────────────────────────────────────┐  │
  │  │          ApplicationsManager (ASM)      │  │            Pluggable Scheduler           │  │
  │  │ (Accepts jobs, spawns initial AppMaster)│  │ (Fair Scheduler, Capacity Scheduler, DRF)│  │
  │  └─────────────────────────────────────────┘  └──────────────────────────────────────────┘  │
  └──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                                 │ Allocates Container for ApplicationMaster
                                                 ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │                                    WORKER NODES (NodeManagers)                              │
  │                                                                                             │
  │  [ Worker Node 1 (NodeManager) ]                 [ Worker Node 2 (NodeManager) ]            │
  │  ┌──────────────────────────────┐                ┌──────────────────────────────┐           │
  │  │ Container: ApplicationMaster │◄── Heartbeats ─┤ Container: Spark Executor 1  │           │
  │  │ (Supervises Spark DAG)       ├────────────────┤ (Executes compute task)      │           │
  │  └──────────────────────────────┘                └──────────────────────────────┘           │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

## ⚙️ 2. Core YARN Components & Lifecycle

1. **ResourceManager (RM):** The ultimate cluster authority. Tracks global resource availability across all nodes via NodeManager heartbeats.
2. **NodeManager (NM):** The per-node worker agent. Meters physical CPU and memory consumption using Linux **cgroups**, enforcing container limits.
3. **ApplicationMaster (AM):** A lightweight, job-specific coordinator. When a job is submitted, the RM launches the AM inside a container on an arbitrary worker node. The AM negotiates additional resource containers from the RM and directly coordinates its own worker tasks.
4. **Resource Container:** A logical allocation of resources (e.g., $4\text{ vCPUs}$ and $16\text{ GB RAM}$).

## ⚖️ 3. YARN Scheduling Policies & Dominant Resource Fairness (DRF)

In multi-tenant clusters where hundreds of data engineers share compute, YARN provides three scheduling paradigms:

### 3.1 FIFO vs. Capacity vs. Fair Scheduler
- **FIFO Scheduler:** Jobs execute strictly in arrival order. A 10-hour batch ETL job blocks an urgent 2-second interactive SQL query indefinitely.
- **Capacity Scheduler (Yahoo):** Partitions cluster into hierarchical queues (e.g., `prod` gets $70\%$, `dev` gets $30\%$). Allows elastic borrowing of idle capacity while guaranteeing minimum SLAs.
- **Fair Scheduler (Meta):** Dynamically reallocates resources so that all active jobs receive an equal share of cluster capacity over time.

---

### 3.2 Dominant Resource Fairness (DRF)
In reality, workloads are multi-dimensional:
- Job $A$ is **CPU-heavy** ($2\text{ vCPUs}, 2\text{ GB RAM}$ per task).
- Job $B$ is **Memory-heavy** ($1\text{ vCPU}, 8\text{ GB RAM}$ per task).

**DRF** computes each job’s **dominant share** (the maximum percentage of any single cluster resource consumed):
$$\text{Dominant Share} = \max\left( \frac{\text{Allocated CPU}}{\text{Total Cluster CPU}},\ \frac{\text{Allocated RAM}}{\text{Total Cluster RAM}} \right)$$
The scheduler prioritizes the job with the **lowest dominant share**, mathematically guaranteeing Pareto-efficient, fair multi-resource allocation!

## ☸️ 4. The Cloud-Native Paradigm: Big Data on Kubernetes

Today, the industry is aggressively migrating from YARN to **Kubernetes (K8s)** as the universal orchestrator for both microservices and big data processing.

```text
===================================================================================================
                                  APACHE SPARK NATIVE ON KUBERNETES
===================================================================================================

  Data Engineer: spark-submit --master k8s://https://k8s-apiserver:6443 ...
       │
       ▼
  Kubernetes API Server
       │
       ├─ 1. Schedules Spark Driver Pod: [ spark-driver-pod ]
       │                                           │
       │                                           ▼
       │                          Driver contacts K8s API directly!
       │                          Requests 50 Executor Pods dynamically
       │                                           │
       ├─ 2. Kubernetes schedules:                 ▼
       │  [ spark-executor-pod-1 ]   [ spark-executor-pod-2 ] ... [ spark-executor-pod-50 ]
       │
       ▼ (Cloud Node Autoscaler / Karpenter launches EC2 instances on-demand!)
  AWS S3 / Cloud Data Lake (Processes petabytes directly via S3A connector!)
       │
       ▼ When job finishes: Executor pods TERMINATE! EC2 instances SCALE DOWN TO ZERO!
```

### 4.1 Why Kubernetes is Replacing YARN
1. **Unified Infrastructure Stack:** Operators manage a single Kubernetes platform instead of operating isolated YARN clusters alongside Kubernetes clusters.
2. **True Container Isolation:** Spark tasks run inside full OCI Docker containers with customized Python environments, CUDA GPU drivers, and isolated library versions.
3. **Dynamic Cloud Elasticity:** Kubernetes integrates natively with cloud autoscalers (Karpenter), provisioning spot instances for heavy ETL runs and deallocating them immediately upon job completion.
