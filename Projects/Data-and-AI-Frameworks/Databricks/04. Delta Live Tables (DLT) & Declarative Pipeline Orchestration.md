# Chapter 04: Delta Live Tables (DLT) & Declarative Pipeline Orchestration

> "Traditional Spark ETL pipelines are imperative: engineers write hundreds of lines of boilerplate managing checkpoint paths, cluster sizing, failure retries, and data validation loops. Delta Live Tables shifts the paradigm to declarative engineering: you declare what tables to build and what quality expectations to enforce; the DLT runtime optimizes the physical execution graph."  
> — *Databricks Delta Live Tables Architecture Guide*

## 1. Canonical Motivation & Theoretical Foundation

### The Friction of Imperative Spark ETL
Building production data pipelines with raw PySpark requires managing immense operational complexity:
1. **Checkpointing Overhead:** Every streaming query requires explicit configuration of `checkpointLocation`. A typo in the path causes data duplication or silent loss of streaming state.
2. **Infrastructure Sizing Guesswork:** Sizing clusters for varying batch workloads leads to either over-provisioned idle clusters or under-provisioned out-of-memory crashes.
3. **Absence of Native Data Quality:** Engineers must handcraft `try-catch` validation scripts or bolt on external testing frameworks. If bad data passes through, corrupt rows pollute the lakehouse.

### The Declarative DLT Paradigm
In **Delta Live Tables (DLT)**, the developer defines the **target state of data** using simple Python decorators (`@dlt.table`, `@dlt.view`) or SQL statements:
- **Automatic DAG Resolution:** DLT inspects table dependencies and builds the execution Directed Acyclic Graph automatically.
- **Automated Cluster Management:** Automatically provisions, autoscales, and terminates dedicated Enhanced Autoscaling clusters.
- **Built-in Quality Expectations:** Enforces data quality rules natively, logging metrics to an audit event log without slowing down execution.

### DLT Table Primitives: Streaming Tables vs. Materialized Views

```
┌────────────────────────────────────────────────────────────────────────────────┐
│ 1. Streaming Tables                                                            │
│    • Consumes append-only streaming sources (Kafka, Auto Loader).              │
│    • Processes each incoming row exactly once; maintains internal checkpoint.  │
│    • Syntax: dlt.read_stream("source_table")                                   │
├────────────────────────────────────────────────────────────────────────────────┤
│ 2. Materialized Views                                                          │
│    • Represents a query over one or more tables that updates incrementally.   │
│    • Ideal for aggregations, joins, and deduplication.                         │
│    • Syntax: dlt.read("source_table")                                          │
├────────────────────────────────────────────────────────────────────────────────┤
│ 3. Temporary Views                                                             │
│    • In-memory intermediate transforms that are NOT persisted to Delta storage.│
│    • Syntax: @dlt.view                                                         │
└────────────────────────────────────────────────────────────────────────────────┘
```

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Auto Loader (`cloudFiles`) Ingestion Engine
Auto Loader processes new data files as they arrive in cloud object storage without state degradation:
- **Directory Listing Mode:** Periodically scans storage prefixes (optimal for $< 1\text{M}$ files).
- **File Notification Mode:** Automatically provisions cloud messaging queues (AWS SQS / Azure Event Grid) to receive instant notifications as files are uploaded, scaling to **billions of files with zero S3 LIST calls**.
- **Rescued Data Column:** Corrupted rows or unexpected extra columns are automatically captured in a JSON `_rescued_data` column rather than crashing the pipeline.

---

### DLT Quality Expectations Matrix

| Decorator | Action on Violation | Use Case |
| :--- | :--- | :--- |
| `@dlt.expect("rule", "condition")` | Records metric in Event Log; **keeps row**. | Non-critical tracking (e.g. tracking null marketing referral codes). |
| `@dlt.expect_or_drop("rule", "condition")`| Records metric; **drops corrupt row**. | Cleaning bad inputs (e.g. dropping records with negative pricing). |
| `@dlt.expect_or_fail("rule", "condition")`| Records metric; **aborts entire pipeline**.| Critical primary keys or financial balance discrepancies. |

## 4. Practical Systems & Production Use Cases

### Pipeline Modes: Continuous vs. Triggered
- **Triggered Mode (Cost-Optimized Batch):** Clusters spin up, process all available pending data from Bronze to Gold, update tables, and immediately terminate. Ideal for hourly/nightly schedules.
- **Continuous Mode (Low-Latency Streaming):** Clusters stay online, streaming updates through Medallion tables with sub-10-second end-to-end latency. Ideal for fraud detection and live dashboards.

## 5. Annotated Production Implementations

### 1. Python DLT Pipeline: Complete Production Medallion Architecture
A complete declarative DLT script (`medallion_pipeline.py`) defining Bronze Auto Loader ingestion, Silver conformed deduplication with Expectations, and Gold aggregated KPI views.

```python
import dlt
from pyspark.sql.functions import col, current_timestamp, to_date

# -------------------------------------------------------------------------
# 1. BRONZE LAYER: Ingest raw streaming JSON via Auto Loader
# -------------------------------------------------------------------------
@dlt.table(
    name="bronze_orders_raw",
    comment="Raw streaming orders ingested via Auto Loader",
    table_properties={
        "quality": "bronze",
        "pipelines.autoOptimize.zOrderCols": "order_id"
    }
)
def bronze_orders_raw():
    return (
        spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", "/Volumes/enterprise_prod/schemas/orders_autoloader/")
        .option("cloudFiles.inferColumnTypes", "true")
        .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
        .load("s3://enterprise-lakehouse-prod-us-east-1/landing/orders/")
    )

# -------------------------------------------------------------------------
# 2. SILVER LAYER: Cleansed & Validated Table with Quality Expectations
# -------------------------------------------------------------------------
@dlt.table(
    name="silver_orders_clean",
    comment="Cleansed, typed, and validated customer orders",
    table_properties={"quality": "silver"}
)
@dlt.expect_or_fail("valid_order_id", "order_id IS NOT NULL")
@dlt.expect_or_drop("valid_customer", "customer_id IS NOT NULL")
@dlt.expect("positive_amount", "order_amount > 0.0")
def silver_orders_clean():
    return (
        dlt.read_stream("bronze_orders_raw")
        .select(
            col("order_id").cast("string"),
            col("customer_id").cast("string"),
            col("order_amount").cast("double"),
            col("status").cast("string"),
            col("timestamp").cast("timestamp").alias("order_time")
        )
        .withColumn("order_date", to_date(col("order_time")))
        .withColumn("_silver_processed_at", current_timestamp())
    )

# -------------------------------------------------------------------------
# 3. GOLD LAYER: Curated Materialized View for Executive Reporting
# -------------------------------------------------------------------------
@dlt.table(
    name="gold_daily_sales_kpis",
    comment="Aggregated daily revenue metrics for executive dashboards",
    table_properties={"quality": "gold"}
)
def gold_daily_sales_kpis():
    return (
        dlt.read("silver_orders_clean")
        .groupBy("order_date", "status")
        .agg(
            {"order_amount": "sum", "order_id": "count"}
        )
        .withColumnRenamed("sum(order_amount)", "total_revenue")
        .withColumnRenamed("count(order_id)", "order_count")
    )
```

### 2. SQL: Inspecting DLT Event Log for Quality SLA Metrics
Queries the internal DLT Event Log to calculate rule pass/fail percentages across production pipeline executions.

```sql
-- Query DLT Pipeline Quality Audit Event Log
SELECT 
    timestamp,
    message,
    details:flow_definition.output_dataset as dataset_name,
    details:flow_progress.metrics.num_output_rows as rows_processed,
    details:flow_progress.data_quality.expectations as quality_expectations
FROM event_log("a1b2c3d4-pipeline-id-guid")
WHERE event_type = 'flow_progress'
ORDER BY timestamp DESC
LIMIT 10;
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. Mixing Streaming and Batch Operations in DLT
- **The Pitfall:** Calling `dlt.read("table")` (batch read) inside a function that returns a stream, or calling `dlt.read_stream("table")` inside a function calculating non-incremental `groupBy()` aggregations.
- **Failure Mode:** DLT throws an `AnalysisException: Queries with streaming sources must be executed with writeStream`.
- **Rule:** Use `dlt.read_stream()` for **Streaming Tables** (Bronze/Silver append pipelines); use `dlt.read()` for **Materialized Views** (Gold analytical rollups and complex joins).

### 2. The Auto Loader Schema Drift Silent Failure
- **The Pitfall:** Running Auto Loader with `cloudFiles.schemaEvolutionMode = "none"`.
- **Failure Mode:** If upstream systems add a new column (e.g. `discount_code`), Auto Loader drops the column silently or routes data to `_rescued_data` without notifying the engineering team.
- **Remediation:** Set `cloudFiles.schemaEvolutionMode = "addNewColumns"` and configure pipeline alerts when schema evolution events are detected in the DLT event log.

### 3. Outage Triage: Pipeline Failure from `expect_or_fail`
- **Symptom:** A critical DLT pipeline halts at 02:00 AM with error: `FlowExecutionException: Expectation 'valid_order_id' failed`.
- **Root Cause:** Upstream payment microservice deployed a bug that emitted 5 records with `order_id = NULL`. Because the expectation was configured as `expect_or_fail`, the entire pipeline aborted.
- **Resolution:** For non-fatal errors, transition the rule to `@dlt.expect_or_drop` to quarantine bad rows while allowing the remaining 10 million valid transactions to flow to production dashboards.
