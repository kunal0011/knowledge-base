# Chapter 10: Distributed File Systems — NFS, AFS, GFS & Ceph

> "A distributed file system provides the illusion of a traditional local file system, yet its data is transparently distributed, replicated, and accessed across hundreds or thousands of networked machines. Designing such a system requires balancing three conflicting demands: transparency, consistency, and fault tolerance."  
> — *Andrew S. Tanenbaum & Maarten van Steen, Distributed Systems: Principles and Paradigms*

## 🌐 1. The Distributed File System (DFS) Abstraction & Core Challenges

A **Distributed File System (DFS)** transparently extends the operating system's Virtual File System (VFS) across a network. To user-space applications, reading or writing a file in a remote directory (`/mnt/shared/data.csv`) is indistinguishable from accessing a local NVMe SSD (`/home/user/data.csv`).

```text
===================================================================================================
                               DISTRIBUTED FILE SYSTEM ARCHITECTURE
===================================================================================================

  [ Client Machine 1 ]                                [ Client Machine 2 ]
  User Application (POSIX: open, read, write)         User Application (POSIX: open, read, write)
          │                                                   │
          ▼                                                   ▼
  Linux Virtual File System (VFS)                     Linux Virtual File System (VFS)
          │                                                   │
          ▼                                                   ▼
  DFS Client Driver (NFS / CephFS / FUSE)             DFS Client Driver (NFS / CephFS / FUSE)
          │                                                   │
          │ Local Client Cache (RAM / Disk)                   │ Local Client Cache (RAM / Disk)
          ▼                                                   ▼
  ═══════════════════════════════════════════════════════════════════════════════════════════════
                 Network Interconnect (TCP/IP, RPC, RDMA, Network Partitions, Latency)
  ═══════════════════════════════════════════════════════════════════════════════════════════════
                                             ▲
                                             │
                                             ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │                           DISTRIBUTED STORAGE SERVER CLUSTER                                │
  │                                                                                             │
  │   ┌───────────────────────────┐                      ┌───────────────────────────┐          │
  │   │  Metadata Server (MDS)    │                      │  Storage Daemons / OSDs   │          │
  │   │  (Namespace, Inodes,      │                      │  (ChunkServers, Block     │          │
  │   │   Directory Trees, Leases)│                      │   Replication, Disk I/O)  │          │
  │   └───────────────────────────┘                      └───────────────────────────┘          │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.1 The Four Dimensions of Distributed Transparency
1. **Location Transparency:** The file path reveals nothing about the file's physical server location.
2. **Access Transparency:** Identical system call interface (`open()`, `read()`, `write()`, `close()`) for both local and remote files.
3. **Migration Transparency:** Files can move across physical servers or storage pools without breaking client paths or active sessions.
4. **Replication Transparency:** Clients are oblivious to the number of physical replicas maintained behind the scenes.

### 1.2 The Fallacies of Distributed Systems in DFS
Unlike local disks (which fail fail-stop or return immediate I/O errors), distributed networks introduce:
- **Packet Drop and Unbounded Latency:** A client cannot distinguish between a dead server, an overloaded network, and a dropped acknowledgment packet.
- **Server and Client Crashes:** Either side can crash midway through an atomic multi-step operation.
- **Network Partitions:** The network can split into isolated halves, risking split-brain updates where two clients modify the same file concurrently.

## ⚖️ 2. File Sharing & Consistency Semantics

When multiple clients access and modify shared files concurrently, what guarantees does the file system provide? Classical OS literature categorizes four distinct models:

```text
===================================================================================================
                                FILE SHARING CONSISTENCY SEMANTICS
===================================================================================================

  Client 1:  open() ───────► write("A") ──────────────────────► close()
                                 │                                │
  Client 2:         open() ──────┼──────────────► read() ─────────┼───────► read()
                                 │                  │             │           │
  ───────────────────────────────┼──────────────────┼─────────────┼───────────┼────────────────────
  1. UNIX Semantics:             │ Reads "A" instantly            │ Reads "A"
                                 │ (Requires distributed locking) │
  ───────────────────────────────┼────────────────────────────────┼────────────────────────────────
  2. Session Semantics (AFS):    │ Reads OLD data (pre-open)      │ Reads "A" (only after close!)
                                 │ (Write-on-close flush)         │
  ───────────────────────────────┼────────────────────────────────┴────────────────────────────────
  3. Immutable Files (WORM):     │ Modification is forbidden! Files can only be created or replaced.
  ───────────────────────────────┼─────────────────────────────────────────────────────────────────
  4. Transactional Semantics:    │ Changes visible only after atomic COMMIT; rolled back on ABORT.
```

| Semantics | Mechanism | Pros | Cons | Real-World System |
| :--- | :--- | :--- | :--- | :--- |
| **UNIX Semantics** | Every single write is immediately visible to all concurrent readers on all nodes. | Intuitive; identical to local multi-process behavior. | Catastrophic scalability: requires distributed locks on every byte write and constant cache invalidations. | Local filesystems, clustered SAN filesystems (GFS2, OCFS2). |
| **Session Semantics** | Writes are buffered in the client's local cache during an open session; flushed to server atomically on `close()`. | High performance; clients read and write locally at RAM/disk speed. | "Last-Close-Wins" conflict: if two clients edit the file simultaneously, the second client's `close()` overwrites the first! | Andrew File System (AFS). |
| **Close-to-Open** | Modified blocks flushed on `close()`; reader invalidates its cache and checks server attributes on `open()`. | Practical compromise between Unix and Session semantics. | Mid-session writes are not guaranteed to be visible to already-open readers. | Sun NFS (Network File System). |
| **Append-Only** | In-place overwrites are disallowed; concurrent clients only append new chunks or records. | Eliminates complex write locking; trivially scalable. | Requires specialized non-POSIX application APIs. | Google File System (GFS), Hadoop HDFS. |

## 💾 3. Client Caching & The Invalidation Dilemma

Without client-side caching, every `read()` and `write()` must traverse the network, crippling performance. However, caching introduces the **Cache Consistency Problem**: if Client 1 caches File $X$ and Client 2 updates File $X$ on the server, how does Client 1 discover that its cached copy is stale?

```text
===================================================================================================
                         CACHE INVALIDATION: CLIENT POLL VS. SERVER CALLBACK
===================================================================================================

  [ Method 1: Client Polling / TTL (NFS Style) ]
  Client                                                  Server
    │                                                       │
    │─── GETATTR(file.txt) ────────────────────────────────►│ (Client asks: "Has mtime changed?")
    │◄── mtime = T_server, TTL = 30s ───────────────────────│
    │                                                       │
    │ [Satisfies all reads from local cache for 30 seconds] │
    │ ⚠️ Risk: If another client writes at T+5s,             │
    │   Client continues reading STALE data until T+30s!    │

  [ Method 2: Server Callbacks / Leases (AFS Style) ]
  Client                                                  Server
    │                                                       │
    │─── FetchFile(file.txt) ──────────────────────────────►│
    │◄── File Data + "Callback Promise" ────────────────────│ (Server pledges: "I will alert you!")
    │                                                       │
    │ [Reads from local cache indefinitely with 0 network!] │
    │                                                       │
    │                                      (Another client writes & closes file.txt)
    │                                                       │
    │◄── BreakCallback(file.txt) ───────────────────────────│ (Server invalidates Client's cache)
    │ [Client purges local copy; fetches fresh version]     │
```

### 3.1 Lease-Based Cache Consistency
What happens if the server in Method 2 crashes or a network partition severs communication? The server would be blocked forever waiting to contact unreachable clients before permitting a write.

The industry solution is **Leases**:
- A lease is a time-bounded callback promise (e.g., valid for 60 seconds).
- While the lease is active, the client is guaranteed that the file will not be modified by others.
- If the lease expires, the client must renew it before reading cached data.
- If a client becomes unreachable, the server simply waits for the 60-second lease timer to expire before granting write access to another client, guaranteeing safety without indefinite deadlocks!

## 🏛️ 4. Stateless vs. Stateful Server Architectures

A foundational architectural decision in distributed systems (highlighted in *OSTEP*) is whether storage servers maintain state across RPC calls.

```text
===================================================================================================
                            STATELESS VS. STATEFUL SERVER ARCHITECTURE
===================================================================================================

  [ Stateless Server: NFS v2 / v3 ]                 [ Stateful Server: AFS / NFS v4 / CephFS ]

  Client sends self-contained RPC:                  Client establishes persistent session:
  READ(FileHandle, Offset=4096, Length=1024)        open("/dir/file.txt") -> returns File Descriptor 3
          │                                                 │
          ▼                                                 ▼
  Server needs ZERO memory of client:               Server tracks in RAM:
  - No open file tables                             - Active client sessions
  - No client connection state                      - Open file descriptors & current file offsets
  - No seek position tracking                       - Active locks and client callback promises
          │                                                 │
  Server Crashes & Reboots:                         Server Crashes & Reboots:
  - Client just sleeps and retries RPC!             - Disaster! Server loses all lock and open state!
  - Server reboot is 100% INVISIBLE to client!      - Requires complex recovery: Grace Periods,
                                                      Re-lease negotiations, Client lock reclamation.
```

### 4.1 Idempotency & The NFS File Handle
To enable statelessness, NFS requires every Remote Procedure Call (RPC) to be **Idempotent**:
$$\text{Exec}(x) \equiv \text{Exec}(\text{Exec}(x))$$
Executing an idempotent operation once has the exact same effect as executing it ten times.
- `READ(offset, length)` is inherently idempotent.
- `WRITE(offset, length, data)` with an absolute file offset is idempotent.
- But `APPEND(data)` is **NOT** idempotent (repeating it appends the data multiple times!).

#### The Anatomy of an NFS File Handle (`nfs_fh`)
Because a stateless server does not maintain open file descriptors, every request transmits an opaque identifier called a **File Handle**:
```c
struct nfs_fh {
    uint32_t fsid;       /* Filesystem identifier (which disk partition) */
    uint64_t inode_num;  /* Internal filesystem inode number */
    uint32_t generation; /* Generation count (detects deleted/reused inodes!) */
};
```
If a file is deleted and its inode is reassigned to a new file, the server uses the `generation` counter to return `ESTALE` (Stale File Handle) rather than silently serving the wrong file!

## 📁 5. Case Study 1: Sun's Network File System (NFS)

Developed by Sun Microsystems in 1984, **NFS** became the ubiquitous standard for network storage in Unix environments.

### 5.1 Protocol Evolution: NFSv3 vs. NFSv4

| Dimension | NFSv3 (RFC 1813) | NFSv4 (RFC 7530) |
| :--- | :--- | :--- |
| **Server State** | **Stateless**: Uses auxiliary daemons (`mountd`, `lockd`, `statd`). | **Stateful**: Integrated locking, compound RPCs, lease-based open files. |
| **Transport & Ports** | Multi-port nightmare: Uses Portmapper (port 111) and dynamic RPC ports. Firewall unfriendly. | Clean single well-known TCP port: **Port 2049**. |
| **Security** | Primitive: Relies on client UID/GID trust (`AUTH_UNIX`). Trivially spoofed! | Robust: Mandatory Kerberos 5 integration (`RPCSEC_GSS`), user identity strings (`user@domain`). |
| **Compound RPCs** | No: Opening, seeking, reading, and closing a file requires 4 round-trip network hops. | **Yes**: Bundles `LOOKUP + OPEN + READ + CLOSE` into a single combined network RPC! |
| **Caching Model** | Close-to-open with periodic attribute polling (`acregmin`, `acregmax`). | File Delegations: Server grants temporary read/write delegation leases to clients. |

### 5.2 The NFS Close-to-Open Consistency Model
NFS compromises between full consistency and performance through **Close-to-Open Consistency**:
1. When Process $A$ calls `close()`: The NFS client blocks until all dirty buffer cache pages are flushed to the remote server disk.
2. When Process $B$ calls `open()`: The NFS client invalidates its local cache and fetches the file's latest modification time (`mtime`) from the server. If `mtime` matches its cached value, it reuses cached data; otherwise, it purges its cache and re-reads from the server.

## 🏛️ 6. Case Study 2: The Andrew File System (AFS)

Developed at Carnegie Mellon University (CMU) and commercialized by Transarc/IBM, **AFS** prioritized massive institutional scalability ($10,000+$ client workstations on campus).

```text
===================================================================================================
                                       AFS WORKSTATION PIPELINE
===================================================================================================

  User Application: open("/afs/cs.cmu.edu/user/alice/paper.tex")
           │
           ▼
  [ AFS Cache Manager (Venus Daemon) ]
           │
           ├─► Check Local Workstation Disk Cache (/usr/vice/cache)
           │
  ┌────────┴──────────────────────────┐
  ▼ Cache HIT (Callback Valid)        ▼ Cache MISS (or First Open)
  Open file directly from local disk! Contact Server (Vice Daemon):
  Zero network latency!               - Fetches ENTIRE file to local disk
  Runs at native local NVMe speed!    - Server registers a "Callback Promise"
           │                          - Caches file permanently on client disk
           ▼                                   │
  Application edits and writes...              ▼
  Calls close():                               Application reads/writes locally...
  - Flushes entire file back to Vice!          Calls close():
  - Vice sends "Callback Breaks"               - Transmits modifications to Vice
    to all other workstations!
```

### 6.1 Why AFS Outperformed NFS at Scale
1. **Whole-File Caching on Local Disk:** NFS caches individual pages in RAM. AFS caches entire files on the client's local hard disk. Even if the server reboots or the network goes down, clients can read already-cached files uninterrupted.
2. **Callbacks instead of Polling:** NFS clients bombard the server with `GETATTR` packets every few seconds to check for updates. AFS clients never ask; the server notifies them only when a change occurs. Server CPU load is reduced by over $90\%$.

## 🏢 7. Case Study 3: Google File System (GFS) & Hadoop HDFS

Published in 2003 by Sanjay Ghemawat, Howard Gobioff, and Shun-Tak Leung, the **Google File System (GFS)** (and its open-source counterpart **Hadoop HDFS**) revolutionized storage for massive data-parallel analytics (MapReduce, BigQuery).

### 7.1 Radical Design Assumptions
1. **Commodity Components Fail Continuously:** Thousands of nodes mean disk crashes, network switches failing, and memory bit-flips happen hourly. Fault tolerance must be an automated, constant process.
2. **Files are Massive:** Standard files are $100\text{ GB}$ to multi-terabytes in size. Managing millions of $4\text{ KB}$ blocks wastes metadata memory.
3. **Appends Dominate:** Random in-place overwrites virtually never happen. Workloads consist of appending web crawls, log streams, and sequential scans.
4. **Co-Design with Applications:** Relaxing strict POSIX standards allows dramatic architectural simplifications.

```text
===================================================================================================
                                 GOOGLE FILE SYSTEM (GFS) ARCHITECTURE
===================================================================================================

                    ┌─────────────────────────────────────────────────────────┐
                    │                       GFS MASTER                        │
                    │  - Namespace / Directory Hierarchy in RAM               │
                    │  - File-to-Chunk Mapping (64 MB Chunk Size)             │
                    │  - Chunk replica locations (3x Replication)             │
                    │  - Operation Log & Checkpoints (Disaster Recovery)      │
                    └────────────────────────────┬────────────────────────────┘
                                                 │
                         1. Metadata Request     │ 2. Returns Chunk Handles
                            ("Where is Chunk 3?")│    & Replica IP Addresses
                                                 │
  ┌───────────────────────────────┐              │
  │          GFS CLIENT           │◄─────────────┘
  └──────────────┬────────────────┘
                 │
                 │ 3. Direct Data Stream (Master is completely out of the data path!)
                 ▼
  ┌───────────────────────────────┐  Pipelined Transfer  ┌───────────────────────────────┐
  │   ChunkServer A (Primary)     ├─────────────────────►│  ChunkServer B (Secondary)   │
  │   - Stores 64 MB chunk on     │                      │  - Replicates chunk to disk   │
  │     local Linux ext4 disk     │                      └───────────────┬───────────────┘
  └───────────────────────────────┘                                      │ Pipelined Transfer
                                                                         ▼
                                                         ┌───────────────────────────────┐
                                                         │  ChunkServer C (Secondary)   │
                                                         │  - Replicates chunk to disk   │
                                                         └───────────────────────────────┘
```

### 7.2 The 64 MB Chunk Size Innovation
Standard OS pages are $4\text{ KB}$; GFS chunks are **$64\text{ MB}$**.
- **Metadata Fits in Master RAM:** A $1\text{ Petabyte}$ cluster requires only $\approx 16,000,000$ chunk mappings. The entire metadata table fits inside a few gigabytes of server RAM, enabling instant lookup without disk seeks!
- **Reduced Network Overhead:** Clients establish a single TCP connection and stream tens of megabytes sequentially.

### 7.3 Chunk Leases & Atomic Record Append
When multiple clients concurrently append logs to the same file:
1. The Master grants a **Lease** to one ChunkServer, designating it as the **Primary**.
2. The Primary dictates the exact serialization order of all concurrent writes.
3. **Atomic Record Append (`RecordAppend`):** Guarantees that client data is appended atomically *at least once* at an offset chosen by GFS, even under concurrent writes from dozens of parallel workers.

## 🐙 8. Case Study 4: Ceph & The CRUSH Algorithm

While GFS scales to petabytes, its centralized Master remains a single point of failure and bottleneck for billions of small files. **Ceph** (created by Sage Weil) achieves exabyte-scale storage with **zero centralized metadata lookup** for data blocks.

```text
===================================================================================================
                                      CEPH ARCHITECTURE LAYERS
===================================================================================================

  Application Interfaces:
  ┌───────────────────────────┐ ┌───────────────────────────┐ ┌───────────────────────────┐
  │  CephFS (POSIX File Sys)  │ │  RBD (Block Storage/VMs)  │ │  RGW (S3/Swift Object API)│
  └─────────────┬─────────────┘ └─────────────┬─────────────┘ └─────────────┬─────────────┘
                │                             │                             │
                └─────────────────────────────┼─────────────────────────────┘
                                              ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │                            RADOS (Reliable Autonomic Distributed Object Store)              │
  │                                                                                             │
  │   CRUSH Algorithm: [ Object ID ] + [ Cluster Map ] ──► Computes Physical OSD IDs in CPU!   │
  │                                                                                             │
  │  ┌────────────────────┐  ┌────────────────────┐  ┌────────────────────┐  ┌────────────────┐ │
  │  │   Ceph OSD 1       │  │   Ceph OSD 2       │  │   Ceph OSD 3       │  │   Ceph OSD 4   │ │
  │  │ (NVMe / BlueStore) │  │ (NVMe / BlueStore) │  │ (NVMe / BlueStore) │  │ (NVMe/BlueStore│ │
  │  └────────────────────┘  └────────────────────┘  └────────────────────┘  └────────────────┘ │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 8.1 The CRUSH Algorithm (Controlled Replication Under Scalable Hashing)
In traditional systems (NFS, GFS), the client queries a centralized lookup table: *"Which server holds File A?"*

In Ceph, **there is no lookup table!** The client calculates the exact target disk using a deterministic, pseudo-random mathematical function:
$$\text{Target OSDs} = \text{CRUSH}(\text{Object ID},\ \text{Cluster Map},\ \text{Placement Rule})$$

#### Why CRUSH is Revolutionary:
1. **Algorithmic Complexity $\mathcal{O}(1)$:** Both clients and storage nodes independently compute where any object belongs in microseconds of CPU math.
2. **Failure-Domain Awareness:** CRUSH rules encode the physical topology of the datacenter:
   ```text
   rule replicate_across_datacenters {
       step take root
       step chooseleaf datacenter
       step emit
   }
   ```
   CRUSH mathematically guarantees that replicas of an object are placed on servers in **different physical racks, power circuits, and availability zones**!
3. **Autonomic Self-Healing:** When a storage drive dies, surviving OSDs detect the failure via peer heartbeats, recalculate CRUSH placements, and replicate missing data among themselves without human intervention.

## 🩺 10. Production Troubleshooting & Disaster Scenarios

### 10.1 The `ESTALE` (Stale File Handle) Nightmare in NFS
```text
 Application receives error:
 [errno 116] ESTALE: Stale file handle

 Root Cause:
 1. Client opens File A; holds File Handle containing Inode #4012, Gen=1.
 2. On the server, an admin or script deletes File A (rm file_a).
 3. Server filesystem frees Inode #4012.
 4. Server creates a new File B, re-allocating Inode #4012 with Gen=2.
 5. Client transmits: READ(Inode #4012, Gen=1).
 6. Server detects generation mismatch (Gen 1 != Gen 2) -> Rejects request with ESTALE!

 Resolution:
 - Re-mount the NFS share on the client to refresh the dentry and inode cache.
 - In application code, handle ESTALE by explicitly closing and re-opening the path.
```

### 10.2 Split-Brain in Distributed File Systems
When network links between storage nodes break, each partition may believe the other has died:
```text
                    [ Network Partition Break ]
     Data Center US-East                     Data Center US-West
     ┌────────────────────────┐              ┌────────────────────────┐
     │ Node A elects itself   │              │ Node B elects itself   │
     │ Primary Leader!        │              │ Primary Leader!        │
     │ Accepts client writes: │              │ Accepts client writes: │
     │ file.txt = "Version 1" │              │ file.txt = "Version 2" │
     └────────────────────────┘              └────────────────────────┘
```
**Production Fix:** Modern distributed file systems strictly forbid unilateral promotion. Leaders can only be elected if they secure a **Quorum** ($> 50\%$ of votes, $Q = \lfloor \frac{N}{2} \rfloor + 1$) via consensus protocols (Raft, Paxos). The minority partition immediately enters read-only mode, guaranteeing data integrity!
