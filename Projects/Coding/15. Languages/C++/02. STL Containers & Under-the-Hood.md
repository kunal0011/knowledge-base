## 2. `std::vector` Internals

On 64-bit platforms, a `std::vector` object itself is exactly **24 bytes** on the stack, consisting of three raw pointers:

```
Stack Frame (24 bytes):
+-------------------------------------------------------------+
| T* _M_start           -> Pointer to first allocated element |
| T* _M_finish          -> Pointer one past the last element  |
| T* _M_end_of_storage  -> Pointer to end of allocated buffer |
+-------------------------------------------------------------+
       |                  |                  |
       v                  v                  v
Heap: [ e0 | e1 | e2 | e3 | uninitialized... |
      <---- size() ------>
      <-------------- capacity() ------------>
```

### 2.1 Growth Factors: GCC/Clang ($2.0\times$) vs MSVC ($1.5\times$)
When capacity is exceeded during `push_back()`:
- **GCC / Clang:** Doubles capacity ($2.0\times$).
- **MSVC:** Multiplies capacity by $1.5\times$.

```
Why 1.5x is mathematically advantageous:
With a 2.0x factor:
Allocations: 1, 2, 4, 8, 16, 32...
Notice: 1 + 2 + 4 + 8 + 16 = 31 < 32.
The new memory block is always strictly larger than the sum of all previously
freed blocks. The OS allocator can never reuse prior contiguous addresses!

With a factor < 1.618 (e.g., 1.5x):
Allocations: 4, 6, 9, 14, 21, 32...
Later allocations can fit into the consolidated memory left behind by earlier allocations.
```

### 2.2 `reserve()` vs `resize()`
- `v.reserve(N)`: Allocates capacity for $N$ elements on the heap without constructing objects. `size()` remains unchanged. Prevents reallocation overhead.
- `v.resize(N)`: Changes `size()` to $N$, default-constructing new elements if growing, or calling destructors if shrinking.

### 2.3 `push_back()` vs `emplace_back()`
- `push_back(val)`: Takes an object by `const T&` or `T&&`. Requires a temporary to be constructed and then moved/copied into the vector.
- `emplace_back(args...)`: Forwards constructor arguments directly to `placement new` in uninitialized memory, constructing the object directly inside the buffer.

### 2.4 The `std::vector<bool>` Anomaly
`std::vector<bool>` is a specialized template that packs booleans into individual bits ($8$ booleans per byte).
**Gotcha:** It does **not** return a true `bool&` from `operator[]`; it returns a temporary proxy object (`std::vector<bool>::reference`).
```cpp
auto& b = v[0]; // COMPILE ERROR! Cannot bind non-const lvalue reference to proxy object!
```

## 3. Small String Optimization (SSO) in `std::string`

Heap allocations via `malloc` carry latency and CPU cache miss overhead. To optimize short strings, modern C++ implementations utilize **Small String Optimization (SSO)**.

```
std::string Internal Layout (Union):
+-----------------------------------------------------------------+
| Heap Mode:                                                      |
|   char* data_ptr  (8 bytes) -> Pointer to heap string           |
|   size_t size     (8 bytes)                                     |
|   size_t capacity (8 bytes)                                     |
+-----------------------------------------------------------------+
| SSO Mode (Strings <= 15 or 22 characters):                      |
|   char local_buffer[16 or 24 bytes]  (Resides directly on STACK)|
|   - Zero heap allocation!                                       |
+-----------------------------------------------------------------+
```

- In **libc++** (Apple/LLVM): Strings up to **22 bytes** fit within SSO stack buffer.
- In **libstdc++** (GCC): Strings up to **15 bytes** fit within SSO stack buffer.
Passing short strings or creating temporary tokens incurs zero heap allocation overhead.

## 4. `std::unordered_map` Under the Hood

`std::unordered_map` is implemented using **Separate Chaining with a vector of buckets and singly-linked list nodes**.

```
Bucket Array (std::vector<Node*>):
[ 0 ] -> Node("key1", val) -> Node("key7", val) -> nullptr
[ 1 ] -> nullptr
[ 2 ] -> Node("key3", val) -> nullptr
[ 3 ] -> nullptr
```

### 4.1 Rehashing & Load Factor
$$\text{Load Factor} = \frac{\text{size}}{\text{bucket\_count}}$$
- When the load factor exceeds `max_load_factor()` (default: $1.0$), the container doubles the bucket count and rehashes every key.
- Node pointers remain valid across rehashing; only the bucket table itself reallocates.

### 4.2 Cache Locality Drawback
Because each bucket entry is a separately allocated heap node (`Node*`), searching an `unordered_map` involves **pointer chasing** across fragmented heap memory, causing frequent CPU L1/L2 cache misses.

## 5. `std::deque`: The Chunked Buffer Deque

Unlike `std::vector` (single contiguous buffer) or `std::list` (individual node per element), `std::deque` uses a **two-level chunked architecture**:

```
Map (Array of Pointers):
+-------+-------+-------+-------+
| Ptr0  | Ptr1  | Ptr2  | Ptr3  |
+-------+-------+-------+-------+
    |       |       |       |
    v       v       v       v
[Block 0] [Block 1] [Block 2] [Block 3]  (Each block is a 512-byte fixed array)
```

### Properties:
1. **$\mathcal{O}(1)$ Push/Pop at Both Ends:** Can prepend or append elements without relocating existing elements.
2. **Reference Stability:** Pushing elements to either end of a deque **never invalidates pointers or references** to existing elements (only iterators may be invalidated).

## 6. `std::priority_queue`: Max-Heap Default Trap

In C++, `std::priority_queue` is a container adapter over `std::vector` that defaults to a **MAX-HEAP** (using `std::less<T>`), directly opposite to Java and Python!

```cpp
// 1. DEFAULT: MAX-HEAP (Largest element on top)
std::priority_queue<int> max_heap;
max_heap.push(10);
max_heap.push(30);
max_heap.push(20);
std::cout << max_heap.top(); // Prints 30!

// 2. MIN-HEAP: Requires 3 template parameters: Type, Container, Comparator
std::priority_queue<int, std::vector<int>, std::greater<int>> min_heap;
min_heap.push(10);
min_heap.push(30);
min_heap.push(20);
std::cout << min_heap.top(); // Prints 10!
```
