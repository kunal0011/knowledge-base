### 1.1 Device Addressing: PMIO vs. MMIO
1. **Port-Mapped I/O (PMIO):** Uses dedicated CPU instructions (`in` and `out` on x86) and a distinct 16-bit I/O address space. Legacy design; rarely used for modern high-speed peripherals.
2. **Memory-Mapped I/O (MMIO):** The device's hardware control registers and on-board memory buffers are mapped directly into the CPU's physical address space. The CPU reads and writes to device hardware using standard memory instructions (`mov`, `load`, `store`), governed by MMU page tables.

## ⚡ 2. Polling, Interrupts & Direct Memory Access (DMA)

The OS coordinates data transfers using three evolutionary techniques:

```text
===================================================================================================
                               DATA TRANSFER MECHANISMS COMPARISON
===================================================================================================

 [ 1. Polling ]                      [ 2. Interrupts ]                   [ 3. Direct Memory Access (DMA) ]
 CPU spins checking Status Reg       CPU tells device: "Read sector"     CPU programs DMA Engine:
 while (reg->status == BUSY);        CPU runs other tasks!               - Src: Disk Controller
 -> Wastes 100% CPU on slow disk!    Device fires electronic IRQ         - Dst: RAM 0x8000000
                                     CPU traps to Interrupt Handler      - Len: 64 KB
                                     -> Eliminates CPU busy-waiting!     DMA transfers data directly to RAM!
                                                                         Fires 1 interrupt when DONE.
                                                                         -> Zero CPU copying overhead!
```

### 2.1 Linux Two-Half Interrupt Architecture
Servicing hardware interrupts must be fast; holding interrupts disabled risks dropping subsequent hardware packets. Linux splits interrupt handling into two distinct phases:
- **Top Half (HardIRQ):** The immediate interrupt handler executed with CPU hardware interrupts disabled. Acknowledges hardware, reads critical status registers, queues work, and returns immediately ($\approx 1\ \mu\text{s}$).
- **Bottom Half (SoftIRQ / Tasklets / Workqueues):** Executes asynchronously with interrupts re-enabled. Handles heavy data processing (e.g., parsing TCP/IP packets, filesystem buffer allocation).

## 💽 3. Hard Disk Drives (HDD): Geometry & Physics

A classical magnetic hard drive stores data on rotating magnetic platters read by robotic mechanical arms.

```text
===================================================================================================
                                  HARD DISK DRIVE (HDD) PHYSICS
===================================================================================================

                         Spindle Center
                              │
                    ┌─────────▼─────────┐
                    │  Track (Ring)     │ ◄── Head seeks radially (Seek Time)
                    │  ┌─────────────┐  │
                    │  │   Sector    │  │ ◄── Platter rotates under head (Rotational Latency)
                    │  │  (512 B /   │  │
                    │  │    4 KB)    │  │
                    │  └─────────────┘  │
                    └───────────────────┘
```

### 3.1 Total I/O Service Time Equation
$$T_{\text{I/O}} = T_{\text{seek}} + T_{\text{rotational}} + T_{\text{transfer}}$$
- **Seek Time ($T_{\text{seek}}$):** Physical mechanical movement of the arm to the target track ($4\text{ to }10\text{ ms}$). This is the single slowest operation in computing!
- **Rotational Latency ($T_{\text{rotational}}$):** Waiting for the platter to rotate the sector under the head. At $7200\text{ RPM}$, a full rotation is $8.3\text{ ms}$; average latency is half a rotation ($\approx 4.16\text{ ms}$).
- **Transfer Time ($T_{\text{transfer}}$):** Electronic transfer of data off the media ($\approx 50\ \mu\text{s}$).

## ⚡ 4. Solid-State Drives (SSD) & Flash Memory Physics

Unlike magnetic platters, **Solid-State Drives (SSDs)** have zero moving parts, constructed from non-volatile **NAND Flash Memory**.

### 4.1 The Fundamental Asymmetry of Flash
Flash memory operates under strict physical silicon constraints:
1. **Read:** Performed at **Page Granularity** ($4\text{ KB} - 16\text{ KB}$) in $\approx 10\ \mu\text{s}$.
2. **Write (Program):** Performed at **Page Granularity** in $\approx 100\ \mu\text{s}$.
3. **Erase:** CANNOT be performed at page granularity! Erase operations can only be performed across an entire **Block** (composed of $128\text{ to }512\text{ pages}$, typically $2\text{ MB} - 8\text{ MB}$) in $\approx 2\text{ ms}$!

> [!IMPORTANT]
> **The Flash Invariant:** You cannot write (program) a Flash page that already contains data! To overwrite a single byte in Page 4, the entire $4\text{ MB}$ block must be erased first!

## 🧬 5. The Flash Translation Layer (FTL) & Wear Leveling

To hide the erase-before-write constraint from operating systems (which expect ordinary block interfaces), SSDs incorporate an embedded computer system: the **Flash Translation Layer (FTL)**.

```text
===================================================================================================
                                  FTL LOG-STRUCTURED WRITING
===================================================================================================

  OS issues: Write Logical Block Address (LBA) 50
       │
       ▼
  FTL does NOT overwrite physical Page 50!
  1. Writes data to a new, empty, pre-erased physical page (e.g., Physical Page 200).
  2. Updates internal LBA-to-PBA mapping table: LBA 50 ──► Physical Page 200.
  3. Marks the old Physical Page (Page 50) as "INVALID / DIRTY".
```

### 5.1 Garbage Collection & Write Amplification Factor (WAF)
Over time, Flash blocks fill up with invalid pages. The FTL's background **Garbage Collector (GC)** must:
1. Select a block with many invalid pages.
2. Read all surviving *valid* pages into internal RAM.
3. Write those valid pages to a fresh block.
4. Erase the old block (resetting all bits to $1$).

This introduces **Write Amplification (WAF)**:
$$\text{WAF} = \frac{\text{Bytes Written to NAND Flash Silicon}}{\text{Bytes Written by Host OS}}$$
In poorly tuned workloads, a host write of $4\text{ KB}$ can force the SSD to copy and rewrite $64\text{ KB}$ of data, yielding $\text{WAF} = 16$, degrading performance and wearing out Flash cells.

### 5.2 The TRIM Command
When an OS deletes a file (`rm database.db`), traditional filesystems simply clear the inode pointer; they do not zero the disk blocks. As a result, the SSD continues to treat those deleted sectors as "valid" during garbage collection!

The **TRIM Command** (or `UNMAP` in SCSI) allows the OS to explicitly notify the SSD: *"Logical blocks 1,000 through 50,000 have been freed by the filesystem."* The FTL instantly marks those physical pages as invalid, preventing unnecessary copy operations during GC and prolonging SSD lifespan.
