## ⚡ 2. Trino / Presto Architecture: Coordinator & Workers

Trino operates as a classic **Massively Parallel Processing (MPP)** cluster consisting of one central Coordinator and a pool of Workers:

```text
===================================================================================================
                                     TRINO CLUSTER TOPOLOGY
===================================================================================================

  BI Tool / SQL Client (Tableau, Superset, dbt)
             │
```

## 🚀 3. Pipelined In-Memory Execution & Dynamic Filtering

Unlike Spark (which can spill intermediate shuffle partitions to local NVMe disks), Trino processes data entirely in **in-memory streaming pipelines**.

```text
===================================================================================================
                                PIPELINED IN-MEMORY DATA EXCHANGE
===================================================================================================

  Stage 1: Table Scan (S3 Parquet)
  [ Operator: ScanFilterProject ] ──► Pushes streaming byte chunks directly over network!
                                            │
                                            ▼ (Direct TCP / HTTP/2 Memory Buffers)
  Stage 2: Hash Join
  [ Operator: HashJoinProbe ] ──────► Computes join in RAM without ever touching disk!
```

### 3.1 Dynamic Filtering: Pushing Runtime State into Scans
Consider a join between a massive fact table ($10\text{ billion rows}$) and a small dimension table:
```sql
SELECT o.order_id, o.amount 
FROM orders o 
JOIN customers c ON o.customer_id = c.customer_id 
WHERE c.country = 'Norway';
```
In traditional engines, the database scans all 10 billion order rows before joining.

**Dynamic Filtering in Trino:**
1. The engine scans the small `customers` table first, identifying the 500 matching `customer_id` values in Norway.
2. It builds a compact runtime **Bloom filter** or hash set containing those 500 IDs.
3. It broadcasts this filter down to the worker nodes scanning the `orders` table **while the scan is running**!
4. The Parquet readers evaluate the filter against Parquet row-group statistics, skipping $99.9\%$ of data blocks directly at the S3 reader layer!

## 🌐 4. The Connector Architecture: The Federated Query Engine

Trino does not own a proprietary storage format. It separates query processing from storage via the **SPI (Service Provider Interface) Connector Model**.

```text
===================================================================================================
                                TRINO FEDERATED QUERY ARCHITECTURE
===================================================================================================

                                   ┌───────────────────────┐
                                   │  Trino Query Engine   │
                                   └───────────┬───────────┘
                                               │
         ┌─────────────────────────┬───────────┴───────────┬─────────────────────────┐
         ▼                         ▼                       ▼                         ▼
  [ Hive/Iceberg SPI ]      [ PostgreSQL SPI ]      [ Kafka SPI ]            [ MongoDB SPI ]
         │                         │                       │                         │
         ▼                         ▼                       ▼                         ▼
  AWS S3 Parquet Tables     Production OLTP DB      Real-Time Event Stream   Document Store
```

### The Ultimate Federated SQL Query:
```sql
-- Single SQL query joining across S3 Lakehouse, Operational PostgreSQL, and Kafka in real-time!
SELECT 
    u.user_name,
    p.email,
    SUM(o.amount) AS total_spent,
    k.last_login_device
FROM iceberg.analytics.orders o
JOIN postgresql.public.users p ON o.user_id = p.id
JOIN kafka.telemetry.user_sessions k ON o.user_id = k.user_id
WHERE o.order_date >= CURRENT_DATE - INTERVAL '7' DAY
GROUP BY u.user_name, p.email, k.last_login_device;
```
Trino queries all three heterogeneous storage systems concurrently, executes the distributed join entirely in memory, and returns results in seconds without data migration!
