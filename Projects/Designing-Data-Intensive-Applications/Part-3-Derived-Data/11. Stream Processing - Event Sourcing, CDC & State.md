# Chapter 11: Stream Processing — Event Sourcing, CDC & State

> "A batch process works with bounded inputs: a finite collection of data. In reality, very little data is truly bounded: data is generated continuously over time... A stream is simply an unbounded sequence of events arriving in real time."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

In traditional data architectures, batch jobs run periodically (e.g. every midnight) to process the previous day's data. While robust, batch systems introduce an inherent latency floor of 24 hours.

If a business requires sub-second reaction times—to detect fraudulent credit card transactions, update flight schedules, or recalculate live recommendation feeds—it cannot wait for a dataset to "finish."

**Stream Processing** operates over **unbounded datasets**: data that arrives continuously and has no theoretical end. The stream processing paradigm transforms continuous streams of events into real-time alerts, updated in-memory state stores, and low-latency derived views.

## 2. Underlying Runtime, Memory & Execution Architecture

### Messaging Systems: Transient Brokers vs. Partitioned Logs

How systems transport streaming events is split between two competing designs:

```
─────────────────────────────────────────────────────────────────────────────
Design A: Traditional Message Broker (RabbitMQ / ActiveMQ / AMQP)
 Producer ──> [ Exchange / Queue ] ──> Consumer Worker (Pulls message)
                                              │
                                              └──> Sends ACK ──> Broker DELETES Message!
 • Messages are transient; destroyed upon successful consumption.
 • Cannot re-read past events. If a consumer crashes without ACK, message is redelivered.
─────────────────────────────────────────────────────────────────────────────
Design B: Partitioned Append-Only Log Broker (Apache Kafka / AWS Kinesis)
 Producer ──> [ Partition 0: [0][1][2][3][4][5][6]... (Persisted on Disk) ]
                                  ▲               ▲
                                  │ (Offset 2)    │ (Offset 5)
                            Consumer Group A   Consumer Group B
 • Messages are immutable, persistent log entries stored on disk for days or months.
 • Consumers are completely decoupled: each tracks its own monotonic offset.
 • Any consumer can rewind its offset and REPLAY historical data at will.
─────────────────────────────────────────────────────────────────────────────
```

### Databases and Streams: The Dual Writes Problem vs. CDC

When building architectures where a primary database (e.g. PostgreSQL) must keep external systems (e.g. an Elasticsearch search index and Redis cache) synchronized, naive architectures rely on **Dual Writes**:

```
 The Dual Writes Disaster (Concurrent Race Condition):
 Client 1: Wants to set balance = $100
 Client 2: Wants to set balance = $200

 Time t1: Client 1 writes DB: balance = $100
 Time t2: Client 2 writes DB: balance = $200  ──> DB Final State: $200!

 Time t3: Client 2 publishes to Kafka: balance = $200
 Time t4: Client 1 publishes to Kafka: balance = $100 (Delayed by network!)
          ──> Search Index / Cache Final State: $100!
          
 RESULT: The Database and the Search Index have SILENTLY DIVERGED forever!
```

#### The Architectural Solution: Change Data Capture (CDC)
Instead of the application attempting to write to two systems simultaneously, the application writes **only to the primary database**. 

A **Change Data Capture (CDC)** engine (such as Debezium) directly parses the database's internal transaction write-ahead log (PostgreSQL WAL or MySQL Binlog) and emits an ordered, authoritative stream of row mutations into Kafka. Downstream consumers update search indexes and caches strictly in lockstep with the database log.

```
 [ Client Write ] ──> [ Primary DB ] ──(WAL)──> [ CDC Engine (Debezium) ] ──> [ Kafka ] ──> [ Elasticsearch ]
```

## 3. Core Mechanics, Algorithms & Invariants

### Event Sourcing

Pioneered in Domain-Driven Design (DDD), **Event Sourcing** takes the stream-database duality to its logical conclusion:
- **Traditional CRUD:** Mutates current state in-place (`UPDATE users SET email = 'new@corp.com'`). The previous email is destroyed.
- **Event Sourcing:** The application state is recorded as an append-only sequence of **immutable domain events** (`UserCreated`, `EmailUpdated`, `OrderPlaced`).

$$\text{Current State} = \int \text{Event Stream } dt = \sum_{i=0}^{N} \text{Event}_i$$

The event log is the ultimate source of truth. The current state is simply a **materialized projection** derived by rolling forward through the event log. If business logic changes, new read models can be built retroactively from historical events.

### Stream Joins

Joining continuous data streams requires bounding state in memory:

```
 ┌───────────────────────────────────┬─────────────────────────────────────────────────────────────┐
 │ Stream Join Paradigm              │ Mechanics & State Lifecycles                                │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Stream-Stream Join**            │ Correlating two transient events arriving within a bounded  │
 │ (Windowed Correlation)            │ time interval (e.g. Ad Impression joined with Ad Click      │
 │                                   │ occurring within 30 minutes). Both streams buffer state.    │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Stream-Table Join**             │ Continuous event stream enriched by querying current state  │
 │ (Stream Enrichment)               │ of a dimension table (e.g. Transaction enriched with        │
 │                                   │ latest customer profile from a CDC changelog table).        │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Table-Table Join**              │ Correlating two changelog streams to maintain a continuous  │
 │ (Materialized View Maintenance)   │ materialized join view across two mutating database tables. │
 └───────────────────────────────────┴─────────────────────────────────────────────────────────────┘
```

## 4. Practical Systems & Production Engineering Trade-offs

1. **Debezium + Kafka:** The gold standard for non-invasive, linearizable Change Data Capture across PostgreSQL, MySQL, and MongoDB.

## 5. Annotated Code Implementations & Algorithmic Engines

### Stream-Table Enrichment Join Engine with Event-Time Watermarks

The following production Python program implements a stateful stream processor that enriches incoming financial transaction streams against a dynamic customer profile changelog (CDC table), evicting state based on advancing event-time watermarks:

```python
"""
Stateful Stream-Table Enrichment Join Engine.
Demonstrates:
  - Event-Time Watermarking with Bounded Out-of-Orderness
  - CDC Changelog Materialization (Stream-Table Duality)
  - Stream-Table stateful enrichment joins
  - Bounded state purging based on watermark progression
"""

from typing import Dict, List, Optional, Tuple


class StreamRecord:
    def __init__(self, key: str, payload: dict, event_time: int):
        self.key = key
        self.payload = payload
        self.event_time = event_time # Milliseconds epoch


class StreamTableEnrichmentEngine:
    def __init__(self, max_allowed_delay_ms: int = 5000):
        self.max_allowed_delay_ms = max_allowed_delay_ms
        self.current_watermark = 0
        
        # Materialized Table State (Key -> Current Profile State)
        self.dimension_table: Dict[str, dict] = {}
        
        # Output Log
        self.enriched_stream: List[dict] = []

    def update_watermark(self, observed_timestamp: int) -> None:
        """Advances system watermark based on bounded out-of-orderness."""
        potential_watermark = observed_timestamp - self.max_allowed_delay_ms
        if potential_watermark > self.current_watermark:
            self.current_watermark = potential_watermark

    def process_table_changelog(self, cdc_event: StreamRecord) -> None:
        """Applies incoming CDC mutations to update the local dimension table state."""
        self.update_watermark(cdc_event.event_time)
        user_id = cdc_event.key
        
        # Tombstone deletion check
        if cdc_event.payload is None:
            if user_id in self.dimension_table:
                del self.dimension_table[user_id]
        else:
            # Upsert into materialized state
            self.dimension_table[user_id] = cdc_event.payload

    def process_stream_transaction(self, tx_event: StreamRecord) -> Optional[dict]:
        """
        Enriches incoming transaction stream with current table dimension state.
        Discards late records whose timestamp falls behind the system watermark.
        """
        self.update_watermark(tx_event.event_time)

        # Check if record is late
        if tx_event.event_time < self.current_watermark:
            print(f" -> [DROPPED LATE EVENT] Tx {tx_event.payload['tx_id']} "
                  f"(ts={tx_event.event_time}) < Watermark={self.current_watermark}")
            return None

        user_id = tx_event.key
        user_profile = self.dimension_table.get(user_id, {"tier": "STANDARD", "country": "UNKNOWN"})

        enriched = {
            "tx_id": tx_event.payload["tx_id"],
            "user_id": user_id,
            "amount": tx_event.payload["amount"],
            "user_tier": user_profile.get("tier"),
            "user_country": user_profile.get("country"),
            "event_time": tx_event.event_time,
        }
        self.enriched_stream.append(enriched)
        return enriched


# Verification Execution
if __name__ == "__main__":
    engine = StreamTableEnrichmentEngine(max_allowed_delay_ms=3000)

    # 1. Ingest CDC dimension updates (Stream-Table Duality)
    print("=== 1. Ingesting Dimension CDC Changelog ===")
    engine.process_table_changelog(StreamRecord("user-1", {"tier": "PLATINUM", "country": "US"}, event_time=1000))
    engine.process_table_changelog(StreamRecord("user-2", {"tier": "GOLD", "country": "UK"}, event_time=2000))

    # 2. Ingest continuous transaction event stream
    print("\n=== 2. Ingesting Real-Time Transactions ===")
    res1 = engine.process_stream_transaction(StreamRecord("user-1", {"tx_id": "TX-101", "amount": 250.0}, event_time=3000))
    print(f"Enriched: {res1}")

    # Advance clock with a future event (ts = 15,000 -> Watermark advances to 15000 - 3000 = 12,000)
    engine.process_stream_transaction(StreamRecord("user-2", {"tx_id": "TX-102", "amount": 80.0}, event_time=15000))

    # 3. Test late-arriving event (ts = 4,000 < Watermark 12,000)
    print("\n=== 3. Late Event Ingestion Test ===")
    late_res = engine.process_stream_transaction(StreamRecord("user-1", {"tx_id": "TX-103", "amount": 10.0}, event_time=4000))
    assert late_res is None, "Late arrival protection failed!"

    print(f"\nFinal Watermark: {engine.current_watermark}ms. Total enriched records: {len(engine.enriched_stream)}")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Dual-Writes State Corruption Trap
- **Antipattern:** Updating a relational database row and publishing an event to Kafka in separate try-catch blocks inside an API controller.
- **System Consequence:** If the network hiccups or the app container crashes between the database commit and the Kafka publish, Kafka never receives the event. Downstream search indexes and data lakes permanently diverge from the primary database with no automated way to detect the mismatch.
- **Fix:** Use **Change Data Capture (CDC)** or the **Transactional Outbox Pattern** with log tailing.

### 2. Stream-Stream Join Unbounded State Memory Leak
- **Antipattern:** Joining two streams on a key without specifying a temporal time window bound or TTL.
- **System Consequence:** The stream processor must retain every event from both streams in state storage indefinitely, anticipating that a match might arrive years later. State grows to tens of gigabytes, exhausting TaskManager memory or RocksDB disk space.
- **Fix:** Always enforce an explicit bounded window interval (e.g. `intervalJoin().between(Time.minutes(-5), Time.minutes(15))`).

### 3. Processing Time Windows Breaking Historical Replays
- **Antipattern:** Defining streaming aggregation windows using processing time (`Time.minutes(5)`) while occasionally backfilling historical data.
- **System Consequence:** During an offline replay of events from 2024, the stream processor buckets the historical records into *current wall-clock intervals* (2026). The historical analytical output is completely corrupted.
- **Fix:** Always construct windowing logic around **Event Time** with robust **Watermark Strategies**.
