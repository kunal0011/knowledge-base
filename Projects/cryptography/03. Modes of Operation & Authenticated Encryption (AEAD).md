# Chapter 03: Modes of Operation & Authenticated Encryption (AEAD)

> "Encryption without authentication is insecure. A cipher that guarantees confidentiality against a passive eavesdropper can be completely dismantled by an active attacker who tampers with ciphertexts. Modern cryptographic engineering demands Authenticated Encryption with Associated Data (AEAD)."  
> — *Mihir Bellare & Phillip Rogaway, Authenticated Encryption: Relations among Notions*

---

## ⚠️ 1. The Block Cipher Gap & The ECB Disaster

A block cipher (like AES) is merely an algorithm that encrypts a single, fixed-size $128\text{-bit}$ ($16\text{-byte}$) block. To encrypt an arbitrary-length message (a $10\text{ MB}$ video or a database record), we must apply a **Mode of Operation**.

### 1.1 Electronic Codebook (ECB) Mode: The Fatal Flaw
In ECB mode, each 16-byte plaintext block is encrypted independently using the same key:
$$C_i = E_K(P_i)$$

```text
===================================================================================================
                             THE ELECTRONIC CODEBOOK (ECB) TRAP
===================================================================================================

  Plaintext:   [ Block 1: "USER: ALICE; ACC" ] [ Block 2: "OUNT: 1234; TRAN" ] [ Block 3: "SFER: $10,000;  " ]
  Key:         [ Key K                       ] [ Key K                       ] [ Key K                       ]
  Ciphertext:  [ C1                          ] [ C2                          ] [ C3                          ]
  
  ⚠️ The ECB Invariant: IDENTICAL PLAINTEXT BLOCKS ALWAYS PRODUCE IDENTICAL CIPHERTEXT BLOCKS!
  
  [ The Famous "ECB Penguin" Example ]
  If you encrypt a bitmap image of the Linux Tux penguin using ECB:
  - Large swathes of identical pixels (the white belly, black feathers, background)
    encrypt to identical ciphertext bytes.
  - The encrypted ciphertext STILL CLEARLY OUTLINES THE PENGUIN!
  - Result: ZERO Confidentiality! ECB is strictly forbidden in modern engineering!
```

## ⛓️ 2. Cipher Block Chaining (CBC) & The Padding Oracle Attack

To break the determinism of ECB, **Cipher Block Chaining (CBC)** introduces dependency between successive blocks:

```text
===================================================================================================
                                 CIPHER BLOCK CHAINING (CBC)
===================================================================================================

  Plaintext P1                   Plaintext P2                   Plaintext P3
       │                              │                              │
  IV ──►XOR                      ┌─────►XOR                      ┌─────►XOR
       │                         │    │                         │    │
       ▼                         │    ▼                         │    ▼
  ┌─────────┐                    │ ┌─────────┐                  │ ┌─────────┐
  │ Block E │                    │ │ Block E │                  │ │ Block E │
  └────┬────┘                    │ └────┬────┘                  │ └────┬────┘
       │                         │      │                       │      │
       ▼                         │      ▼                       │      ▼
  Ciphertext C1 ─────────────────┘ Ciphertext C2 ───────────────┘ Ciphertext C3
```

### 2.1 Encryption & Decryption Formulas
$$C_0 = \text{IV}$$
$$C_i = E_K(P_i \oplus C_{i-1})$$
$$P_i = D_K(C_i) \oplus C_{i-1}$$

### 2.2 PKCS#7 Padding
Because CBC operates on strict 16-byte boundaries, messages must be padded. In **PKCS#7**, if $k$ bytes are needed to reach a multiple of 16, the value $k$ is repeated $k$ times:
- Need 1 byte: `0x01`
- Need 3 bytes: `0x03 0x03 0x03`
- If message is already a multiple of 16 bytes, a **full dummy block of 16 bytes** (`0x10 ... 0x10`) is appended!

---

### 2.3 The Padding Oracle Attack (Vaudenay's Attack / POODLE)
Discovered by Serge Vaudenay in 2002, this attack allows an active adversary to **decrypt entire ciphertexts without knowing the key** if a server returns different errors for invalid padding vs. invalid data.

```text
===================================================================================================
                                  PADDING ORACLE MECHANICS
===================================================================================================

  Adversary intercepts C1 and C2 (Goal: Decrypt P2)
  Recall: P2 = D_K(C2) ⊕ C1
  
  1. Attacker crafts a corrupted C1' where they modify the last byte: C1'[15] = guess.
  2. Sends [C1', C2] to server.
  3. Server attempts to decrypt C2: Intermediary I = D_K(C2).
     Computes: P2'[15] = I[15] ⊕ C1'[15].
  4. Server inspects PKCS#7 padding:
     - Case A: Padding is INVALID -> Server throws HTTP 500 "Padding Error".
     - Case B: Padding is VALID (ends in 0x01) -> Server proceeds to data parse!
  5. By cycling through only 256 guesses for C1'[15], exactly ONE guess yields valid padding:
     I[15] ⊕ C1'[15] = 0x01  ===>  I[15] = C1'[15] ⊕ 0x01!
  6. Now attacker knows I[15]! Since P2[15] = I[15] ⊕ C1[15], the PLAINTEXT BYTE IS RECOVERED!
```
In just $256 \times 16 = 4,096$ requests, an attacker decrypts an entire 16-byte block!

## 🔢 3. Counter Mode (CTR): Turning Block Ciphers into Stream Ciphers

**Counter (CTR) Mode** transforms a block cipher into a high-performance stream cipher:

```text
===================================================================================================
                                       COUNTER (CTR) MODE
===================================================================================================

  Counter 1: [ Nonce || 0x0001 ]   Counter 2: [ Nonce || 0x0002 ]   Counter 3: [ Nonce || 0x0003 ]
             │                                │                                │
             ▼                                ▼                                ▼
      ┌──────────────┐                 ┌──────────────┐                 ┌──────────────┐
      │   AES E_K    │                 │   AES E_K    │                 │   AES E_K    │
      └──────┬───────┘                 └──────┬───────┘                 └──────┬───────┘
             │ Keystream 1                    │ Keystream 2                    │ Keystream 3
             ▼                                ▼                                ▼
   P1 ─────►XOR                     P2 ─────►XOR                     P3 ─────►XOR
             │                                │                                │
             ▼                                ▼                                ▼
       Ciphertext C1                    Ciphertext C2                    Ciphertext C3
```

$$C_i = P_i \oplus E_K(\text{Nonce} \parallel i)$$
$$P_i = C_i \oplus E_K(\text{Nonce} \parallel i)$$

### 3.1 Architectural Advantages of CTR Mode
1. **Zero Padding:** Messages can be any arbitrary byte length (no PKCS#7; completely immune to padding oracle attacks!).
2. **Massive Parallelism:** Unlike CBC (where block $i$ cannot be encrypted until block $i-1$ is finished), CTR blocks can be encrypted and decrypted completely out of order across 64 CPU cores simultaneously!
3. **Random Access:** Reading byte 5,000,000 of an encrypted disk image requires evaluating only that single counter block without decrypting preceding gigabytes.

> [!CAUTION]
> **The Nonce Reuse Disaster in CTR Mode:**
> If a sender ever encrypts two messages with the same `(Key, Nonce)` pair, their keystreams are identical:
> $$C_1 \oplus C_2 = (P_1 \oplus K_{\text{stream}}) \oplus (P_2 \oplus K_{\text{stream}}) = P_1 \oplus P_2$$
> It instantly degenerates into the catastrophic Two-Time Pad vulnerability!

## 🛡️ 4. Authenticated Encryption with Associated Data (AEAD)

Historically, systems attempted to combine encryption and Message Authentication Codes (MACs) naively:
1. **MAC-then-Encrypt (SSL/TLS 1.0):** Compute MAC over plaintext, append MAC, then encrypt. *(Broken by padding oracles!)*
2. **Encrypt-and-MAC (SSH):** Encrypt plaintext; independently compute MAC over plaintext. *(Leaked plaintext information via MAC!)*
3. **Encrypt-then-MAC (IPSec):** Encrypt plaintext; compute MAC over the resulting ciphertext:
   $$\text{Ciphertext } C = \text{Enc}_K(P), \quad \text{Tag } T = \text{MAC}_{K_{\text{auth}}}(C)$$
   *Provably secure against Adaptive Chosen-Ciphertext Attacks (IND-CCA2)!*

---

### 4.1 AES-GCM (Galois/Counter Mode - NIST SP 800-38D)
The global gold standard for high-throughput secure communications (TLS 1.2/1.3, IPSec, Kubernetes Secrets).

```text
===================================================================================================
                                      AES-GCM ARCHITECTURE
===================================================================================================

  1. Payload Encryption: Counter Mode (CTR) generates Ciphertext C.
  2. Associated Data (AAD): Unencrypted metadata (e.g., IP packet headers).
  3. Authentication Engine: GHASH function over Galois Field GF(2^128).
  
  H = AES_K(0^128)  <-- Hash Key derived from AES
  
  GHASH(AAD, C):
  Processes AAD blocks and Ciphertext blocks via polynomial evaluation:
  S = (AAD_1 * H^4 + AAD_2 * H^3 + C_1 * H^2 + C_2 * H + Lengths) * H mod (x^128 + x^7 + x^2 + x + 1)
  
  Authentication Tag T = S ⊕ AES_K(Nonce || 1)
```

**Hardware Acceleration:** Modern x86 and ARM processors include the **`PCLMULQDQ`** (Carryless Multiplication) instruction, computing 128-bit Galois Field multiplications in silicon at over **$10\text{ GB/sec}$**!

---

### 4.2 ChaCha20-Poly1305 (RFC 8439)
Designed by Daniel J. Bernstein (djb) as a high-speed, constant-time alternative to AES-GCM for platforms lacking hardware AES-NI instructions (mobile phones, IoT microcontrollers).

- **ChaCha20:** Stream cipher based on an **ARX (Add-Rotate-Xor)** architecture operating on a $4 \times 4$ matrix of 32-bit words. Completely free of lookup tables, making it intrinsically immune to cache-timing attacks.
- **Poly1305:** One-time polynomial authenticator evaluated modulo the prime $2^{130} - 5$.
- Standardized as the primary default cipher in **WireGuard VPN** and mandatory in **TLS 1.3**.
