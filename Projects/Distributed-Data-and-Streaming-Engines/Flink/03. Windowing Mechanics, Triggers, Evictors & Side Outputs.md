# Chapter 03: Windowing Mechanics, Triggers, Evictors & Side Outputs

> "Windows convert an infinite, unbounded stream of events into finite buckets over which stateful computations and aggregations can be executed."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

Because data streams are inherently unbounded, operations such as counts, sums, percentiles, or joins cannot be evaluated over the "entire stream." Instead, computations must be bounded by slicing continuous time or event sequences into discrete, finite segments called **Windows**.

Flink provides the industry’s most expressive and mathematically rigorous windowing model, supporting:
- **Tumbling Windows:** Fixed-size, non-overlapping time buckets.
- **Sliding (Hopping) Windows:** Fixed-size, overlapping buckets sliding by a specified interval.
- **Session Windows:** Dynamically sized, activity-based buckets defined by periods of inactivity (gaps).
- **Global Windows:** Unbounded buckets that rely strictly on custom triggers to fire evaluations.

Understanding how Flink structures window lifecycles—from record assignment to incremental accumulation, trigger evaluation, state eviction, and late-data handling—is critical for architecting high-performance streaming pipelines.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Anatomy of a Window Operator

When an event enters a keyed window operation (`stream.keyBy(...).window(...)`), it passes through a sequence of modular architectural components:

```
                                [ Incoming Event: Record(k, t) ]
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │    WindowAssigner     │ (Assigns to 1 or more Windows)
                                    └───────────┬───────────┘
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │      State Store      │ (Incremental Accumulator OR ListState)
                                    └───────────┬───────────┘
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │        Trigger        │ (Evaluates: CONTINUE, FIRE, PURGE)
                                    └───────────┬───────────┘
                                                │
                         ┌──────────────────────┴──────────────────────┐
                         │ FIRE                                        │ CONTINUE
                         ▼                                             ▼
             ┌───────────────────────┐                        (Wait for more events
             │    Evictor (Opt)      │                         or watermark advance)
             └───────────┬───────────┘
                         │
                         ▼
             ┌───────────────────────┐
             │ WindowFunction / ProcessWindowFunction │
             └───────────┬───────────┘
                         │
                         ▼
             [ Emitted Window Result ]
```

#### 1. WindowAssigner
Determines which window(s) an incoming element belongs to. For a tumbling window of size $S$, a record with timestamp $t$ is assigned to:

$$\text{Window} = \left[ t - (t \bmod S), \; t - (t \bmod S) + S \right)$$

For a sliding window of size $S$ and slide $D$, a single incoming record is simultaneously assigned to $\frac{S}{D}$ overlapping windows, multiplying state retention.

#### 2. Incremental Aggregation vs. Full Buffering
- **Full-Window Buffering (`ProcessWindowFunction` alone):** Flink stores every raw incoming record in a `ListState` until the window triggers. If a 1-hour window receives 10,000,000 events, all 10 million POJOs sit in memory/RocksDB, creating massive serialization and heap pressure.
- **Incremental Aggregation (`AggregateFunction` / `ReduceFunction`):** Flink updates an in-flight accumulator state eagerly upon the arrival of each individual record ($O(1)$ space).
- **The Modern Golden Standard (Combined):** Combining an incremental `AggregateFunction` with an enriching `ProcessWindowFunction`. Flink computes the aggregate incrementally in $O(1)$ memory while exposing the final window metadata (start/end timestamps) upon emission.

#### 3. Triggers & Evictors
- **Trigger:** Dictates *when* a window is evaluated. A trigger returns a `TriggerResult`:
  - `CONTINUE`: Do nothing; retain state.
  - `FIRE`: Execute the window function and emit the result.
  - `PURGE`: Discard all state inside the window.
  - `FIRE_AND_PURGE`: Execute the window function and immediately clear window state.
- **Evictor:** An optional hook allowing removal of elements from buffer state before or after the window function runs. (Note: Evictors prevent incremental aggregation because they require a full element buffer).

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Lifecycle Management: Allowed Lateness

When an event arrives after the watermark has passed the window end timestamp, it is considered **late**. By default, late events are immediately dropped.

With **Allowed Lateness**:
- The window maintains its state in RocksDB for an additional duration: $[T_{\text{end}}, T_{\text{end}} + L_{\text{allowed}}]$.
- Any late record arriving within this grace period triggers an immediate recalculation and emits an updated result.
- Once the watermark advances past $T_{\text{end}} + L_{\text{allowed}}$, the window is permanently purged, and subsequent arrivals are redirected to side outputs.

1. **Volume-Weighted Average Price (VWAP) Calculation:** Financial exchange order books aggregated over 1-minute tumbling windows using incremental accumulators.

## 5. Annotated Code Implementations & Execution Traces

### Production Pipeline: Combined Incremental Aggregation with Window Metadata & Allowed Lateness

The following Java implementation aggregates web traffic requests per endpoint, computing request counts and average latency incrementally, handling late data, and tagging dropped records:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.api.common.functions.AggregateFunction;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.datastream.SingleOutputStreamOperator;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.functions.windowing.ProcessWindowFunction;
import org.apache.flink.streaming.api.windowing.assigners.TumblingEventTimeWindows;
import org.apache.flink.streaming.api.windowing.time.Time;
import org.apache.flink.streaming.api.windowing.windows.TimeWindow;
import org.apache.flink.util.Collector;
import org.apache.flink.util.OutputTag;

import java.time.Duration;

public class AdvancedWindowingMechanicsJob {

    // Domain Models
    public static class WebLog {
        public String endpoint;
        public long latencyMs;
        public long timestamp;

        public WebLog() {}
        public WebLog(String endpoint, long latencyMs, long timestamp) {
            this.endpoint = endpoint;
            this.latencyMs = latencyMs;
            this.timestamp = timestamp;
        }
    }

    // Accumulator for Incremental Computation
    public static class LatencyAccumulator {
        public long totalLatency = 0;
        public long requestCount = 0;
    }

    // Final Output Record
    public static class EndpointWindowStats {
        public String endpoint;
        public double avgLatency;
        public long count;
        public long windowStart;
        public long windowEnd;

        @Override
        public String toString() {
            return String.format("Endpoint [%s] | Window [%d - %d] | Count: %d | Avg Latency: %.2f ms",
                    endpoint, windowStart, windowEnd, count, avgLatency);
        }
    }

    public static final OutputTag<WebLog> DROPPED_TAG = new OutputTag<WebLog>("purged-late-logs") {};

    // 1. Incremental Aggregation Function: O(1) Memory
    public static class LatencyAggregator implements AggregateFunction<WebLog, LatencyAccumulator, Double> {
        @Override
        public LatencyAccumulator createAccumulator() {
            return new LatencyAccumulator();
        }

        @Override
        public LatencyAccumulator add(WebLog value, LatencyAccumulator acc) {
            acc.totalLatency += value.latencyMs;
            acc.requestCount += 1;
            return acc;
        }

        @Override
        public Double getResult(LatencyAccumulator acc) {
            return acc.requestCount == 0 ? 0.0 : (double) acc.totalLatency / acc.requestCount;
        }

        @Override
        public LatencyAccumulator merge(LatencyAccumulator a, LatencyAccumulator b) {
            a.totalLatency += b.totalLatency;
            a.requestCount += b.requestCount;
            return a;
        }
    }

    // 2. ProcessWindowFunction for Decorating with Window Metadata
    public static class WindowMetadataDecorator 
            extends ProcessWindowFunction<Double, EndpointWindowStats, String, TimeWindow> {
        @Override
        public void process(String endpoint, Context context, Iterable<Double> elements, Collector<EndpointWindowStats> out) {
            Double avgLatency = elements.iterator().next();
            EndpointWindowStats stats = new EndpointWindowStats();
            stats.endpoint = endpoint;
            stats.avgLatency = avgLatency;
            stats.windowStart = context.window().getStart();
            stats.windowEnd = context.window().getEnd();
            // Count can be extracted or tracked in accumulator
            out.collect(stats);
        }
    }

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        DataStream<WebLog> inputStream = env.fromElements(
                new WebLog("/api/v1/checkout", 120, 1000),
                new WebLog("/api/v1/checkout", 240, 2000),
                new WebLog("/api/v1/cart", 45, 2500),
                new WebLog("/api/v1/checkout", 180, 4500),
                new WebLog("/api/v1/checkout", 300, 12000) // Advances watermark past 5000ms window
        ).assignTimestampsAndWatermarks(
                WatermarkStrategy.<WebLog>forBoundedOutOfOrderness(Duration.ofSeconds(1))
                        .withTimestampAssigner((log, ts) -> log.timestamp)
        );

        SingleOutputStreamOperator<EndpointWindowStats> statsStream = inputStream
                .keyBy(log -> log.endpoint)
                // 5-Second Tumbling Event-Time Window
                .window(TumblingEventTimeWindows.of(Time.seconds(5)))
                // Allow late records for an extra 2 seconds before purging state
                .allowedLateness(Time.seconds(2))
                .sideOutputLateData(DROPPED_TAG)
                // Combined Incremental Aggregator + Process Function
                .aggregate(new LatencyAggregator(), new WindowMetadataDecorator());

        statsStream.print().name("WindowStatsOutput");
        statsStream.getSideOutput(DROPPED_TAG).print().name("DroppedLateLogs");

        env.execute("AdvancedWindowingMechanicsJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Raw `ProcessWindowFunction` OOM Trap
- **Antipattern:** Applying a pure `ProcessWindowFunction` (or `WindowFunction`) to high-throughput streams without an accompanying `AggregateFunction` or `ReduceFunction`.
- **System Consequence:** Flink is forced to buffer every incoming record into an in-memory or RocksDB `ListState`. In high-throughput environments (e.g. 100k events/sec across 1-hour windows), this buffers 360 million objects, causing extreme GC pauses, heap exhaustion, or massive RocksDB SST file write amplification.
- **Fix:** Always pair `ProcessWindowFunction` with an incremental `AggregateFunction` or `ReduceFunction`.

### 2. The Sliding Window State Multiplication Explosion
- **Antipattern:** Defining a sliding window with a massive window size and an ultra-fine slide step (e.g., `SlidingEventTimeWindows.of(Time.hours(24), Time.seconds(1))`).
- **System Consequence:** Every single incoming event is assigned simultaneously to $\frac{24 \times 3600}{1} = 86,400$ distinct active windows! Storage and write amplification explode by $86,400\times$, completely incapacitating the storage engine.
- **Fix:** Avoid micro-sliding intervals over large windows. If running fine-grained sliding metrics, use a combination of tumbling window micro-aggregates (e.g. 1-second buckets) rolled up downstream via stateful `KeyedProcessFunction` circular buffers.

### 3. Evictor Incremental Bypassing
- **Antipattern:** Adding an `Evictor` to a window intending to drop outlier values, expecting incremental aggregations to continue functioning.
- **System Consequence:** Flink explicitly disables incremental aggregation whenever an `Evictor` is attached to a window. The system silently falls back to full-buffering mode, keeping all records in memory until eviction evaluation.
- **Fix:** Filter outliers *prior* to the window operator using a preceding `.filter()` transformation.
