## 1. Process Memory Segments in C++

When an operating system loads an ELF / Mach-O executable, it maps the virtual address space into five distinct segments:

```
High Memory Addresses (0x7FFF_FFFF_FFFF)
+-------------------------------------------------------------+
| Stack (Grows Downward |)                                     |
| - Local variables, stack frames, return addresses           |
| - Automatic storage duration, extremely fast                |
+-------------------------------------------------------------+
|                              |                              |
|                              v                              |
|                                                             |
|                              ^                              |
|                              |                              |
+-------------------------------------------------------------+
| Heap (Grows Upward ^)                                       |
| - Dynamic allocations: new / malloc                         |
| - Managed via RAII / Smart Pointers                         |
+-------------------------------------------------------------+
| BSS Segment (Uninitialized Data)                            |
| - Uninitialized global and static variables                 |
| - Zero-initialized by kernel loader at startup              |
+-------------------------------------------------------------+
| Data Segment (Initialized Data)                             |
| - Explicitly initialized global and static variables        |
+-------------------------------------------------------------+
| Text Segment (Code Segment - Read Only)                     |
| - Compiled binary machine instructions, string literals     |
+-------------------------------------------------------------+
Low Memory Addresses (0x0000_0000_0000)
```

### Memory Segments Comparison:
| Segment | Allocation Mechanism | Lifetime | Overhead / Access Speed |
|:---|:---|:---|:---|
| **Stack** | CPU stack pointer adjustment (`RSP`) | Current scope / function frame | Single-cycle instructions, peak cache locality |
| **Heap** | Syscall / Allocator (`brk`, `mmap`, `malloc`) | Manual (`free`) or RAII destruction | Allocator book-keeping, pointer indirection |
| **BSS** | Virtual memory page mapping | Program lifetime | Zero runtime cost (backed by OS zero-pages) |
| **Data** | Stored directly in executable binary | Program lifetime | Read-write global access |
| **Text** | Loaded into memory by OS exec | Program lifetime | Read-only; write triggers SIGSEGV |

## 2. Pointers vs References

```cpp
int x = 10;
int y = 20;

// Pointer: Variable holding memory address
int* ptr = &x;
ptr = &y;       // Pointers can be reassigned (reseated)
ptr = nullptr;  // Pointers can be null

// Reference: Syntactic alias for an existing object
int& ref = x;
ref = y;        // DOES NOT reseat ref to y! It assigns value 20 into x!
```

### Architectural Distinctions:
1. **Nullability:** Pointers can be `nullptr`. References **must** bind to a valid object upon declaration (binding to a dereferenced null pointer is Undefined Behavior).
2. **Re-binding:** Pointers can be reseated to point to different memory addresses throughout their lifecycle. References cannot be reseated; assigning to a reference assigns through to the bound object.
3. **Internal Assembly Representation:** In generated assembly, references are compiled identically to `T* const` (a constant non-reseatable pointer that is automatically dereferenced).

## 3. RAII (Resource Acquisition Is Initialization)

RAII is the core idiom that makes modern C++ memory-safe without requiring a garbage collector.

### The Core Invariant:
1. **Acquire** a resource (heap memory, mutex lock, file descriptor, database socket) in a class constructor (`T()`).
2. **Release** the resource deterministically in the class destructor (`~T()`).
3. Allocate the managing object with **automatic (stack) storage duration**.

```cpp
class FileHandler {
private:
    FILE* file;
public:
    FileHandler(const char* path) {
        file = fopen(path, "r");
        if (!file) throw std::runtime_error("Failed to open file");
    }
    ~FileHandler() {
        if (file) {
            fclose(file); // Guaranteed to execute even if exceptions occur!
        }
    }
};
```

When the object falls out of scope—whether through standard control flow or during stack unwinding caused by an exception—its destructor is **guaranteed** to run immediately.

## 4. Modern Smart Pointers (`<memory>`)

```
unique_ptr<T>                           shared_ptr<T>
+---------------+                       +---------------+     +---------------+
| Ptr -> Heap T |                       | Ptr -> Heap T |     | Control Block |
+---------------+                       +---------------+     | - Ref Count: 2|
(Zero overhead! Same as raw pointer)    | Ctrl Block Ptr|---->| - Weak Count: 1|
                                        +---------------+     +---------------+
                                                                     ^
                                        shared_ptr<T> (Copy)         |
                                        +---------------+            |
                                        | Ptr -> Heap T |            |
                                        +---------------+            |
                                        | Ctrl Block Ptr|-------------+
```

### 4.1 `std::unique_ptr<T>` (Exclusive Ownership)
- Owns and manages a heap object exclusively.
- Copy constructor and copy assignment are **deleted** (`= delete`).
- Transfer ownership using `std::move`.
- **Zero runtime overhead:** Compiles to the exact same assembly as a raw pointer.
```cpp
auto u1 = std::make_unique<int>(42);
// auto u2 = u1;            // Compile Error: Copying deleted!
auto u2 = std::move(u1);    // Legal: u1 is now nullptr, u2 owns 42
```

### 4.2 `std::shared_ptr<T>` (Shared Reference Counting)
- Multiple `shared_ptr` instances share ownership of the same object.
- Contains two pointers: a pointer to the managed object and a pointer to an atomic reference counting **Control Block**.
- Control block increments ref count on copy, decrements on destruction. When ref count reaches 0, the managed object is destroyed.
- **`std::make_shared` Optimization:** Allocates the control block and the target object in a **single contiguous heap memory block**, cutting heap allocations from 2 to 1 and improving cache locality.

### 4.3 `std::weak_ptr<T>` (Breaking Circular References)
If object A holds `shared_ptr<B>` and object B holds `shared_ptr<A>`, their reference counts never hit zero, causing a catastrophic memory leak.
`std::weak_ptr` observes a `shared_ptr` without incrementing the strong reference count:
```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev; // Break cycle!
};
```

## 5. Move Semantics & Rvalue References (C++11+)

Prior to C++11, passing or returning large collections (`std::vector`, `std::string`) forced expensive deep copies of underlying heap buffers.

### 5.1 Value Categories: Lvalues vs Rvalues
- **Lvalue (Locator Value):** An expression that has an identifiable identity and memory address (e.g., named variables `int x`, `v[0]`). Can appear on the left side of `=`.
- **Rvalue (Read Value):** Temporary values, literals, or expressions with no persistent address (e.g., `42`, `x + 5`, `std::string("temp")`). Cannot appear on the left side of `=`.

### 5.2 Rvalue References (`T&&`) & `std::move`
An rvalue reference (`T&&`) binds strictly to temporary objects, signaling that their internal resources can be "stolen" rather than copied.

```cpp
// std::move does NOT move anything!
// It is merely an unconditional static_cast to an rvalue reference:
template <typename T>
constexpr std::remove_reference_t<T>&& move(T&& arg) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(arg);
}
```

```cpp
std::vector<int> source = {1, 2, 3, 4, 5};

// Copy Constructor: Allocates new heap buffer, copies all 5 integers: O(N)
std::vector<int> copy_constructed = source;

// Move Constructor: Steals internal pointer, sets source pointer to null: O(1)
std::vector<int> move_constructed = std::move(source);
// source is now in a "valid but unspecified" empty state
```

### 5.3 Rule of 0 / 3 / 5
- **Rule of Zero:** Design classes using standard RAII types (`std::string`, `std::vector`, `std::unique_ptr`). Do not define custom destructors or copy/move operations.
- **Rule of Three (C++98):** If a class manages raw resources and defines a custom Destructor, Copy Constructor, or Copy Assignment Operator, it must explicitly implement all three.
- **Rule of Five (C++11+):** When defining the Rule of Three, you should also implement the **Move Constructor** and **Move Assignment Operator** to prevent costly fallback copies.

## 6. Undefined Behavior (UB) in C++

Undefined Behavior (UB) occurs when code violates the C++ ISO language specification. The compiler is legally permitted to assume UB **can never occur**, enabling aggressive code optimizations that can silently alter program logic.

### 6.1 Critical UB Scenarios in Interviews:
1. **Signed Integer Overflow:**
   In C++, `INT_MAX + 1` is **Undefined Behavior** (unlike Java where it wraps to `INT_MIN`). The compiler may optimize away loop termination conditions:
   ```cpp
   // Dangerous: Compiler can optimize this into an infinite loop!
   for (int i = 1; i > 0; i *= 2) { ... }
   ```
2. **Dangling Pointers & References:**
   Returning a reference or pointer to a stack-allocated local variable that has already been popped off the stack.
3. **Uninitialized Primitive Variables:**
   ```cpp
   int x; // Holds garbage memory bytes. Reading x is UB!
   ```
4. **Out-of-bounds Array Access:**
   Accessing `arr[size]` does not throw an exception in C++; it corrupts neighboring stack or heap memory.
5. **Null Pointer Dereference:**
   Dereferencing `nullptr` triggers an OS page fault or crash (`SIGSEGV`).
