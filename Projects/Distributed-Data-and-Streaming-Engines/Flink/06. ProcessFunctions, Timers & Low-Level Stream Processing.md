# Chapter 06: ProcessFunctions, Timers & Low-Level Stream Processing

> "ProcessFunctions are Flink's sharpest tool: when high-level declarative APIs cannot express your complex business invariants, ProcessFunctions give you raw, unconstrained access to time, state, and timers."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

High-level declarative transformations in the DataStream API (`map`, `filter`, `window`, `join`) cover standard stream transformations cleanly. However, complex enterprise event-driven architectures routinely encounter requirements that cannot be captured by rigid window buckets:
- **Absence of Events Detection:** Emitting an alert if a user initiates a checkout but does **not** complete payment within 15 minutes. High-level windowing functions can only trigger *when* records arrive; they cannot detect when records *fail to arrive*.
- **Dynamic State-Driven Routing:** Emitting side outputs conditionally based on in-memory blacklists updated on the fly.
- **Custom Asynchronous Timers:** Scheduling delayed callbacks tied precisely to the advancement of event-time watermarks.

To address these requirements, Flink exposes **ProcessFunctions**: low-level, stateful, event-driven operators that expose direct programmatic hooks to:
1. Every individual incoming record (`processElement`).
2. Both processing-time and event-time clocks.
3. The internal distributed **TimerService** (`registerEventTimeTimer`, `registerProcessingTimeTimer`).
4. Deferred callback handlers (`onTimer`).
5. Multi-stream side outputs.

## 2. Underlying Runtime, Memory & Execution Architecture

### The ProcessFunction Hierarchy

```
                                  ┌───────────────────────────┐
                                  │      ProcessFunction      │
                                  │(Non-keyed single stream)  │
                                  └─────────────┬─────────────┘
                                                │
                 ┌──────────────────────────────┼──────────────────────────────┐
                 ▼                              ▼                              ▼
    ┌───────────────────────────┐ ┌───────────────────────────┐ ┌───────────────────────────┐
    │    KeyedProcessFunction   │ │     CoProcessFunction     │ │  BroadcastProcessFunction │
    ├───────────────────────────┤ ├───────────────────────────┤ ├───────────────────────────┤
    │ Attached to KeyedStream   │ │ Processes two independent │ │ Joins broadcast stream    │
    │ Full TimerService access  │ │ streams without keying    │ │ (dynamic rules) with      │
    │ Key-isolated state        │ │                           │ │ regular data stream       │
    └───────────────────────────┘ └───────────────────────────┘ └───────────────────────────┘
```

### The Internal TimerService & Timer Storage

When a user calls `context.timerService().registerEventTimeTimer(t)` inside a `KeyedProcessFunction`, Flink registers a timer tuple:

$$\text{Timer} = (\text{Key}, \; \text{Timestamp } t)$$

- **Timer Deduplication:** In Flink, **timers are strictly deduplicated per key and timestamp**. Registering 1,000 timers for Key `"USER_42"` at timestamp $t=10000$ creates exactly **one** physical timer.
- **Timer Execution:** Timers are stored in a priority queue sorted by timestamp. As the system watermark advances past timestamp $t$, the operator automatically drains all timers with timestamps $\le t$ and invokes `onTimer(...)`.

```
 Watermark Advances to W=15000 ──> Drains TimerQueue: [ (User1, 12000), (User2, 14500) ]
                                   └── Invokes onTimer(timestamp, ctx, out) for each!
```

#### Timer Storage Backends: Heap vs. RocksDB
By default, timers are stored in JVM Heap memory as a Java `PriorityQueue`. When managing millions of concurrent timers, heap overhead can trigger severe GC pauses. Flink allows offloading timers directly into RocksDB:

```properties
state.backend.rocksdb.timer-service.factory: ROCKSDB
```

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Anatomy of `KeyedProcessFunction<K, I, O>`

A `KeyedProcessFunction` defines two primary callback methods:

```java
public class MyKeyedProcessFunction extends KeyedProcessFunction<String, Event, Alert> {

    @Override
    public void processElement(Event value, Context ctx, Collector<Alert> out) throws Exception {
        // 1. Current record timestamp
        Long currentTs = ctx.timestamp();
        // 2. Current key
        String currentKey = ctx.getCurrentKey();
        // 3. Register timer (e.g. 10 minutes into the future)
        ctx.timerService().registerEventTimeTimer(currentTs + 600000L);
        // 4. Emit side output
        ctx.output(SIDE_TAG, "Log message");
    }

    @Override
    public void onTimer(long timestamp, OnTimerContext ctx, Collector<Alert> out) throws Exception {
        // Callback invoked when Watermark (or Wall Clock) passes registered timestamp
        out.collect(new Alert("Timeout expired for key: " + ctx.getCurrentKey()));
    }
}
```

## 4. Practical Systems & Production Use Cases

1. **Unpaid Order Timeout Expiration:** An e-commerce pipeline registers a 15-minute event-time timer upon order creation. If a payment event arrives before the timer fires, the timer is deleted. If the timer fires, the order is automatically cancelled and inventory restored.
2. **Dynamic Rule Injection via Broadcast Streams:** A security fraud pipeline broadcasts dynamic IP blacklists to all parallel worker nodes, dynamically enriching high-volume transaction streams without stopping the cluster.
3. **Session Inactivity Watchdogs:** Emitting user engagement summaries when no interactions have occurred for a sliding 30-minute period.

## 5. Annotated Code Implementations & Execution Traces

### Order Payment Timeout Detector with Dynamic Timers & State Cleanup

The following production Java implementation monitors an e-commerce order lifecycle, cancelling orders and emitting alerts if payment is not received within 10 minutes of order placement:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.api.common.state.ValueState;
import org.apache.flink.api.common.state.ValueStateDescriptor;
import org.apache.flink.api.common.typeinfo.Types;
import org.apache.flink.configuration.Configuration;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.functions.KeyedProcessFunction;
import org.apache.flink.util.Collector;
import org.apache.flink.util.OutputTag;

import java.time.Duration;

public class OrderTimeoutDetectionJob {

    public enum EventType { ORDER_CREATED, PAYMENT_RECEIVED }

    public static class OrderEvent {
        public String orderId;
        public EventType eventType;
        public long eventTimeMs;

        public OrderEvent() {}
        public OrderEvent(String orderId, EventType eventType, long eventTimeMs) {
            this.orderId = orderId;
            this.eventType = eventType;
            this.eventTimeMs = eventTimeMs;
        }
    }

    public static final OutputTag<String> TIMEOUT_ALERT_TAG = 
            new OutputTag<String>("order-timeout-alerts") {};

    public static class OrderTimeoutProcessFunction 
            extends KeyedProcessFunction<String, OrderEvent, String> {

        // State to track if payment has been received
        private transient ValueState<Boolean> isPaidState;
        // State to track the registered timer timestamp for cleanup
        private transient ValueState<Long> timerTimestampState;

        @Override
        public void open(Configuration parameters) {
            isPaidState = getRuntimeContext().getState(
                    new ValueStateDescriptor<>("is-paid", Types.BOOLEAN));
            timerTimestampState = getRuntimeContext().getState(
                    new ValueStateDescriptor<>("timer-timestamp", Types.LONG));
        }

        @Override
        public void processElement(OrderEvent event, Context ctx, Collector<String> out) throws Exception {
            if (event.eventType == EventType.ORDER_CREATED) {
                // If payment already arrived out of order, do nothing
                if (Boolean.TRUE.equals(isPaidState.value())) {
                    out.collect(String.format("Order [%s] already settled.", event.orderId));
                    return;
                }

                // Schedule timeout timer: 10 minutes (600,000 ms) after order creation
                long timeoutTimestamp = event.eventTimeMs + 600000L;
                ctx.timerService().registerEventTimeTimer(timeoutTimestamp);
                timerTimestampState.update(timeoutTimestamp);

                out.collect(String.format("Order [%s] created. Timeout watch scheduled for t=%d", 
                        event.orderId, timeoutTimestamp));

            } else if (event.eventType == EventType.PAYMENT_RECEIVED) {
                isPaidState.update(true);

                // Cancel the registered timer if it exists
                Long registeredTimer = timerTimestampState.value();
                if (registeredTimer != null) {
                    ctx.timerService().deleteEventTimeTimer(registeredTimer);
                    timerTimestampState.clear();
                }

                out.collect(String.format("Order [%s] paid successfully. Timeout cancelled.", event.orderId));
            }
        }

        @Override
        public void onTimer(long timestamp, OnTimerContext ctx, Collector<String> out) throws Exception {
            // If timer fires and order remains unpaid -> Emit alert and trigger cancellation
            if (!Boolean.TRUE.equals(isPaidState.value())) {
                String alert = String.format("ALERT: Order [%s] timed out! No payment received after 10m.", 
                        ctx.getCurrentKey());
                ctx.output(TIMEOUT_ALERT_TAG, alert);
            }

            // Cleanup state to prevent memory leaks
            isPaidState.clear();
            timerTimestampState.clear();
        }
    }

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        DataStream<OrderEvent> stream = env.fromElements(
                new OrderEvent("ORD-1", EventType.ORDER_CREATED, 1000L),
                new OrderEvent("ORD-2", EventType.ORDER_CREATED, 2000L),
                new OrderEvent("ORD-1", EventType.PAYMENT_RECEIVED, 50000L), // Paid within 50s
                new OrderEvent("ORD-3", EventType.ORDER_CREATED, 3000L),
                new OrderEvent("ORD-2", EventType.ORDER_CREATED, 700000L)    // Watermark advance past 602000 -> Triggers ORD-2 timeout!
        ).assignTimestampsAndWatermarks(
                WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(1))
                        .withTimestampAssigner((evt, ts) -> evt.eventTimeMs)
        );

        org.apache.flink.streaming.api.datastream.SingleOutputStreamOperator<String> mainStream = stream
                .keyBy(evt -> evt.orderId)
                .process(new OrderTimeoutProcessFunction());

        mainStream.print().name("ProcessedOrdersOutput");
        mainStream.getSideOutput(TIMEOUT_ALERT_TAG).print().name("TimedOutAlertsOutput");

        env.execute("OrderTimeoutDetectionJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Processing-Time Timer Backfill Disaster
- **Antipattern:** Using `registerProcessingTimeTimer(...)` in pipelines that periodically reprocess historical data feeds or run offline backfills.
- **System Consequence:** Processing-time timers fire based on the local system wall-clock, completely divorced from historical data timestamps. While replaying events from 2024, the timers will register for 15 minutes in *current real time* (2026). The job produces nonsensical, nondeterministic outputs during backfills.
- **Fix:** Always use `registerEventTimeTimer(...)` for business domain logic, ensuring the timers fire strictly in lockstep with the advancing event stream watermark.

### 2. The Unbounded Timer Heap Explosion
- **Antipattern:** Registering a unique timer for every record with varying millisecond offsets (e.g. `ctx.timestamp() + record.getDynamicDelay()`) across billions of distinct keys.
- **System Consequence:** If timers are stored in JVM heap memory (`state.backend.rocksdb.timer-service.factory: HEAP`), millions of active timer instances can consume gigabytes of heap, triggering Stop-the-World GC pauses.
- **Fix:** Either round timer timestamps to coarse intervals (e.g., align to the nearest second: `(ts + delay) / 1000 * 1000`) to maximize deduplication, or configure off-heap timer storage via RocksDB.

### 3. Forgetting to Clean Up State in `onTimer`
- **Antipattern:** Emitting a timeout alert in `onTimer(...)` without explicitly invoking `.clear()` on all associated `ValueState`, `MapState`, or `ListState` handles.
- **System Consequence:** The state for expired keys remains permanently allocated inside the state backend. Over months of continuous operation, dead keys accumulate into hundreds of millions of zombie records, exhausting disk space.
- **Fix:** Always explicitly purge all key state handles at the end of the `onTimer()` callback execution.
