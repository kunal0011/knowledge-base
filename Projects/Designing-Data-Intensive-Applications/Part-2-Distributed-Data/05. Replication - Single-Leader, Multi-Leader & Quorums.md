# Chapter 05: Replication — Single-Leader, Multi-Leader & Quorums

> "Replication means keeping a copy of the same data on multiple machines that are connected via a network. If the data that you're storing does not change over time, replication is trivial... All of the difficulty in replication lies in handling changes to replicated data."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

Replicating data across multiple physically independent nodes is necessary for three primary reasons:
1. **High Availability:** Keeping the system operational even when some hardware nodes crash or experience network disconnections.
2. **Latency Reduction:** Placing data geographically closer to global end-users to eliminate intercontinental network transit times.
3. **Read Throughput Scaling:** Distributing query read traffic across multiple replica nodes to scale beyond single-node I/O capacity.

Every mutation (write) to the database must be propagated to all replicas. How systems coordinate these writes defines the three classical replication topologies:
- **Single-Leader Replication (Active-Passive)**
- **Multi-Leader Replication (Active-Active)**
- **Leaderless Replication (Dynamo-style)**

## 2. Underlying Runtime, Memory & Execution Architecture

### Single-Leader Replication & Replication Log Mechanics

```
 [ Client Write ]
        │
        ▼
 ┌──────────────┐
 │ Leader Node  │ ──> Writes locally to WAL / Storage Engine
 └──────┬───────┘
        │
        ├───────────────────────────────┐ (Replication Stream)
        ▼ (Synchronous ACK)             ▼ (Asynchronous ACK)
 ┌──────────────┐                ┌──────────────┐
 │ Follower 1   │                │ Follower 2   │
 │ (In-Sync)    │                │ (Lagging)    │
 └──────────────┘                └──────────────┘
```

#### 1. Synchronous vs. Asynchronous Replication
- **Synchronous:** The leader waits until the follower confirms it wrote the record before acknowledging the client. Guarantees zero data loss on leader crash, but if the synchronous follower stalls or disconnects, **all writes across the cluster freeze**.
- **Semi-Synchronous (Production Standard):** Exactly one follower is synchronous; if it becomes slow, another asynchronous follower is promoted to synchronous. All remaining followers replicate asynchronously.

#### 2. How Replication Logs Work Under the Hood
- **Statement-Based Replication (Legacy MySQL):** The leader logs every SQL statement (`INSERT INTO users ...`).  
  *Fatal Flaw:* Nondeterministic functions (`NOW()`, `RAND()`, `UUID()`) evaluate to different values on followers, silently corrupting data.
- **Write-Ahead Log (WAL) Shipping (PostgreSQL, Oracle):** Shipping exact low-level disk byte changes (memory page byte offsets).  
  *Fatal Flaw:* Couples replication tightly to storage engine byte layout, preventing zero-downtime rolling upgrades across database minor versions.
- **Logical (Row-Based) Log Replication (MySQL Binlog, CDC):** Decouples replication from disk storage: records granular row mutations (`INSERT table (col1=v1, col2=v2)`). This format enables Change Data Capture (CDC) and cross-version rolling upgrades.

## 3. Core Mechanics, Algorithms & Invariants

### The Three Classic Replication Lag Anomalies

When applications read from asynchronous follower replicas to scale read throughput, **Replication Lag** introduces severe anomalies:

#### 1. Reading Your Own Writes (Read-After-Write Consistency)
- *The Anomaly:* A user updates their profile photo, submits the form, and refreshes the page. The read is routed to a lagging follower replica that has not received the update yet. The user sees their old photo and assumes the update was lost.
- *System Fix:* When reading data that the user may have modified (e.g. user's own profile), read **strictly from the leader**. Alternatively, track the client's last update timestamp and route reads only to replicas whose replication watermark exceeds that timestamp.

#### 2. Monotonic Reads (Preventing Time Travel)
- *The Anomaly:* A user refreshes a page multiple times. Read 1 hits Follower A (lag = 100ms, shows comment 42). Read 2 hits Follower B (lag = 5000ms, comment 42 does not exist yet). The user observes time moving backwards!
- *System Fix:* Route a given user's consecutive reads to the **same replica** (e.g. by hashing `user_id` in the load balancer).

#### 3. Consistent Prefix Reads (Preserving Causality)
- *The Anomaly:* A sequence of questions and answers:
  - Alice: *"How many stars are in the galaxy?"*
  - Bob: *"Billions of stars."*
  - A third party reading from a lagging replica sees Bob's answer *before* Alice's question!
- *System Fix:* Ensure all causally related writes are directed to the **same partition**.

### Leaderless Replication (Dynamo-Style) & Quorum Mathematics

Pioneered by Amazon's Dynamo paper and adopted by Apache Cassandra and Riak, leaderless architectures allow clients to write directly to any replica without a centralized coordinator.

#### The Quorum Invariant
If there are $N$ total replicas, every write must be confirmed by $W$ nodes, and every read must query $R$ nodes:

$$W + R > N$$

```
 Total Replicas N = 5. Configured: W = 3, R = 3 (W + R = 6 > 5)

 Replicas:   [ Node 1 ]   [ Node 2 ]   [ Node 3 ]   [ Node 4 ]   [ Node 5 ]
 Write (W=3):   [ OK ]       [ OK ]       [ OK ]
 Read  (R=3):                             [ OK ]       [ OK ]       [ OK ]
                                             ▲
                                             │
                        OVERLAP NODE GUARANTEES FRESH READ!
```

Because $W + R > N$, by the Pigeonhole Principle, **at least one node in the read set $R$ must overlap with the write set $W$**. The client compares version numbers across all $R$ responses and takes the latest value.

#### Healing Divergent Replicas
1. **Read Repair:** When a client reads from $R$ nodes and detects that Node 5 returned stale data, the client asynchronously pushes the latest version to Node 5.
2. **Anti-Entropy via Merkle Trees:** Background daemon threads compare cryptographic Merkle trees of keys across replicas to detect and sync missing data without scanning entire tables.

## 4. Practical Systems & Production Engineering Trade-offs

| Replication Model | Write Latency | Conflict Resolution | Best Use Case |
| :--- | :--- | :--- | :--- |
| **Single-Leader** (Postgres, MySQL) | Medium (Leader lock) | None (Leader defines order) | Standard OLTP, relational banking ledgers. |
| **Multi-Leader** (CouchDB, Git) | Ultra-low (Local write) | Complex (CRDTs, LWW, manual) | Multi-region writes, disconnected mobile sync. |
| **Leaderless** (Cassandra, Dynamo) | Low ($W$ nodes) | Vector Clocks, Read Repair | High write availability, metric telemetry. |

## 5. Annotated Code Implementations & Algorithmic Engines

### Dynamo-Style Leaderless Quorum Engine with Read Repair

The following production Python program implements a complete leaderless quorum storage coordinator, simulating network partition delays, quorum validation ($W + R > N$), and automatic client-driven **Read Repair**:

```python
"""
Dynamo-Style Leaderless Quorum Storage Engine.
Demonstrates:
  - Quorum consistency evaluation (W + R > N)
  - Monotonic version numbering and conflict tracking
  - Automatic Read Repair on divergent replicas
"""

import time
from typing import Dict, List, Optional, Tuple


class StorageNode:
    """Simulates an individual distributed storage node."""
    def __init__(self, node_id: str):
        self.node_id = node_id
        # Local state: key -> (value, version, timestamp)
        self.store: Dict[str, Tuple[str, int, float]] = {}
        self.is_online = True

    def write(self, key: str, value: str, version: int) -> bool:
        if not self.is_online:
            return False
        # Last-Write-Wins based on version
        current = self.store.get(key)
        if current is None or version > current[1]:
            self.store[key] = (value, version, time.time())
        return True

    def read(self, key: str) -> Optional[Tuple[str, int]]:
        if not self.is_online:
            return None
        res = self.store.get(key)
        return (res[0], res[1]) if res else None


class LeaderlessClusterCoordinator:
    """Coordinates quorum reads and writes across N nodes."""

    def __init__(self, nodes: List[StorageNode], w: int, r: int):
        self.nodes = nodes
        self.n = len(nodes)
        self.w = w
        self.r = r
        assert self.w + self.r > self.n, f"Invalid quorum! W({w}) + R({r}) must be > N({self.n})"

    def put(self, key: str, value: str) -> bool:
        """Executes Quorum Write."""
        # Read current highest version across cluster
        current_val, max_version = self.get(key, trigger_repair=False)
        new_version = max_version + 1

        successful_writes = 0
        for node in self.nodes:
            if node.write(key, value, new_version):
                successful_writes += 1

        # Check if write quorum satisfied
        return successful_writes >= self.w

    def get(self, key: str, trigger_repair: bool = True) -> Tuple[Optional[str], int]:
        """Executes Quorum Read with automatic Read Repair."""
        responses: List[Tuple[StorageNode, Tuple[str, int]]] = []

        for node in self.nodes:
            val = node.read(key)
            if val is not None:
                responses.append((node, val))

        if len(responses) < self.r:
            raise RuntimeError(f"Read quorum failed! Got {len(responses)} ACKs, needed R={self.r}")

        # Find value with highest version
        highest_version = 0
        latest_value = None
        for node, (val, ver) in responses:
            if ver > highest_version:
                highest_version = ver
                latest_value = val

        # Execute Read Repair on stale nodes
        if trigger_repair and latest_value is not None:
            for node, (val, ver) in responses:
                if ver < highest_version:
                    print(f" -> [Read Repair] Updating stale Node [{node.node_id}] (v{ver} -> v{highest_version})")
                    node.write(key, latest_value, highest_version)

        return latest_value, highest_version


# Verification Execution
if __name__ == "__main__":
    # Cluster of 5 nodes, W=3, R=3
    cluster_nodes = [StorageNode(f"node-{i}") for i in range(1, 6)]
    coordinator = LeaderlessClusterCoordinator(cluster_nodes, w=3, r=3)

    print("=== 1. Quorum Write (W=3) ===")
    success = coordinator.put("account_balance", "$1,000")
    print(f"Write successful: {success}")

    # Artificially simulate Node 5 falling behind
    cluster_nodes[4].store["account_balance"] = ("$500", 0, time.time())
    print(f"Simulated stale Node 5: {cluster_nodes[4].store['account_balance']}")

    print("\n=== 2. Quorum Read with Automatic Read Repair (R=3) ===")
    val, ver = coordinator.get("account_balance")
    print(f"Quorum returned: {val} (Version {ver})")

    # Verify Node 5 was repaired
    print(f"Node 5 state after Read Repair: {cluster_nodes[4].store['account_balance']}")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Last-Write-Wins (LWW) Silent Data Loss Trap
- **Antipattern:** Resolving multi-leader or Cassandra write conflicts by comparing wall-clock timestamps (`NTP`).
- **System Consequence:** Clock skew across physical servers is inevitable (often $10\text{ms} - 100\text{ms}$). If Node B has a clock drifting 50ms fast, a write on Node A occurring *after* Node B in physical real time will receive an older timestamp. The database silently drops Node A's write.
- **Fix:** Use monotonic version numbers, **Vector Clocks**, or Conflict-Free Replicated Data Types (CRDTs).

### 2. Split-Brain Disasters in Automated Failover
- **Antipattern:** Promoting a follower to leader upon network timeout without cryptographic fencing tokens or quorum consensus.
- **System Consequence:** If a network partition isolates the old leader, the cluster now has **two active leaders**. Both accept writes, conflicting data diverge permanently, and downstream storage files corrupt.
- **Fix:** Enforce Raft/Paxos quorum-based leader election with **Fencing Tokens** on all writes.

### 3. The Sloppy Quorum Read Bleed
- **Antipattern:** Relying on Sloppy Quorums and Hinted Handoff in Dynamo-style databases expecting linearizable consistency.
- **System Consequence:** During network partitions, writes are accepted by surrogate nodes outside the primary hash ring ($W$ nodes confirmed, but not the *designated* nodes). A subsequent read query contacting primary nodes will fail to see the write, breaking $W + R > N$.
- **Fix:** Enforce strict quorums if read-your-writes guarantees are mandatory.
