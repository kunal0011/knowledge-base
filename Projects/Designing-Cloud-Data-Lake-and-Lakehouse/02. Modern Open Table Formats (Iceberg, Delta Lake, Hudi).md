# Chapter 02: Modern Open Table Formats (Iceberg, Delta Lake, Hudi)

> "A table format is the bridge between a collection of individual data files and a logical SQL table. By moving the definition of a table from physical directory paths to an immutable tree of metadata files, we unlocked ACID transactions, hidden partitioning, and independent schema evolution on cloud object storage."  
> — *Ryan Blue, Creator of Apache Iceberg*

---

## 1. Canonical Motivation & Theoretical Foundation

### Why Raw Parquet on Cloud Storage Fails
In first-generation cloud data lakes, an Apache Hive Metastore (HMS) mapped table partitions directly to physical directory structures on S3:
$$\texttt{s3://my-bucket/sales/country=US/year=2026/month=09/}$$

This primitive directory-based paradigm suffers from five fatal flaws:
1. **The Directory Listing Bottleneck:** Executing a query across a 10,000-partition table required issuing thousands of recursive `LIST` requests to S3. In large multi-terabyte datasets, query planning alone took several minutes before a single data byte was read.
2. **Lack of ACID Transactions:** If a Spark job crashed halfway through writing 100 Parquet files, half the data was visible to concurrent queries, producing dirty reads and corrupt reports.
3. **Partition Coupling & User Error:** Queries had to explicitly filter on physical partition columns (e.g. `WHERE year=2026 AND month=9`). If a user queried `WHERE event_timestamp >= '2026-09-01'`, the engine could not prune directories and scanned the entire multi-terabyte table.
4. **Catastrophic Schema Evolution:** In raw Parquet, columns were tracked by name or ordinal position. Renaming or reordering columns corrupted historical files read by old readers.
5. **No True Row-Level Mutations:** Executing an `UPDATE` or `DELETE` (required for GDPR compliance) meant rewriting an entire 500GB directory partition.

## 2. Underlying Runtime, Memory & Storage Architecture

### 1. Apache Iceberg: The Immutable Metadata Hierarchy
Apache Iceberg abandons directory listing entirely. A table is defined as an **explicit, immutable tree of metadata files**:

```
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ ICEBERG CATALOG (AWS Glue / Project Nessie / REST / Polaris)                │
 │ Points to current Table Metadata: s3://bucket/metadata/v3.metadata.json     │
 └──────────────────────────────────────┬──────────────────────────────────────┘
                                        │
                                        ▼
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ TABLE METADATA FILE (v3.metadata.json)                                      │
 │  • Current Schema (Field IDs)       • Partition Spec                        │
 │  • Snapshot History                 • Current Snapshot ID: 1002             │
 └──────────────────────────────────────┬──────────────────────────────────────┘
                                        │
                                        ▼
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ MANIFEST LIST FILE (snap-1002-manifest-list.avro)                           │
 │ Contains pointers to Manifest Files + Partition Range Summaries:            │
 │  - manifest-A.avro (date range: 2026-09-01 to 2026-09-10)                   │
 │  - manifest-B.avro (date range: 2026-09-11 to 2026-09-20)                   │
 └───────────────────────┬─────────────────────────────────────────────────────┘
                         │
                         ├────────────────────────────────────────┐
                         ▼                                        ▼
 ┌──────────────────────────────────────────┐ ┌──────────────────────────────────────────┐
 │ MANIFEST FILE (manifest-A.avro)          │ │ MANIFEST FILE (manifest-B.avro)          │
 │ Tracks individual data files + column    │ │ Tracks individual data files + column    │
 │ metrics (lower/upper bounds, null count) │ │ metrics (lower/upper bounds, null count) │
 └───────────────────┬──────────────────────┘ └───────────────────┬──────────────────────┘
                     │                                            │
                     ▼                                            ▼
 ┌──────────────────────────────────────────┐ ┌──────────────────────────────────────────┐
 │ DATA FILES: Parquet / ORC                │ │ DATA FILES: Parquet / ORC                │
 │ s3://bucket/data/file-001.parquet        │ │ s3://bucket/data/file-002.parquet        │
 └──────────────────────────────────────────┘ └──────────────────────────────────────────┘
```

#### Query Planning Velocity:
Because the Manifest List and Manifest Files contain **pre-computed lower/upper column bounds and null counts**, query engines (Trino/Spark) prune $95\%$ of data files **in memory at the coordinator without issuing a single S3 LIST request or reading Parquet footers**.

### 2. Delta Lake: The Linear JSON Transaction Log
Delta Lake structures its metadata as a single, monotonically increasing sequence of JSON commit files inside a `_delta_log/` directory:

```
_delta_log/
├── 00000000000000000000.json      # Commit 0: Table created + Add files
├── 00000000000000000001.json      # Commit 1: Append 5 Parquet files
├── ...
├── 00000000000000000010.json      # Commit 10: Delete 2 files, add 1 file
├── 00000000000000000010.checkpoint.parquet # Compacted state of commits 0-10
└── 00000000000000000011.json      # Commit 11: Subsequent write
```

- **Commit Protocol:** Commits add actions (`AddFile`, `RemoveFile`, `SetTransaction`, `ChangeMetadata`).
- **Checkpointing:** Every 10 commits, Delta Lake automatically writes an optimized Parquet checkpoint file consolidating the cumulative state. Engines read the latest checkpoint plus subsequent JSON files, avoiding full log replays.

### 3. Apache Hudi: The Streaming & Timeline Engine
Engineered at Uber for high-frequency CDC ingestion, Hudi organizes files into **File Groups** and **File Slices**:

```
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ HUDI FILE SLICE ARCHITECTURE (Merge-On-Read - MOR)                          │
 │                                                                             │
 │                   ┌───────────────────────────────────┐                     │
 │                   │   Base File (Parquet Columnar)    │                     │
 │                   │   Optimized for high-speed reads  │                     │
 │                   └─────────────────┬─────────────────┘                     │
 │                                     │                                       │
 │                      Incremental Streaming Updates                          │
 │                                     │                                       │
 │                   ┌─────────────────▼─────────────────┐                     │
 │                   │  Delta Log File 1 (.log.avro)     │                     │
 │                   │  Appended updates / deletes       │                     │
 │                   └─────────────────┬─────────────────┘                     │
 │                                     │                                       │
 │                   ┌─────────────────▼─────────────────┐                     │
 │                   │  Delta Log File 2 (.log.avro)     │                     │
 │                   └───────────────────────────────────┘                     │
 │                                                                             │
 │   • Read-Optimized View: Scans only the Base Parquet file (fast, stale).    │
 │   • Real-Time View: Merges Base Parquet + Delta Avro logs on-the-fly.       │
 │   • Asynchronous Compactor: Periodically coalesces base + logs into a new   │
 │     base Parquet file.                                                      │
 └─────────────────────────────────────────────────────────────────────────────┘
```

## 3. Core Mechanics, Algorithms & Invariants

### 1. Optimistic Concurrency Control (OCC)
Both Iceberg and Delta Lake use **Optimistic Concurrency Control (OCC)** to support concurrent writes without distributed database row locks:
1. **Read:** Transaction reads the current table snapshot $S_{\text{base}}$.
2. **Write:** Transaction writes new data files to storage (completely isolated and uncommitted).
3. **Validate & Conflict Detection:** Before committing, the engine checks whether a concurrent transaction committed snapshot $S_{\text{new}} > S_{\text{base}}$.
   - If the files modified by the concurrent transaction do **not intersect** with the files touched by the current transaction, the commit proceeds safely.
   - If a conflict exists (e.g. both modified the same partition or file), the current transaction aborts and retries.
4. **Commit:** Atomically swaps the metadata pointer (via Catalog compare-and-swap or atomic file creation).

---

### 2. Hidden Partitioning (Apache Iceberg)
In traditional systems, partitioning is physical and tied to directory paths. In Apache Iceberg, partitioning is **logical and declarative via partition transforms**:

```sql
-- Iceberg Table Definition with Hidden Partitioning
CREATE TABLE orders (
    order_id STRING,
    customer_id STRING,
    order_amount DOUBLE,
    order_timestamp TIMESTAMP
)
USING iceberg
PARTITIONED BY (days(order_timestamp), bucket(16, customer_id));
```

#### Why Hidden Partitioning is Revolutionary:
- **No Synthetic Columns:** Users do not need to create extra `order_year`, `order_month`, `order_day` columns.
- **Zero Query Leakage:** When a user queries `WHERE order_timestamp >= TIMESTAMP '2026-09-01 00:00:00'`, Iceberg automatically applies the `days()` transform and prunes partitions without requiring the user to know how the table is partitioned.
- **Partition Evolution:** An admin can change the partition spec from `days(order_timestamp)` to `hours(order_timestamp)`. Old data remains partitioned by day; new data is partitioned by hour. **Zero data rewriting is required.**

---

### 3. Row-Level Deletes & Deletion Vectors
Executing a `DELETE WHERE customer_id = 'CUST-101'` in a 50GB Parquet file can be handled in two ways:
1. **Copy-On-Write (COW):** Read the 50GB file, remove the matching rows, and write a brand-new 49.9GB Parquet file. (Extremely expensive write amplification).
2. **Merge-On-Read (MOR) with Deletion Vectors:** Leave the original Parquet file untouched. Write a lightweight **Deletion Vector** (stored as a Roaring Bitmap) tracking the exact row offsets to skip:

$$\text{Row Offset 42,819} \longrightarrow \text{MARKED DELETED}$$

During query scanning, the reader loads the base Parquet file and bitwise-masks out the deleted row indexes.

## 4. Practical Systems & Production Engineering Trade-offs

| Criterion | Apache Iceberg | Delta Lake | Apache Hudi |
| :--- | :--- | :--- | :--- |
| **Vendor Independence** | **100% Open Governance (Apache)** | Linux Foundation (Databricks steered) | Apache Software Foundation |
| **Multi-Engine Support** | **Superior (Trino, Spark, Flink, DuckDB, Snowflake, BigQuery)** | Strong (Spark first-class, Trino, DuckDB) | Strong (Spark, Flink, Presto) |
| **Partitioning Agility** | **Hidden Partitioning & Partition Evolution** | Physical directory paths | Physical directory paths |
| **Streaming CDC Performance**| Good (Merge-On-Read v2) | Good (Change Data Feed) | **Industry Best (File Slices, native record-level indexing)** |
| **Catalog Decoupling** | **Strictly Decoupled (REST, Nessie, Glue, Polaris)** | Storage-bound (`_delta_log/`) | Storage-bound (`.hoodie/`) |

### 2. Spark SQL: DDL, Hidden Partitioning, ACID Upsert & Time Travel
Complete SQL workflow demonstrating Iceberg table creation, schema evolution, ACID `MERGE INTO`, and historical time-travel auditing.

```sql
-- 1. Create Iceberg Table with Hidden Partitioning
CREATE TABLE glue_catalog.ecommerce.customer_orders (
    order_id STRING,
    customer_id STRING,
    order_amount DOUBLE,
    status STRING,
    created_at TIMESTAMP
)
USING iceberg
PARTITIONED BY (days(created_at), bucket(8, customer_id))
TBLPROPERTIES (
    'write.format.default' = 'parquet',
    'write.parquet.compression-codec' = 'zstd',
    'write.delete.mode' = 'merge-on-read',
    'history.expire.max-snapshot-age-ms' = '604800000' -- 7 Days Retention
);

-- 2. Schema Evolution: In-place column addition (Zero data rewrites)
ALTER TABLE glue_catalog.ecommerce.customer_orders 
ADD COLUMN loyalty_discount DOUBLE AFTER order_amount;

-- 3. ACID Upsert via MERGE INTO (Deduplication / CDC stream merge)
MERGE INTO glue_catalog.ecommerce.customer_orders target
USING incoming_orders_stage source
ON target.order_id = source.order_id
WHEN MATCHED AND source.status = 'CANCELLED' THEN
    UPDATE SET target.status = 'CANCELLED', target.loyalty_discount = source.loyalty_discount
WHEN MATCHED THEN
    UPDATE SET *
WHEN NOT MATCHED THEN
    INSERT *;

-- 4. Historical Time-Travel Auditing
-- Query the exact table state as it existed 2 days ago
SELECT status, count(*) 
FROM glue_catalog.ecommerce.customer_orders
TIMESTAMP AS OF '2026-09-14 10:00:00'
GROUP BY status;

-- Query specific historical snapshot by ID
SELECT * FROM glue_catalog.ecommerce.customer_orders
VERSION AS OF 889213847291823749;
```

### 3. Delta Lake: ACID Merge with Deletion Vectors
PySpark script demonstrating Delta Lake table initialization with Deletion Vectors enabled for high-performance updates.

```python
from delta import configure_spark_with_delta_pip, DeltaTable
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

builder = SparkSession.builder \
    .appName("DeltaLakeProduction") \
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension") \
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")

spark = configure_spark_with_delta_pip(builder).getOrCreate()

delta_table_path = "s3a://enterprise-lakehouse-prod-us-east-1/delta/orders/"

# Enable Deletion Vectors on Delta Table to eliminate full-file copy amplification
spark.sql(f"""
    ALTER TABLE delta.`{delta_table_path}` 
    SET TBLPROPERTIES (
        'delta.enableDeletionVectors' = true,
        'delta.autoOptimize.optimizeWrite' = true
    )
""")

deltaTable = DeltaTable.forPath(spark, delta_table_path)

# Incoming micro-batch updates
incoming_df = spark.read.json("s3a://enterprise-lakehouse-prod-us-east-1/raw/updates.json")

# Execute atomic MERGE INTO using Deletion Vectors
deltaTable.alias("target").merge(
    source=incoming_df.alias("source"),
    condition="target.order_id = source.order_id"
).whenMatchedUpdate(
    condition="source.updated_at > target.updated_at",
    set={"status": col("source.status"), "order_amount": col("source.order_amount")}
).whenNotMatchedInsertAll().execute()

print("Delta Lake ACID Merge successfully committed with Deletion Vectors.")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Outage Triage

### 1. Metadata File Explosion (The Manifest Driver OOM)
- **The Pitfall:** In high-frequency streaming ingestion (e.g. micro-batches writing every 30 seconds), an Iceberg table accumulates $100,000+$ manifest files and metadata JSON snapshots over a few months.
- **Failure Mode:** When a Trino coordinator or Spark driver initiates query planning, it attempts to load all active manifests into memory. The JVM heap exhausts, throwing `java.lang.OutOfMemoryError: Java heap space` during query planning before any data tasks launch.
- **Remediation:** Schedule automated maintenance procedures:
  ```sql
  -- Expire historical snapshots older than 7 days
  CALL glue_catalog.system.expire_snapshots(
      table => 'ecommerce.customer_orders',
      older_than => TIMESTAMP '2026-09-09 00:00:00',
      retain_last => 10
  );
  -- Rewrite and coalesce small manifest files
  CALL glue_catalog.system.rewrite_manifests('ecommerce.customer_orders');
  ```

### 2. The OCC Write-Conflict Avalanche (`CommitFailedException`)
- **The Pitfall:** 20 concurrent Spark streaming or batch jobs attempt to write to the same Iceberg/Delta partition simultaneously.
- **Failure Mode:** All 20 jobs read Snapshot $N$. The first job commits Snapshot $N+1$. The remaining 19 jobs fail validation, throw `CommitFailedException`, and retry simultaneously, generating an exponential write-contention storm.
- **Remediation:** Design ingestion pipelines to isolate target partitions by tenant or source stream, or serialize writes through a single orchestration worker (e.g. Apache Flink or Kafka Connect sink).

### 3. Outage Triage: Orphan Data Files Leaking S3 Storage
- **Symptom:** Cloud billing alerts show S3 bucket storage growing continuously, but `SELECT count(*) FROM table` remains constant.
- **Root Cause:** Failed Spark writes or aborted commits left physical `.parquet` files on S3 that are unreferenced by any valid metadata snapshot.
- **Resolution:** Run the Iceberg orphan file removal procedure:
  ```sql
  CALL glue_catalog.system.remove_orphan_files(
      table => 'ecommerce.customer_orders',
      older_than => TIMESTAMP '2026-09-13 00:00:00'
  );
  ```
