# Chapter 09: Consistency & Consensus — Linearizability to Raft

> "Consensus is one of the most important and fundamental problems in distributed computing: getting several nodes to agree on something. Once you have a consensus algorithm, you can build a linearizable, fault-tolerant system."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

## 1. Canonical Motivation & Theoretical Foundation

In distributed architectures, many critical operations require multiple independent nodes to reach unanimous or majority agreement:
- **Leader Election:** Deciding which node is the current authoritative leader to avoid split-brain.
- **Distributed Atomic Commit (2PC):** Deciding whether a cross-shard transaction should be committed or aborted.
- **Distributed Locking:** Agreeing on which client holds exclusive access to a resource.

### The FLP Impossibility Result (1985)
In a landmark 1985 paper, researchers Fischer, Lynch, and Paterson mathematically proved that **in an asynchronous network model, no deterministic consensus algorithm can guarantee termination if even a single node can fail by crashing**.

Modern consensus algorithms (Paxos, Raft, Zab) circumvent FLP impossibility by assuming a **Partially Synchronous System Model**: they rely on randomized clocks and timeouts to detect suspected failures, ensuring that whenever network conditions normalize, consensus is guaranteed to terminate safely.

## 2. Underlying Runtime, Memory & Execution Architecture

### Linearizability vs. Serializability

These two terms are frequently confused, but address orthogonal dimensions of distributed correctness:

```
 ┌───────────────────────────────────┬─────────────────────────────────────────────────────────────┐
 │ Concept                           │ Core Definition & Guarantee                                 │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Serializability**               │ A **multi-operation, multi-object transaction** isolation   │
 │                                   │ property. Ensures transactions behave as if executed in      │
 │                                   │ some serial order. Does NOT require real-time recency!       │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Linearizability**               │ A **single-operation, single-object** recency guarantee.    │
 │ (Strong Consistency)              │ Makes the system appear as if there is only a single copy   │
 │                                   │ of the data, and all mutations take effect instantaneously. │
 ├───────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **Strict Serializability**        │ Combines both: transactions are serializable, AND their     │
 │ (External Consistency)            │ order reflects real-world physical wall-clock time.         │
 └───────────────────────────────────┴─────────────────────────────────────────────────────────────┘
```

#### Visualizing Linearizability:
Once a read operation returns the new value $B$, **no subsequent read can ever return the old value $A$**:

```
 Client 1: ───[ Write x = B ]─────────────────────────────────────────>
                     ▲
                     │ (Operation takes effect at this instant)
 Client 2: ────────────────[ Read x -> returns B ]─────────────────────>
                                       ▲
                                       │
 Client 3: ─────────────────────────────────[ Read x -> MUST RETURN B! ]
                                             (Cannot return old value A!)
```

### The Cost of Linearizability (The Real CAP Theorem)
The CAP theorem states that if a network partition occurs between datacenter clusters, a system must choose between:
- **Linearizability (Consistency):** Refusing writes on minority partitions to maintain strong consistency (sacrificing availability).
- **Availability:** Allowing writes on minority partitions (violating linearizability).

## 3. Core Mechanics, Algorithms & Invariants

### Distributed Transactions: Two-Phase Commit (2PC)

When a transaction spans multiple database nodes (e.g. transferring money between two accounts on different shards), standard single-node commit is insufficient. The classic solution is **Two-Phase Commit (2PC)** coordinated by a Transaction Coordinator:

```
       [ Coordinator ]                     [ Node 1 ]               [ Node 2 ]
              │                                │                        │
              │ 1. PREPARE ───────────────────>│                        │
              │ 1. PREPARE ────────────────────┼───────────────────────>│
              │                                │                        │
              │<── 2. VOTE: YES (WAL Flushed) ─┤                        │
              │<── 2. VOTE: YES (WAL Flushed) ─┼────────────────────────┘
              │                                │
              ├── 3. Write COMMIT to local WAL │
              │                                │
              │ 4. COMMIT ────────────────────>│
              │ 4. COMMIT ─────────────────────┼───────────────────────>│
              │                                │                        │
              │<── 5. ACK ─────────────────────┤                        │
              │<── 5. ACK ─────────────────────┼────────────────────────┘
```

#### The Fatal Flaw of 2PC: The Coordinator Single Point of Failure
If the Coordinator sends `PREPARE` to all nodes, receives `YES` votes from all nodes, writes `COMMIT` to its local disk, and then **immediately crashes** before broadcasting the `COMMIT` messages:
- Node 1 and Node 2 have promised to commit and cannot abort.
- But they do not know whether the coordinator decided to commit or abort!
- The transaction enters an **In-Doubt State**. Node 1 and Node 2 must hold locks on those rows **indefinitely** until the coordinator is manually recovered.

---

### Fault-Tolerant Consensus: Raft, Paxos, and Zab

Unlike 2PC (which requires $100\%$ of nodes to participate and blocks if one fails), **Consensus Algorithms** (Paxos, Raft, Zab) only require a **Quorum (Majority)** of nodes:

$$\text{Quorum} = \left\lfloor \frac{N}{2} \right\rfloor + 1$$

A 5-node Raft cluster can safely continue operating and committing writes even if 2 nodes crash!

```
 Raft Node State Machine:
 ┌───────────┐      Election Timeout       ┌───────────┐      Receives Votes from Majority     ┌──────────┐
 │ Follower  │ ──────────────────────────> │ Candidate │ ────────────────────────────────────> │  Leader  │
 └─────▲─────┘                             └─────┬─────┘                                       └────┬─────┘
       │                                         │                                                  │
       └─────────────────────────────────────────┴──────────────────────────────────────────────────┘
                            Discovers Leader with Higher Term (Heartbeat)
```

#### Raft Core Invariants:
1. **Term Numbers:** Logical time is divided into monotonically increasing **Terms** (acting as fencing tokens).
2. **Leader Election:** Nodes start as Followers. If a follower does not receive a heartbeat within a randomized timeout (150ms–300ms), it transitions to Candidate and requests votes. If it collects a majority of votes, it becomes Leader.
3. **Log Matching Property:** If two logs contain an entry with the same index and term, they are identical up to that index.
4. **Leader Completeness:** A candidate can only be elected if its log is at least as up-to-date as any other node in the majority.

## 4. Practical Systems & Production Engineering Trade-offs

1. **Etcd (Raft):** Powers the Kubernetes control plane, maintaining cluster state and configuration.
2. **Apache ZooKeeper (Zab):** Historically coordinated Hadoop, HBase, and Kafka clusters, managing distributed leader locks.
3. **KRaft (Kafka Raft):** Replaced ZooKeeper in Apache Kafka 3.x, embedding consensus directly inside broker nodes to scale partitions past 1,000,000.

## 5. Annotated Code Implementations & Algorithmic Engines

### Simplified Raft Consensus Node (Leader Election & Heartbeats)

The following complete Python program implements a working simulation of a Raft consensus node, demonstrating randomized election timeouts, vote solicitation, and majority quorum counting:

```python
"""
Raft Consensus Engine Simulation: Leader Election & Heartbeat Protocol.
Demonstrates:
  - Role state machine (Follower -> Candidate -> Leader)
  - Randomized election timeout countdowns
  - Majority quorum voting (N // 2 + 1)
  - Heartbeat broadcasting to maintain leadership authority
"""

import random
import time
from typing import Dict, List, Optional


class RaftNode:
    def __init__(self, node_id: str, peers: List[str]):
        self.node_id = node_id
        self.peers = peers
        self.total_cluster_size = len(peers) + 1

        # Persistent State
        self.current_term = 0
        self.voted_for: Optional[str] = None
        self.log: List[Dict[str, any]] = []

        # Volatile State
        self.state = "FOLLOWER" # FOLLOWER, CANDIDATE, LEADER
        self.votes_received: Set[str] = set()
        self.last_heartbeat = time.time()
        self.election_timeout = random.uniform(0.15, 0.30) # 150ms - 300ms

    def tick(self, current_time: float, cluster_registry: Dict[str, "RaftNode"]) -> None:
        """Executed on every periodic timer tick."""
        if self.state == "FOLLOWER":
            if current_time - self.last_heartbeat > self.election_timeout:
                print(f"[Timeout] {self.node_id} received no heartbeat. Starting Election!")
                self.start_election(cluster_registry)

        elif self.state == "CANDIDATE":
            if current_time - self.last_heartbeat > self.election_timeout:
                self.start_election(cluster_registry)

        elif self.state == "LEADER":
            # Broadcast heartbeats to all followers
            self.broadcast_heartbeats(cluster_registry)

    def start_election(self, cluster_registry: Dict[str, "RaftNode"]) -> None:
        """Transitions to Candidate and solicits votes from peers."""
        self.state = "CANDIDATE"
        self.current_term += 1
        self.voted_for = self.node_id
        self.votes_received = {self.node_id} # Vote for self
        self.last_heartbeat = time.time()
        self.election_timeout = random.uniform(0.15, 0.30)

        print(f"[{self.node_id}] Soliciting votes for Term {self.current_term}...")
        for peer_id in self.peers:
            peer = cluster_registry[peer_id]
            vote_granted = peer.request_vote(self.node_id, self.current_term)
            if vote_granted:
                self.votes_received.add(peer_id)

        # Check if majority quorum achieved
        majority = (self.total_cluster_size // 2) + 1
        if len(self.votes_received) >= majority:
            self.state = "LEADER"
            print(f"*** [{self.node_id}] ELECTED LEADER for Term {self.current_term} with {len(self.votes_received)}/{self.total_cluster_size} votes! ***")

    def request_vote(self, candidate_id: str, term: int) -> bool:
        """RPC callback: evaluate incoming vote request from candidate."""
        if term > self.current_term:
            self.current_term = term
            self.state = "FOLLOWER"
            self.voted_for = None

        if term == self.current_term and (self.voted_for is None or self.voted_for == candidate_id):
            self.voted_for = candidate_id
            self.last_heartbeat = time.time()
            return True
        return False

    def broadcast_heartbeats(self, cluster_registry: Dict[str, "RaftNode"]) -> None:
        """Leader broadcasts periodic empty AppendEntries RPCs."""
        for peer_id in self.peers:
            peer = cluster_registry[peer_id]
            peer.receive_heartbeat(self.node_id, self.current_term)

    def receive_heartbeat(self, leader_id: str, term: int) -> None:
        """Follower receives heartbeat from leader."""
        if term >= self.current_term:
            self.current_term = term
            self.state = "FOLLOWER"
            self.voted_for = leader_id
            self.last_heartbeat = time.time()


# Verification Execution
if __name__ == "__main__":
    node_ids = ["node-1", "node-2", "node-3"]
    registry: Dict[str, RaftNode] = {}

    for nid in node_ids:
        peers = [p for p in node_ids if p != nid]
        registry[nid] = RaftNode(nid, peers)

    # Fast-forward time to trigger election
    print("=== Starting Raft Cluster Simulation (3 Nodes) ===")
    start = time.time()
    while not any(n.state == "LEADER" for n in registry.values()):
        simulated_time = time.time()
        for node in registry.values():
            node.tick(simulated_time, registry)
        time.sleep(0.05)

    print("Raft consensus leader election completed successfully!")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. In-Doubt Transactions Locking 2PC Databases Forever
- **Antipattern:** Using Two-Phase Commit (XA Transactions) across microservices without an automated coordinator recovery protocol.
- **System Consequence:** If the coordinator process crashes during the commit phase, participant databases remain locked indefinitely holding exclusive row locks. Sibling read/write queries queue up and eventually crash the database.
- **Fix:** Avoid heterogeneous 2PC across microservices. Use asynchronous **Saga Orchestration** with compensating transactions.

### 2. ZooKeeper / Etcd Flapping Under GC Pauses
- **Antipattern:** Setting ZooKeeper session timeouts too aggressively (e.g. 1,000ms) on worker nodes running heavy JVM heaps.
- **System Consequence:** A minor 1.2-second Stop-the-World GC pause causes the coordinator to believe the node has died. ZooKeeper reaps the ephemeral lock, triggers leader re-election, and wakes the cluster up into a storm of rebalances.
- **Fix:** Keep heartbeat session timeouts between **10 to 30 seconds**.

### 3. Raft Leader Split-Brain Under Asymmetric Partitions
- **Antipattern:** Running a Raft cluster with an even number of nodes (e.g. 4 nodes) across two datacenters (2 in DC1, 2 in DC2).
- **System Consequence:** If the network link between DC1 and DC2 is severed, neither partition can form a majority quorum ($2/4 = 50\% < 3$). The entire cluster becomes **$100\%$ unavailable** for writes.
- **Fix:** Always deploy an **odd number of nodes** (3, 5, or 7) and maintain an odd distribution across failure zones.
