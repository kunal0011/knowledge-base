## ⚖️ 1. Kubernetes Resource Model & Kernel Enforcements

Kubernetes models two primary computational resources:
1. **CPU (Compressible):** Expressed in millicores ($1000\text{m} = 1\text{ vCPU}$). When a container exceeds its CPU limit, the Linux kernel **throttles** execution using the Completely Fair Scheduler (CFS) bandwidth control (`cfs_quota_us` / `cfs_period_us`). The process slows down, but does not crash.
2. **Memory (Incompressible):** Expressed in bytes (`Mi`, `Gi`). When a container exceeds its memory limit, the Linux kernel cannot throttle it. The kernel invokes the **Out-Of-Memory (OOM) Killer**, terminating the process immediately with Exit Code `137` (`SIGKILL`).

```text
===================================================================================================
                             REQUESTS VS. LIMITS: SYSTEM ROLES
===================================================================================================

                Pod Manifest Spec
                ├── requests.cpu: 500m      ──► Used exclusively by kube-scheduler for Bin-Packing
                ├── requests.memory: 1Gi        (Guarantees allocation; reserves node capacity)
                │
                ├── limits.cpu: 2000m       ──► Kernel CFS Bandwidth Quota (Throttles if exceeded)
                └── limits.memory: 2Gi      ──► Kernel cgroup memory.max (OOMKills if exceeded)
```

## 🎯 2. Quality of Service (QoS) Classes & Linux OOM Scoring

Kubernetes automatically classifies every Pod into one of three QoS classes based strictly on its declared resource requests and limits. This classification determines the Linux kernel's `/proc/$PID/oom_score_adj`.

```text
===================================================================================================
                                  QoS CLASS EVICTION HIERARCHY
===================================================================================================

  Node Under Memory Pressure
  │
  ├─► [ Killed First ]  BestEffort
  │   - Condition: No requests or limits set on any container.
  │   - Kernel oom_score_adj: 1000
  │
  ├─► [ Killed Second ] Burstable
  │   - Condition: requests < limits (or only requests set).
  │   - Kernel oom_score_adj: 1000 - (1000 * requests.memory) / NodeCapacity.memory
  │
  └─► [ Killed Last ]   Guaranteed
      - Condition: requests == limits for CPU AND memory across ALL containers.
      - Kernel oom_score_adj: -997 (Protected system processes are -1000)
```

> [!IMPORTANT]
> In production environments, critical databases and zero-tolerance message brokers (PostgreSQL, Kafka, Redis) **must** be deployed with identical requests and limits to receive the `Guaranteed` QoS class, shielding them from node eviction cascades.

## 🧩 3. Advanced Pod Placement & Topology Distribution

`kube-scheduler` filters nodes (predicates) and scores surviving nodes (priorities). Operators direct placement via three complementary mechanisms:

### 3.1 Affinities & Anti-Affinities
- **`nodeAffinity`:** Directs pods to specific node groups (e.g., GPU instances, specific cloud availability zones).
- **`podAntiAffinity`:** Prevents pods of the same application from sharing the same failure domain (nodes or AZs).

```yaml
# Production Anti-Affinity: Never schedule two replicas on the same physical host
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - order-service
        topologyKey: "kubernetes.io/hostname"
```

### 3.2 Taints and Tolerations
While affinities attract Pods to nodes, **Taints** repel Pods unless they possess matching **Tolerations**.
- `NoSchedule`: Prevent scheduling new pods without matching toleration.
- `PreferNoSchedule`: Soft rejection.
- `NoExecute`: Evict already-running pods immediately if they lack the toleration.

```bash
# Taint dedicated GPU node
kubectl taint nodes gpu-node-01 dedicated=gpu:NoSchedule
```
```yaml
# Pod toleration to permit running on the tainted GPU node
tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```

### 3.3 Topology Spread Constraints (Even Zone Balancing)
To survive whole Availability Zone outages in AWS or GCP:
```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: payment-api
```

## 📈 4. The Autoscaling Triad: HPA, VPA & Karpenter

Modern cloud-native systems require autoscaling across both the application layer (Pods) and the infrastructure layer (Nodes).

```text
===================================================================================================
                                AUTOSCALING CONTROL ARCHITECTURE
===================================================================================================

                 [ Application Demand Spike / Traffic Surge ]
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
   Horizontal Pod Autoscaler (HPA)           Vertical Pod Autoscaler (VPA)
   (Scales Pod Count Out: 3 -> 12)           (Scales Pod Size Up: 1Gi -> 4Gi)
                 │                                         │
                 └────────────────────┬────────────────────┘
                                      │
                         Pods enter "Pending" state
                         (Cluster out of CPU/Memory)
                                      │
                                      ▼
                        Karpenter / Cluster Autoscaler
                        (Provisions new worker nodes)
```

### 4.1 Horizontal Pod Autoscaler (HPA v2) Math
The HPA controller runs periodically (default every 15 seconds) inside `kube-controller-manager`:
$$\text{DesiredReplicas} = \left\lceil \text{CurrentReplicas} \times \left( \frac{\text{CurrentMetricValue}}{\text{TargetMetricValue}} \right) \right\rceil$$

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-autoscaler
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-service
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "1500m"
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Prevent flapping
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
```

## ⚡ 5. Next-Gen Node Autoscaling: Karpenter vs. Legacy Cluster Autoscaler

| Architectural Dimension | Legacy Cluster Autoscaler (CAS) | Karpenter (Next-Generation) |
| :--- | :--- | :--- |
| **Abstraction Level** | Bound to cloud provider Node Groups / AWS Auto Scaling Groups (ASGs). | Group-less; bypasses ASGs, communicates directly with cloud EC2 Fleet API. |
| **Scheduling Speed** | Slow ($2\text{ to }5\text{ minutes}$ per node spin-up). | Fast ($30\text{ to }45\text{ seconds}$ from pending pod to running). |
| **Instance Selection** | Rigid: scales predefined instance types within a single ASG. | Dynamic: computes optimal instance type, architecture (x86 vs ARM Graviton), and Spot vs On-Demand based on exact pending pod specs. |
| **Node Consolidation** | Clunky drain algorithms; frequently leaves nodes underutilized. | Active bin-packing consolidation: constantly deletes underutilized nodes or replaces them with cheaper instances. |

### Karpenter NodePool Configuration
```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: general-compute
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: kubernetes.io/arch
          operator: In
          values: ["arm64", "amd64"]
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["c6g.xlarge", "c6i.xlarge", "m6g.xlarge", "m6i.xlarge"]
      nodeClassRef:
        name: default-ec2-node-class
  disruption:
    consolidationPolicy: WhenUnderutilized
    expireAfter: 720h # 30-day node rotation
```
