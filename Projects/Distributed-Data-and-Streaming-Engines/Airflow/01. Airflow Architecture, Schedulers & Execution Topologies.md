# Chapter 01: Airflow Architecture, Schedulers & Execution Topologies

> "Airflow is an orchestrator, not an execution engine: its purpose is to trigger, monitor, and coordinate distributed systems—not to crunch petabytes of data inside Python worker processes."  
> — *Bas P. Harenslak & Julian Rutger de Ruiter, Data Pipelines with Apache Airflow*

---

## 1. Canonical Motivation & Theoretical Foundation

In modern enterprise data platforms, data workflows span dozens of heterogeneous systems: extracting relational data from PostgreSQL, triggering Apache Spark jobs on Kubernetes, copying data to Snowflake, training models in PyTorch, and invalidating caches in Redis.

Attempting to orchestrate these workflows using cron jobs, bash scripts, or point-to-point microservice calls quickly leads to catastrophic architectural failure:
1. **No Dependency Graph Representation:** Cron cannot express: *"Run Job C only after Job A and Job B succeed, but if Job A fails, run Alert D."*
2. **Zero Centralized Observability:** Failures are buried across disparate log directories across dozens of virtual machines.
3. **No Dynamic Backfilling or Idempotency:** Re-running historical date intervals requires hazardous manual script modifications.

**Apache Airflow** was created to solve workflow orchestration by representing pipelines as **Directed Acyclic Graphs (DAGs)** defined entirely as **Configuration-as-Code** in standard Python. 

The fundamental architectural tenet of Airflow is the **Separation of Orchestration from Compute**:
Airflow functions as the distributed control plane. It determines *when* and *in what order* tasks run, passing workloads to specialized compute engines (Spark, Trino, Snowflake, Kubernetes) rather than processing raw data directly inside its own workers.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Distributed Airflow Component Ecosystem

A production Apache Airflow deployment consists of five primary distributed components:

```
                            ┌───────────────────────────────────┐
                            │           Webserver (UI)          │
                            │ Reads metadata, triggers DAG runs │
                            └─────────────────┬─────────────────┘
                                              │ (SQL Queries)
                                              ▼
 ┌───────────────────────┐         ┌─────────────────────┐         ┌───────────────────────┐
 │   DAG Directory       │         │  Metadata Database  │         │       Triggerer       │
 │  (Shared Volume /     ├────────>│ (PostgreSQL / MySQL)│<────────┤ (Asyncio event loop   │
 │   Git-Sync Daemon)    │         │  Heart of Airflow   │         │  for deferrable tasks)│
 └──────────┬────────────┘         └──────────┬──────────┘         └───────────────────────┘
            │                                 │ (Locks / State updates)
            ▼                                 ▼
 ┌───────────────────────────────────────────────────────────────┐
 │                    Scheduler (HA Multi-Node)                  │
 │  1. DagFileProcessor: Parses Python files into Serialized DAGs │
 │  2. SchedulerLoop: Evaluates dependencies & marks tasks QUEUED│

 └───────────────────────────────┬───────────────────────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
    ┌───────────────────────────┐   ┌───────────────────────────┐
    │  Celery / Redis / Rabbit  │   │   Kubernetes API Server   │
    │  (Task Queue Broker)      │   │   (Pods launched on demand│

    └───────────────────────────┘   └───────────────────────────┘
```

#### 1. The Metadata Database
The single source of truth for the entire cluster. It stores DAG structures (`dag`), historical runs (`dag_run`), individual task instance states (`task_instance`), user variables, connections, and distributed execution locks.

#### 2. The Scheduler
The heartbeat of Airflow. Multiple schedulers can run concurrently in High Availability (HA) mode:
- **`DagFileProcessor`:** Periodically executes DAG Python files in isolated child processes, serializing the resulting DAG objects into JSON inside the metadata DB (`serialized_dag` table).
- **Scheduler Loop:** Queries the metadata DB for tasks whose upstream dependencies have succeeded and whose execution schedules are satisfied, transitioning task states from `NONE` $\to$ `SCHEDULED` $\to$ `QUEUED`.

#### 3. Execution Topologies (Executors)

| Executor Type | Architecture & Scalability | Worker Lifecycle | Best Use Case |
| :--- | :--- | :--- | :--- |
| **`SequentialExecutor`** | Single process, SQLite only. Strictly 1 task at a time. | N/A (In-process) | Local development / quick smoke testing only. |
| **`LocalExecutor`** | Multi-process worker pool on single host. Scales to host CPU cores. | Long-running worker processes | Small-to-medium single-server production deployments. |
| **`CeleryExecutor`** | Distributed queue-based execution via Redis/RabbitMQ. | Long-running dedicated worker VMs/containers | High-throughput steady-state workloads across fixed worker clusters. |
| **`KubernetesExecutor`** | Native dynamic pod creation per task via K8s API. | Ephemeral (pod created on task start, destroyed on task exit) | Variable workloads, multi-tenant isolation, custom Docker images per task. |
| **`CeleryKubernetesExecutor`**| Hybrid: lightweight tasks route to Celery; heavy isolated tasks route to K8s. | Mixed | Massive enterprise clusters with heterogeneous workloads. |

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Task State Machine

Every task execution progresses through a deterministic distributed state machine tracked inside the `task_instance` table:

```
 [ None ] ──> [ Scheduled ] ──> [ Queued ] ──> [ Running ] ──┬──> [ Success ]
                                    ▲               │        │
                                    │ (Retry)       │        ├──> [ Failed ]
                                    └───────────────┴────────┤
                                                             └──> [ Upstream Failed ]
```

## 5. Annotated Code Implementations & Execution Traces

### Production DAG with Heterogeneous Executor Queue Routing & Retries

The following production Python DAG demonstrates robust configuration, queue-specific routing, retry policies, and dependency chaining:

```python
"""
Production Orchestration DAG: Data Extraction, Validation, and External Compute.
Demonstrates:
  - Robust default arguments (retries, timeouts, SLA)
  - Queue targeting for CeleryExecutor
  - Dependency branching and failure callbacks
"""

from datetime import datetime, timedelta
import logging

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.empty import EmptyOperator
from airflow.operators.python import PythonOperator

logger = logging.getLogger(__name__)


def on_failure_callback(context):
    """Global failure hook sending alerts to incident response."""
    dag_id = context.get("dag").dag_id
    task_id = context.get("task_instance").task_id
    execution_date = context.get("execution_date")
    error = context.get("exception")
    logger.error(
        f"CRITICAL: Task Failed! DAG: {dag_id}, Task: {task_id}, "
        f"Execution Date: {execution_date}, Error: {error}"
    )


# Standard enterprise default arguments
DEFAULT_ARGS = {
    "owner": "data-platform-team",
    "depends_on_past": False,
    "email_on_failure": False,
    "email_on_retry": False,
    "retries": 3,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,
    "max_retry_delay": timedelta(minutes=30),
    "execution_timeout": timedelta(hours=2),
    "on_failure_callback": on_failure_callback,
}


def perform_data_validation(**context):
    """Simulates validating ingested records."""
    logger.info("Executing row-count and schema validation checks...")
    # Business logic verification
    return True


with DAG(
    dag_id="enterprise_orders_orchestrator_v1",
    default_args=DEFAULT_ARGS,
    description="Orchestrates ingestion, spark transform, and data mart publishing",
    schedule_interval="0 2 * * *",  # Daily at 02:00 UTC
    start_date=datetime(2026, 1, 1),
    catchup=False,  # Prevent automatic backfill stampedes on deployment
    max_active_runs=1,  # Serial execution across execution dates
    tags=["production", "orders", "lakehouse"],
) as dag:

    start = EmptyOperator(task_id="start_pipeline")

    # Step 1: Lightweight database extraction task running on standard worker queue
    extract_orders = BashOperator(
        task_id="extract_raw_orders",
        bash_command="echo 'Extracting orders via CDC dump...' && sleep 2",
        queue="default",  # Celery queue targeting
    )

    # Step 2: Ingest validation executed via Python callable
    validate_extraction = PythonOperator(
        task_id="validate_raw_data",
        python_callable=perform_data_validation,
        queue="default",
    )

    # Step 3: Heavy compute delegated to external Spark cluster via submit script
    # Targeted to specialized compute queue or K8s pod operator
    run_spark_lakehouse_transform = BashOperator(
        task_id="submit_spark_transform",
        bash_command=(
            "echo 'Submitting Apache Spark job to Kubernetes cluster...' "
            "&& echo 'Job completed successfully.'"
        ),
        queue="heavy_compute",
        execution_timeout=timedelta(hours=4),
    )

    # Step 4: Publish to data warehouse
    publish_data_mart = EmptyOperator(task_id="publish_gold_tables")

    end = EmptyOperator(task_id="end_pipeline")

    # Express dependencies explicitly
    start >> extract_orders >> validate_extraction >> run_spark_lakehouse_transform >> publish_data_mart >> end
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Heavy Compute in Worker Anti-Pattern
- **Antipattern:** Writing custom Python functions that load 50GB Pandas DataFrames directly inside `PythonOperator` workers.
- **System Consequence:** Airflow workers are not distributed compute engines. Memory consumption spikes violently, causing Linux OOM-killer to terminate the worker process (`SIGKILL`). Sibling tasks running on the same worker crash without clean state reporting, turning into "Zombie Tasks."
- **Fix:** Delegate all heavy computation to external systems using dedicated operators (`SparkSubmitOperator`, `SnowflakeOperator`, `KubernetesPodOperator`). Keep Airflow worker tasks strictly orchestrational (making API requests and checking statuses).

### 2. Top-Level Code in DAG Files
- **Antipattern:** Executing database queries, HTTP requests, or heavy computations at the top level of a DAG file (outside of operator execute callables).
  ```python
  # CATASTROPHIC ANTI-PATTERN:
  db_connection = psycopg2.connect(...)
  table_list = db_connection.cursor().execute("SELECT table_name FROM ...")
  ```
- **System Consequence:** The Airflow `DagFileProcessor` parses **every single Python file** in the `dags/` folder once every few seconds (`scheduler.dag_dir_list_interval`). Executing network calls at the top level causes the scheduler parsing loop to stall, starving the scheduler and freezing cluster task progression.
- **Fix:** Confine all dynamic operations, network calls, and heavy imports inside task execution callbacks or custom operators.

### 3. Catchup Stampede on DAG Deployment
- **Antipattern:** Deploying a new DAG with `start_date = datetime(2025, 1, 1)` and leaving the default `catchup=True`.
- **System Consequence:** The instant the DAG is unpaused, the scheduler immediately creates and queues hundreds of DAG runs (one for every historical scheduling interval from 2025 to 2026). The metadata database is inundated with hundreds of concurrent queries, and workers are overwhelmed.
- **Fix:** Always set `catchup=False` unless historical backfilling is explicitly planned, and use CLI backfills with bounded concurrency (`airflow dags backfill -s <start> -e <end>`).
