## 🌐 1. The Fundamental Kubernetes Network Model

In traditional virtualized or container environments (such as standard Docker bridge networks), containers obtain private host-internal IPs (e.g., `172.17.0.x`) and rely on port-mapping (DNAT) on the host interface to expose services. This creates port allocation conflicts, hides the original source IP, and complicates service-to-service discovery.

Kubernetes establishes **The Fundamental IP-per-Pod Networking Model**:
1. **Uniqueness:** Every Pod receives a unique, routable IP address within the cluster's Pod CIDR.
2. **Direct Pod-to-Pod Communication:** Any Pod can communicate with any other Pod on any node directly by IP without NAT.
3. **Node-to-Pod Communication:** Daemons on a host (e.g., `kubelet`) can communicate with all Pods on that host.
4. **Self-Consistency:** The IP that a Pod sees as its own address is the exact same IP that all other Pods observe when communicating with it.

## 🔌 2. Container Network Interface (CNI) Architecture

The **Container Network Interface (CNI)** is a CNCF specification providing a standard interface between container runtimes (like `containerd`, `CRI-O`) and network implementations.

### 2.1 CNI Execution Protocol
When `kubelet` instructs the runtime to create a Pod sandbox:
1. The runtime creates a dedicated network namespace (`/proc/$PID/ns/net`).
2. The runtime invokes CNI plugin binaries located in `/opt/cni/bin/` with environment variables:
   - `CNI_COMMAND`: `ADD`, `DEL`, or `CHECK`.
   - `CNI_CONTAINERID`: Unique container identifier.
   - `CNI_NETNS`: Path to the network namespace file.
   - `CNI_IFNAME`: Target interface name inside the Pod (usually `eth0`).
   - `CNI_PATH`: Search path for CNI binaries.
3. Network configuration JSON is passed via `STDIN` (from `/etc/cni/net.d/`).

```text
 kubelet ──(CRI gRPC: RunPodSandbox)──► containerd
                                             │
                                             ▼
                                  Executes CNI Plugin
                                  (e.g., /opt/cni/bin/calico)
                                             │
                       ┌─────────────────────┴─────────────────────┐
                       ▼                                           ▼
             1. IPAM Plugin (Alloc IP)                 2. Interface Creation
             - Allocates 10.244.1.2                    - Creates veth pair
             - Updates IPAM host-local / etcd          - Moves one peer into Pod netns
                                                       - Renames to eth0, sets MAC/IP
                                                       - Sets default route via host
```

### 2.2 Overlay vs. Flat / Underlay Networks

| Architecture | Mechanism | Pros | Cons | Popular Plugins |
| :--- | :--- | :--- | :--- | :--- |
| **Overlay (Encapsulated)** | Encapsulates Pod traffic inside outer UDP/IP packets (VXLAN, Geneve) on port `4789`. | Runs on top of any L2/L3 network without network team or router reconfigurations. | 50-byte header overhead; reduces effective MTU (1450 vs 1500); CPU encapsulation cost. | Flannel (VXLAN), Calico (VXLAN mode), Weave Net. |
| **Flat / Underlay (Routed)** | Node acts as an L3 router. Advertises Pod CIDR blocks via BGP directly to physical ToR (Top-of-Rack) switches. | Line-rate wire speed; zero packet encapsulation overhead; MTU 1500 maintained. | Requires BGP-enabled network fabric and Top-of-Rack switch peering permissions. | Calico (BGP mode), Cilium (Direct Routing). |
| **Cloud VPC Native** | Secondary Elastic Network Interfaces (ENIs) attached to worker EC2/VM instances. | Pods get native VPC IPs; direct access to AWS RDS/GCP BigQuery without NAT. | Limited number of Pods per node based on AWS ENI/IP limits per EC2 instance type. | AWS VPC CNI, Azure CNI, GCP GKE CNI. |

## 🔀 3. Kubernetes Services & kube-proxy Deep Dive

A **Service** is an abstract REST object providing a stable virtual IP (`ClusterIP`) and stable DNS name for a dynamic, ephemeral pool of Pod endpoints.

### 3.1 Service Types & Traffic Flow

1. **`ClusterIP` (Default):** Accessible only from within the cluster.
2. **`NodePort`:** Allocates a dedicated port (`30000-32767`) on every node interface.
3. **`LoadBalancer`:** Provisions an external cloud load balancer (AWS NLB, GCP Cloud LB) routing traffic to NodePorts or directly to Pod IPs.
4. **`ExternalName`:** Maps the Service to a DNS CNAME record (e.g., `my-db.rds.amazonaws.com`) without proxying.

### 3.2 kube-proxy Data Plane Modes: iptables vs. IPVS vs. eBPF

`kube-proxy` runs on every worker node, watching the API Server for `Service` and `EndpointSlice` mutations, translating virtual IPs into actual Pod destination IPs.

```text
===================================================================================================
                                kube-proxy PACKET PATH COMPARISON
===================================================================================================

[ Mode 1: iptables ]
Packet destined to ClusterIP (10.96.0.10:80)
       │
       ▼
   PREROUTING ──► KUBE-SERVICES ──► KUBE-SVC-XXXX ──► KUBE-SEP-YYYY (DNAT to 10.244.1.5:8080)
                  (O(N) search)     (Random prob)     (Packet rewritten & routed)

[ Mode 2: IPVS ]
Packet destined to ClusterIP (10.96.0.10:80)
       │
       ▼
   Netfilter IPVS Hook ──► ipset Hash Lookup O(1) ──► IPVS Balancer (Round Robin / Least Conn)
                                                  ──► DNAT to Pod IP (10.244.1.5:8080)

[ Mode 3: Cilium eBPF (kube-proxy Replacement) ]
Packet generated by application socket: connect(10.96.0.10:80)
       │
       ▼
   eBPF sock_addr Hook (sock_ops)
   - Intercepts syscall inside kernel socket layer before packet is even created!
   - Translates destination directly to Pod IP 10.244.1.5:8080
   - Zero netfilter traversal, zero packet overhead, maximum possible throughput!
```

### 3.3 EndpointSlices: Solving the Large Cluster Scalability Bottleneck
In early Kubernetes versions, a single `Endpoints` resource contained all Pod IPs for a service. When a cluster had a service with 5,000 pods:
- A single pod restart caused `kube-apiserver` to serialize and broadcast a multi-megabyte `Endpoints` object to thousands of nodes.
- **EndpointSlices** partition large endpoint sets into discrete chunks (default: 100 endpoints per slice). An update touches only a single slice, reducing network bandwidth and serialization overhead by over 95%.

## 🏷️ 4. DNS Service Discovery Internals (CoreDNS)

Kubernetes deploys **CoreDNS** as the in-cluster DNS server. 

### 4.1 DNS Record Conventions
Given Service `order-api` in namespace `prod`, cluster domain `cluster.local`:
- **A/AAAA Record:** `order-api.prod.svc.cluster.local` $\longrightarrow$ `10.96.14.85`
- **SRV Record:** `_http._tcp.order-api.prod.svc.cluster.local` $\longrightarrow$ Port `80`
- **Headless Service (`clusterIP: None`):** Returns the individual `A` records of all backing healthy Pod IPs (`10.244.1.2`, `10.244.2.5`).
- **Pod A Record:** `10-244-1-2.prod.pod.cluster.local` $\longrightarrow$ `10.244.1.2`

### 4.2 The `ndots: 5` Problem & DNS Latency
By default, `/etc/resolv.conf` injected into every Pod contains:
```text
nameserver 10.96.0.10
search prod.svc.cluster.local svc.cluster.local cluster.local c.internal
options ndots:5
```
Because `ndots: 5` requires any query with fewer than 5 dots to traverse all search domains first, resolving an external domain like `api.stripe.com` (2 dots) generates 4 failed internal queries before querying the external upstream:
1. `api.stripe.com.prod.svc.cluster.local` $\rightarrow$ NXDOMAIN
2. `api.stripe.com.svc.cluster.local` $\rightarrow$ NXDOMAIN
3. `api.stripe.com.cluster.local` $\rightarrow$ NXDOMAIN
4. `api.stripe.com.c.internal` $\rightarrow$ NXDOMAIN
5. `api.stripe.com` $\rightarrow$ Resolved (Success)

**Production Fix:** Add trailing dot (`api.stripe.com.`) in application code, deploy **NodeLocal DNSCache**, or customize Pod `dnsConfig`:
```yaml
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
```

## 🚪 5. Ingress Controllers & Gateway API

While Services operate at Layer 4 (TCP/UDP), modern web architectures require Layer 7 routing (HTTP path, host headers, SSL termination, rate limiting).

```text
===================================================================================================
                                 INGRESS VS. GATEWAY API ARCHITECTURE
===================================================================================================

[ Legacy Ingress Model ]
Client ──► Cloud NLB ──► Ingress Controller (Nginx / Envoy Pod) ──► Pod IPs directly
                               │
                Ingress YAML: monolithic spec combining TLS, host, path, backend

[ Modern Gateway API Model (Role-Oriented) ]
Infrastructure Provider:   GatewayClass (e.g. cilium, envoy, alb)
                                   │
Cluster Operator:           Gateway (IP allocation, TLS termination, Ports 80/443)
                                   │
Application Developer:      HTTPRoute (Path /api/v1 -> Service A; /auth -> Service B)
```

### 5.1 Gateway API Production Example
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: prod-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: envoy-gateway
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - name: wild-card-tls-cert
      allowedRoutes:
        namespaces:
          from: All
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: checkout-route
  namespace: e-commerce
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
  hostnames:
    - "shop.production.com"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /checkout
      backendRefs:
        - name: checkout-service
          port: 8080
          weight: 90
        - name: checkout-canary-service
          port: 8080
          weight: 10
```

## 🩺 6. Production Troubleshooting & Debugging Guide

```text
===================================================================================================
                             KUBERNETES NETWORK TROUBLESHOOTING RUNBOOK
===================================================================================================

                        Pod A cannot communicate with Pod B
                                       │
                                       ▼
                     Can Pod A resolve Pod B's DNS name?
                                ├── NO ──► Check CoreDNS pods: kubectl get pods -n kube-system -l k8s-app=kube-dns
                                │          Check DNS endpoints: kubectl get ep -n kube-system kube-dns
                                │          Test query: dig @10.96.0.10 my-service.default.svc.cluster.local
                                └── YES
                                       │
                                       ▼
                     Can Pod A ping/curl Pod B directly by IP?
                                ├── NO ──► Check CNI agent logs (calico-node, cilium-agent) on both nodes
                                │          Check MTU mismatches (VXLAN requires MTU = Interface MTU - 50)
                                │          Verify NetworkPolicies: kubectl get netpol -A
                                └── YES
                                       │
                                       ▼
                     Can Pod A curl Pod B via its ClusterIP?
                                ├── NO ──► Verify EndpointSlice: kubectl get endpointslices -l kubernetes.io/service-name=svc
                                │          Check kube-proxy logs on Pod A's node
                                │          Verify iptables rules: iptables-save | grep <ClusterIP>
                                └── YES
                                       │
                                       ▼
                       Traffic flow healthy! Check App Layer (L7)
```
