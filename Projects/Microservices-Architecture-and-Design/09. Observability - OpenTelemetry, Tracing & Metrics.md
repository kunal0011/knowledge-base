# Chapter 09: Observability - OpenTelemetry, Tracing & Metrics

> "If you cannot measure what happens between the seams of your microservices, you are operating in total blindness. Observability is not about collecting more logs; it is the mathematical ability to infer the internal states of a distributed system based on its external outputs."  
> — *Charity Majors, Observability Engineering*

---

## 1. Canonical Motivation & Theoretical Foundation

### The Distributed Debugging Dilemma
In a monolith, inspecting a `NullPointerException` or database timeout is straightforward: open the application log file and inspect the sequential stack trace. 

In a distributed microservice mesh:
- A single customer click triggers 15 synchronous gRPC calls, 4 asynchronous Kafka messages, and updates across 6 databases across 20 distinct container instances.
- Standard host-level logs are scattered across isolated container filesystems.
- When an API call returns `HTTP 500 Internal Server Error` after 4.2 seconds, which service failed? Which database query stalled? Was it a GC pause or network packet loss?

### The Three Pillars of Observability
Modern cloud-native engineering synthesizes three telemetry signals:
1. **Metrics (Aggregatable Numbers):** Numeric measurements recorded over time intervals (e.g. CPU utilization, request throughput, p99 latency). Ideal for alerting and detecting *that* a problem exists.
2. **Logs (Discrete Events):** Structured records containing rich contextual metadata. Essential for deep root-cause forensics.
3. **Traces (Causal Journeys):** Tracks the end-to-end execution path of a request across all network boundaries, visualizing bottlenecks, network hops, and execution hierarchy.

### OpenTelemetry (OTel): The Industry Standard
Vendor lock-in formerly plagued observability (e.g. proprietary agents for Datadog, New Relic, Dynatrace). **OpenTelemetry (CNCF)** establishes a single open standard for APIs, SDKs, and wire protocols (OTLP), separating telemetry generation from downstream storage backends (Prometheus, Jaeger, Tempo, Loki).

### W3C TraceContext Standard (RFC)
Distributed context is propagated across HTTP headers, gRPC metadata, and Kafka record headers using the **W3C `traceparent`** format:

$$\texttt{version} - \texttt{trace\_id} - \texttt{parent\_id} - \texttt{trace\_flags}$$

$$\texttt{00} - \texttt{4bf92f3577b34da6a3ce929d0e0e4736} - \texttt{00f067aa0ba902b7} - \texttt{01}$$

- **Version (2 hex):** Currently `00`.
- **Trace ID (32 hex):** Globally unique identifier for the entire distributed journey.
- **Parent / Span ID (16 hex):** Identifies the immediate parent operation.
- **Trace Flags (8-bit bitmap):** `01` indicates that the trace was sampled and recorded.

## 3. Core Mechanics, Algorithms & Invariants

### Tracing Sampling Strategies
Collecting $100\%$ of distributed traces across billions of requests is cost-prohibitive.
1. **Head-Based Sampling:** The root service decides whether to sample the trace at ingress (e.g. sample $1\%$ of requests uniformly). Cheap to operate, but statistically likely to miss rare, low-frequency error spikes.
2. **Tail-Based Sampling:** Telemetry is collected by an OpenTelemetry Collector cluster. The sampling decision is deferred until the trace **completes**. The collector retains $100\%$ of traces that contain errors or latencies $> 2\,000\text{ms}$, while sampling only $0.1\%$ of normal executions.

### The Four Golden Signals (Google SRE)
1. **Latency:** Time taken to service a request (differentiated between successful and failed requests).
2. **Traffic:** Demand placed on the service (e.g. HTTP requests per second).
3. **Errors:** Rate of requests that fail (explicit 5xx errors or implicit business failures).
4. **Saturation:** Measure of resource constraint (e.g. memory pool exhaustion, thread pool queue depth).

## 4. Practical Systems & Production Engineering Trade-offs

### The Metric Cardinality Explosion Hazard
- **The Anti-Pattern:** Adding high-cardinality values (e.g. `user_id`, `order_id`, `email`) as labels in Prometheus metrics:
  ```promql
  # FATAL ANTI-PATTERN: Creates millions of unique time series
  http_requests_total{path="/orders", user_id="USR-98213"}
  ```
- **Consequence:** Every distinct label combination spawns a new in-memory time-series in Prometheus. Memory consumption scales linearly $O(N)$ with active users, causing immediate Out-of-Memory (OOM) crashes of Prometheus servers.
- **Rule:** Prometheus labels must have **low, bounded cardinality** (e.g. `http_status`, `method`, `service_name`). High-cardinality identifiers belong exclusively in traces and structured logs.

### Java (Spring Boot 3 + Micrometer Tracing & Prometheus Actuator)
Production configuration integrating Micrometer, OpenTelemetry bridge, and automated HTTP trace context propagation.

```java
package com.example.observability.controller;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.tracing.Tracer;
import io.micrometer.tracing.Span;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestTemplate;

@Slf4j
@RestController
@RequestMapping("/api/v1/orders")
public class OrderObservabilityController {

    private final Counter orderCounter;
    private final Tracer tracer;
    private final RestTemplate restTemplate;

    public OrderObservabilityController(MeterRegistry registry, Tracer tracer, RestTemplate restTemplate) {
        this.tracer = tracer;
        this.restTemplate = restTemplate;
        // Low-cardinality Prometheus counter
        this.orderCounter = Counter.builder("microservice_orders_created_total")
                .description("Total number of orders created")
                .tag("service", "order-service")
                .register(registry);
    }

    @PostMapping
    public String createOrder(@RequestParam String customerId) {
        orderCounter.increment();

        // Custom child span inside distributed trace
        Span customSpan = tracer.nextSpan().name("custom-order-validation").start();
        try (Tracer.SpanInScope ws = tracer.withSpan(customSpan)) {
            log.info("Processing order for customer: {}", customerId); // Trace ID & Span ID auto-injected by MDC
            Thread.sleep(20); // Simulate local processing
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            customSpan.end();
        }

        // RestTemplate automatically propagates W3C 'traceparent' header downstream
        return "Order Accepted";
    }
}
```

### Go (Cloud-Native Go + OpenTelemetry SDK & Prometheus Metric Export)
Initializing OTel tracer provider, propagating context across HTTP handlers, and recording request duration histograms.

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/propagation"
	"go.opentelemetry.io/otel/trace"
)

var (
	tracer = otel.Tracer("order-service")

	// Prometheus Histogram with exponential buckets
	httpDuration = prometheus.NewHistogramVec(
		prometheus.HistogramOpts{
			Name:    "http_request_duration_seconds",
			Help:    "HTTP request latency in seconds",
			Buckets: prometheus.DefBuckets,
		},
		[]string{"path", "status"},
	)
)

func init() {
	prometheus.MustRegister(httpDuration)
	// Set global W3C TraceContext propagator
	otel.SetTextMapPropagator(propagation.TraceContext{})
}

func OrderHandler(w http.ResponseWriter, r *http.Request) {
	start := time.Now()

	// 1. Extract incoming W3C traceparent header
	ctx := otel.GetTextMapPropagator().Extract(r.Context(), propagation.HeaderCarrier(r.Header))

	// 2. Start child span
	ctx, span := tracer.Start(ctx, "HandleOrder",
		trace.WithAttributes(attribute.String("http.method", r.Method)))
	defer span.End()

	// Simulate work with context propagation
	time.Sleep(35 * time.Millisecond)
	span.AddEvent("Order database record inserted")

	w.WriteHeader(http.StatusCreated)
	w.Write([]byte(`{"status":"created"}`))

	// Record Prometheus metrics
	duration := time.Since(start).Seconds()
	httpDuration.WithLabelValues("/orders", "201").Observe(duration)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/orders", OrderHandler)
	mux.Handle("/metrics", promhttp.Handler())

	fmt.Println("Observability service running on :8080...")
	http.ListenAndServe(":8080", mux)
}
```

### Python (FastAPI + OpenTelemetry SDK & Prometheus Client)
FastAPI instrumentation with context propagation and structured JSON log correlation.

```python
import time
import logging
from fastapi import FastAPI, Request
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from prometheus_client import Counter, Histogram, make_asgi_app

# Setup OpenTelemetry Tracer Provider
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer(__name__)

# Prometheus Metrics Definition
REQUEST_LATENCY = Histogram(
    "fastapi_request_duration_seconds",
    "Request duration in seconds",
    ["endpoint"]
)
ORDER_TOTAL = Counter(
    "fastapi_orders_created_total",
    "Total orders created"
)

app = FastAPI(title="Observability Native Service")

# Expose /metrics endpoint for Prometheus scraper
metrics_app = make_asgi_app()
app.mount("/metrics", metrics_app)

# Auto-instrument FastAPI routes with OpenTelemetry
FastAPIInstrumentor.instrument_app(app)

@app.post("/orders")
async def create_order(request: Request):
    start_time = time.time()
    current_span = trace.get_current_span()
    trace_id = format(current_span.get_span_context().trace_id, "032x")
    span_id = format(current_span.get_span_context().span_id, "016x")

    # Correlate logs with active OpenTelemetry trace
    logging.info(f"Processing order | trace_id={trace_id} span_id={span_id}")

    # Custom internal sub-span
    with tracer.start_as_current_span("fraud_check_internal"):
        current_span.set_attribute("customer.tier", "GOLD")
        time.sleep(0.05) # Simulate fraud verification

    ORDER_TOTAL.inc()
    REQUEST_LATENCY.labels(endpoint="/orders").observe(time.time() - start_time)

    return {"status": "SUCCESS", "trace_id": trace_id}
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Outage Triage

### 1. Context Detachment in Concurrency (Go Goroutines & Python Async Tasks)
- **The Pitfall:** In Go, launching a background goroutine with `go processTask()` while passing `context.Background()` instead of the request `ctx` drops the `trace_id`. In Python, spinning up an un-contextualized `asyncio.create_task` loses Python `contextvars`.
- **Consequence:** Downstream spans appear as orphaned root traces in Jaeger/Tempo, breaking the causal execution graph.
- **Rule:** Always derive child contexts: in Go, pass `ctx` directly; in Python, ensure `contextvars.copy_context()` is propagated to tasks.

### 2. Synchronous Telemetry Exporter Freezing Request Threads
- **The Pitfall:** Using a non-batching synchronous OpenTelemetry exporter (or writing directly to a remote syslog server).
- **Failure Mode:** If the collector becomes slow or network congestion occurs, every HTTP request latency degrades by the exporter's timeout (e.g. 5 seconds), causing an immediate outage.
- **Remediation:** Always configure `BatchSpanProcessor` with an bounded in-memory queue that drops spans under backpressure rather than blocking application threads.

### 3. Outage Triage: Identifying the Bottleneck Span
- **Procedure:** When investigating a latency spike in Grafana Tempo / Jaeger:
  1. Filter traces by `http.status_code >= 500` or `duration > 2000ms`.
  2. Inspect the waterfall view: locate the widest span in the critical path.
  3. Check span events and tags: verify whether the bottleneck is database queue wait time (`db.wait_ms`), socket connection establishment, or an un-circuit-broken downstream HTTP timeout.
