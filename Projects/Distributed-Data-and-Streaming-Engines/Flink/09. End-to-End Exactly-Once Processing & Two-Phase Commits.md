# Chapter 09: End-to-End Exactly-Once Processing & Two-Phase Commits

> "Internal state consistency is half the battle; true end-to-end exactly-once guarantees that every external consumer observes each event exactly once, regardless of node crashes or network partitions."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

A common misconception in distributed streaming is that enabling Flink's checkpointing automatically guarantees end-to-end exactly-once processing. 

In reality, Flink's checkpointing guarantees **internal state consistency**: if a failure occurs, internal counters, accumulators, and window states are restored to the exact snapshot timestamp. However, if the output sink (e.g., Kafka, PostgreSQL, S3) has already written records downstream during the failed interval, restarting the stream will re-emit those records, creating **downstream duplicates**.

Achieving **End-to-End Exactly-Once Processing (E2E EOS)** requires three coordinating pillars:
1. **Replayable Sources:** Sources that can seek back to specific committed offsets (e.g. Apache Kafka, AWS Kinesis).
2. **Deterministic Stateful Engine:** A snapshotting mechanism that restores internal state deterministically (Flink Checkpoints via Chandy-Lamport).
3. **Transactional or Idempotent Sinks:** Sinks that coordinate with the checkpoint lifecycle using either idempotent upserts or a **Two-Phase Commit (2PC)** protocol.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Two-Phase Commit Protocol Coordinated by Checkpoints

Flink implements the classical Two-Phase Commit protocol across distributed sinks using the `TwoPhaseCommitSinkFunction` (and the modern unified `SinkV2` Two-Phase Committer interface).

The phases of the 2PC protocol are directly driven by the propagation of **Checkpoint Barriers**:

```
      [ JobManager CheckpointCoordinator ]
            │
            │ 1. Injects Checkpoint Barrier N into Sources
            ▼
      [ Source Operator ]
            │ (Data Records + Barrier N)
            ▼
      [ Transform / State Operator ]
            │ (Data Records + Barrier N)
            ▼
      [ Two-Phase Commit Sink Task ]
            │
            ├── A. Before Barrier: Writes records into open Transaction T1
            │
            ├── B. Barrier N Arrives:
            │      1. Calls sink.preCommit(T1) -> Flushes transaction to external system
            │      2. Opens new Transaction T2 for records following Barrier N
            │      3. Acknowledges Barrier N to JobManager CheckpointCoordinator
            │
            ▼
      [ JobManager CheckpointCoordinator ]
            │
            │ C. All tasks acknowledge -> Checkpoint N committed!
            │    Emits Commit Notification RPC to Sink Tasks
            ▼
      [ Two-Phase Commit Sink Task ]
            │
            └── D. Calls sink.commit(T1) -> Permanently commits external transaction!
```

#### 1. The Pre-Commit Phase
When Checkpoint Barrier $n$ reaches the sink operator:
- The sink flushes its current active transaction ($T_{\text{active}}$) to the external system.
- It prepares the transaction for commit (in Kafka, this means ending the transactional batch).
- It writes the transaction identifier into its local checkpoint state.
- It opens a new transaction ($T_{\text{next}}$) for all incoming records belonging to the next epoch.
- It acknowledges completion to the JobManager.

#### 2. The Commit Phase
- The JobManager verifies that *all* parallel operators have successfully taken their snapshot.
- The JobManager broadcasts a `notifyCheckpointComplete(checkpointId)` callback down the topology.
- Upon receiving this notification, the sink task formally commits $T_{\text{active}}$ in the external datastore.
- Once committed, downstream consumers configuring `read_committed` can finally observe the records.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### The Modern `KafkaSink` with `DeliveryGuarantee.EXACTLY_ONCE`

In modern Flink (1.14+), the legacy `FlinkKafkaProducer` is replaced by the high-performance, non-blocking `KafkaSink`:

```java
KafkaSink<String> sink = KafkaSink.<String>builder()
    .setBootstrapServers("broker1:9092,broker2:9092")
    .setRecordSerializer(
        KafkaRecordSerializationSchema.builder()
            .setTopic("financial.settlements.v1")
            .setValueSerializationSchema(new SimpleStringSchema())
            .build()
    )
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .setTransactionalIdPrefix("flink-settlement-sink-")
    .setProperty("transaction.timeout.ms", "900000") // 15 minutes
    .build();
```

## 5. Annotated Code Implementations & Execution Traces

### End-to-End Exactly-Once Kafka Pipeline

The following production Java program configures an end-to-end exactly-once pipeline reading from a Kafka topic, performing stateful deduplication, and writing to an output Kafka topic using 2PC transactional sinks:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.api.common.serialization.SimpleStringSchema;
import org.apache.flink.configuration.Configuration;
import org.apache.flink.connector.base.DeliveryGuarantee;
import org.apache.flink.connector.kafka.sink.KafkaRecordSerializationSchema;
import org.apache.flink.connector.kafka.sink.KafkaSink;
import org.apache.flink.connector.kafka.source.KafkaSource;
import org.apache.flink.connector.kafka.source.enumerator.initializer.OffsetsInitializer;
import org.apache.flink.contrib.streaming.state.EmbeddedRocksDBStateBackend;
import org.apache.flink.streaming.api.CheckpointingMode;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;

public class EndToEndExactlyOncePipelineJob {

    public static final String BOOTSTRAP_SERVERS = "broker1:9092,broker2:9092";
    public static final String INPUT_TOPIC = "banking.payments.raw";
    public static final String OUTPUT_TOPIC = "banking.payments.settled";

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        // Step 1: Enforce Exactly-Once Checkpointing
        env.enableCheckpointing(30000L, CheckpointingMode.EXACTLY_ONCE);
        env.getCheckpointConfig().setMinPauseBetweenCheckpoints(15000L);
        env.getCheckpointConfig().setCheckpointTimeout(120000L); // 2 minutes
        env.setStateBackend(new EmbeddedRocksDBStateBackend(true));

        // Step 2: Configure Replayable Kafka Source
        KafkaSource<String> kafkaSource = KafkaSource.<String>builder()
                .setBootstrapServers(BOOTSTRAP_SERVERS)
                .setTopics(INPUT_TOPIC)
                .setGroupId("flink-e2e-settlement-group")
                .setStartingOffsets(OffsetsInitializer.committedOffsets())
                .setValueOnlyDeserializer(new SimpleStringSchema())
                .build();

        DataStream<String> sourceStream = env.fromSource(
                kafkaSource,
                WatermarkStrategy.forMonotonousTimestamps(),
                "KafkaReplayableSource"
        );

        // Step 3: Stateful Processing / Business Logic
        DataStream<String> processedStream = sourceStream
                .filter(record -> record != null && !record.isEmpty())
                .map(record -> "PROCESSED_SETTLEMENT: " + record);

        // Step 4: Configure Transactional Two-Phase Commit Kafka Sink
        Configuration kafkaProps = new Configuration();
        // Crucial: Set transaction timeout higher than checkpoint interval + timeout!
        kafkaProps.setString("transaction.timeout.ms", "900000"); // 15 minutes

        KafkaSink<String> exactlyOnceSink = KafkaSink.<String>builder()
                .setBootstrapServers(BOOTSTRAP_SERVERS)
                .setKafkaProducerConfig(kafkaProps)
                .setRecordSerializer(
                        KafkaRecordSerializationSchema.builder()
                                .setTopic(OUTPUT_TOPIC)
                                .setValueSerializationSchema(new SimpleStringSchema())
                                .build()
                )
                .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
                // Transactional ID prefix must be unique across all jobs on the cluster
                .setTransactionalIdPrefix("flink-settlement-e2e-")
                .build();

        processedStream.sinkTo(exactlyOnceSink).name("TransactionalKafkaSink");

        env.execute("EndToEndExactlyOncePipelineJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Broker `transaction.max.timeout.ms` Expiration Trap
- **Antipattern:** Configuring Flink's `transaction.timeout.ms` to 1 hour while the Kafka broker's global cluster configuration `transaction.max.timeout.ms` remains at its default of 15 minutes (`900000ms`).
- **System Consequence:** If backpressure or node recovery delays a Flink checkpoint past 15 minutes, the Kafka broker transaction coordinator unilaterally aborts the active transaction. When Flink recovers and tries to invoke `commit()`, Kafka returns a fatal `InvalidTxnStateException`. The Flink job enters a crash loop and cannot recover.
- **Fix:** Align Kafka broker settings (`transaction.max.timeout.ms`) with Flink client settings, and ensure Flink checkpoint intervals + checkpoint timeouts are well within the transaction expiration ceiling.

### 2. Downstream Consumers Using Default `read_uncommitted`
- **Antipattern:** Spending weeks configuring Flink 2PC exactly-once sinks, but downstream microservices read the destination Kafka topic using default consumer settings (`isolation.level=read_uncommitted`).
- **System Consequence:** Downstream consumers immediately read uncommitted transactional messages while Flink is still in the pre-commit phase. If Flink crashes and aborts that transaction, the downstream consumers have already acted on phantom, aborted data, breaking EOS downstream.
- **Fix:** All downstream consumers reading from transactional Kafka topics **must** set:
  ```properties
  isolation.level = read_committed
  ```

### 3. Orphaned Transactions Blocking the Last Stable Offset (LSO)
- **Antipattern:** Manually terminating a Flink job or crashing without proper savepoint resumption, leaving open transactions uncommitted in Kafka.
- **System Consequence:** In Kafka, the **Last Stable Offset (LSO)** on a partition cannot advance past the offset of the earliest open transaction. Even if new messages are successfully produced and committed later, all consumers with `isolation.level=read_committed` will be **blocked from advancing past the orphaned transaction**, halting downstream consumption.
- **Fix:** Clean up orphaned transactions using dedicated administrative tools, or ensure Flink resumes from the latest checkpoint so the `KafkaSink` committer can explicitly abort uncommitted pre-commit handles.
