# Chapter 04: Columnar Storage Architecture — Apache Parquet & ORC Deep Dive

> "In data warehousing and analytical processing, the single most expensive operation is disk and network I/O. Columnar storage architectures like Apache Parquet and Apache ORC eliminate over 90% of data transfer by storing contiguous values of the same column together, enabling extreme compression and aggressive predicate pushdown."  
> — *Martin Kleppmann, Designing Data-Intensive Applications (DDIA)*

---

## 🏛️ 1. OLTP vs. OLAP: The Physical Access Pattern Divergence

The choice of data layout is dictated entirely by query access patterns:

```text
===================================================================================================
                               ROW-ORIENTED VS. COLUMNAR ACCESS
===================================================================================================

  [ OLTP Access: Row-Oriented (PostgreSQL / MySQL / Avro) ]
  Query: SELECT * FROM orders WHERE order_id = 98124;
  - Fetches all fields of ONE customer record.
  - Row storage keeps all fields of a single record adjacent on disk. Optimal for writes & single lookups!

  [ OLAP Analytical Access: Columnar (Parquet / ORC / ClickHouse) ]
  Query: SELECT state, AVG(purchase_amount) FROM transactions WHERE year = 2026 GROUP BY state;
  - Table has 150 columns (user address, IP, browser, payment details, items...).
  - Analytical query touches ONLY TWO columns: `state` and `purchase_amount`!
  - ⚠️ Row storage forces reading ALL 150 columns off disk, discarding 98% of bytes in RAM!
  - 🌟 Columnar storage reads ONLY the bytes for `state` and `purchase_amount` directly from S3!
```

## 🗄️ 2. Apache Parquet File Layout Internals

Created jointly by Twitter and Cloudera based on Google's seminal **Dremel paper**, **Apache Parquet** organizes data in a multi-tiered physical hierarchy:

```text
===================================================================================================
                                PARQUET PHYSICAL FILE STRUCTURE
===================================================================================================

  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 4-Byte Magic Number: "PAR1"                                                                 │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ ROW GROUP 1 (e.g. 128 MB to 512 MB chunk of logical rows)                                   │
  │  ┌───────────────────────────────────────────────────────────────────────────────────────┐  │
  │  │ Column Chunk 1: "user_id"                                                             │  │
  │  │   [ Dictionary Page ] [ Data Page 1 ] [ Data Page 2 ]                                 │  │
  │  ├───────────────────────────────────────────────────────────────────────────────────────┤  │
  │  │ Column Chunk 2: "purchase_amount"                                                     │  │
  │  │   [ Data Page 1 ] [ Data Page 2 ]                                                     │  │
  │  └───────────────────────────────────────────────────────────────────────────────────────┘  │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ ROW GROUP 2                                                                                 │
  │  ...                                                                                        │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ FILE FOOTER (WRITTEN AT THE VERY END OF THE FILE!)                                          │
  │ - Complete Table Schema (Types, nesting, nullability)                                       │
  │ - Row Group Metadata & Byte Offsets                                                         │
  │ - Column Chunk Statistics: [ Min_Value, Max_Value, Null_Count, Bloom Filter Offsets ]       │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 4-Byte Footer Length + 4-Byte Magic Number: "PAR1"                                          │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Why the Footer is at the End of the File
When generating Parquet files in Spark or Trino, the write stream processes data sequentially. The query engine cannot know the row group statistics (Min/Max values, exact dictionary sizes, row counts) until all records have been compressed and written! Placing the metadata footer at the end allows the engine to write the file in a **single pass without seeking back to the beginning**.

## 🗜️ 3. Advanced Columnar Encoding Algorithms

Because a column stores values of the **exact same data type** consecutively, columnar storage unlocks dramatic mathematical compression impossible in row formats:

### 3.1 Dictionary Encoding
Replaces repetitive values with compact integer IDs.
```text
 Raw Column Values:   [ "USA", "USA", "CAN", "USA", "MEX", "CAN" ]
 Dictionary:          { 0: "USA", 1: "CAN", 2: "MEX" }
 Encoded Integer IDs: [ 0, 0, 1, 0, 2, 1 ]  <-- Fits in 2 bits per value instead of strings!
```

### 3.2 Run-Length Encoding (RLE) & Bit-Packing
Consecutive identical values are compressed into `(count, value)` tuples:
```text
 Raw Values:     [ 5, 5, 5, 5, 5, 5, 5, 5, 9, 9, 9 ]
 RLE Compressed: [ (8, 5), (3, 9) ]  <-- 11 values compressed into 2 tuples!
```
With **Bit-Packing**, if the maximum value in a column page is $3$, Parquet stores each integer using only **2 bits** instead of 32 bits, achieving an immediate $16\times$ compression factor!

## 🚀 4. Performance Acceleration: Projection & Predicate Pushdown

Parquet enables distributed query engines (Spark, Trino, DuckDB) to eliminate massive volumes of disk and network I/O:

```text
===================================================================================================
                                   PREDICATE PUSHDOWN IN ACTION
===================================================================================================

  SQL Query: SELECT user_name FROM events WHERE age > 65;
  
  1. Engine reads ONLY the 4-byte Footer Length from S3 (HTTP Range Request: bytes=-4).
  2. Engine reads the Parquet File Footer Metadata into RAM.
  
  Row Group 1 Statistics:  age -> [ Min: 18, Max: 35 ]  ──► SKIP ENTIRE ROW GROUP! (Zero S3 I/O!)
  Row Group 2 Statistics:  age -> [ Min: 21, Max: 50 ]  ──► SKIP ENTIRE ROW GROUP!
  Row Group 3 Statistics:  age -> [ Min: 40, Max: 78 ]  ──► MATCH! Download ONLY "user_name" Chunk!
```

### 4.1 Parquet Bloom Filters
For high-cardinality point lookups (`WHERE uuid = 'a9f1-...'`):
- Min/Max bounds cannot rule out row groups because Min is `0000...` and Max is `ffff...`.
- Parquet incorporates **Split Block Bloom Filters** inside column metadata.
- The engine checks the Bloom filter: if it returns negative, the UUID **definitely does not exist** in that row group, skipping the entire $512\text{ MB}$ block without decompressing a single page!

## ⚖️ 5. Parquet vs. Apache ORC: Architectural Comparison

| Dimension | Apache Parquet | Apache ORC (Optimized Row Columnar) |
| :--- | :--- | :--- |
| **Origin & Heritage** | Twitter / Cloudera (Dremel-based) | Hortonworks / Meta (Engineered for Apache Hive) |
| **Physical Chunks** | **Row Groups** (Default $128\text{ MB} - 512\text{ MB}$) | **Stripes** (Default $64\text{ MB} - 256\text{ MB}$) |
| **Nested Data Handling** | Dremel Definition/Repetition Levels | Separate streams for parent/child structs |
| **Index Granularity** | Row group chunk statistics & Bloom filters | Row indexes inside stripes every $10,000$ rows |
| **Primary Ecosystem** | **The Universal Lakehouse Standard** (Spark, Iceberg, Delta Lake, Snowflake, DuckDB) | Strongly bound to Apache Hive and Trino in enterprise Hadoop deployments |
