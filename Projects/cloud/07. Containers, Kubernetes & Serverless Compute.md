## ☸️ 2. Managed Kubernetes: EKS vs. AKS vs. GKE

Google Kubernetes Engine (GKE) was the first managed Kubernetes service (2014), followed by Azure AKS and AWS EKS (2018). While all three certify upstream Kubernetes conformance, their architectural implementations diverge significantly:

```text
===================================================================================================
                     MANAGED KUBERNETES ARCHITECTURES (EKS VS. AKS VS. GKE)
===================================================================================================

 [ Amazon EKS ]                      [ Azure AKS ]                       [ Google GKE ]
 
 ┌──────────────────────────────┐    ┌──────────────────────────────┐    ┌──────────────────────────────┐
 │ Control Plane:               │    │ Control Plane:               │    │ Control Plane:               │
 │ - 3 Multi-AZ Master Instances│    │ - Hosted Azure Master Nodes  │    │ - Fully Autonomous Master    │
 │ - Fixed $0.10/hr Cluster Fee │    │ - Free Tier or Uptime SLA    │    │ - $0.10/hr Fee (1 free)      │
 ├──────────────────────────────┤    ├──────────────────────────────┤    ├──────────────────────────────┤
 │ Networking (VPC CNI):        │    │ Networking (Azure CNI):      │    │ Networking (Datapath v2):    │
 │ - Pods get native VPC IPs    │    │ - Azure CNI Overlay or       │    │ - Powered by Cilium & eBPF!  │
 │ - Heavy IP consumption!      │    │   Cilium eBPF data path      │    │ - Bypasses iptables!         │
 ├──────────────────────────────┤    ├──────────────────────────────┤    ├──────────────────────────────┤
 │ Node Autoprovisioning:       │    │ Node Autoprovisioning:       │    │ Node Autoprovisioning:       │
 │ - EKS Auto Mode / Karpenter  │    │ - AKS Karpenter Integration  │    │ - GKE Autopilot (Zero worker │
 │   (Bypasses Cluster Autoscl) │    │   or Virtual Node (ACI)      │    │   management; pay per pod!)  │
 └──────────────────────────────┘    └──────────────────────────────┘    └──────────────────────────────┘
```

### 2.1 Pod Networking & CNI Mechanics
1. **AWS VPC CNI:** Pods are first-class citizens on the AWS VPC. The CNI attaches secondary private IP addresses directly to the instance's Elastic Network Interfaces (ENIs).
   - *Limitation:* A single `m5.large` instance supports a maximum of 3 ENIs with 10 IPs each $\implies$ capped at 30 Pods per node regardless of spare CPU/RAM! Small subnets can be drained rapidly.
2. **Azure CNI (Cilium eBPF):** Replaces legacy iptables packet routing with Linux kernel eBPF programs, delivering sub-millisecond inter-Pod network routing and native network policy enforcement.
3. **Google GKE Datapath v2:** Leverages Cilium eBPF natively. Packet forwarding, service load balancing (`kube-proxy` replacement), and network security policies are executed directly inside the Linux kernel hook points, completely avoiding the $O(N)$ lookup degradation of Linux `iptables` tables.

## 📦 3. Serverless Containers (CaaS): Fargate vs. Container Apps vs. Cloud Run

Serverless container engines allow developers to deploy OCI-compliant container images without managing the underlying virtual machines or Kubernetes cluster nodes:

```text
===================================================================================================
                       SERVERLESS CONTAINER PLATFORMS COMPARISON
===================================================================================================

  Feature                AWS Fargate              Azure Container Apps     Google Cloud Run
  ─────────────────────────────────────────────────────────────────────────────────────────────────
  Underlying Engine      Amazon ECS / EKS         Kubernetes (KEDA + Dapr) Knative + Google Borg
  Isolation Technology   Firecracker MicroVMs     Hyper-V Containers       gVisor Sandbox
  Scale-to-Zero          No (Always at least 1)   Yes (via KEDA scaling)   Yes (Scales to 0 in 15 mins)
  Concurrency per Pod    1 Task per MicroVM       Configurable concurrent  Up to 250 concurrent
                         (Single-request proxy)   HTTP requests            HTTP requests per instance!
  Cold-Start Latency     15 - 45 seconds          5 - 15 seconds           500ms - 2 seconds
  Max Timeout            No hard execution limit  No hard limit            60 minutes (HTTP / Jobs)
```

### 3.1 Google Cloud Run: The Architectural Gold Standard
Google Cloud Run excels due to its **concurrent request multiplexing**:
- In AWS Lambda, 100 simultaneous HTTP requests spawn **100 independent microVM instances**, driving high costs and potential connection pool thrashing.
- In Google Cloud Run, a single container instance can process up to **250 concurrent HTTP requests** via async event loops (Node.js, Go, Python asyncio), reducing container footprint and costs by up to $90\%$.

## ⚡ 4. Function-as-a-Service (FaaS): Lambda vs. Functions

FaaS platforms execute transient, stateless functions in response to event triggers (HTTP gateways, S3 object uploads, Kafka streams):

```text
===================================================================================================
                         ANATOMY OF A SERVERLESS COLD START
===================================================================================================

 Incoming Request Trigger
           │
           ▼
 ┌────────────────────────────────────────────────────────┐
 │ 1. MicroVM Allocation (Firecracker / gVisor) [~50ms]   │
 ├────────────────────────────────────────────────────────┤
 │ 2. Container / Filesystem Layer Download     [~150ms]  │
 ├────────────────────────────────────────────────────────┤
 │ 3. Runtime Initialization (Python / Node / JVM)[~200ms]│
 ├────────────────────────────────────────────────────────┤
 │ 4. Application Code Bootstrap & DB Connect   [~800ms]  │ <── Cold Start Penalty!
 ├────────────────────────────────────────────────────────┤
 │ 5. Handler Execution (Actual Business Logic) [~10ms]   │ <── Warm Invocations!
 └────────────────────────────────────────────────────────┘
```

### 4.1 Cold-Start Mitigation Strategies
- **AWS Provisioned Concurrency:** Pre-initializes a pool of execution environments that remain continuously warm, eliminating initialization spikes for mission-critical APIs.
- **SnapStart (AWS Lambda for Java):** Takes a Firecracker microVM snapshot of the initialized memory and disk state after running application bootstrap, restoring subsequent invocations from cache in $<200\text{ ms}$.
- **Lightweight Runtimes:** Compiling binaries with Go or Rust rather than heavy JVM or Python frameworks reduces runtime initialization from $1,500\text{ ms}$ to $<15\text{ ms}$.

## 💥 6. Real-World Failure Scenario: Kubernetes Pod IP Exhaustion

### The Incident: Subnet IP Depletion via AWS VPC CNI
A engineering team provisions a production Amazon EKS cluster in a VPC with a standard `/24` private subnet ($251$ usable IPv4 addresses):

```text
===================================================================================================
                      THE POD IP EXHAUSTION COLLAPSE
===================================================================================================

 Subnet CIDR: 10.0.1.0/24 (Total Usable Host IPs = 251)
 
 1. Team provisions 8 worker nodes using `m5.2xlarge` instances.
 2. AWS VPC CNI initializes on each node:
    - An `m5.2xlarge` supports 4 ENIs with 30 IPs per ENI = 120 IPs per node!
    - The CNI pre-allocates an entire warm pool of ENIs and IP addresses upon boot.
                         │
                         ▼
 3. 8 nodes × 30 IPs pre-warmed = 240 IP addresses claimed immediately!
                         │
                         ▼
 4. Subnet IP pool is 100% EXHAUSTED!
                         │
                         ▼
 5. Developers deploy a new microservice deployment (10 replicas):
    - Kubernetes schedules Pods to nodes.
    - VPC CNI fails to allocate private IP from AWS EC2 API.
    - All Pods remain perpetually stuck in `ContainerCreating` or `FailedCreatePodSandBox`!
    - Autoscaler attempts to launch new nodes to resolve capacity, but new EC2 instances
      cannot even receive a primary private IP and fail to join the cluster!
```

#### Architectural Remediations:
1. **Enable CNI Prefix Delegation:** Enable `ENABLE_PREFIX_DELEGATION=true` in AWS VPC CNI. Instead of allocating single `/32` IPs, the node allocates an entire `/28` IPv4 prefix (16 IPs) per slot, dramatically reducing ENI limits and IP fragmentation.
2. **Dedicated Pod Secondary CIDR:** Attach a non-routable secondary CIDR block (e.g., `100.64.0.0/16` CGNAT space) to the VPC and configure custom networking so Pods receive IPs from the secondary space while worker nodes remain on primary subnets.

## 🛠️ 7. Production Kubernetes Manifest: Resilient Deployment with HPA

```yaml
# ==============================================================================
# PRODUCTION KUBERNETES WORKLOAD WITH HORIZONTAL POD AUTOSCALER
# ==============================================================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-processing-service
  namespace: production
  labels:
    app: order-processor
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-processor
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0 # Zero downtime deployments
  template:
    metadata:
      labels:
        app: order-processor
    spec:
      affinity:
        podAntiAffinity: # Ensure Pods land on different physical AZs
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: ["order-processor"]
                topologyKey: "topology.kubernetes.io/zone"
      containers:
        - name: application
          image: 123456789012.dkr.ecr.us-east-1.amazonaws.com/order-processor:v2.4.1
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080

            periodSeconds: 10

            httpGet:
              path: /healthz
```

## 🎯 8. Architectural Takeaways & Compute Checklist

1. **Pick the Right Compute Abstraction:** Do not deploy an operational Kubernetes cluster if your application consists of simple REST APIs that can run seamlessly on **Google Cloud Run** or **AWS Fargate**.
2. **Adopt Prefix Delegation for EKS:** Always configure prefix delegation on AWS VPC CNI to avoid running out of IPv4 addresses in cluster subnets.
3. **Multi-AZ Pod Anti-Affinity:** Always define `podAntiAffinity` on Kubernetes Deployments to guarantee that Pod replicas are scheduled across multiple distinct Availability Zones.
