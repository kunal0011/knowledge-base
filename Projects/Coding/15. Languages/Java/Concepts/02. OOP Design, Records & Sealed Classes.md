# Java Concepts: OOP Design, Records & Sealed Classes

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapters 6 & 7  
- *Effective Java (3rd Ed.)* by Joshua Bloch, Items 18, 19, & 20  

---

## 1. Theoretical Motivation: The Evolution Beyond Classical OOP

Classical Java relied heavily on deep inheritance hierarchies, mutable JavaBeans with getters/setters, and defensive boilerplate. However, over decades of industry experience, deep class inheritance proved brittle:
- **The Fragile Base Class Problem:** Modifying a superclass can silently break invariants in subclasses.
- **Excessive Boilerplate:** Simple data transfer objects required hundreds of lines of handwritten `equals()`, `hashCode()`, and `toString()`.

Modern Java (Java 17/21) fundamentally modernizes object-oriented design by introducing **Records** (transparent immutable data carriers) and **Sealed Classes** (algebraic data types with exhaustive compile-time bounds).

## 2. Underlying Architecture: Class Initialization Order

Understanding the exact deterministic sequence of memory allocation and initialization in HotSpot is essential for avoiding insidious null-state bugs:

```
                      JVM Class Loading & Initialization Order
                                         |
Step 1: Superclass STATIC fields & static initializers (once per ClassLoader)
                                         |
Step 2: Subclass STATIC fields & static initializers   (once per ClassLoader)
                                         |
Step 3: Superclass INSTANCE variables & instance initializers (top to bottom)
                                         |
Step 4: Superclass CONSTRUCTOR body
                                         |
Step 5: Subclass INSTANCE variables & instance initializers   (top to bottom)
                                         |
Step 6: Subclass CONSTRUCTOR body
```

## 3. Modern Value Types: Records (Java 16+)

A **Record** is a specialized, immutable data carrier class defined by JEP 395. When you declare a record:
```java
public record Point(int x, int y) {}
```

### What HotSpot Generates Automatically:
1. A `final` class extending `java.lang.Record`.
2. `private final` fields for every component.
3. Accessor methods: `x()` and `y()` (Note: No `get` prefix!).
4. Canonical constructor initializing all components.
5. Canonical implementations of `equals()`, `hashCode()`, and `toString()`.

### 3.1 Compact Constructor for Invariant Validation
Records support a **compact constructor** where parameter declarations are omitted:
```java
public record Range(int start, int end) {
    // Compact constructor: runs BEFORE assignment to final fields!
    public Range {
        if (start > end) {
            throw new IllegalArgumentException(
                String.format("start (%d) cannot be greater than end (%d)", start, end)
            );
        }
        // No explicit 'this.start = start' needed; compiler assigns automatically!
    }
}
```

> [!WARNING]
> **Shallow Immutability Gotcha:** Records are only shallowly immutable. If a record holds a reference to a mutable collection (`record UserGroup(String name, List<User> users)`), external code can still mutate the internal list! Use `List.copyOf(users)` in a defensive constructor.

## 4. Algebraic Data Types: Sealed Classes (Java 17+)

Sealed classes and interfaces (JEP 409) restrict which other classes or interfaces may extend or implement them. This allows modeling **Algebraic Data Types (Sum Types)** with compile-time exhaustiveness checking.

```
                         [ <<sealed>> Shape ]
                       permits Circle, Rectangle
                                 /     \
                                /       \
          [ final Circle ]                 [ final Rectangle ]
```

### 4.1 Declaration Syntax & Modifier Rules
Every direct subclass of a sealed class **MUST** declare exactly one of three modifiers:
1. **`final`:** No further subclasses permitted.
2. **`sealed`:** Must specify its own `permits` clause, extending the closed hierarchy.
3. **`non-sealed`:** Opens the hierarchy back up to unrestricted subclassing.

```java
public sealed interface PaymentMethod permits CreditCard, BankTransfer, Crypto {}

public final record CreditCard(String cardNumber, String cvv) implements PaymentMethod {}
public final record BankTransfer(String iban) implements PaymentMethod {}
public final record Crypto(String walletAddress) implements PaymentMethod {}
```

### 4.2 Exhaustive Pattern Matching without `default`
Because the compiler knows every possible implementation of `PaymentMethod`, a `switch` expression requires **no `default` branch**:

```java
static String processPayment(PaymentMethod method) {
    return switch (method) {
        case CreditCard cc   -> "Processing Card: " + cc.cardNumber();
        case BankTransfer bt -> "Wire to IBAN: " + bt.iban();
        case Crypto c        -> "Transfer to Wallet: " + c.walletAddress();
        // No 'default' needed! If someone adds a new permitted class,
        // this switch will refuse to compile until handled!
    };
}
```

## 5. Modern Interface Architecture: Default & Private Methods

Interfaces in modern Java are no longer purely abstract contracts:

```java
public interface DataService {
    // Abstract method:
    void execute();

    // 1. Default method (Java 8): Provides default implementation to prevent breaking clients
    default void executeWithRetry(int retries) {
        logAttempt();
        // ... retry logic calling execute() ...
    }

    // 2. Static utility method (Java 8):
    static DataService createDefault() {
        return new ConcreteDataService();
    }

    // 3. Private helper method (Java 9): Deduplicates shared logic between default methods
    private void logAttempt() {
        System.out.println("Initiating service execution...");
    }
}
```

### Diamond Problem Resolution:
If a class implements two interfaces declaring identical default signatures (`A.foo()` and `B.foo()`), the compiler **forces** the implementing class to explicitly override the method and resolve ambiguity:
```java
@Override
public void foo() {
    A.super.foo(); // Explicitly delegates to Interface A
}
```

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 Joshua Bloch's Item 18: Inheritance Breaks Encapsulation
In *Effective Java*, Bloch presents the classic `InstrumentedHashSet` disaster:

```java
// ANTI-PATTERN: Attempting to count added elements via inheritance
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c); // BUG! HashSet.addAll() internally calls add()!
    }
}
```
If you call `set.addAll(List.of("A", "B", "C"))`, `addCount` becomes **6 instead of 3** because `HashSet.addAll()` internally invokes `this.add()`, double-counting every element!  
**Rule:** **Favor composition over inheritance**. Wrap the set as a private member (Decorator pattern).

### 6.2 Never Call Overridable Methods in Constructors (Item 19)
```java
class Super {
    public Super() {
        overrideMe(); // FATAL BUG!
    }
    public void overrideMe() {}
}

class Sub extends Super {
    private final Instant instant;
    public Sub() {
        instant = Instant.now();
    }
    @Override
    public void overrideMe() {
        System.out.println(instant); // NullPointerException or null!
    }
}
```
**Why it fails:** When `new Sub()` executes, the superclass constructor runs **before** the subclass instance field `instant = Instant.now()` is initialized! The overridden method accesses `instant` while it is still `null`.

## 7. Actionable Summary Checklist

- [x] Use **Records** for immutable data transfer objects to eliminate handwritten boilerplate and gain structural equality.
- [x] Use **Sealed Classes** to build closed domain models and unlock compiler-enforced exhaustive pattern matching.
- [x] Favor **composition over inheritance** (Effective Java Item 18) to avoid fragile base class dependencies.
- [x] **Never invoke overridable methods inside a constructor** (Effective Java Item 19); subclass state is uninitialized at that moment.
- [x] Remember that interfaces support `default`, `static`, and `private` methods to provide reusable behavioral templates.
