# Chapter 02: Event Time Semantics, Watermarks & Out-of-Order Data

> "Watermarks are the clock of the streaming system: they allow an operator to advance its internal event-time clock and declare that no older events will ever arrive."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

In distributed streaming systems, the order in which events are generated in the real world rarely matches the order in which they are received by the streaming engine. Network jitter, mobile device disconnections, retry loops, and multi-partition shuffles inevitably cause events to arrive **out-of-order**.

### The Three Notions of Time
1. **Event Time:** The exact timestamp when an event occurred on the originating device (embedded directly in the record payload). This is the only notion of time that produces **reproducible, deterministic results** during replays, historical backfills, or network outages.
2. **Ingestion Time:** The timestamp when an event enters the Flink cluster at the source operator (attached as record metadata).
3. **Processing Time:** The local wall-clock time of the TaskManager machine executing the operation. It is fast and requires no state tracking, but produces nondeterministic results because processing speed varies with cluster load, GC pauses, and backpressure.

```
 [ Event Occurs: t=10:00:01 ]  ──> [ Mobile Offline 10m ] ──> [ Arrives Flink: t=10:10:05 ]
       (Event Time)                                                (Processing Time)
```

If a system computes a 5-minute aggregation window using processing time, this event is incorrectly counted in the `10:10 - 10:15` window instead of its rightful `10:00 - 10:05` window.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Watermark Mechanism

A **Watermark** is a specialized control element embedded directly into the stream of data records. 

Formally, a watermark with timestamp $t$, denoted as $\text{Watermark}(t)$, is an assertion that **all records with an event timestamp $t' \le t$ have already been observed by the system**.

```
[Record (t=14)] ──> [Record (t=11)] ──> [Watermark (t=10)] ──> [Record (t=10)] ──> [Record (t=8)]
                                              │
                                              ▼
                    "The stream has now progressed to t=10.
                     All event-time windows ending at <= 10 can safely fire."
```

### Watermark Propagation Across Parallel Channels

When an operator receives streams from multiple upstream parallel channels (e.g. consuming 4 Kafka partitions), the operator's current event-time clock is determined by the **minimum watermark across all active incoming channels**:

$$\text{Operator Event Time} = \min \left( \text{Watermark}_1, \text{Watermark}_2, \dots, \text{Watermark}_N \right)$$

```
Channel 0: ───[Watermark 15]───[Record 16]───────────────────────┐
Channel 1: ───[Watermark 12]───[Record 14]───[Record 13]─────────┼──> [Window Operator]
Channel 2: ───[Watermark 18]─────────────────────────────────────┘    Current Clock = min(15, 12, 18) = 12!
                                                                      (Window [0-10] fires, Window [10-15] waits)
```

Because Channel 1 is lagging at Watermark 12, the downstream operator cannot advance its clock past 12. This conservative invariant guarantees completeness and prevents premature window evaluation.

### Generation Strategies: Periodic vs. Punctuated
- **Periodic Watermarks (Default):** Generated at regular wall-clock intervals (configured via `pipeline.auto-watermark-interval`, default 200ms). The watermark generator queries the maximum observed timestamp minus a configured out-of-orderness bound.
- **Punctuated Watermarks:** Generated based on internal record attributes (e.g., whenever a record contains a special control payload).

## 3. Core API Mechanics & Modern Idiomatic Patterns

### The Modern `WatermarkStrategy` API

In modern Flink (1.11+), watermarks and timestamp extractors are defined together using the declarative `WatermarkStrategy` interface.

```java
WatermarkStrategy<TransactionEvent> strategy = WatermarkStrategy
    // Step 1: Bound out-of-orderness tolerance (e.g., up to 5 seconds late)
    .<TransactionEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
    // Step 2: Extract timestamp from domain object (in milliseconds)
    .withTimestampAssigner((event, timestamp) -> event.getTimestampEpochMs())
    // Step 3: Handle idle partitions
    .withIdleness(Duration.ofMinutes(1));
```

### Built-in Strategies
- `WatermarkStrategy.forMonotonousTimestamps()`: Generates tightly ascending watermarks where timestamps never decrease (zero delay).
- `WatermarkStrategy.forBoundedOutOfOrderness(Duration maxDelay)`: Generates watermarks lagging $maxDelay$ behind the highest observed timestamp, accommodating bounded out-of-order records.
- `WatermarkStrategy.noWatermarks()`: For pure processing-time pipelines.

## 5. Annotated Code Implementations & Execution Traces

### Event-Time Windowing with WatermarkStrategy & Dead Letter Side Output

The following production pipeline configures bounded out-of-order watermarking, detects late records arriving after the window and grace period have closed, and routes them to a side output for triage:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.api.common.eventtime.*;
import org.apache.flink.api.common.functions.MapFunction;
import org.apache.flink.api.common.typeinfo.Types;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.datastream.SingleOutputStreamOperator;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.functions.windowing.ProcessWindowFunction;
import org.apache.flink.streaming.api.windowing.assigners.TumblingEventTimeWindows;
import org.apache.flink.streaming.api.windowing.time.Time;
import org.apache.flink.streaming.api.windowing.windows.TimeWindow;
import org.apache.flink.util.Collector;
import org.apache.flink.util.OutputTag;

import java.time.Duration;

public class EventTimeWatermarkProcessingJob {

    // Domain Model
    public static class SensorReading {
        public String deviceId;
        public long timestamp; // Epoch millisecond
        public double temperature;

        public SensorReading() {}
        public SensorReading(String deviceId, long timestamp, double temperature) {
            this.deviceId = deviceId;
            this.timestamp = timestamp;
            this.temperature = temperature;
        }

        @Override
        public String toString() {
            return String.format("SensorReading[id=%s, ts=%d, temp=%.2f]", deviceId, timestamp, temperature);
        }
    }

    // Define Side Output Tag for late-arriving events
    public static final OutputTag<SensorReading> LATE_DATA_TAG = 
            new OutputTag<SensorReading>("late-sensor-readings") {};

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        // Periodic watermark emission interval (default is 200ms)
        env.getConfig().setAutoWatermarkInterval(200);

        // Raw input feed
        DataStream<String> rawStream = env.fromElements(
                "DEV-1,1000,21.5",
                "DEV-1,2500,22.0",
                "DEV-1,7000,24.5",  // Advances watermark to 7000 - 3000 = 4000
                "DEV-1,3500,22.8",  // Arrives out of order (3500 <= 4000), but within window [0 - 5000]
                "DEV-1,15000,26.0", // Advances watermark to 15000 - 3000 = 12000 (Closes window [0 - 5000])
                "DEV-1,1500,21.0"   // Arrives severely late after window closure -> Route to Side Output
        );

        // Step 1: Parse raw strings into typed objects
        DataStream<SensorReading> parsedStream = rawStream.map((MapFunction<String, SensorReading>) line -> {
            String[] parts = line.split(",");
            return new SensorReading(parts[0], Long.parseLong(parts[1]), Double.parseDouble(parts[2]));
        }).returns(Types.POJO(SensorReading.class));

        // Step 2: Configure WatermarkStrategy (3 seconds bounded out-of-orderness, 10s idleness timeout)
        WatermarkStrategy<SensorReading> watermarkStrategy = WatermarkStrategy
                .<SensorReading>forBoundedOutOfOrderness(Duration.ofSeconds(3))
                .withTimestampAssigner((reading, recordTimestamp) -> reading.timestamp)
                .withIdleness(Duration.ofSeconds(10));

        // Step 3: Assign timestamps and generate watermarks
        DataStream<SensorReading> watermarkedStream = parsedStream.assignTimestampsAndWatermarks(watermarkStrategy);

        // Step 4: Keyed Tumbling Event-Time Window (5 seconds) with Side Output
        SingleOutputStreamOperator<String> windowedAggregates = watermarkedStream
                .keyBy(r -> r.deviceId)
                .window(TumblingEventTimeWindows.of(Time.seconds(5)))
                .sideOutputLateData(LATE_DATA_TAG) // Late data routing
                .process(new ProcessWindowFunction<SensorReading, String, String, TimeWindow>() {
                    @Override
                    public void process(String key, Context context, Iterable<SensorReading> elements, Collector<String> out) {
                        double sum = 0;
                        int count = 0;
                        for (SensorReading r : elements) {
                            sum += r.temperature;
                            count++;
                        }
                        double avg = sum / count;
                        out.collect(String.format("Window [%d - %d] Device [%s] Avg Temp: %.2f (Count: %d)",
                                context.window().getStart(), context.window().getEnd(), key, avg, count));
                    }
                });

        // Main Output
        windowedAggregates.print().name("MainWindowOutput");

        // Late Data Side Output
        DataStream<SensorReading> lateDataStream = windowedAggregates.getSideOutput(LATE_DATA_TAG);
        lateDataStream.map(r -> "DROPPED LATE EVENT: " + r.toString())
                .print()
                .name("LateDataOutput");

        env.execute("EventTimeWatermarkProcessingJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Idle Partition Watermark Freeze Bug
- **Antipattern:** Consuming from a multi-partition Kafka topic where one partition is completely inactive (e.g., low-volume key partition or paused producer), without configuring partition idleness.
- **System Consequence:** Recall the operator clock rule: $\text{Clock} = \min(W_1, W_2, \dots, W_N)$. If partition $k$ emits zero records, its watermark remains stuck at $-\infty$. Consequently, downstream operators **never advance their watermarks**, causing event-time windows and timers to stall forever, leaking unbounded state memory.
- **Fix:** Always append `.withIdleness(Duration)` to the `WatermarkStrategy`. Flink will temporarily mark inactive partitions as "idle" and exclude them from downstream watermark minimum calculations.

### 2. Overly Generous Out-of-Orderness Latency Tax
- **Antipattern:** Setting `forBoundedOutOfOrderness(Duration.ofHours(2))` to avoid dropping any late-arriving events.
- **System Consequence:** Flink holds open event-time window state and postpones window evaluations by 2 hours. Downstream consumers experience a 2-hour latency penalty before receiving window output, and TaskManagers must retain 2 hours worth of un-evicted state in RocksDB.
- **Fix:** Set bounded out-of-orderness tightly (e.g., 5–30 seconds) to ensure responsive stream output, and handle the small tail of extreme outliers via `.sideOutputLateData()` or allowed lateness.

### 3. Timestamp Assigner Ephemeral Millisecond Conversions
- **Antipattern:** Passing microsecond or nanosecond epoch timestamps directly to `withTimestampAssigner` without dividing by 1,000 or 1,000,000.
- **System Consequence:** Flink’s internal event-time clock is strictly denominated in **milliseconds**. Passing nanoseconds ($10^{18}$) advances the system watermark to the year 50,000 AD instantly. All subsequent valid incoming records are immediately flagged as late arrivals and dropped.
- **Fix:** Normalize all source epoch timestamps to epoch milliseconds prior to watermark assignment.
