# Chapter 06: Partitioning — Strategies, Secondary Indexes & Skew

> "For very large datasets, or very high query throughput, replication is not sufficient: we need to break the data up into partitions, also known as sharding. Each partition is a small database in its own right."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

While replication creates multiple redundant copies of the *same* dataset across nodes, **Partitioning** (also known as **Sharding**) divides a massive dataset into non-overlapping subsets.

The primary motivation for partitioning is **Scalability**:
- A single machine cannot hold a 100TB database or sustain 1,000,000 writes per second.
- By partitioning data across a shared-nothing cluster of 100 nodes, each node only holds 1TB of data and processes 10,000 writes per second.

In production architectures, **Partitioning and Replication are combined**: each partition is assigned a primary leader and multiple follower replicas across physically distinct servers.

---

## 2. Underlying Runtime, Memory & Execution Architecture

### Partitioning Strategies: Key-Range vs. Hash Partitioning

```
Approach 1: Partitioning by Key Range (Alphabetical / Temporal Boundaries)
 Node 1: [ A - C ]   Node 2: [ D - G ]   Node 3: [ H - M ] ... Node N: [ T - Z ]
  -> Advantage: Range queries are fast and local (e.g. scan all users from 'Bar' to 'Baz').
  -> Fatal Flaw: Hotspots! If you partition by date (YYYY-MM-DD), today's partition 
                 absorbs 100% of cluster write traffic while others sit idle.

Approach 2: Partitioning by Hash of Key (Uniform Pseudo-Random Distribution)
 Key "user_42" ──> Hash Function (MurmurHash3) ──> 0x8F4A... ──> Modulo Partitions ──> Node 4
  -> Advantage: Destroys hotspots; spreads keys evenly across all nodes.
  -> Fatal Flaw: Destroys range queries! Adjacent keys (user_1, user_2) hash to 
                 completely different nodes. Range scans must query ALL nodes.
```

#### The Production Hybrid: Compound Primary Keys (Cassandra)
Apache Cassandra solves this trade-off using **Compound Primary Keys**:
```sql
CREATE TABLE sensor_readings (
    device_id UUID,
    recorded_at TIMESTAMP,
    temperature DOUBLE,
    PRIMARY KEY ((device_id), recorded_at)
);
```
- **Partition Key (`device_id`):** Hashed to determine which cluster node holds the data.
- **Clustering Column (`recorded_at`):** Kept in **sorted contiguous order** inside that node's SSTable.
- *Result:* Writes are distributed uniformly across nodes by device, but time-range queries for a single device (`WHERE device_id = ? AND recorded_at > ?`) execute in a single sequential disk scan.

## 3. Core Mechanics, Algorithms & Invariants

### Secondary Indexes & Partitioning

Secondary indexes (e.g. searching for users by `email` when the table is partitioned by `user_id`) introduce severe architectural challenges:

#### 1. Document-Partitioned Indexes (Local Indexes)
Each partition independently maintains a secondary index covering **only the records stored in that local partition**:

```
 Partition 0 (Users 1-1000)        Partition 1 (Users 1001-2000)
 ┌───────────────────────────┐     ┌───────────────────────────┐
 │ Data: User 42 (Red Car)   │     │ Data: User 1050 (Red Car) │
 ├───────────────────────────┤     ├───────────────────────────┤
 │ Local Index:              │     │ Local Index:              │
 │   "Red Car" -> [ User 42 ]│     │   "Red Car" -> [User 1050]│
 └───────────────────────────┘     └───────────────────────────┘
```
- **Writes are fast:** Updating a record only modifies the local partition index.
- **Reads require Scatter-Gather:** Querying `WHERE car_color = 'Red'` forces the coordinator to **broadcast the query to every single partition in the cluster** and aggregate results!

#### 2. Term-Partitioned Indexes (Global Indexes)
The secondary index is partitioned globally based on the value of the indexed term itself:
- Partition A holds index entries for letters `A-M`; Partition B holds `N-Z`.
- **Reads are fast:** Point query directed to a single index partition.
- **Writes are slow and complex:** Updating a user record requires a distributed transaction across two different nodes (the data partition and the index partition).

---

### Rebalancing Partitions

As traffic grows, new hardware nodes are added to the cluster. Data and query load must be migrated without downtime:

| Rebalancing Strategy | Mechanism | Used By |
| :--- | :--- | :--- |
| **Fixed Number of Partitions** | Create $1000$ partitions upfront; assign 100 partitions per node on a 10-node cluster. When adding a node, steal a few partitions from existing nodes. | Elasticsearch, Apache Kafka, Riak |
| **Dynamic Partitioning** | When a partition exceeds a size threshold (e.g. 10GB), it splits in half (like B-Tree splits). | HBase, MongoDB, CockroachDB |
| **Proportional to Nodes** | Keep a fixed number of partitions *per node*. Partition size grows with data volume. | Apache Cassandra |

## 4. Practical Systems & Production Engineering Trade-offs

1. **Handling Celebrity Hotspots (Salting):** If a celebrity user (e.g. with 50 million followers) causes a single partition key to receive millions of writes per minute, the application appends a random two-digit salt to the key: `user_id + "_" + random(0, 99)`. Writes split evenly across 100 partitions; reads must scatter-gather across all 100 partitions.
2. **Consistent Hashing (Dynamo / Cassandra):** Nodes and keys are mapped onto a circular hash ring ($0 \dots 2^{64}-1$). Adding a node only moves keys from its immediate neighbor on the ring ($1/N$ fraction of keys).

## 5. Annotated Code Implementations & Algorithmic Engines

### Production-Grade Consistent Hashing Ring with Virtual Nodes

The following complete Python implementation constructs a Consistent Hashing ring featuring **Virtual Nodes** for uniform distribution and demonstrates minimal partition movement upon cluster scaling:

```python
"""
Consistent Hashing Ring with Virtual Nodes.
Demonstrates:
  - Uniform hash ring mapping via MurmurHash-style MD5
  - Virtual Node replication for skew mitigation
  - O(log N) binary search key lookup (bisect)
  - Minimal key redistribution verification upon node addition
"""

import bisect
import hashlib
from typing import Dict, List, Optional


class ConsistentHashRing:
    def __init__(self, replicas: int = 100):
        # Number of virtual nodes per physical node
        self.replicas = replicas
        self.ring: List[int] = [] # Sorted hash tokens
        self.token_to_node: Dict[int, str] = {}
        self.nodes: Set[str] = set()

    def _hash(self, key: str) -> int:
        """Returns 32-bit integer hash."""
        return int(hashlib.md5(key.encode("utf-8")).hexdigest()[:8], 16)

    def add_node(self, node: str) -> None:
        """Adds physical node and inserts its virtual node tokens onto ring."""
        self.nodes.add(node)
        for i in range(self.replicas):
            vnode_key = f"{node}#vnode-{i}"
            token = self._hash(vnode_key)
            bisect.insort(self.ring, token)
            self.token_to_node[token] = node

    def remove_node(self, node: str) -> None:
        """Removes physical node and all associated virtual tokens."""
        if node not in self.nodes:
            return
        self.nodes.remove(node)
        for i in range(self.replicas):
            vnode_key = f"{node}#vnode-{i}"
            token = self._hash(vnode_key)
            idx = bisect.bisect_left(self.ring, token)
            if idx < len(self.ring) and self.ring[idx] == token:
                del self.ring[idx]
                del self.token_to_node[token]

    def get_node(self, key: str) -> Optional[str]:
        """Finds target physical node for key in O(log N) time."""
        if not self.ring:
            return None

        key_token = self._hash(key)
        # Find first token on ring >= key_token
        idx = bisect.bisect_right(self.ring, key_token)
        if idx == len(self.ring):
            idx = 0 # Wrap around ring

        return self.token_to_node[self.ring[idx]]


# Verification Execution
if __name__ == "__main__":
    ring = ConsistentHashRing(replicas=150)
    for node in ["node-alpha", "node-bravo", "node-charlie"]:
        ring.add_node(node)

    # Distribute 10,000 keys
    num_keys = 10000
    initial_assignment: Dict[str, str] = {}
    node_counts: Dict[str, int] = {"node-alpha": 0, "node-bravo": 0, "node-charlie": 0}

    for i in range(num_keys):
        k = f"order-uuid-{i}"
        target = ring.get_node(k)
        initial_assignment[k] = target
        node_counts[target] += 1

    print("=== Initial Key Distribution (3 Nodes) ===")
    for node, count in node_counts.items():
        print(f" {node:>14}: {count} keys ({count / num_keys * 100:.1f}%)")

    # Add a 4th node: verify minimal migration (should be approx 25%)
    print("\nAdding 'node-delta' to cluster...")
    ring.add_node("node-delta")

    migrated_keys = 0
    for k, original_node in initial_assignment.items():
        new_node = ring.get_node(k)
        if new_node != original_node:
            migrated_keys += 1

    print(f"Total keys migrated: {migrated_keys} / {num_keys} ({migrated_keys / num_keys * 100:.1f}%)")
    print("Expected theoretical migration: ~25.0%. Consistent hashing validated!")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Scatter-Gather Tail Latency Disaster
- **Antipattern:** Partitioning a database into 100 shards using document-partitioned secondary indexes, and executing searches by non-partition keys.
- **System Consequence:** Recall Chapter 1: $P_{\text{slow}} = 1 - (0.99)^{100} \approx 63.4\%$. Because every query must wait for all 100 partitions to respond, the overall latency is bound to the **slowest node in the entire cluster**.
- **Fix:** Avoid scatter-gather on high-frequency latency-sensitive paths. Route queries by primary partition key whenever possible.

### 2. Hash Modulo Rebalancing Pitfall (`hash(key) % N`)
- **Antipattern:** Assigning partitions using simple modulo arithmetic: `node = hash(key) % num_nodes`.
- **System Consequence:** When adding node $N+1$, nearly **every single key** hashes to a different node. Rebalancing moves $90\%+$ of all data across the network, knocking down the cluster.
- **Fix:** Always use **Consistent Hashing** or a **Fixed Number of Partitions**.

### 3. Automated Rebalancing Cascades
- **Antipattern:** Configuring aggressive, automatic rebalancing with short timeouts when a node appears slow.
- **System Consequence:** Node A experiences a brief GC pause. The orchestrator assumes Node A is dead and triggers massive partition rebalancing across the remaining nodes. The rebalancing network traffic overloads Node B, causing it to pause. The cluster enters an irreversible cascading rebalance loop.
- **Fix:** Require human approval or set conservative dead-node timeouts before initiating automated cluster-wide data rebalancing.
