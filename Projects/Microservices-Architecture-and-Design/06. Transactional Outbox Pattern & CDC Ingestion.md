# Chapter 06: Transactional Outbox Pattern & CDC Ingestion

> "When an application updates a database and publishes an event, it cannot do both atomically without distributed transactions. The Transactional Outbox pattern resolves this fundamental dual-write dilemma by storing outgoing events in an Outbox table within the same local database transaction, guaranteeing at-least-once delivery via Change Data Capture."  
> — *Chris Richardson, Microservice Patterns*

---

## 1. Canonical Motivation & Theoretical Foundation

### The Dual-Write Race Hazard
In distributed data architectures, a microservice frequently needs to update its local database and notify other services via an event broker (e.g. Apache Kafka or RabbitMQ). 

Consider the naive implementation:

```
Scenario A (DB first, then Broker):
1. db.save(order);        // [1] Success: Database updated
2. kafka.send(event);     // [2] NETWORK TIMEOUT / POD CRASH!
Result: Order exists in DB, but no event published. Downstream billing never occurs.

Scenario B (Broker first, then DB):
1. kafka.send(event);     // [1] Success: Kafka receives event
2. db.save(order);        // [2] DB ERROR: Constraint violation / Out of memory!
Result: Downstream services billed customer for an order that does not exist in DB.
```

No combination of `try-catch`, retries, or execution ordering can solve this without a distributed coordinator. However, as established in Chapter 05, Two-Phase Commit (XA transactions across Postgres and Kafka) is an anti-pattern that destroys throughput and system availability.

### The Transactional Outbox Pattern
The **Transactional Outbox Pattern** solves the dual-write problem by leveraging the local ACID properties of the service's relational database:
1. Whenever a business entity is inserted, updated, or deleted, an event record is written to an **Outbox Table** within the **same local database transaction**.
2. If the database transaction commits, both the entity modification and the outbox event are guaranteed to be persisted atomically.
3. If the transaction rolls back, neither is persisted.
4. A decoupled background process reads the Outbox table and reliably publishes the events to the message broker with **at-least-once** delivery semantics.

### Outbox Table Schema Design
A production-grade Outbox table requires attributes for routing, partitioning, and lifecycle management:

```sql
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(64) NOT NULL,      -- e.g. 'Order'
    aggregate_id VARCHAR(128) NOT NULL,       -- e.g. 'ORD-98231' (used as Kafka partition key)
    event_type VARCHAR(128) NOT NULL,         -- e.g. 'OrderCreated'
    payload JSONB NOT NULL,                   -- Canonical event payload
    headers JSONB,                            -- Correlation ID, Traceparent, Tenant ID
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    published BOOLEAN NOT NULL DEFAULT FALSE   -- Only required for Polling Publisher pattern
);

CREATE INDEX idx_outbox_unpublished ON outbox_events (created_at) WHERE published = FALSE;
```

## 3. Core Mechanics, Algorithms & Invariants

### Extraction Topologies: Polling Publisher vs. Transaction Log Tailing (CDC)

| Dimension | Polling Publisher (`SELECT ... FOR UPDATE`) | Transaction Log Tailing (CDC / Debezium) |
| :--- | :--- | :--- |
| **Mechanism** | Periodic background thread queries Outbox table via SQL. | Tails low-level DB transaction logs (PostgreSQL WAL, MySQL Binlog). |
| **DB Latency Impact**| High lock contention and query overhead under high write volume. | Near-zero DB query load; log reading is asynchronous. |
| **Publish Latency** | Governed by polling interval (e.g. 500ms - 2s). | Millisecond-level (streams as soon as WAL flushes to disk). |
| **Operational Cost**| Zero external infrastructure; runs within service pod. | Requires Kafka Connect cluster and database replication permissions. |
| **DB Support** | Works across all SQL and NoSQL engines. | Requires specific storage engine support (`pgoutput`, `maxwell`). |

### At-Least-Once Delivery & Deduplication (The Transactional Inbox)
Because network partitions can occur between the CDC engine and Kafka, messages may be published more than once. Consumers **must** implement deduplication. 

The **Transactional Inbox Pattern** mirrors the Outbox on the consumer side:
1. Consumer receives event with unique `event_id`.
2. Inside a local database transaction, consumer attempts to insert `event_id` into an `inbox` table with a unique primary key.
3. If insertion succeeds, consumer processes the domain update and commits both.
4. If a duplicate key violation occurs, consumer acknowledges the message to Kafka and skips execution.

## 4. Practical Systems & Production Engineering Trade-offs

### The Danger of Inactive Replication Slots (The WAL Disk Fill Outage)
When using Debezium CDC with PostgreSQL, the database creates a **logical replication slot**. 
- PostgreSQL will **refuse to truncate WAL segments** that have not yet been acknowledged by the replication slot's Log Sequence Number (`restart_lsn`).
- **Production Incident Scenario:** If the Kafka Connect worker crashes or Kafka is unreachable for several hours, the Debezium slot remains open but inactive. PostgreSQL accumulates WAL files until **100% of the storage volume is exhausted**, immediately causing PostgreSQL to crash and refuse all incoming connections.
- **Remediation:** Configure `max_slot_wal_keep_size` (PostgreSQL 13+) to cap WAL retention and monitor replication lag via Prometheus alerts (`pg_replication_slots`).

### Outbox Table Bloat & High-Throughput Vacuuming
If using a Polling Publisher where rows are updated (`published = TRUE`) or deleted:
- Frequent `UPDATE` and `DELETE` queries cause severe table and index bloat in PostgreSQL MVCC.
- **Remediation:** Implement daily table partitioning (`PARTITION BY RANGE (created_at)`) and drop old partitions with `DROP TABLE` instead of vacuuming billions of deleted rows.

## 5. Annotated Multi-Language Implementations

### Java (Spring Boot 3 + Spring Data JPA)
Atomic Outbox insertion within a single `@Transactional` service boundary.

```java
package com.example.outbox.service;

import com.example.outbox.domain.Order;
import com.example.outbox.domain.OutboxEvent;
import com.example.outbox.repository.OrderRepository;
import com.example.outbox.repository.OutboxRepository;
import com.fasterxml.jackson.databind.ObjectMapper;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Instant;
import java.util.UUID;

@Service
@RequiredArgsConstructor
public class OrderApplicationService {

    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository;
    private final ObjectMapper objectMapper;

    @Transactional
    public UUID createOrder(String customerId, double amount) {
        // 1. Mutate Domain Entity
        Order order = new Order(UUID.randomUUID(), customerId, amount, "CREATED");
        orderRepository.save(order);

        // 2. Prepare Outbox Event inside the SAME transaction
        try {
            String payloadJson = objectMapper.writeValueAsString(order);
            OutboxEvent outboxEvent = OutboxEvent.builder()
                .id(UUID.randomUUID())
                .aggregateType("Order")
                .aggregateId(order.getId().toString())
                .eventType("OrderCreatedEvent")
                .payload(payloadJson)
                .createdAt(Instant.now())
                .published(false)
                .build();

            outboxRepository.save(outboxEvent);
        } catch (Exception e) {
            throw new RuntimeException("Failed to serialize outbox event", e);
        }

        // Both order and outbox record commit atomically here
        return order.getId();
    }
}
```

### Go (Cloud-Native Go + pgx / Kafka Polling Publisher)
Atomic SQL transaction writing order and outbox record, accompanied by a resilient polling publisher goroutine.

```go
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/google/uuid"
	_ "github.com/lib/pq"
)

type Order struct {
	ID         string  `json:"id"`
	CustomerID string  `json:"customer_id"`
	Amount     float64 `json:"amount"`
}

// CreateOrderTx executes atomic write of Order and Outbox record
func CreateOrderTx(ctx context.Context, db *sql.DB, customerID string, amount float64) (string, error) {
	tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
	if err != nil {
		return "", fmt.Errorf("failed to begin tx: %w", err)
	}
	defer tx.Rollback()

	orderID := uuid.New().String()
	eventID := uuid.New().String()

	// 1. Insert domain record
	_, err = tx.ExecContext(ctx, 
		`INSERT INTO orders (id, customer_id, amount, status) VALUES ($1, $2, $3, 'CREATED')`,
		orderID, customerID, amount)
	if err != nil {
		return "", fmt.Errorf("failed to insert order: %w", err)
	}

	// 2. Insert outbox record
	payload, _ := json.Marshal(Order{ID: orderID, CustomerID: customerID, Amount: amount})
	_, err = tx.ExecContext(ctx,
		`INSERT INTO outbox_events (id, aggregate_type, aggregate_id, event_type, payload, published) 
		 VALUES ($1, 'Order', $2, 'OrderCreated', $3, FALSE)`,
		eventID, orderID, payload)
	if err != nil {
		return "", fmt.Errorf("failed to insert outbox event: %w", err)
	}

	if err := tx.Commit(); err != nil {
		return "", fmt.Errorf("failed to commit tx: %w", err)
	}

	return orderID, nil
}

// OutboxPublisherWorker polls for unpublished events and publishes to broker
func OutboxPublisherWorker(ctx context.Context, db *sql.DB) {
	ticker := time.NewTicker(500 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			rows, err := db.QueryContext(ctx, 
				`SELECT id, aggregate_id, payload FROM outbox_events WHERE published = FALSE ORDER BY created_at LIMIT 50 FOR UPDATE SKIP LOCKED`)
			if err != nil {
				log.Printf("polling error: %v", err)
				continue
			}

			for rows.Next() {
				var id, aggregateID string
				var payload []byte
				if err := rows.Scan(&id, &aggregateID, &payload); err == nil {
					// Simulate Kafka publish: kafkaProducer.Produce(aggregateID, payload)
					log.Printf("[Kafka] Published event %s for aggregate %s", id, aggregateID)
					db.ExecContext(ctx, `UPDATE outbox_events SET published = TRUE WHERE id = $1`, id)
				}
			}
			rows.Close()
		}
	}
}
```

### Python (FastAPI + SQLAlchemy Async + Transactional Inbox Consumer)
FastAPI implementation with asynchronous transactional outbox insertion and an idempotent consumer using the Inbox pattern.

```python
import uuid
from datetime import datetime, timezone
from fastapi import FastAPI, Depends, HTTPException, status
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine
from sqlalchemy.orm import sessionmaker, declarative_base
from sqlalchemy import Column, String, Float, DateTime, Boolean, Text, select
from sqlalchemy.exc import IntegrityError
from pydantic import BaseModel

Base = declarative_base()

class OrderModel(Base):
    __tablename__ = "orders"
    id = Column(String, primary_key=True)
    customer_id = Column(String, nullable=False)
    amount = Column(Float, nullable=False)
    status = Column(String, default="CREATED")

class OutboxEventModel(Base):
    __tablename__ = "outbox_events"
    id = Column(String, primary_key=True)
    aggregate_type = Column(String, nullable=False)
    aggregate_id = Column(String, nullable=False)
    event_type = Column(String, nullable=False)
    payload = Column(Text, nullable=False)
    created_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

class InboxModel(Base):
    __tablename__ = "inbox_processed_events"
    event_id = Column(String, primary_key=True)
    processed_at = Column(DateTime, default=lambda: datetime.now(timezone.utc))

app = FastAPI(title="Outbox & Inbox Service")

# Dependency Injection for Database Session
async def get_db_session() -> AsyncSession:
    # In production, injected from application connection pool
    pass

class OrderCreateRequest(BaseModel):
    customer_id: str
    amount: float

@app.post("/orders", status_code=status.HTTP_201_CREATED)
async def create_order(request: OrderCreateRequest, db: AsyncSession = Depends(get_db_session)):
    order_id = str(uuid.uuid4())
    event_id = str(uuid.uuid4())

    async with db.begin():
        # 1. Insert domain entity
        new_order = OrderModel(id=order_id, customer_id=request.customer_id, amount=request.amount)
        db.add(new_order)

        # 2. Insert outbox record within SAME database transaction
        outbox_event = OutboxEventModel(
            id=event_id,
            aggregate_type="Order",
            aggregate_id=order_id,
            event_type="OrderCreated",
            payload=f'{{"order_id": "{order_id}", "amount": {request.amount}}}'
        )
        db.add(outbox_event)

    return {"order_id": order_id, "status": "CREATED"}

# Idempotent Consumer handler for incoming Kafka events
async def process_incoming_order_event(event_id: str, payload: dict, db: AsyncSession):
    async with db.begin():
        # Check Inbox for deduplication
        inbox_record = InboxModel(event_id=event_id)
        db.add(inbox_record)
        try:
            await db.flush() # Fails immediately if event_id already exists (duplicate)
        except IntegrityError:
            # Duplicate event detected: skip processing safely
            return {"status": "SKIPPED_DUPLICATE"}

        # Process business logic idempotently
        # e.g., reserve inventory or send confirmation notification
        return {"status": "PROCESSED"}
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Outage Triage

### 1. Partition Key Invariant in Kafka CDC
- **The Pitfall:** If Debezium is configured without explicitly designating `aggregate_id` as the message key, Kafka distributes outbox events across partitions round-robin.
- **Failure Mode:** An `OrderCancelled` event can land on Partition 2 and be processed before an `OrderCreated` event on Partition 1, leaving the database in an invalid state.
- **Rule:** Always configure Kafka Connect SMT (Single Message Transformation) `ValueToKey` to extract `aggregate_id` into the record key.

### 2. Phantom Rows & Transaction Isolation
- **The Pitfall:** A Polling Publisher querying `SELECT * FROM outbox_events WHERE published = FALSE` without concurrency controls will cause multiple publisher instances to race and re-publish the same events.
- **Remediation:** Use `SELECT ... FOR UPDATE SKIP LOCKED` (supported in PostgreSQL, MySQL 8.0+, Oracle). `SKIP LOCKED` instructs Postgres to bypass rows currently locked by concurrent publisher transactions, eliminating lock contention and duplicate publishing.

### 3. Outage Triage: The Deadlock During Table Truncation
- **Symptom:** Application threads stall on `INSERT INTO outbox_events`.
- **Root Cause:** A cleanup cron job issued `TRUNCATE TABLE outbox_events` or an unindexed `DELETE FROM outbox_events WHERE published = TRUE`. In PostgreSQL, `TRUNCATE` acquires an `ACCESS EXCLUSIVE` lock on the table, blocking all concurrent `INSERT` operations.
- **Resolution:** Kill the blocker using `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE query LIKE '%TRUNCATE%';` and transition cleanup to time-partitioned table drops.
