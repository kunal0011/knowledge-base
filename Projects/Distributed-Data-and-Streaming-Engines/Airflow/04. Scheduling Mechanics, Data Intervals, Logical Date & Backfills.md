# Chapter 04: Scheduling Mechanics, Data Intervals, Logical Date & Backfills

> "Airflow does not run a task when the interval begins; it runs a task when the interval has ended. You cannot process yesterday's complete dataset until yesterday is actually over."  
> — *Bas P. Harenslak & Julian Rutger de Ruiter, Data Pipelines with Apache Airflow*

---

## 1. Canonical Motivation & Theoretical Foundation

The most common source of confusion for engineers adopting Apache Airflow is the scheduling timeline. In naive crontab systems, a job scheduled for `0 0 * * *` (midnight) executes at `00:00:00` and processes whatever data is currently available.

In batch data orchestration, however, pipelines operate over **bounded temporal partitions**. Consider a daily batch job calculating sales for May 1st:
- Sales for May 1st occur between `2026-05-01 00:00:00` and `2026-05-01 23:59:59`.
- Therefore, the pipeline calculating May 1st sales **cannot execute until `2026-05-02 00:00:00`**—the exact moment the May 1st time window closes.

Historically, Airflow labelled this run using the start timestamp (`2026-05-01`), calling it `execution_date`. This naming caused endless confusion because the job was executing on May 2nd, while its `execution_date` was labelled May 1st.

To resolve this ambiguity, modern Airflow (2.2+) introduced formal **Data Intervals** and the **Timetables API (AIP-39)**, clearly distinguishing between the *data window being processed* and the *moment of execution*.

## 2. Underlying Runtime, Memory & Execution Architecture

### Data Intervals & Temporal Terminology

```
   Data Interval Start                  Data Interval End (Run Triggered!)
 [ 2026-05-01 00:00:00 ] ─────────────> [ 2026-05-02 00:00:00 ] ────> Pipeline Executes
           │                                      │
           └─────────── DATA INTERVAL ────────────┘
                         (1 Day)
```

1. **`data_interval_start`:** The exact beginning timestamp of the period of data covered by this DAG run (inclusive).
2. **`data_interval_end`:** The exact end timestamp of the period of data covered by this DAG run (exclusive). The DAG run is triggered by the scheduler immediately after this timestamp passes.
3. **`logical_date` (formerly `execution_date`):** The logical label identifying the run. In standard interval-based schedules, `logical_date` is identical to `data_interval_start`.

### The Modern Timetable Engine (AIP-39)

Prior to Airflow 2.2, scheduling was rigidly bound to cron expressions or `timedelta` intervals. This made it nearly impossible to support business schedules such as *"Run at 6 PM on the last business day of every month"* or *"Run every 30 minutes, but skip market holidays."*

The **Timetables API** decouples scheduling logic from cron expressions:
- A custom `Timetable` class registers hooks: `next_dagrun_info(last_automated_data_interval, restriction)`.
- It returns a `DagRunInfo` object explicitly declaring both the `DataInterval` and the `run_after` timestamp.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Built-in Jinja Macro References

When parameterizing SQL queries, S3 prefixes, or bash scripts, always use modern Jinja temporal macros rather than calculating dates dynamically:

| Jinja Macro | Value Format | Description |
| :--- | :--- | :--- |
| **`{{ ds }}`** | `YYYY-MM-DD` | Logical date as date string (e.g. `2026-05-01`). |
| **`{{ ds_nodash }}`** | `YYYYMMDD` | Logical date without dashes (useful for S3 prefixes). |
| **`{{ data_interval_start }}`** | `DateTime` object | Beginning of data interval (e.g. `2026-05-01T00:00:00+00:00`). |
| **`{{ data_interval_end }}`** | `DateTime` object | End of data interval / moment of trigger. |
| **`{{ ts }}`** | ISO 8601 string | Full timestamp of the logical date. |

### The Golden Rule of Idempotency

A data pipeline is **idempotent** if running it multiple times with the exact same inputs produces the exact same final state. 

```
                          ┌───────────────────────────┐
                          │   Non-Idempotent SQL      │
                          │ INSERT INTO sales_report  │  (Creates duplicate rows on retry!)
                          └───────────────────────────┘
                          ┌───────────────────────────┐
                          │     Idempotent SQL        │
                          │ DELETE FROM sales_report  │  (Safe to retry infinite times)
                          │ WHERE dt = '{{ ds }}';    │
                          │ INSERT INTO sales_report  │
                          └───────────────────────────┘
```

## 4. Practical Systems & Production Use Cases

1. **Partition-Aligned Lakehouse Ingestion:** Templating SQL queries with `WHERE event_time >= '{{ data_interval_start }}' AND event_time < '{{ data_interval_end }}'`.
2. **Financial Month-End Close Runs:** Using custom timetables to trigger accounting balance reconciliations on business days, skipping weekends and banking holidays.
3. **Historical Backfills:** Backfilling 5 years of historical partitions safely using `airflow dags backfill` without altering production DAG definitions.

## 5. Annotated Code Implementations & Execution Traces

### Custom Business-Day Timetable & Idempotent Templated DAG

The following production code implements a custom Airflow Timetable that schedules DAG runs strictly on Monday through Friday, skipping weekends, paired with an idempotent parameterized DAG:

```python
"""
Custom Business-Day Timetable and Idempotent SQL Ingestion DAG.
Demonstrates:
  - Custom Timetable subclassing (AIP-39)
  - Next run calculation skipping weekends
  - Idempotent data loading using Jinja date macros
"""

from datetime import datetime, time
from typing import Optional
import pendulum
from pendulum import Date, DateTime, Time

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.timetables.base import DagRunInfo, DataInterval, TimeRestriction, Timetable


class BusinessDayTimetable(Timetable):
    """
    Schedules DAGs to run at 18:00 UTC on business days (Mon-Fri).
    Each run covers data from 00:00 to 23:59:59 of that business day.
    """

    def next_dagrun_info(
        self,
        *,
        last_automated_data_interval: Optional[DataInterval],
        restriction: TimeRestriction,
    ) -> Optional[DagRunInfo]:
        if last_automated_data_interval is not None:
            # Start from the day after the last automated run
            last_date = last_automated_data_interval.end.in_timezone(pendulum.UTC).date()
            next_date = last_date.add(days=1)
        else:
            # First run: start from earliest allowed start_date
            if restriction.earliest is None:
                return None
            next_date = restriction.earliest.in_timezone(pendulum.UTC).date()

        # Advance through weekends until Monday (weekday 1..5 = Mon..Fri in Pendulum)
        while next_date.day_of_week in (pendulum.SATURDAY, pendulum.SUNDAY):
            next_date = next_date.add(days=1)

        start = DateTime.combine(next_date, Time(0, 0, 0)).replace(tzinfo=pendulum.UTC)
        end = DateTime.combine(next_date, Time(23, 59, 59)).replace(tzinfo=pendulum.UTC)
        # Execute immediately after business day closes at 18:00
        run_after = DateTime.combine(next_date, Time(18, 0, 0)).replace(tzinfo=pendulum.UTC)

        return DagRunInfo.interval(start=start, end=end)


# Registering DAG using Custom Business-Day Timetable
with DAG(
    dag_id="financial_settlements_business_days_v1",
    timetable=BusinessDayTimetable(),
    start_date=pendulum.datetime(2026, 1, 1, tz="UTC"),
    catchup=False,
    tags=["finance", "timetable", "idempotent"],
) as dag:

    # Idempotent ETL Task: Extracts partition bounded strictly by data interval
    extract_partition = BashOperator(
        task_id="extract_daily_partition",
        bash_command=(
            "echo 'Processing partition between "
            "{{ data_interval_start.to_iso8601_string() }} and "
            "{{ data_interval_end.to_iso8601_string() }}' "
            "&& echo 'Target partition date ds={{ ds }}'"
        ),
    )

    # Idempotent Database Load: Atomically replaces the target partition
    load_idempotent_gold = BashOperator(
        task_id="load_gold_mart",
        bash_command=(
            "echo 'Executing SQL: "
            "INSERT OVERWRITE TABLE gold_settlements PARTITION (dt=\"{{ ds }}\") "
            "SELECT * FROM staging WHERE dt=\"{{ ds }}\";'"
        ),
    )

    extract_partition >> load_idempotent_gold
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. Using `datetime.now()` Inside SQL Queries
- **Antipattern:** Generating timestamps dynamically inside tasks or queries:
  ```sql
  -- CATASTROPHIC BACKFILL ANTI-PATTERN:
  SELECT * FROM transactions WHERE created_at >= NOW() - INTERVAL '1 DAY';
  ```
- **System Consequence:** If the pipeline fails and is retried tomorrow, or if you run a historical backfill for 2024, `NOW()` evaluates to the *current moment in 2026*. The query extracts completely wrong data, corrupting historical partitions.
- **Fix:** Always bind date queries strictly to Jinja templated interval macros (`{{ data_interval_start }}` and `{{ data_interval_end }}`).

### 2. Dynamic `start_date = datetime.now()`
- **Antipattern:** Setting `start_date = datetime.now()` in the `DAG` definition.
- **System Consequence:** `datetime.now()` changes every time the scheduler parses the DAG file. Because `start_date` continuously advances into the future, the scheduler believes the start threshold has never been met, and the DAG **never executes**.
- **Fix:** Hardcode `start_date` to a fixed, static point in the past (e.g., `datetime(2026, 1, 1)`).

### 3. Conflating Run Time with Data Interval in Alerts
- **Antipattern:** Alerting on pipeline delays by comparing wall-clock execution time directly against `logical_date` without accounting for interval duration.
- **System Consequence:** An hourly DAG running for the `10:00 - 11:00` interval naturally triggers at `11:00:05`. Comparing against `logical_date` (10:00) causes false alert fires claiming the job is 60 minutes late before it even starts.
- **Fix:** Base SLA calculations on `data_interval_end` rather than `logical_date`.
