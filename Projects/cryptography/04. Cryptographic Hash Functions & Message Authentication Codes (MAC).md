# Chapter 04: Cryptographic Hash Functions & Message Authentication Codes (MAC)

> "A cryptographic hash function is the mathematical Swiss Army knife of information security. It transforms an arbitrary-length message into a compact, fixed-size digital fingerprint that is computationally impossible to invert or forge."  
> — *Jonathan Katz & Yehuda Lindell, Introduction to Modern Cryptography*

---

## 📐 1. The Three Foundational Security Properties

A **Cryptographic Hash Function** is a deterministic, public algorithm:
$$H : \{0, 1\}^* \longrightarrow \{0, 1\}^n$$
mapping an input of arbitrary bit length to a fixed output of $n$ bits (e.g., $n = 256$ in SHA-256).

```text
===================================================================================================
                                HASH FUNCTION SECURITY PROPERTIES
===================================================================================================

  [ 1. Pre-image Resistance (One-Way) ]
  Given a hash output y = H(x):
  - It is computationally infeasible to find ANY input x such that H(x) = y.
  - Work Required: O(2^n) brute-force operations.

  [ 2. Second Pre-image Resistance (Weak Collision Resistance) ]
  Given a specific input x and its hash H(x):
  - It is computationally infeasible to find a DIFFERENT input x' != x such that H(x') = H(x).
  - Work Required: O(2^n) operations.

  [ 3. Collision Resistance (Strong Collision Resistance) ]
  It is computationally infeasible to find ANY two distinct inputs (x, x') such that:
  - x != x'  AND  H(x) = H(x').
  - ⚠️ Work Required: ONLY O(2^(n/2)) operations due to the Birthday Paradox!
```

---

## 🎂 2. The Birthday Paradox & Collision Resistance Bounds

A common mistake in security design is assuming that a 128-bit hash function requires $2^{128}$ operations to find a collision.

### 2.1 The Mathematics of the Birthday Problem
In a room of only **23 people**, what is the probability that at least two people share the exact same birthday?
$$\Pr[\text{No Match}] = 1 \times \left(1 - \frac{1}{365}\right) \times \left(1 - \frac{2}{365}\right) \times \dots \times \left(1 - \frac{22}{365}\right) \approx 0.4927$$
$$\Pr[\text{At Least One Shared Birthday}] = 1 - 0.4927 = \mathbf{50.73\%}!$$

### 2.2 Application to Cryptographic Hashes
Using the Taylor approximation $1 - x \approx e^{-x}$, for $k$ random samples drawn from an $N$-element space ($N = 2^n$):
$$\Pr[\text{Collision}] \approx 1 - e^{-\frac{k(k-1)}{2N}} \approx 1 - e^{-\frac{k^2}{2 \cdot 2^n}}$$
Setting $\Pr[\text{Collision}] = 0.5$:
$$\frac{k^2}{2 \cdot 2^n} = \ln(2) \implies k \approx \sqrt{2 \ln(2) \cdot 2^n} \approx \mathbf{1.177 \times 2^{n/2}}$$

> [!IMPORTANT]
> **The $n/2$ Security Bound:**
> An $n$-bit hash function provides at most **$n/2$ bits of collision security**:
> - **MD5 ($n=128$ bits):** Collision resistance $= 2^{64}$. Broken in 2004 by Wang et al.; collisions generated in seconds on a laptop.
> - **SHA-1 ($n=160$ bits):** Collision resistance $= 2^{80}$. Broken by Google (SHAttered attack) in 2017 using $2^{63.1}$ evaluations.
> - **SHA-256 ($n=256$ bits):** Collision resistance $= 2^{128}$ operations. Remains cryptographically unbroken.

## 🔨 3. Merkle-Damgård Construction & Length Extension Attacks

Most legacy and modern hash functions (MD5, SHA-1, SHA-256, SHA-512) are built on the **Merkle-Damgård Construction**:

```text
===================================================================================================
                                MERKLE-DAMGÅRD HASH CONSTRUCTION
===================================================================================================

  Message M is padded and sliced into fixed 512-bit blocks: M_1, M_2, ..., M_k
  
          M_1                     M_2                     M_k
           │                       │                       │
           ▼                       ▼                       ▼
  IV ──►┌───────┐         ┌───►┌───────┐         ┌───►┌───────┐
        │   f   ├─────────┘    │   f   ├─────────┘    │   f   ├──────► Hash Output H(M)
        └───────┘  State h1     └───────┘  State h2    └───────┘
```

The compression function $f(h_{i-1}, M_i)$ iteratively mixes each message block with the running state.

---

### 3.1 The Length Extension Attack: Why Naive MACs Fail
A developer might attempt to create a Message Authentication Code by prepending a secret key to a message:
$$\text{Auth}(M) = H(\text{SecretKey} \parallel M)$$

#### How an Attacker Exploits Merkle-Damgård:
1. The attacker intercepts a legitimate message $M$ and its authentication tag $T = H(\text{SecretKey} \parallel M)$.
2. Notice that **$T$ is the exact internal state ($h_k$) of the compression function after processing $M$!**
3. The attacker does not need to know the `SecretKey`! They initialize the Merkle-Damgård compression function with the state set to $T$, and process an extension block $M_{\text{evil}}$:
   $$T_{\text{forged}} = f(T, M_{\text{evil}})$$
4. The server verifies $T_{\text{forged}}$ against $H(\text{SecretKey} \parallel M \parallel \text{padding} \parallel M_{\text{evil}})$ and accepts the forged command!

## 🧽 4. The Sponge Construction: Keccak & SHA-3 (FIPS 202)

To create an architecture completely immune to length extension attacks, NIST selected **Keccak** as **SHA-3**:

```text
===================================================================================================
                                  THE SHA-3 SPONGE CONSTRUCTION
===================================================================================================

                [ Absorbing Phase ]                           [ Squeezing Phase ]
  
  M_1           M_2                                           Z_1           Z_2
   │             │                                             ▲             ▲
   ▼             ▼                                             │             │
  XOR           XOR                                            │             │
 ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐       ┌─┴───────┐   ┌─┴───────┐
 │ State r ├──►│ State r ├──►│ State r ├──►│ State r ├──────►│ State r ├──►│ State r │
 ├─────────┤   ├─────────┤   ├─────────┤   ├─────────┤       ├─────────┤   ├─────────┤
 │ State c │   │ State c │   │ State c │   │ State c │       │ State c │   │ State c │
 └────┬────┘   └────┬────┘   └────┬────┘   └────┬────┘       └────┬────┘   └────┬────┘
      │             │             │             │                 │             │
      ▼             ▼             ▼             ▼                 ▼             ▼
   [ Permutation f ]           [ Permutation f ]               [ Permutation f ]
```

- Total State: $b = r + c = 1600\text{ bits}$.
- **Rate ($r$):** The portion of the state XORed with message blocks ($1088\text{ bits}$ in SHA3-256).
- **Capacity ($c$):** The hidden internal state ($512\text{ bits}$). The capacity is never exposed directly in the output, mathematically defeating length extension attacks!

## 🔒 5. Hash-Based Message Authentication Codes (HMAC - RFC 2104)

**HMAC** is the provably secure standard for message authentication over Merkle-Damgård hash functions:

$$\text{HMAC}_K(M) = H\Big( (K' \oplus \text{opad}) \mathbin{\Vert} H\big( (K' \oplus \text{ipad}) \mathbin{\Vert} M \big) \Big)$$

where:
- $\text{ipad} = 0x3636\dots36$ (Inner padding byte repeated across block size).
- $\text{opad} = 0x5C5C\dots5C$ (Outer padding byte repeated across block size).
- $K'$ is the key padded with trailing zeros to match the hash block size.

```text
===================================================================================================
                                      HMAC DATA FLOW
===================================================================================================

  Key K' ──► XOR ipad ──► [ Inner Hash H ] ◄── Message M
                                 │
                                 ▼ Inner Hash Output (32 bytes)
  Key K' ──► XOR opad ──► [ Outer Hash H ]
                                 │
                                 ▼
                     Final HMAC Tag (32 bytes)
```

Because the outer hash consumes the secret $(K' \oplus \text{opad})$ *after* processing the message, **an attacker cannot append data to the inner hash state**, completely neutralizing length extension attacks!

## 🔑 6. Password Hashing & Memory-Hard Functions

> [!CAUTION]
> **Never use standard cryptographic hash functions (SHA-256, SHA-512) for passwords!**  
> Modern cryptocurrency mining ASICs and consumer GPUs compute over **$100\text{ billion SHA-256 hashes per second}$**, brute-forcing an 8-character password in minutes!

### 6.1 The Password Hashing Evolution
1. **Salt:** A cryptographically random unique value appended to each user's password before hashing. Defeats **Rainbow Tables** (precomputed hash tables) and prevents identical passwords from producing identical hashes.
2. **PBKDF2 (RFC 2898):** CPU-bound iteration looping: $T_i = F(P, S, c)$. Work factor is adjusted by increasing iterations $c$ (e.g., $600,000$ rounds).
3. **bcrypt:** Based on the Blowfish block cipher's expensive key schedule. Memory-bound; harder to parallelize on GPUs.
4. **Argon2id (Winner of the Password Hashing Competition - RFC 9106):**
   - **Memory-Hard:** Fills hundreds of megabytes of RAM with pseudo-random data.
   - Requires an adversary to allocate vast amounts of dedicated silicon SRAM on an ASIC, making large-scale parallel GPU attacks economically and physically prohibitive.
   - **Argon2id** combines data-dependent memory accesses (resisting GPU cracking) with data-independent accesses (resisting side-channel cache-timing attacks).
