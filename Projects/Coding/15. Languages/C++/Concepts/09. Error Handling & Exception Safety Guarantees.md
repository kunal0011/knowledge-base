# C++ Concepts: Error Handling & Exception Safety Guarantees

**Foundational Texts:**  
- *The C++ Programming Language (4th Ed.)* by Bjarne Stroustrup, Chapter 13  
- *Effective Modern C++* by Scott Meyers, Item 14  
- *Exceptional C++* by Herb Sutter (The Definitive Exception Safety Authority)  

---

## 1. Theoretical Motivation: Why Exceptions Exist

In C, functions return integer error codes. However, error codes suffer from three systemic failures:
1. **Ignorability:** Callers frequently forget to check return codes (`if (res != 0)`), allowing invalid state to cascade.
2. **Constructors Cannot Return Values:** A constructor has no return type; without exceptions, a failed constructor leaves a half-initialized, corrupted object.
3. **Control Flow Pollution:** Error propagation forces intermediate functions to clutter their logic with repetitive error-checking cascades.

Exceptions separate **error detection** (the low-level routine that discovers an impossible state) from **error handling** (the high-level caller that knows how to recover).

---

## 2. The Four Exception Safety Guarantees (Herb Sutter)

In *Exceptional C++*, Herb Sutter formalized the universal four-tier exception safety classification:

```
+-----------------------------------------------------------------------------------------+
|                               EXCEPTION SAFETY TIERS                                    |
+-------------------+---------------------------------------------------------------------+
| Tier              | Guarantee Invariant                                                 |
+-------------------+---------------------------------------------------------------------+
| 1. Nothrow        | Operation is **guaranteed never to throw** under any condition.     |
|    (Noexcept)     | Essential for destructors, move operations, and swap routines.      |
+-------------------+---------------------------------------------------------------------+
| 2. Strong         | **Commit-or-Rollback:** If an exception is thrown, program state    |
|    Guarantee      | remains exactly as it was before the call was initiated!            |
+-------------------+---------------------------------------------------------------------+
| 3. Basic          | **No Leaks:** Resources are safely reclaimed and class invariants   |
|    Guarantee      | hold, but state may be modified (valid but unspecified state).      |
+-------------------+---------------------------------------------------------------------+
| 4. No Guarantee   | **Undefined Behavior:** Memory leaked, locks left locked, pointers  |
|                   | left dangling. Completely unacceptable in production.               |
+-------------------+---------------------------------------------------------------------+
```

## 3. The Copy-and-Swap Idiom: Delivering the Strong Guarantee

How do you guarantee that an assignment operator or mutation provides the **Strong Guarantee** (commit-or-rollback)?
By performing all work on a **temporary local copy**, and then committing the change using a non-throwing `swap`:

```cpp
class SafeArray {
private:
    size_t size;
    int* data;

public:
    // Non-throwing swap:
    friend void swap(SafeArray& first, SafeArray& second) noexcept {
        using std::swap;
        swap(first.size, second.size);
        swap(first.data, second.data);
    }

    // Copy constructor (Provides Strong Guarantee):
    SafeArray(const SafeArray& other) 
        : size(other.size), data(other.size ? new int[other.size] : nullptr) {
        std::copy(other.data, other.data + size, data);
    }

    // Copy-and-Swap Assignment:
    SafeArray& operator=(SafeArray other) noexcept { // Passed by VALUE (makes copy!)
        // If copy constructor threw, execution NEVER reached here!
        swap(*this, other); // Commit change via noexcept pointer swap!
        return *this;
        // 'other' destructor frees the old underlying buffer automatically!
    }
};
```

## 4. The `noexcept` Specifier (Scott Meyers Item 14)

Declaring a function `noexcept` is a contractual guarantee to the compiler and runtime that no exception will escape.

### 4.1 What Happens if a `noexcept` Function Throws?
If an exception attempts to propagate out of a `noexcept` function, the C++ runtime **immediately invokes `std::terminate()`**, aborting the process without running further destructors!

### 4.2 Why `noexcept` Enables Massive Performance Gains:
1. **Container Reallocations:** When `std::vector` expands, it checks `std::is_nothrow_move_constructible_v<T>`. If `noexcept`, it uses **move operations ($\mathcal{O}(1)$)**. If not, it falls back to **copying all elements ($\mathcal{O}(N)$)** to preserve the Strong Guarantee!
2. **Optimizer Freedom:** In `noexcept` functions, the compiler does not need to generate stack unwinding exception tables, reducing binary code size and improving instruction cache density.

```cpp
// Move operations MUST be noexcept:
Widget(Widget&& other) noexcept : data(other.data) { other.data = nullptr; }
```

## 5. Modern Functional Error Handling: `std::expected` (C++23)

For performance-critical code where stack-unwinding exceptions are undesirable, C++23 introduces **`std::expected<T, E>`** (inspired by Rust's `Result<T, E>`):

```cpp
#include <expected>
#include <string>

enum class ParseError { InvalidChar, Overflow };

std::expected<int, ParseError> parseInteger(const std::string& s) {
    if (s.empty()) return std::unexpected(ParseError::InvalidChar);
    // ... parse logic ...
    return 42; // Returns success payload
}

// Client Code: Zero exception overhead!
auto result = parseInteger("42");
if (result.has_value()) {
    std::cout << "Parsed: " << result.value();
} else {
    std::cout << "Error Code: " << static_cast<int>(result.error());
}
```

## 6. Authoritative Gotchas & Traps (Stroustrup & Meyers)

### 6.1 Destructors Must NEVER Emit Exceptions!
```cpp
// FATAL DISASTER:
class Connection {
public:
    ~Connection() {
        if (failed) throw std::runtime_error("Close failed!"); // TERMINATES PROCESS!
    }
};
```

#### Why it Aborts:
If an exception is currently active and causing stack unwinding, and an object being unwound throws an exception from its destructor:
**Two simultaneous exceptions are active at the same time.** The C++ runtime cannot resolve which exception to propagate, and immediately halts execution with **`std::terminate()`**.  
**The Rule:** Destructors in C++11+ are implicitly `noexcept`. If a destructor operation can fail, swallow or log the error internally; never let it escape!

### 6.2 Catching Exceptions by Value Causes Object Slicing
```cpp
// ANTI-PATTERN:
try {
    throw NetworkException("Timeout error");
} catch (std::exception e) { // Caught by VALUE! Slices derived class!
    std::cout << e.what();   // Prints generic std::exception, losing Network details!
}

// CORRECT: Always catch by const reference:
catch (const std::exception& e) { ... }
```

## 7. Actionable Summary Checklist

- [x] Guarantee at least the **Basic Exception Safety Guarantee** for all code: zero resource leaks upon failure.
- [x] Use the **Copy-and-Swap idiom** to achieve the Strong Guarantee (commit-or-rollback) on mutations.
- [x] Always mark move constructors, move assignment operators, and swap functions **`noexcept`** (Effective Modern C++ Item 14).
- [x] **Never allow an exception to escape from a destructor**; it causes an immediate crash via `std::terminate`.
- [x] Always catch exceptions by **`const &`** to prevent object slicing and preserve polymorphic diagnostics.
- [x] Use `std::expected` (C++23) or `std::optional` for expected operational failures where exception unwinding overhead is prohibited.
