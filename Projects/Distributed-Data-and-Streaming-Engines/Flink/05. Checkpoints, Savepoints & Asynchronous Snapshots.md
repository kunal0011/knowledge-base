# Chapter 05: Checkpoints, Savepoints & Asynchronous Snapshots

> "The Chandy-Lamport algorithm allows a distributed streaming engine to draw a globally consistent line across execution time without pausing stream ingestion."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

In a distributed stream processing cluster with hundreds of nodes running continuously for months, node failures, network partitions, and hardware crashes are statistical certainties. 

Early streaming systems responded to failures with two deeply flawed extremes:
1. **At-Least-Once Replay from Origin:** Restarting the stream from the source beginning and replaying billions of events, resulting in hours of recovery downtime and duplicate counts.
2. **Synchronous Stop-the-World Snapshots:** Halting all ingestion across the entire cluster while every node flushed its memory to disk, causing unacceptable latency spikes.

Flink solves distributed fault tolerance by implementing an industrial adaptation of the **Chandy-Lamport Distributed Snapshot Algorithm**. Flink achieves **asynchronous, non-blocking snapshots** of all distributed state, guaranteeing that in the event of any failure, the entire system can restore to a mathematically consistent point in time with **Exactly-Once Semantics**.

## 2. Underlying Runtime, Memory & Execution Architecture

### Checkpoint Barrier Injection & Flow

The **CheckpointCoordinator** on the JobMaster periodically triggers snapshots by injecting special control markers called **Checkpoint Barriers** into the input streams at the source operators:

```
[Source Task] ──> [Record] ──> [Record] ──> [Barrier n] ──> [Record] ──> [Record]
```

Barriers flow strictly alongside data records through the execution topology. A barrier divides the stream into two distinct logical epochs:
- Records preceding Barrier $n$ belong to Snapshot $n$.
- Records following Barrier $n$ belong to Snapshot $n+1$.

### Aligned vs. Unaligned Checkpoints

When an operator receives input from multiple upstream channels, it must process barriers across all channels before committing its snapshot.

#### 1. Aligned Checkpoints (Standard)
- When Barrier $n$ arrives on Channel 0, but has not yet arrived on Channel 1, the operator **pauses consumption on Channel 0**.
- Incoming records on Channel 0 are buffered in memory while the operator waits for Barrier $n$ to arrive on Channel 1.
- Once all barriers arrive, the operator takes its local snapshot, emits Barrier $n$ downstream, and resumes processing buffered records.

```
Channel 0: ──[Record]──[Record]──[Barrier n]──> [ OPERATOR ]  (Buffer Channel 0 records)
Channel 1: ──[Record]──[Record]───────────────> [ OPERATOR ]  (Waiting for Barrier n)
```

*Vulnerability:* Under severe downstream backpressure, network buffers fill up completely. Checkpoint barriers get trapped behind thousands of unconsumed data records, causing the checkpoint to exceed its timeout and abort.

#### 2. Unaligned Checkpoints (FLIP-27 / Flink 1.11+)
- To eliminate barrier alignment delays under backpressure, Flink introduced **Unaligned Checkpoints**:
- The instant Barrier $n$ arrives on *any* input channel, the operator immediately overtakes all in-flight data records in its input buffers.
- It snapshots:
  1. Its current local state.
  2. All unconsumed in-flight records currently sitting in its input network buffers.
  3. All in-flight records sitting in its output network buffers.
- The barrier is forwarded downstream immediately without waiting for alignment.

```
       [ In-flight Buffer Snapshot ] + [ Operator Local State ] = Unaligned Snapshot
```

### The Two-Phase Asynchronous Snapshot

To avoid stalling record processing, Flink executes snapshots in two decoupled phases:
1. **Synchronous Phase (Microseconds):** The operator pauses processing briefly to copy pointers to its current state structures (or triggers an LSM-tree memtable flush in RocksDB).
2. **Asynchronous Phase (Seconds):** The operator resumes processing incoming stream records immediately on the main thread, while a background I/O thread pool uploads the serialized state files and SSTables to persistent remote storage (e.g. S3, GCS, HDFS).
3. **Acknowledgment:** Once background upload completes, the task sends an acknowledgment RPC to the JobManager. When all tasks acknowledge, the JobManager marks Checkpoint $n$ as complete and writes the master `_metadata` file.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Checkpoints vs. Savepoints

| Feature | Checkpoint | Savepoint |
| :--- | :--- | :--- |
| **Trigger Mechanism** | System-driven, automatic periodic schedule. | User-driven via CLI (`flink savepoint <jobId>`). |
| **Primary Purpose** | Automatic failover recovery from unexpected crashes. | Intentional lifecycle operations: upgrades, rescales, migrations. |
| **Format & Storage** | Optimized, incremental (RocksDB SST files). Cluster-tied. | Canonical, portable, unified format. Cross-version portable. |
| **Lifecycle** | Automatically purged upon job cancellation or retention limit. | Retained forever until explicitly deleted by the operator. |

## 4. Practical Systems & Production Use Cases

1. **Zero-Downtime Cluster Version Upgrades:** Creating a savepoint, terminating a running Flink 1.16 cluster, deploying Flink 1.18, and resuming the job from the savepoint without losing state.
2. **Elastic Cloud Autoscaling:** Triggering a savepoint, altering cluster TaskSlot parallelism from 16 to 64, and resuming with automatic key-group state redistribution.
3. **Disaster Recovery & Blue-Green Testing:** Restoring production state into a staging environment from a recent savepoint to validate new business logic before deployment.

## 5. Annotated Code Implementations & Execution Traces

### Production Checkpoint Configuration: Unaligned Checkpoints & Externalized Storage

The following Java code demonstrates an enterprise-grade checkpointing configuration optimized for large state, high backpressure resistance, and externalized retention:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.configuration.Configuration;
import org.apache.flink.configuration.ExternalizedCheckpointRetention;
import org.apache.flink.contrib.streaming.state.EmbeddedRocksDBStateBackend;
import org.apache.flink.streaming.api.CheckpointingMode;
import org.apache.flink.streaming.api.environment.CheckpointConfig;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;

import java.time.Duration;

public class ProductionCheckpointingConfigurationJob {

    public static void configureCheckpointing(StreamExecutionEnvironment env) {
        // Step 1: Enable checkpointing every 60 seconds
        env.enableCheckpointing(60000L, CheckpointingMode.EXACTLY_ONCE);

        CheckpointConfig config = env.getCheckpointConfig();

        // Step 2: Minimum pause between checkpoints (prevents checkpoint storms)
        // Guarantees that the pipeline processes stream records for at least 30s between snapshots
        config.setMinPauseBetweenCheckpoints(30000L);

        // Step 3: Checkpoint timeout (abort if snapshot takes longer than 5 minutes)
        config.setCheckpointTimeout(300000L);

        // Step 4: Max concurrent checkpoints (strictly 1 to conserve disk and network I/O)
        config.setMaxConcurrentCheckpoints(1);

        // Step 5: Externalize checkpoints so state survives manual job cancellations
        config.setExternalizedCheckpointRetention(
                ExternalizedCheckpointRetention.RETAIN_ON_CANCELLATION
        );

        // Step 6: Enable Unaligned Checkpoints to survive severe backpressure
        config.enableUnalignedCheckpoints();
        // Allow 10 seconds of alignment before switching to unaligned mode
        config.setAlignmentTimeout(Duration.ofSeconds(10));

        // Step 7: Configure incremental RocksDB checkpointing to persistent storage
        EmbeddedRocksDBStateBackend rocksDbBackend = new EmbeddedRocksDBStateBackend(true); // true = incremental
        env.setStateBackend(rocksDbBackend);
        
        // Remote persistent storage for state snapshots
        config.setCheckpointStorage("s3://enterprise-flink-checkpoints/production-pipelines/order-engine/");
    }

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        configureCheckpointing(env);

        // Simple mock streaming flow
        env.fromSequence(1, 1000000)
                .map(val -> "EVENT-RECORD-" + val)
                .print();

        env.execute("ProductionCheckpointingConfigurationJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Checkpoint Storm Anti-Pattern
- **Antipattern:** Setting a short checkpoint interval (e.g., `enableCheckpointing(5000)`) without configuring `setMinPauseBetweenCheckpoints(...)`.
- **System Consequence:** If network congestion or large state causes an incremental checkpoint to take 8 seconds, the CheckpointCoordinator will immediately launch the next checkpoint the millisecond the previous one finishes. The cluster becomes permanently trapped in continuous checkpoint serialization and S3 network uploads, starving data processing threads.
- **Fix:** Always set `setMinPauseBetweenCheckpoints(30000)` and keep `setMaxConcurrentCheckpoints(1)`.

### 2. The Unaligned Checkpoint Storage Bloat Trap
- **Antipattern:** Enabling unaligned checkpoints in pipelines where massive 100MB network buffers are severely congested with heavy batch-like payloads.
- **System Consequence:** Unaligned checkpoints persist all in-flight network buffers directly into the checkpoint storage. If downstream sinks are completely stalled, snapshot sizes can inflate by orders of magnitude (from a few megabytes of state to tens of gigabytes of raw network buffer payloads), exhausting remote storage bandwidth.
- **Fix:** Configure `setAlignmentTimeout(Duration.ofSeconds(15))` to give barriers a reasonable chance to align normally before falling back to unaligned mode.

### 3. Deleting Checkpoint Directories on Manual Cancellation
- **Antipattern:** Failing to configure `RETAIN_ON_CANCELLATION` on externalized checkpoints.
- **System Consequence:** If an engineer cancels a job (`flink cancel <jobId>`) without manually generating a savepoint, Flink’s default behavior deletes all historical checkpoints from remote storage (S3/HDFS). The application state is permanently erased, rendering disaster recovery impossible.
- **Fix:** Always enforce `setExternalizedCheckpointRetention(RETAIN_ON_CANCELLATION)` across all production pipelines.
