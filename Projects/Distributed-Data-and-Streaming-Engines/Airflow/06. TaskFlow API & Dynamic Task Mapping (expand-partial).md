> — *Bas P. Harenslak & Julian Rutger de Ruiter, Data Pipelines with Apache Airflow*

## 1. Canonical Motivation & Theoretical Foundation

In legacy Airflow (1.x and early 2.x), authoring Python-based workflows suffered from excessive boilerplate:
1. Every task required instantiating a `PythonOperator`, explicitly providing a `python_callable`, and passing explicit dictionaries for arguments.
2. Data sharing required manually pushing and pulling string keys via XCom (`ti.xcom_push` and `ti.xcom_pull`), divorcing function inputs from outputs.
3. Most critically, **the number of tasks in a DAG had to be known at DAG parse time**. If an upstream task discovered 15 new files in S3, Airflow could not dynamically spawn 15 parallel tasks to process them without resorting to ugly hacks like dynamic DAG file generation.

Modern Airflow revolutionized this through two major milestones:
- **TaskFlow API (AIP-31):** Decorator-based syntax (`@dag`, `@task`) allowing developers to write clean, idiomatic Python code with automatic XCom wiring.
- **Dynamic Task Mapping (AIP-42):** Runtime task expansion based on the MapReduce paradigm, allowing tasks to spawn dynamically based on the length of an upstream collection using `.expand()` and `.partial()`.

## 2. Underlying Runtime, Memory & Execution Architecture

### Dynamic Task Mapping Internals (AIP-42)

```
 [ Upstream Task: Discover Files ]
             │
             │ Returns list: ["file_A.parquet", "file_B.parquet", "file_C.parquet"]
             ▼
 ┌─────────────────────────────────────────────────────────────┐
 │       Mapped Task: Process File (.expand(file=...))         │
 │                                                             │
 │  ┌─────────────────┐ ┌─────────────────┐ ┌────────────────┐ │
 │  │ TaskInstance 0  │ │ TaskInstance 1  │ │ TaskInstance 2 │ │
 │  │ (map_index = 0) │ │ (map_index = 1) │ │(map_index = 2)│ │
 │  │ file_A.parquet  │ │ file_B.parquet  │ │file_C.parquet  │ │
 │  └────────┬────────┘ └────────┬────────┘ └────────┬───────┘ │
 └───────────┼───────────────────┼───────────────────┼─────────┘
             │                   │                   │
             └───────────────────┼───────────────────┘
                                 │
                                 ▼
                 [ Downstream Reduction Task: Aggregate ]
                 (Ingests list of all mapped results)
```

#### The `map_index` State Machine
In the metadata database, traditional tasks are identified by `(dag_id, task_id, run_id)`. With dynamic task mapping:
- A new column `map_index` is introduced (defaulting to `-1` for unmapped tasks).
- When a task is dynamically expanded into $N$ instances, Airflow instantiates $N$ rows in the `task_instance` table, numbered `map_index = 0` through `map_index = N - 1`.
- Each mapped task instance behaves as an independent unit of scheduling, retrying, and alerting.

#### `.partial()` vs. `.expand()`
- **`.partial(...)`:** Supplies **static arguments** shared across all mapped instances (e.g. database credentials, timeout configurations).
- **`.expand(...)`:** Supplies the **dynamic collection** (list, dict, or XComArg) that dictates how many parallel tasks to spawn at runtime.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### TaskFlow Decorator Suite

Modern Airflow provides first-class decorators for diverse runtimes:
- `@task`: Standard Python callable running in worker environment.
- `@task.virtualenv`: Executes in an isolated, dynamically provisioned Python virtualenv.
- `@task.docker`: Runs inside an isolated Docker container.
- `@task.kubernetes`: Runs inside a dedicated Kubernetes pod.
- `@task.branch`: Conditional branching evaluated directly from function return.

## 5. Annotated Code Implementations & Execution Traces

### Production Pipeline: Dynamic Task Mapping with Fan-Out and Reduction

The following complete TaskFlow DAG dynamically discovers daily raw transaction partitions, fans out parallel validation tasks, and reduces results into a single analytical summary:

```python
"""
Production TaskFlow DAG: Dynamic Task Mapping (Fan-Out / Fan-In).
Demonstrates:
  - @dag and @task decorators (AIP-31)
  - Dynamic Task Mapping via .expand() and .partial() (AIP-42)
  - Automatic XCom dependency resolution
  - Downstream reduction of mapped tasks
"""

from datetime import datetime, timedelta
import logging
from typing import Dict, List

from airflow.decorators import dag, task

logger = logging.getLogger(__name__)


@dag(
    dag_id="taskflow_dynamic_mapping_production_v1",
    schedule_interval="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    default_args={
        "owner": "data-engineering",
        "retries": 2,
        "retry_delay": timedelta(minutes=3),
    },
    tags=["taskflow", "dynamic_mapping", "modern_airflow"],
)
def dynamic_mapping_workflow():

    @task
    def discover_daily_partitions() -> List[str]:
        """
        Scans storage for available partitions.
        Returns a dynamic list of partition keys.
        """
        # In production, list prefixes from S3 or Cloud Storage
        discovered_partitions = [
            "region=us-east/year=2026/month=05/day=01",
            "region=eu-west/year=2026/month=05/day=01",
            "region=ap-south/year=2026/month=05/day=01",
        ]
        logger.info(f"Discovered {len(discovered_partitions)} partitions for processing.")
        return discovered_partitions

    @task
    def process_partition(partition_path: str, environment: str, timeout_sec: int) -> Dict[str, any]:
        """
        Executed in parallel for EACH partition discovered upstream.
        Takes static parameters (environment, timeout) and dynamic (partition_path).
        """
        logger.info(f"Processing partition [{partition_path}] in [{environment}] (Timeout: {timeout_sec}s)")
        
        # Simulate row count extraction
        simulated_records = len(partition_path) * 1000
        return {
            "partition": partition_path,
            "record_count": simulated_records,
            "status": "VALIDATED",
        }

    @task
    def reduce_and_summarize(all_partition_results: List[Dict[str, any]]) -> int:
        """
        Downstream reduction task.
        Automatically gathers the outputs of all mapped instances into a single list!
        """
        total_records = 0
        for res in all_partition_results:
            logger.info(f"Summary: Partition [{res['partition']}] processed {res['record_count']} records.")
            total_records += res["record_count"]

        logger.info(f"TOTAL Pipeline Records Processed: {total_records}")
        return total_records

    # 1. Discover partitions dynamically
    partitions = discover_daily_partitions()

    # 2. Dynamic Fan-Out: .partial() provides static args; .expand() maps dynamic list
    processed_results = process_partition.partial(
        environment="production",
        timeout_sec=300
    ).expand(partition_path=partitions)

    # 3. Dynamic Fan-In: Downstream task receives the complete mapped output list
    reduce_and_summarize(processed_results)


# Instantiate the DAG
dag_instance = dynamic_mapping_workflow()
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The 10,000 Mapped Task Explosion
- **Antipattern:** Calling `.expand(...)` on a collection containing 50,000 items (e.g., mapping a task per individual customer ID).
- **System Consequence:** Airflow attempts to insert 50,000 rows into the `task_instance` table simultaneously. The scheduler loop halts as it evaluates dependency states for 50,000 tasks, overwhelming the database and queuing system.
- **Fix:** Batch your items into reasonable chunks upstream (e.g. 50 chunks of 1,000 items) or enforce the global ceiling:
  ```properties
  [core]
  max_map_length = 1024
  ```

### 2. Passing Heavy Non-JSON Objects Across TaskFlow Tasks
- **Antipattern:** Returning complex unpicklable objects or giant dataframes from `@task` decorated functions expecting TaskFlow to handle them in memory.
- **System Consequence:** Under the hood, TaskFlow still uses XCom. Complex objects fail serialization, or large objects overload the metadata database with multi-megabyte payloads.
- **Fix:** Keep TaskFlow function inputs and outputs strictly constrained to JSON-serializable primitives, lists, and dicts.

### 3. Mutating Arguments Shared via `.partial()`
- **Antipattern:** Passing a mutable Python dictionary or list into `.partial(config=my_dict)` and modifying it inside one of the mapped tasks.
- **System Consequence:** Tasks run in separate processes. Mutations made in one mapped task instance are not visible to sibling instances, producing unpredictable data corruption.
- **Fix:** Treat all parameters passed to `.partial(...)` as strictly immutable.
