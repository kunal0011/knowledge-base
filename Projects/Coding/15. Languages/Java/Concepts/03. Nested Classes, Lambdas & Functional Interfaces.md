# Java Concepts: Nested Classes, Lambdas & Functional Interfaces

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapters 7 & 8  
- *Effective Java (3rd Ed.)* by Joshua Bloch, Items 24, 42, 43, & 44  

---

## 1. Theoretical Motivation: Nested Classes Taxonomy

Java permits defining a class within another class. The language provides four distinct categories of nested classes:

```
+-----------------------------------------------------------------------------------------+
|                                  NESTED CLASSES TAXONOMY                                |
+-----------------------+-----------------------+--------------------+--------------------+
| Category              | Scope                 | Has Outer 'this'?  | Can Have Statics?  |
+-----------------------+-----------------------+--------------------+--------------------+
| 1. Static Nested      | Class member (static) | NO                 | YES                |
| 2. Member Inner Class | Class member (instance| YES (Outer.this)   | Java 16+ only      |
| 3. Local Inner Class  | Inside method block   | YES (if non-static)| Java 16+ only      |
| 4. Anonymous Class    | Local expression      | YES (if non-static)| NO                 |
+-----------------------+-----------------------+--------------------+--------------------+
```

### Joshua Bloch's Core Guideline (Item 24):
> *"Each instance of a non-static member class implicitly has an enclosing instance of its containing class... This reference uses time and space, and can result in the enclosing instance being retained when it would otherwise be garbage collected."*

**Rule:** If an inner class does not require access to enclosing instance fields, **always declare it `static`**.

## 2. Underlying Architecture: `invokedynamic` vs. Anonymous Classes

A common misconception is that a Java lambda is merely syntactic sugar for an anonymous inner class (`new Runnable() { ... }`).
This is completely false!

```
Anonymous Inner Class (Old Java):
Source.java ===javac===> Source.class AND Source$1.class (Generates a disk .class file!)
- ClassLoader must load and verify the synthetic class.
- Allocates a distinct object on the heap for every single lambda instantiation.

Modern Lambda (Java 8+):
Source.java ===javac===> Emits a single bytecode opcode: invokedynamic (INDY)
- Invokes LambdaMetafactory at runtime.
- Dynamic call site linkage.
- The JIT can spin lightweight method handles or reuse singleton instances without classloader overhead!
```

```
Compiled Bytecode with invokedynamic:
0: invokedynamic #7, 0 // InvokeDynamic #0:apply:()Ljava/util/function/Function;
5: astore_1
```

## 3. The Four Method Reference Categories (OCP Standard)

Method references provide a more concise syntax than lambdas when a lambda merely forwards its arguments to an existing method:

| Category | Syntax | Equivalent Lambda Expression |
|:---|:---|:---|
| **1. Static Method** | `Integer::parseInt` | `str -> Integer.parseInt(str)` |
| **2. Bound Instance Method** | `str::length` | `() -> str.length()` (Captures specific instance `str`) |
| **3. Unbound Instance Method** | `String::toLowerCase` | `s -> s.toLowerCase()` (1st arg becomes the target!) |
| **4. Constructor Reference** | `ArrayList::new` | `() -> new ArrayList<>()` or `size -> new int[size]` |

### The Unbound Instance Method Nuance:
In an unbound method reference like `String::compareToIgnoreCase`, the first parameter of the functional interface becomes the **receiver object** on which the method is called, and subsequent parameters become arguments:
```java
BiFunction<String, String, Integer> comp = String::compareToIgnoreCase;
// Equivalent to: (s1, s2) -> s1.compareToIgnoreCase(s2)
```

## 4. The Standard `java.util.function` Interface Matrix

Rather than creating custom single-abstract-method interfaces, Joshua Bloch urges developers in Item 44 to prioritize the 6 foundational functional interfaces:

```
+-------------------------------------------------------------------------+
|                    THE 6 CORE FUNCTIONAL INTERFACES                     |
+-----------------------+-------------------+----------------+------------+
| Interface             | Method Signature  | Return Type    | Arguments  |
+-----------------------+-------------------+----------------+------------+
| Predicate<T>          | test(T t)         | boolean        | 1 (T)      |
| Consumer<T>           | accept(T t)       | void           | 1 (T)      |
| Supplier<T>           | get()             | T              | 0          |
| Function<T, R>        | apply(T t)        | R              | 1 (T)      |
| UnaryOperator<T>      | apply(T t)        | T              | 1 (T)      |
| BinaryOperator<T>     | apply(T t1, T t2) | T              | 2 (T, T)   |
+-----------------------+-------------------+----------------+------------+
```

### Primitive Specializations for Zero-Allocation Pipelines:
To prevent boxing primitive numbers into heap wrapper objects, Java provides 36 primitive specializations:
- `IntPredicate`, `LongConsumer`, `DoubleSupplier`
- `ToIntFunction<T>`, `IntToDoubleFunction`
- `IntUnaryOperator`, `LongBinaryOperator`

## 5. Variable Capture & The "Effectively Final" Invariant

When a lambda references a local variable from its enclosing method, that variable **MUST be final or effectively final**.

### What is "Effectively Final"?
A variable is effectively final if its value is never modified after it is initialized, even if it lacks the explicit `final` keyword.

```java
public void process() {
    int factor = 2; // Effectively final
    List<Integer> nums = List.of(1, 2, 3);

    // Legal: captures effectively final variable
    nums.forEach(n -> System.out.println(n * factor));

    // factor = 3; // UNCOMMENTING THIS BREAKS THE LAMBDA ABOVE!
    // Error: local variables referenced from a lambda must be final or effectively final
}
```

### Why Does Java Require This?
Local variables live on the **thread stack**. The lambda may execute asynchronously on a different thread or after the enclosing method has returned and its stack frame has been destroyed.
To make this safe, Java **copies the value of the variable** into the lambda's closure. If the variable could be reassigned, the two copies would diverge, creating unpredictable race conditions.

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 Joshua Bloch's Item 42: Lambdas Lack Names and Documentation
Lambdas should ideally be **one to three lines of code**. If an operation requires complex branching or multi-step logic, extract it into a named private helper method and use a **method reference**.

### 6.2 The Ambiguous Overload Trap with Method References
```java
// Method with overloaded signatures:
public void submit(Runnable r) { ... }
public void submit(Callable<String> c) { ... }

// Ambiguity error:
// submit(() -> "done"); // Compiles fine (Callable returns a value)
// submit(System.out::println); // Compiles fine (Runnable is void)

// AMBIGUOUS: When a method has overloaded forms matching both void and returning types!
```

### 6.3 Mutating Container Elements vs Reassigning References
```java
int[] counter = new int[1]; // Array reference is final!
list.forEach(x -> counter[0] += x); // LEGAL! (Array elements can mutate, reference is final)
```
While this workaround is legal in single-threaded code, it is an **anti-pattern in concurrent code** because it introduces race conditions. Use `AtomicInteger` or reduction streams instead.

## 7. Actionable Summary Checklist

- [x] Always declare member classes `static` unless they explicitly require a live reference to enclosing instance state (Effective Java Item 24).
- [x] Prefer method references to lambdas when they are shorter and clearer (Effective Java Item 43).
- [x] Reuse standard interfaces from `java.util.function` rather than defining redundant custom functional interfaces (Effective Java Item 44).
- [x] Use primitive functional specializations (`IntPredicate`, `LongFunction`) to eliminate boxing overhead in high-throughput loops.
- [x] Keep lambda expressions short (1 to 3 lines); extract complex multi-line algorithms into named methods.
