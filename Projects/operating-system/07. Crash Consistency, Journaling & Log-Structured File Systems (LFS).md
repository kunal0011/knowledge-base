# Chapter 07: Crash Consistency, Journaling & Log-Structured File Systems (LFS)

> "The crash-consistency problem is one of the most fundamental challenges in storage engineering. How do we update on-disk data structures atomically when the underlying hardware can fail between any two arbitrary disk writes?"  
> — *Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau, Operating Systems: Three Easy Pieces (OSTEP)*

---

## 💥 1. The Crash Consistency Problem

Consider the simplest file operation: appending a $4\text{ KB}$ block of data to an existing file. To make this change permanent, the operating system must execute **three separate disk writes**:
1. **Data Block ($D_b$):** The actual payload bytes.
2. **Data Bitmap ($B$):** Mark bit as allocated in the global allocation bitmap.
3. **Inode ($I$):** Update file size, increment block count, and record pointer to $D_b$.

Because storage drives cannot write three separate, non-contiguous disk sectors atomically in a single clock cycle, a sudden power failure or kernel panic between these writes results in severe filesystem corruption:

```text
===================================================================================================
                               CRASH SCENARIO FAILURE MATRIX
===================================================================================================

 [ Crash Scenario 1: Only Inode (I) Written ]
 - Inode points to Data Block Db, but Db was never written to disk!
 - Result: File contains whatever old, sensitive garbage was previously on that sector! (Security Leak)

 [ Crash Scenario 2: Only Data Bitmap (B) Written ]
 - Bit is marked "used", but no inode points to it.
 - Result: Space leak! The block is permanently lost to the filesystem until a manual repair.

 [ Crash Scenario 3: Inode (I) and Bitmap (B) Written, but Data (Db) Lost ]
 - Filesystem metadata is completely valid, but reads return random corrupt noise.
```

---

## 🛠️ 2. The Legacy Fix: File System Checker (`fsck`)

Early Unix systems resolved this using the **`fsck` (File System Checker)** utility:
- On reboot after an unclean shutdown, `fsck` scans the entire storage partition.
- Performs a multi-pass sweep: validates superblock invariants, checks free block bitmaps against all inode pointers, verifies directory linkages, and moves disconnected inodes to `/lost+found`.

### Why `fsck` is Obsolete for Modern Systems
`fsck` runtime scales with the **total size of the partition**, not the amount of data modified before the crash. Scanning an $80\text{ MB}$ drive in 1985 took 10 seconds; scanning a modern $30\text{ TB}$ NVMe RAID array takes **14 hours**. Enterprise servers cannot afford half a day of downtime after an unexpected power trip!

## 📝 3. Write-Ahead Logging (WAL) & Journaling

Modern filesystems (Ext4, XFS, NTFS) solve crash consistency using **Journaling** (borrowed from database transaction theory). Before updating the primary file system structures in-place, the OS writes a descriptive transaction to a dedicated, sequential disk log: the **Journal**.

```text
===================================================================================================
                               JOURNALING TRANSACTION LIFECYCLE
===================================================================================================

  1. Write-Ahead Logging Phase (Sequential Log)
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ [ TxBegin: TxID 104 ] ──► [ Inode Metadata ] ──► [ Bitmap Update ] ──► [ TxEnd: Commit Block]│
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
                                                                                   │
                                                          Only after TxEnd is written to disk!
                                                                                   │
  2. Checkpoint Phase (Primary Filesystem)                                         ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ Inode Table [Update Inode]  ◄───  Data Bitmap [Set Bit]  ◄───  Data Block [Write Payload]   │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
                                                                                   │
  3. Release / Free Phase                                                          ▼
  The transaction is marked committed and can be safely recycled from the circular journal buffer.
```

### 3.1 Fast Crash Recovery
If the server crashes during step 1 (before `TxEnd` is safely flushed), the journal ignores the incomplete transaction on boot. 

If the server crashes during step 2 (after `TxEnd` was committed), the recovery agent simply **replays the journal transaction**, copying the known-valid metadata into place. Recovery takes **less than 200 milliseconds**, regardless of disk capacity!

---

## ⚖️ 4. The Three Linux Journaling Modes

In Ext3 and Ext4, administrators configure the consistency/performance trade-off using the `data=` mount option:

| Journaling Mode | Mechanism | Consistency Level | Performance Impact |
| :--- | :--- | :--- | :--- |
| **`data=journal`** | Writes **both file data and metadata** to the journal before writing to primary storage. | Absolute highest: Guarantees zero stale data reads on crash. | Severe: Doubles write volume; every byte is written twice! |
| **`data=ordered`** *(Default)* | Writes **file data directly to primary blocks first**; only after data is on disk does it write metadata to the journal and commit. | High: Guarantees no stale data pointers. Files will never point to garbage data after a crash. | Optimal: Writes data once and metadata twice. Excellent throughput. |
| **`data=writeback`** | Writes metadata to journal; file data can be written before, during, or after metadata. | Low: Inode can point to unwritten blocks on crash, exposing stale disk data. | Fastest raw throughput; maximum write concurrency. |

## 🚀 5. Log-Structured File Systems (LFS)

Invented by Mendel Rosenblum and John Ousterhout, the **Log-Structured File System (LFS)** is built on a revolutionary architectural premise:
> *"As system RAM grows into gigabytes and terabytes, virtually all read requests are satisfied by the in-memory Page Cache. Therefore, disk workloads are dominated exclusively by writes. Conventional filesystems perform miserably because file updates require small, scattered random writes across the disk."*

### 5.1 The LFS Invariant: The Entire Disk is a Log!
In LFS, **all data and all metadata are written sequentially to the end of a circular append-only log**. An update to an existing block is never overwritten in place!

```text
===================================================================================================
                                      LFS WRITING TIMELINE
===================================================================================================

  Initial State: File A points to Data Block D0
  ┌───────────────────────────────────────────────────────────────────────────┐
  │ ... | Data Block D0 | Inode A0 (points to D0) |                           │
  └───────────────────────────────────────────────────────────────────────────┘
  
  User modifies File A:
  1. Writes new Data Block D0' sequentially to disk head!
  2. Writes new Inode A0' (points to D0') sequentially to disk head!
  3. Writes Inode Map (imap) chunk containing location of Inode A0'!
  
  Updated Disk Layout:
  ┌───────────────────────────────────────────────────────────────────────────┐
  │ ... | D0 (Dead) | A0 (Dead) | D0' (Alive) | A0' (Alive) | imap chunk      │
  └───────────────────────────────────────────────────────────────────────────┘
```

### 5.2 The Inode Map (`imap`) & Floating Inodes
Because updating an inode changes its physical disk location, how does the OS find Inode 5?
- LFS introduces the **Inode Map (`imap`)**: an on-disk array that maps `Inode Number ──► Current Physical Disk Address`.
- Slices of the `imap` are written right next to the data in the log.
- A tiny, fixed-location on-disk pointer called the **Checkpoint Region (CR)** stores the locations of all `imap` pieces, updated periodically (e.g., every 30 seconds).

### 5.3 Segment Cleaning (Garbage Collection)
Because the disk is append-only, old blocks become "dead" (superseded by newer versions). LFS divides the disk into large **Segments** (typically $8\text{ MB} - 16\text{ MB}$).
- The **Segment Cleaner** background thread scans segments, reads surviving "live" blocks, writes them contiguously into a fresh active segment, and marks the old segments as completely free.
- This clean-and-compact pattern directly mirrors modern SSD Flash Translation Layers and Log-Structured Merge (LSM) databases (RocksDB, Cassandra, LevelDB)!
