# Chapter 12: The Future of Data Systems — Unbundled Databases

> "No single database tool can satisfy all processing and storage needs: a modern enterprise architecture is not a collection of isolated databases, but an unbundled database, where heterogeneous storage and processing engines are composed into a cohesive whole via an immutable event log."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

Over the preceding chapters, we explored diverse storage and computation paradigms: relational tables, document stores, graph databases, LSM-trees, B-trees, columnar analytical stores, distributed consensus protocols, batch pipelines, and event streams.

A recurring theme emerges: **There is no single "universal" database that excels at all workloads.**
- A relational database optimized for OLTP point writes cannot perform interactive full-text search across millions of documents.
- A search engine (Elasticsearch) optimized for fuzzy text matching cannot enforce strict ACID financial ledgers.
- A columnar data warehouse (ClickHouse/Snowflake) optimized for multi-billion-row aggregations cannot sustain low-latency sub-millisecond key-value lookups.

In large-scale enterprise architectures, systems inevitably deploy **multiple specialized data engines** concurrently. 

Martin Kleppmann's capstone thesis is the **Unbundled Database**: instead of viewing an enterprise infrastructure as dozens of disconnected applications querying separate databases, we should view the entire system as a **single, decomposed database**, where specialized derived stores are tied together by a shared write-ahead log.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Unbundled Database Analogy

When we look inside the internal components of a traditional single-node relational database, we find exact equivalents in modern distributed architectures:

```
 Traditional Relational Database (Internal)     Distributed Enterprise Architecture (Unbundled)
 ┌────────────────────────────────────────┐     ┌────────────────────────────────────────────┐
 │ SQL Parser & Optimizer                 │ <─> │ Microservice APIs / Federated Query (Trino)│
 ├────────────────────────────────────────┤     ├────────────────────────────────────────────┤
 │ Buffer Pool (In-Memory Page Cache)     │ <─> │ Distributed In-Memory Cache (Redis)        │
 ├────────────────────────────────────────┤     ├────────────────────────────────────────────┤
 │ Write-Ahead Log (WAL)                  │ <─> │ Distributed Event Log (Apache Kafka)       │
 ├────────────────────────────────────────┤     ├────────────────────────────────────────────┤
 │ B-Tree Primary Key Index               │ <─> │ Primary Relational DB (PostgreSQL)         │
 ├────────────────────────────────────────┤     ├────────────────────────────────────────────┤
 │ Secondary Search Index                 │ <─> │ Distributed Search Engine (Elasticsearch)  │
 ├────────────────────────────────────────┤     ├────────────────────────────────────────────┤
 │ Materialized Views                     │ <─> │ Stream Processing Aggregates (Flink)       │
 └────────────────────────────────────────┘     └────────────────────────────────────────────┘
```

In the unbundled architecture:
- **The Write Path:** Writes are submitted to a single authoritative system of record or directly to a partitioned, durable commit log (Apache Kafka).
- **The Read Paths:** Specialized downstream consumers read from the log and project state into specialized read-optimized indices (search indices, graph databases, columnar caches).

### Unifying Batch and Streaming: Lambda vs. Kappa Architecture

```
─────────────────────────────────────────────────────────────────────────────
The Lambda Architecture (Dual-Path Ingestion):
                ┌───> [ Speed Layer: Storm/Flink ] ──> [ Real-time Views ] ──┐
 [ Event Feed ] │                                                            ├──> [ Query Engine ]
                └───> [ Batch Layer: Hadoop/HDFS ] ──> [ Batch Views ] ──────┘
 • Fatal Flaw: Requires writing and maintaining the EXACT SAME business logic
   in two completely different programming models (e.g. Java Storm + Python Spark)!
─────────────────────────────────────────────────────────────────────────────
The Kappa Architecture (Single Stream Engine):
 [ Event Feed ] ──> [ Durable Kafka Log ] ──> [ Stream Processor (Flink) ] ──> [ Serving Store ]
 • Breakthrough: A single stream processing codebase handles BOTH real-time
   events and historical backfills (by simply rewinding log offsets to offset 0).
─────────────────────────────────────────────────────────────────────────────
```

## 3. Core Mechanics, Algorithms & Invariants

### Aiming for Correctness: The End-to-End Argument

In 1981, Saltzer, Reed, and Clark formulated the foundational **End-to-End Argument in System Design**:  
*A function or safety check can only be completely and correctly implemented with the knowledge and help of the application standing at the endpoints of the communication system. Providing that check as a feature of the low-level communication system is not, by itself, sufficient.*

#### Application to Data Systems:
- **TCP Checksums:** While TCP verifies packet checksums, hardware bugs in network interface memory (NIC DMA) or router memory regularly corrupt bytes *before* TCP computes the checksum.
- **Relational Transactions:** Even if a database guarantees ACID transactions, if an application client retries an unacknowledged HTTP request over a flaky network, it can insert duplicate orders unless the application implements **End-to-End Idempotency Keys**.

Low-level fault-tolerance mechanisms (TCP, database transactions, 2PC) are useful performance optimizations, but **true correctness must always be enforced end-to-end at the application boundaries**.

---

### Verifiable Computation & Cryptographic Auditing

As trust in centralized platforms erodes and regulatory compliance (SOX, SOC 2, HIPAA) expands, data systems must transition from *blind trust* to **mathematically verifiable integrity**:
- **Append-Only Cryptographic Logs (Merkle Trees):** Used in Git, Certificate Transparency, and modern financial ledgers. Every state mutation is chained to previous events using cryptographic hashes.
- **Tamper Detection:** If a malicious administrator or compromised database account alters historical records, the root hash of the Merkle tree changes immediately, alerting external auditors.

---

### Privacy, Ethics & The "Right to be Forgotten"

Modern regulations (GDPR, CCPA) grant users the legal "Right to be Forgotten" (erasure of personal data). 

This introduces an acute architectural tension with immutable append-only event logs (Kafka/HDFS), which are designed never to delete past events:
- **The Crypto-Shredding Solution:**
  1. All personal identifiable information (PII) for a user is encrypted using a unique, dedicated symmetric encryption key.
  2. The encrypted ciphertext is written to the immutable event log.
  3. The encryption keys are stored in a separate, mutable key-management database.
  4. When a user requests data erasure, the system **destroys their encryption key**.
  5. While the ciphertext remains permanently on the immutable log, it is mathematically indistinguishable from random noise, effectively erasing the data.

## 4. Practical Systems & Production Engineering Trade-offs

1. **When NOT to Unbundle:** If an application has modest scale ($< 1,000$ RPS and $< 500\text{GB}$ of data), decomposing into an unbundled mesh of Kafka, Elasticsearch, and ClickHouse introduces massive operational overhead. A single, well-indexed PostgreSQL instance with Full-Text Search and JSONB is vastly simpler and more reliable.
2. **Federated Query Engines (Trino, DuckDB):** Allowing analysts to query unbundled architectures using standard ANSI SQL across Kafka topics, PostgreSQL tables, and S3 Parquet lakes in a single query.

## 5. Annotated Code Implementations & Algorithmic Engines

### The "Unbundled Database" Atomic Materialization Pipeline

The following production Python program implements an Unbundled Database pipeline: a single source mutation event stream is consumed by an orchestrator and projected into three specialized derived data models—a **Key-Value Store**, an **Inverted Search Index**, and an **Analytical Counter**—with end-to-end idempotency tracking:

```python
"""
The Unbundled Database Architecture Simulation.
Demonstrates:
  - Single write-path mutation log (Source of Truth)
  - Multi-view projection: Key-Value, Inverted Index, Analytical Aggregates
  - End-to-end idempotency key tracking
  - Replayability for zero-downtime new view materialization
"""

from collections import defaultdict
from typing import Any, Dict, List, Optional, Set


class MutationEvent:
    def __init__(self, idempotency_key: str, doc_id: str, title: str, category: str, price: float):
        self.idempotency_key = idempotency_key
        self.doc_id = doc_id
        self.title = title
        self.category = category
        self.price = price


class UnbundledDatabase:
    def __init__(self):
        # 1. Authoritative Write Log (The Truth)
        self.commit_log: List[MutationEvent] = []
        self.processed_idempotency_keys: Set[str] = set()

        # 2. Derived View A: Primary Key-Value Store (OLTP)
        self.kv_store: Dict[str, Dict[str, any]] = {}

        # 3. Derived View B: Full-Text Inverted Search Index (Search)
        self.search_index: Dict[str, Set[str]] = defaultdict(set)

        # 4. Derived View C: Analytical Category Spend Aggregates (OLAP)
        self.category_revenue: Dict[str, float] = defaultdict(float)

    def write(self, event: MutationEvent) -> bool:
        """Appends event to log and projects to derived views (Idempotent)."""
        # End-to-End Idempotency check
        if event.idempotency_key in self.processed_idempotency_keys:
            print(f" -> [IDEMPOTENT SKIP] Duplicate event rejected: {event.idempotency_key}")
            return False

        # Step 1: Append to Truth Log
        self.commit_log.append(event)
        self.processed_idempotency_keys.add(event.idempotency_key)

        # Step 2: Project into Derived View A (Key-Value Document Store)
        self.kv_store[event.doc_id] = {
            "title": event.title,
            "category": event.category,
            "price": event.price,
        }

        # Step 3: Project into Derived View B (Inverted Search Index)
        words = event.title.lower().split()
        for w in words:
            self.search_index[w].add(event.doc_id)

        # Step 4: Project into Derived View C (OLAP Revenue Aggregate)
        self.category_revenue[event.category] += event.price

        return True

    def search(self, query_term: str) -> List[Dict[str, any]]:
        """Queries Derived View B (Search Index) and enriches from View A (KV Store)."""
        matching_ids = self.search_index.get(query_term.lower(), set())
        return [self.kv_store[doc_id] for doc_id in matching_ids]

    def replay_and_build_new_view(self) -> Dict[str, int]:
        """Demonstrates replaying historical log to build an entirely new derived view!"""
        print("\nReplaying historical log to build NEW Derived View: Category Item Counts...")
        category_counts: Dict[str, int] = defaultdict(int)
        for evt in self.commit_log:
            category_counts[evt.category] += 1
        return dict(category_counts)


# Verification Execution
if __name__ == "__main__":
    db = UnbundledDatabase()

    # Client writes stream of mutations
    e1 = MutationEvent("tx-001", "book-1", "Designing Data Intensive Applications", "Tech", 45.0)
    e2 = MutationEvent("tx-002", "book-2", "Stream Processing with Flink", "Tech", 50.0)
    e3 = MutationEvent("tx-003", "book-3", "The Great Gatsby", "Fiction", 15.0)

    db.write(e1)
    db.write(e2)
    db.write(e3)

    # Test idempotency deduplication
    db.write(e1) # Duplicate write

    print("=== 1. Derived View A: KV Point Lookup ===")
    print(f"book-1: {db.kv_store['book-1']}")

    print("\n=== 2. Derived View B: Full-Text Search Query ('data') ===")
    search_results = db.search("data")
    for res in search_results:
        print(f" -> Found: {res['title']} (${res['price']})")

    print("\n=== 3. Derived View C: OLAP Revenue Aggregates ===")
    for cat, rev in db.category_revenue.items():
        print(f" Category [{cat:>7}]: ${rev:.2f}")

    # Replay historical log to create a new materialized view on the fly
    new_view = db.replay_and_build_new_view()
    print(f"Newly Materialized View: {new_view}")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Resume-Driven Over-Engineering Trap
- **Antipattern:** Deploying a multi-component unbundled architecture (Kafka + Flink + Cassandra + Elasticsearch + Redis) for a startup with 50 daily active users.
- **System Consequence:** The team spends 90% of their engineering cycles managing ZooKeeper quorums, schema registry migrations, and network partition alerts rather than building business features.
- **Fix:** Follow the Rule of Simplicity: Start with a monolithic relational database (PostgreSQL). Only unbundle specific read paths when physical hardware limits are reached.

### 2. GDPR "Right to be Forgotten" in Immutable Event Logs
- **Antipattern:** Storing unencrypted customer personal data directly inside append-only Kafka topics or HDFS logs configured with indefinite retention.
- **System Consequence:** When a user issues a GDPR deletion request, deleting that individual user's data from an append-only log requires rewriting petabytes of historical log segments, which is computationally intractable.
- **Fix:** Employ **Crypto-Shredding**: encrypt PII with per-user keys and delete the key upon receiving an erasure request.

### 3. Event Schema Drift Across Unbundled Views
- **Antipattern:** Mutating the event payload format in Kafka without enforcing schema registry compatibility checks across all downstream view consumers.
- **System Consequence:** The search index projection crashes silently on deserialization, while the OLAP aggregator continues processing with missing fields. The derived systems silently diverge from reality.
- **Fix:** Mandate Schema Registries with strict `BACKWARD` or `FULL` compatibility rules across all event pipelines.
