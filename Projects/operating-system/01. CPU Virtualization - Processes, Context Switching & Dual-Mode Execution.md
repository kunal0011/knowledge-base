# Chapter 01: CPU Virtualization — Processes, Context Switching & Dual-Mode Execution

> "How can the OS provide the illusion of many CPUs when there is only one physical CPU (or a few)? The answer is time-sharing: running one process for a little while, then running another, and so forth. By time-sharing the CPU, virtualization is achieved."  
> — *Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau, Operating Systems: Three Easy Pieces (OSTEP)*

## 🧬 1. The Process Abstraction & Linux `task_struct`

A **process** is an abstraction of a running program. At any point in time, a process can be inventoried by the resources it touches: the memory it can access (its address space), the registers it reads and writes, and the I/O devices (files, sockets) it interacts with.

### 1.1 The Process Control Block (PCB): `task_struct` in the Linux Kernel
In Linux, every thread and process is represented internally by a pointer to a `struct task_struct` (defined in `<linux/sched.h>`):
```c
struct task_struct {
    volatile long state;               /* -1 unrunnable, 0 runnable, >0 stopped */
    pid_t pid;                         /* Process ID */
    pid_t tgid;                        /* Thread Group ID (User-space PID) */
    void *stack;                       /* Pointer to the kernel mode stack */
    
    struct mm_struct *mm;              /* Virtual memory address space */
    struct files_struct *files;        /* Open file descriptor table */
    struct fs_struct *fs;              /* Filesystem info (root and pwd) */
    
    struct sched_entity se;            /* Completely Fair Scheduler (CFS) entity */
    unsigned int policy;               /* Scheduling policy (SCHED_NORMAL, SCHED_FIFO) */
    int prio, static_prio, normal_prio;/* Priority values */
    
    struct task_struct *parent;        /* Parent process pointer */
    struct list_head children;         /* List of children */
    struct list_head sibling;          /* Linkage in parent's children list */
};
```

## 🛡️ 2. Limited Direct Execution (LDE) & Dual-Mode CPU Architecture

To make programs run fast, the OS employs **Direct Execution**: running the user program directly on the bare-metal physical CPU hardware. However, this introduces two existential risks:
1. **Control:** How can the OS prevent a rogue program from monopolizing the CPU indefinitely?
2. **Protection:** How can the OS prevent an untrusted program from accessing raw disk sectors or reading the memory of another user?

The solution is **Limited Direct Execution (LDE)** powered by hardware-enforced CPU privilege rings.

```text
===================================================================================================
                         LIMITED DIRECT EXECUTION (LDE) TIMELINE
===================================================================================================

   Time   User Program (Ring 3)                         Kernel Space (Ring 0)
    │
    │     Running normally in User Mode...
    │     Calls read(fd, buffer, 1024)
    │     Places syscall # in %rax, args in %rdi, %rsi
    │     Executes: SYSCALL instruction
    ├──────────────────────────────────────────────────►
    │                                                   Hardware Trap triggers!
    │                                                   - CPU switches privilege level to Ring 0
    │                                                   - Saves %rsp, %rip, %rflags to Kernel Stack
    │                                                   - Looks up Trap Table entry for SYSCALL
    │                                                   - Jumps to system_call_entry
    │                                                   - Verifies syscall number & arguments
    │                                                   - Executes sys_read() filesystem logic
    │                                                   - Puts return value in %rax
    │                                                   - Executes: SYSRET instruction
    │                                                   Hardware Return-from-trap!
    │                                                   - Restores %rip, %rsp from kernel stack
    │                                                   - Drops CPU privilege to Ring 3
    ◄───────────────────────────────────────────────────┘
    │     Resumes execution in User Mode...
    ▼
```

### 2.1 Regaining Control: The Timer Interrupt
If a program enters an infinite loop (`while (1) {}`) and makes no system calls, how does the OS ever regain control?
- **Cooperative Scheduling:** The OS relies on applications to voluntarily yield the CPU via system calls (e.g., Early MacOS, Windows 3.1). A single buggy program hangs the entire machine.
- **Preemptive Multitasking:** Hardware timers are configured during boot to generate an electronic interrupt every few milliseconds (e.g., every $1\text{ms}$ or $10\text{ms}$). When the timer fires:
  1. The CPU hardware pauses the executing instruction stream.
  2. Saves current registers onto the kernel stack.
  3. Switches to Ring 0 and jumps directly to the OS timer interrupt handler.
  4. The OS scheduler runs and decides whether to continue running the current process or switch to a different one.

## 🔄 3. The Context Switch Mechanics & Cost Analysis

When the scheduler decides to switch from Process $A$ to Process $B$, it invokes a low-level assembly routine: `switch_to()`.

```text
===================================================================================================
                              CONTEXT SWITCHING REGISTER LIFECYCLE
===================================================================================================

  Process A (User Mode)                             Process B (User Mode)
           │                                                 ▲
           ▼                                                 │
  [ Save User Registers ]                           [ Restore User Registers ]
  - %rax, %rbx, %rcx...                             - %rax, %rbx, %rcx...
  onto Process A Kernel Stack                       from Process B Kernel Stack
           │                                                 ▲
           ▼                                                 │
  [ Switch Kernel Stack Pointer ]                   [ Switch Page Table Pointer ]
  movq %rsp, task_A->thread.sp                      movq task_B->mm->pgd, %cr3
  movq task_B->thread.sp, %rsp                      (Invalidates user TLB entries!)
           │                                                 ▲
           └────────────────── switch_to() ──────────────────┘
```

### 3.1 The Hidden Cost of Context Switches
1. **Direct Overhead:** Pushing and popping 16 general-purpose registers, floating-point/AVX state, and switching kernel stack pointers (typically $\approx 1\text{ to }2\ \mu\text{s}$).
2. **Indirect Overhead (Cache Pollution):**
   - When switching to a different process, the CPU's L1/L2/L3 hardware caches are primed with Process $A$'s data. Process $B$ experiences a storm of **cache misses**, running slowly until its working set is re-cached.
   - When the virtual memory page table is swapped (writing a new base pointer into the `%cr3` register on x86), the CPU hardware **flushes all non-global Translation Lookaside Buffer (TLB) entries**, rendering address translation slow until the TLB warms up.

## ⏱️ 4. CPU Scheduling Algorithms & Linux Completely Fair Scheduler (CFS)

The scheduler's responsibility is allocating CPU time among runnable processes to minimize **Turnaround Time** ($T_{\text{turnaround}} = T_{\text{completion}} - T_{\text{arrival}}$) and minimize **Response Time** ($T_{\text{response}} = T_{\text{first\_run}} - T_{\text{arrival}}$).

### 4.1 Classic Scheduling Taxonomies
1. **FIFO (First-In, First-Out):** Non-preemptive. Suffers severely from the **Convoy Effect**, where short tasks wait behind a massive CPU-bound job.
2. **SJF (Shortest Job First) & STCF (Shortest Time-to-Completion First):** Provably optimal for turnaround time, but requires future knowledge of job lengths and causes starvation for long jobs.
3. **Round Robin (RR):** Time-slices execution into quanta. Optimizes response time, but compromises turnaround time when all jobs have equal duration.
4. **Multi-Level Feedback Queue (MLFQ):** Uses past behavior to predict future burst lengths without prior knowledge. Rules adjust priorities dynamically: I/O-bound jobs stay high priority; CPU-bound jobs sink to lower priority queues.

### 4.2 Linux Completely Fair Scheduler (CFS) Deep Dive

Modern Linux implements the **Completely Fair Scheduler (CFS)**. CFS models an "ideal multi-tasking CPU" on real hardware using a virtual runtime metric ($vruntime$).

#### The Virtual Runtime Equation
Every runnable task has a $vruntime$. When a task runs on a physical CPU for physical time $\Delta t_{\text{exec}}$, its $vruntime$ advances proportionally to its priority weight:
$$vruntime \mathrel{+}= \Delta t_{\text{exec}} \times \left( \frac{w_{\text{nice0}}}{w_i} \right)$$
where $w_{\text{nice0}} = 1024$ (the weight of nice value $0$).

- A task with a lower nice value (higher priority, larger $w_i$) accumulates $vruntime$ **slower**.
- A task with a higher nice value (lower priority, smaller $w_i$) accumulates $vruntime$ **faster**.

```text
===================================================================================================
                             CFS RED-BLACK TREE RUNQUEUE (cfs_rq)
===================================================================================================

                                   [ Node: vruntime = 45ms ]
                                          /          \
                                         /            \
                  [ Node: vruntime = 20ms ]          [ Node: vruntime = 70ms ]
                         /
                        /
             [ Most Left Node: vruntime = 5ms ]
             ▲
             │
      rb_leftmost pointer: Always picks the process with the lowest vruntime!
      Guarantees O(1) scheduling selection and O(log N) re-insertion!
```

#### Why CFS is Truly Fair
Because CFS always picks the leftmost task in the Red-Black tree (the one that has received the least CPU time relative to its weight), the scheduler inherently self-balances. If a task goes to sleep waiting for network I/O, its $vruntime$ halts. When it wakes up, its $vruntime$ is far behind running tasks, granting it immediate preemption privilege to deliver instant interactive responsiveness!
