## 1. Theoretical Motivation: The JCF Architecture

The Java Collections Framework (JCF) is a unified architecture for representing and manipulating collections. It decouples the **data abstraction** (interfaces) from the **storage representation** (concrete classes) and the **algorithm execution** (`Collections` / `Arrays` utilities).

```
                            <<interface>> Iterable<T>
                                       |
                            <<interface>> Collection<T>
                    /                  |                 \
                   /                   |                  \
     <<interface>> List<T>   <<interface>> Set<T>   <<interface>> Queue<T>
          /         \                  |                      |
    ArrayList    LinkedList         HashSet             <<interface>> Deque<T>
                                       |                      /         \
                                  <<interface>>          ArrayDeque  LinkedList
                                  NavigableSet<T>
                                       |
                                    TreeSet
```

*(Note: `Map<K, V>` does not extend `Collection<T>` because it models key-value associations rather than individual elements).*

## 2. The `equals()` and `hashCode()` Contract (Bloch Items 10 & 11)

Whenever you define a class that may be stored in a `Set` or used as a key in a `Map`, you **MUST obey the general contract of `Object`**.

### 2.1 The 5 Mathematical Axioms of `equals()`:
1. **Reflexive:** `x.equals(x)` must return `true`.
2. **Symmetric:** `x.equals(y)` returns `true` if and only if `y.equals(x)` returns `true`.
3. **Transitive:** If `x.equals(y)` and `y.equals(z)`, then `x.equals(z)`.
4. **Consistent:** Repeated evaluations return the same result if no fields mutated.
5. **Non-nullity:** `x.equals(null)` must return `false` (never throw NPE).

### 2.2 The `hashCode()` Invariant:
If `x.equals(y)` is `true`, then `x.hashCode() == y.hashCode()` **MUST** be true.

```
What happens if you override equals() but forget hashCode()?
Hash code defaults to identity hash code (memory address).
Point p1 = new Point(1, 2); // Hashes to bucket 4
Point p2 = new Point(1, 2); // Hashes to bucket 11 (Different hash code!)

Map<Point, String> map = new HashMap<>();
map.put(p1, "Location");
map.get(p2); // Searches bucket 11 -> Returns null! (Data lost!)
```

### Production Recipe for `equals()` and `hashCode()`:
```java
public final class Employee {
    private final int id;
    private final String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = Objects.requireNonNull(name);
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true; // 1. Identity optimization
        if (!(o instanceof Employee e)) return false; // 2. Type check & cast
        return id == e.id && name.equals(e.name); // 3. Field comparison
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}
```

## 3. Underlying Architecture: `HashMap` Treeification & Rehash

```
table: Node<K, V>[]
[ 0 ] -> Node("apple", 1) -> Node("banana", 2) -> null
[ 1 ] -> null
[ ... ]
[ 7 ] -> TreeNode (Root of Red-Black Tree)
            /     \
       TreeNode  TreeNode
```

### 3.1 Hash Perturbation Formula
```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```
The bucket index is calculated as `(table.length - 1) & hash`. XORing the high 16 bits into the low 16 bits ensures that variations in upper bits contribute to bucket distribution even when the table is small ($16$ or $32$ buckets).

### 3.2 Treeification Thresholds:
- If a single bucket accumulates **$\ge 8$ entries** AND total table capacity is **$\ge 64$**, the bucket is converted from a linked list into a **Red-Black Tree** (`TreeNode`).
- This guarantees worst-case lookup of **$\mathcal{O}(\log N)$** instead of $\mathcal{O}(N)$ under severe hash collisions.
- If resizing shrinks the bucket count to **$\le 6$**, the tree converts back into a singly-linked list (`untreeify`).

## 4. Ordering Strategies: `Comparable` vs. `Comparator`

- **`Comparable<T>` (Internal Natural Ordering):** The class implements `int compareTo(T o)`.
- **`Comparator<T>` (External Custom Ordering):** A standalone strategy object implementing `int compare(T o1, T o2)`.

### 4.1 Modern Fluent Comparator Chaining (Java 8+)
Avoid messy nested ternary operations. Use `Comparator` combinator methods:

```java
public record Student(String lastName, String firstName, double gpa) {}

Comparator<Student> studentComparator = Comparator
    // 1. Primary: GPA descending
    .comparingDouble(Student::gpa).reversed()
    // 2. Secondary: Last name ascending (nulls last)
    .thenComparing(Student::lastName, Comparator.nullsLast(String::compareToIgnoreCase))
    // 3. Tertiary: First name ascending
    .thenComparing(Student::firstName);
```

## 5. Navigable Collections: `TreeSet` and `TreeMap`

Implemented as Red-Black Trees, `TreeSet` and `TreeMap` provide algorithmic boundary queries in $\mathcal{O}(\log N)$ time:

```java
NavigableMap<Integer, String> map = new TreeMap<>();
map.put(10, "Alpha");
map.put(20, "Beta");
map.put(30, "Gamma");

// Range Queries:
System.out.println(map.floorKey(25));   // 20 (Greatest key <= 25)
System.out.println(map.ceilingKey(25)); // 30 (Smallest key >= 25)
System.out.println(map.lowerKey(20));   // 10 (Greatest key < 20)
System.out.println(map.higherKey(20));  // 30 (Smallest key > 20)

// Sub-range Views:
NavigableMap<Integer, String> window = map.subMap(10, true, 20, true);
```

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 The Inconsistency Between `compareTo` and `equals`
Joshua Bloch highlights Item 14: **It is strongly recommended that `(x.compareTo(y) == 0) == (x.equals(y))`**.
If they are inconsistent, collections like `HashSet` and `TreeSet` will behave unpredictably:

```java
BigDecimal d1 = new BigDecimal("1.0");
BigDecimal d2 = new BigDecimal("1.00");

System.out.println(d1.equals(d2));      // FALSE! (Different scale!)
System.out.println(d1.compareTo(d2));   // 0 (Values are numerically equal!)

Set<BigDecimal> hashSet = new HashSet<>();
hashSet.add(d1); hashSet.add(d2);
System.out.println(hashSet.size());     // 2 (Uses equals())

Set<BigDecimal> treeSet = new TreeSet<>();
treeSet.add(d1); treeSet.add(d2);
System.out.println(treeSet.size());     // 1 ! (Uses compareTo()!)
```

### 6.2 The Comparator Subtraction Overflow Bug
```java
// ANTI-PATTERN:
Comparator<Integer> badComp = (a, b) -> a - b;
```
If `a = -2,147,483,648` and `b = 1`:
$$a - b = -2,147,483,649 \implies \text{Underflows to } +2,147,483,647 > 0$$
The comparator reports `a > b`!  
**Fix:** Always use `Integer.compare(a, b)` or `Comparator.comparingInt()`.

### 6.3 Mutating Keys in a Set or Map
If you mutate an object that is stored as an element in a `HashSet` or as a key in a `HashMap`, its `hashCode()` changes. The object becomes permanently lost in the wrong bucket, causing memory leaks and invisible data corruption.

## 7. Actionable Summary Checklist

- [x] Always override `hashCode()` whenever you override `equals()` (Effective Java Item 11).
- [x] Build multi-key comparators using `Comparator.comparing().thenComparing()` instead of manual if-chains.
- [x] Never use `a - b` in custom numeric comparators to avoid catastrophic integer underflow bugs.
- [x] Ensure that `compareTo` is consistent with `equals` so that `TreeSet`/`TreeMap` behave consistently with `HashSet`/`HashMap`.
- [x] Never mutate the fields of an object after inserting it into a `HashSet` or using it as a key in a `HashMap`.
