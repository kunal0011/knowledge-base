# Chapter 02: DAG Internals, Parsing Loops & Task State Machines

> "A DAG file is not executed once when you submit it—it is repeatedly executed by the scheduler every few seconds forever. Treating parse time as run time is the root of all Airflow performance failures."  
> — *Bas P. Harenslak & Julian Rutger de Ruiter, Data Pipelines with Apache Airflow*

---

## 1. Canonical Motivation & Theoretical Foundation

A fundamental paradox of Apache Airflow is that **DAG definitions are written in arbitrary, Turing-complete Python code**, yet the Airflow runtime requires a static, immutable, and serializable dependency graph to schedule and monitor tasks across distributed workers.

Understanding Airflow's internal execution model requires distinguishing between two entirely distinct phases of lifecycle execution:
1. **DAG Parse Time (Evaluation Time):** The continuous process where the `DagFileProcessorManager` executes the Python script from top to bottom, instantiates `DAG` and `BaseOperator` objects, resolves dependency relationships (`>>`), and serializes the resulting graph structure into the metadata database.
2. **Task Execution Time (Run Time):** The isolated, distributed moment when an individual worker process picks up a single `TaskInstance` and invokes its `execute(context)` method.

Conflating these two lifecycles—such as making database connections, executing REST API calls, or reading environment variables dynamically at parse time—severely degrades cluster scheduling throughput.

## 2. Underlying Runtime, Memory & Execution Architecture

### The Scheduler Parsing & Scheduling Loops

The Airflow Scheduler coordinates two concurrent, decoupled execution loops:

```
 ┌────────────────────────────────────────────────────────────────────────┐
 │                       DagFileProcessorManager Loop                     │
 │  1. Scans dags_folder for .py files                                    │
 │  2. Spawns isolated Child Process per file (multiprocessing pool)      │
 │  3. Child runs: execfile(dag.py)                                       │
 │  4. Serializes DAG object into JSON (SerializedDAG)                    │
 │  5. Writes to DB table: serialized_dag (eliminates Webserver parsing!) │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │                           Scheduler Main Loop                          │
 │  1. Query DB for active DAG runs satisfying schedule interval          │
 │  2. Create DagRun in metadata DB (state: RUNNING)                      │
 │  3. Examine TaskInstances in DagRun: evaluate TriggerRules             │
 │  4. If upstream dependencies met: transition NONE -> SCHEDULED         │
 │  5. Enqueue tasks to Executor: transition SCHEDULED -> QUEUED          │
 │  6. Worker reports task status: QUEUED -> RUNNING -> SUCCESS / FAILED  │
 └────────────────────────────────────────────────────────────────────────┘
```

### Trigger Rule Evaluation Engine

By default, an Airflow task executes only when **all direct upstream tasks have succeeded** (`TriggerRule.ALL_SUCCESS`). However, real-world data engineering architectures frequently require conditional routing, error recovery branches, and guaranteed resource teardown.

Airflow evaluates dependencies dynamically using **Trigger Rules**:

| Trigger Rule | Mathematical / Logical Condition | Common Architecture Pattern |
| :--- | :--- | :--- |
| **`ALL_SUCCESS`** *(Default)*| $\forall u \in \text{Upstream}, \, \text{State}(u) = \text{SUCCESS}$ | Standard sequential processing pipeline. |
| **`ALL_FAILED`** | $\forall u \in \text{Upstream}, \, \text{State}(u) \in \{\text{FAILED}, \text{UPSTREAM\_FAILED}\}$ | Dedicated disaster recovery or error triage pipeline. |
| **`ALL_DONE`** | $\forall u \in \text{Upstream}, \, \text{State}(u) \in \text{TERMINAL}$ | Mandatory cleanup / teardown tasks (e.g., stopping EMR cluster). |
| **`ONE_SUCCESS`** | $\exists u \in \text{Upstream}, \, \text{State}(u) = \text{SUCCESS}$ | Quick-start downstream processing as soon as 1 parallel branch completes. |
| **`ONE_FAILED`** | $\exists u \in \text{Upstream}, \, \text{State}(u) \in \{\text{FAILED}, \text{UPSTREAM\_FAILED}\}$ | Triggering immediate notification alerts upon any parallel failure. |
| **`NONE_FAILED`** | $\forall u \in \text{Upstream}, \, \text{State}(u) \in \{\text{SUCCESS}, \text{SKIPPED}\}$ | Downstream of a `BranchPythonOperator`. |
| **`NONE_SKIPPED`** | $\forall u \in \text{Upstream}, \, \text{State}(u) \ne \text{SKIPPED}$ | Ensuring branches were actively executed, not bypassed. |

## 5. Annotated Code Implementations & Execution Traces

### Production DAG: Branching, Trigger Rules & Guaranteed Cleanup

The following production Python DAG demonstrates the use of `BranchPythonOperator`, conditional task skipping, trigger rules, and mandatory teardown tasks:

```python
"""
Production DAG: Branching Logic and Guaranteed Teardown Execution.
Demonstrates:
  - BranchPythonOperator for dynamic routing
  - trigger_rule=TriggerRule.NONE_FAILED for branch convergence
  - trigger_rule=TriggerRule.ALL_DONE for mandatory resource destruction
"""

from datetime import datetime, timedelta
import random

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.empty import EmptyOperator
from airflow.operators.python import BranchPythonOperator, PythonOperator
from airflow.utils.trigger_rule import TriggerRule


def determine_processing_tier(**context):
    """
    Evaluates incoming partition metrics dynamically at runtime.
    Returns the task_id of the branch to follow.
    """
    # Simulate partition size evaluation
    simulated_partition_size_mb = random.choice([250, 4500])
    
    if simulated_partition_size_mb < 1000:
        print(f"Partition size {simulated_partition_size_mb}MB: Routing to Fast-Path.")
        return "process_small_partition"
    else:
        print(f"Partition size {simulated_partition_size_mb}MB: Routing to Distributed Spark.")
        return "process_large_partition_spark"


with DAG(
    dag_id="advanced_branching_and_teardown_v1",
    schedule_interval="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    default_args={
        "owner": "analytics-infra",
        "retries": 1,
        "retry_delay": timedelta(minutes=2),
    },
    tags=["orchestration", "branching", "patterns"],
) as dag:

    # 1. Provision Ephemeral Compute Infrastructure
    provision_cloud_resources = BashOperator(
        task_id="provision_ephemeral_cluster",
        bash_command="echo 'Creating temporary compute cluster...' && sleep 1",
    )

    # 2. Branch Decision Operator
    evaluate_tier = BranchPythonOperator(
        task_id="branch_on_data_volume",
        python_callable=determine_processing_tier,
    )

    # Branch A: Lightweight processing
    fast_path = BashOperator(
        task_id="process_small_partition",
        bash_command="echo 'Processing in-memory via DuckDB...' && sleep 2",
    )

    # Branch B: Heavy distributed processing
    slow_path = BashOperator(
        task_id="process_large_partition_spark",
        bash_command="echo 'Submitting distributed PySpark job...' && sleep 4",
    )

    # 3. Join / Convergence Node
    # Must use NONE_FAILED so it triggers when one upstream branch succeeds and the other is SKIPPED!
    join_branches = EmptyOperator(
        task_id="join_processing_branches",
        trigger_rule=TriggerRule.NONE_FAILED,
    )

    # 4. Critical Teardown / Cleanup Node
    # Must use ALL_DONE so the temporary cluster is ALWAYS torn down, even if processing fails!
    teardown_resources = BashOperator(
        task_id="teardown_ephemeral_cluster",
        bash_command="echo 'Tearing down temporary compute cluster...' && exit 0",
        trigger_rule=TriggerRule.ALL_DONE,
    )

    # Wiring Graph Topology
    provision_cloud_resources >> evaluate_tier
    evaluate_tier >> [fast_path, slow_path]
    [fast_path, slow_path] >> join_branches
    join_branches >> teardown_resources
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. `Variable.get()` and DB Queries at DAG Parse Time
- **Antipattern:** Calling `Variable.get("my_key")` or establishing database connections at the global module level in the DAG file:
  ```python
  # DISASTROUS ANTI-PATTERN:
  api_key = Variable.get("API_KEY") # Queries metadata DB on EVERY parse cycle!
  ```
- **System Consequence:** If you have 200 DAG files parsed every 30 seconds, this executes 400 SQL queries per minute against the metadata DB just to parse files. The metadata database connection pool is quickly exhausted, leading to timeouts and scheduler starvation.
- **Fix:** Fetch Variables and Connections strictly inside the task's execution callback or pass them via Jinja templates:
  ```python
  # GOOD: Evaluated only at runtime on worker
  op = BashOperator(task_id="t1", bash_command="echo '{{ var.value.API_KEY }}'")
  ```

### 2. The Default `ALL_SUCCESS` Join Deadlock
- **Antipattern:** Following a `BranchPythonOperator` with a downstream task that retains the default `trigger_rule = TriggerRule.ALL_SUCCESS`.
- **System Consequence:** In branching, one path is taken and all other paths are marked `SKIPPED`. If the downstream join task uses `ALL_SUCCESS`, it requires *every* upstream task to have succeeded. Because one branch was skipped, the join task is automatically marked `SKIPPED`, cascading down the entire remaining graph.
- **Fix:** Downstream join operators that merge branches must always specify `trigger_rule = TriggerRule.NONE_FAILED`.

### 3. Dynamic DAG ID Non-Determinism
- **Antipattern:** Generating dynamic task or DAG IDs using current timestamps or random UUIDs at parse time:
  ```python
  # BAD: Non-deterministic IDs break task history
  task_id = f"task_{datetime.now().strftime('%Y%m%d%H%M%S')}"
  ```
- **System Consequence:** Airflow tracks task state by `dag_id` and `task_id` in the database. When the scheduler re-parses the file 30 seconds later, it sees completely different task IDs. Airflow deletes existing state entries, invalidates active runs, and fails running tasks.
- **Fix:** Ensure all generated task IDs and DAG IDs are strictly deterministic based on static configuration arrays.
