# Chapter 07: Streaming Joins, Interval Joins & Temporal Tables

> "Joining two infinite streams is impossible without bounding state: you must define either a window of time or an interval of relative offset within which matching events are permitted to correlate."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

In relational database systems, an `INNER JOIN` evaluates two static, finite tables. Both tables can be scanned, indexed, or hashed in their entirety. 

In stream processing, both sides of the join ($Stream_A$ and $Stream_B$) are **unbounded, continuously arriving feeds**. A naive streaming join would require caching every record from both streams in state storage indefinitely, waiting for a potential match that might arrive seconds, days, or years later. Over time, state size grows toward infinity ($\lim_{t \to \infty} State(t) = \infty$), guaranteeing cluster failure.

To join unbounded streams safely and deterministically, distributed streaming engines must enforce **temporal bounds**:
1. **Windowed Stream Joins:** Slicing both streams into identical discrete time windows (e.g., both events must fall into the exact same 10-minute tumbling window).
2. **Interval Joins:** Correlating events where an event from $Stream_B$ arrives within a relative temporal offset window $[t_A + \Delta_{\text{lower}}, t_A + \Delta_{\text{upper}}]$ relative to an event in $Stream_A$.
3. **Temporal Table Joins:** Correlating an event from an append-only stream with the *point-in-time historical version* of a changing dimension table (changelog stream).

## 2. Underlying Runtime, Memory & Execution Architecture

### The Mechanics of an Interval Join

An **Interval Join** evaluates two keyed streams based on relative event-time intervals:

$$t_B \in \left[ t_A + \text{lowerBound}, \; t_A + \text{upperBound} \right]$$

```
 Stream A (Orders):   ───[ Order A: t=100 ]─────────────────────────────────────>
                                 │
                         Interval: [-20, +60]
                                 │
 Range of B (Payments):       [ t=80 ] <───────────────────────> [ t=160 ]
                                 │                                 │
 Stream B (Payments): ───[ Pay X: t=75 ]───[ Pay Y: t=110 ]───[ Pay Z: t=190 ]──>
                              (Miss)            (MATCH!)            (Miss)
```

#### Dual-State Buffering & Automatic State Purging
Under the hood, Flink manages two internal keyed `MapState` or `ListState` buffers:
- State buffer for $Stream_A$: holds records from $A$ indexed by timestamp.
- State buffer for $Stream_B$: holds records from $B$ indexed by timestamp.

When an event arrives on $A$, it scans the buffer for $B$ to find matching keys within the interval, then inserts itself into $A$'s buffer. 

**Automatic Garbage Collection:** Unlike raw process functions, the interval join operator automatically registers internal event-time cleanup timers. Once the minimum watermark advances past the upper bound of a buffered record:

$$\text{Watermark} > t_{\text{record}} + \text{upperBound}$$

Flink **automatically purges** that record from RocksDB state! This guarantees strictly bounded memory footprints with zero manual cleanup code.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Interval Join API Syntax

```java
DataStream<JoinedResult> joined = orders
    .keyBy(order -> order.userId)
    .intervalJoin(payments.keyBy(payment -> payment.userId))
    // Lower bound: payment may occur up to 5 minutes before order
    // Upper bound: payment may occur up to 15 minutes after order
    .between(Time.minutes(-5), Time.minutes(15))
    .upperBoundInclusive()
    .lowerBoundInclusive()
    .process(new ProcessJoinFunction<Order, Payment, JoinedResult>() {
        @Override
        public void processElement(Order left, Payment right, Context ctx, Collector<JoinedResult> out) {
            out.collect(new JoinedResult(left, right));
        }
    });
```

### Join Types Supported in Modern Flink
- **Inner Interval Join:** Emits records only when matches exist within the interval bounds.
- **Left Outer Interval Join:** Emits the left record with `null` if no matching right record arrives within the interval window (requires watermark advancement past the upper bound).
- **Right Outer / Full Outer Interval Join:** Emits unmatched records on either side upon timeout.

## 5. Annotated Code Implementations & Execution Traces

### Production Interval Join: Correlating Orders and Payments with Automatic Eviction

The following Java pipeline correlates purchase orders with payment gateway records using an event-time interval join:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.api.common.eventtime.WatermarkStrategy;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.functions.co.ProcessJoinFunction;
import org.apache.flink.streaming.api.windowing.time.Time;
import org.apache.flink.util.Collector;

import java.time.Duration;

public class StreamIntervalJoinJob {

    public static class OrderEvent {
        public String orderId;
        public String customerId;
        public double totalAmount;
        public long timestampMs;

        public OrderEvent() {}
        public OrderEvent(String orderId, String customerId, double totalAmount, long timestampMs) {
            this.orderId = orderId;
            this.customerId = customerId;
            this.totalAmount = totalAmount;
            this.timestampMs = timestampMs;
        }
    }

    public static class PaymentEvent {
        public String transactionId;
        public String orderId;
        public String paymentStatus;
        public long paymentTimeMs;

        public PaymentEvent() {}
        public PaymentEvent(String transactionId, String orderId, String paymentStatus, long paymentTimeMs) {
            this.transactionId = transactionId;
            this.orderId = orderId;
            this.paymentStatus = paymentStatus;
            this.paymentTimeMs = paymentTimeMs;
        }
    }

    public static class SettledOrder {
        public String orderId;
        public String customerId;
        public double amount;
        public String paymentTransactionId;
        public long latencyMs;

        public SettledOrder(String orderId, String customerId, double amount, String txId, long latency) {
            this.orderId = orderId;
            this.customerId = customerId;
            this.amount = amount;
            this.paymentTransactionId = txId;
            this.latencyMs = latency;
        }

        @Override
        public String toString() {
            return String.format("SettledOrder[id=%s, customer=%s, amt=%.2f, tx=%s, latency=%dms]",
                    orderId, customerId, amount, paymentTransactionId, latencyMs);
        }
    }

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        // Feed 1: Orders stream
        DataStream<OrderEvent> orders = env.fromElements(
                new OrderEvent("ORD-1", "CUST-A", 120.0, 1000L),
                new OrderEvent("ORD-2", "CUST-B", 450.0, 5000L),
                new OrderEvent("ORD-3", "CUST-C", 85.0, 10000L)
        ).assignTimestampsAndWatermarks(
                WatermarkStrategy.<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(1))
                        .withTimestampAssigner((evt, ts) -> evt.timestampMs)
        );

        // Feed 2: Payments stream
        DataStream<PaymentEvent> payments = env.fromElements(
                new PaymentEvent("TX-991", "ORD-1", "SUCCESS", 2500L),  // Arrives 1.5s after order (Within [-1s, +10s] interval)
                new PaymentEvent("TX-992", "ORD-2", "SUCCESS", 25000L), // Arrives 20s after order (Outside interval -> Dropped)
                new PaymentEvent("TX-993", "ORD-3", "SUCCESS", 10500L)  // Arrives 500ms after order (Within interval)
        ).assignTimestampsAndWatermarks(
                WatermarkStrategy.<PaymentEvent>forBoundedOutOfOrderness(Duration.ofSeconds(1))
                        .withTimestampAssigner((evt, ts) -> evt.paymentTimeMs)
        );

        // Execute Interval Join: Payment must occur within [-1 second, +10 seconds] of order
        orders.keyBy(o -> o.orderId)
                .intervalJoin(payments.keyBy(p -> p.orderId))
                .between(Time.seconds(-1), Time.seconds(10))
                .upperBoundInclusive()
                .lowerBoundInclusive()
                .process(new ProcessJoinFunction<OrderEvent, PaymentEvent, SettledOrder>() {
                    @Override
                    public void processElement(OrderEvent order, PaymentEvent payment, Context ctx, Collector<SettledOrder> out) {
                        long settlementLatency = payment.paymentTimeMs - order.timestampMs;
                        out.collect(new SettledOrder(
                                order.orderId,
                                order.customerId,
                                order.totalAmount,
                                payment.transactionId,
                                settlementLatency
                        ));
                    }
                })
                .name("OrderPaymentIntervalJoin")
                .print();

        env.execute("StreamIntervalJoinJob");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. Flink SQL Unbounded Join State Leak
- **Antipattern:** Writing a standard SQL inner join between two streaming tables without an interval condition or table retention configuration:
  ```sql
  -- DANGEROUS: Accumulates state forever!
  SELECT * FROM Orders o JOIN Payments p ON o.orderId = p.orderId;
  ```
- **System Consequence:** Without a temporal constraint or TTL, Flink SQL assumes any future record could match any historical record. RocksDB state grows indefinitely until the cluster runs out of disk space.
- **Fix:** Either add an interval condition in SQL (`WHERE p.payTime BETWEEN o.orderTime AND o.orderTime + INTERVAL '10' MINUTE`) or configure dynamic table state retention:
  ```java
  tableEnv.getConfig().setIdleStateRetention(Duration.ofHours(1));
  ```

### 2. Mismatched Watermark Stall in Joins
- **Antipattern:** Performing an interval join where one stream has an idle or lagging watermark generator.
- **System Consequence:** The interval join operator cannot advance its internal time or purge expired records until the watermarks of **both** input streams advance past the upper bounds. If one stream stops emitting watermarks, state accumulation in the other stream continues unabated, exhausting memory.
- **Fix:** Ensure both input streams apply `withIdleness(...)` to prevent single inactive partitions from halting watermark progression across join inputs.

### 3. Asymmetric State Sizing
- **Antipattern:** Setting wide interval bounds (e.g. `between(Time.days(-30), Time.days(30))`) on high-throughput streams.
- **System Consequence:** Both sides of the stream must retain 30 days of raw events in RocksDB. For a stream of 10,000 records/sec, this stores over 25 billion records in the join operator state, severely degrading checkpoint performance.
- **Fix:** Keep interval bounds as narrow as mathematically possible for real-time operations. Delegate multi-month joins to batch or lakehouse engines (e.g., Iceberg/Delta).
