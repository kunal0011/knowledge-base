# Chapter 03: Workload Controllers: Deployments, StatefulSets & DaemonSets

---

## 1. The Controller Pattern & Declarative Workloads

In Kubernetes, users rarely create naked Pods directly. If a raw Pod crashes or its underlying node experiences hardware failure, the Pod is lost forever. 

To achieve **self-healing, scaling, and rolling upgrades**, Kubernetes introduces high-level **Workload Controllers**. Controllers observe Pods using label selectors, compute the delta against desired state, and create or destroy Pods using the API server.

```text
===================================================================================================================
                                      WORKLOAD CONTROLLER HIERARCHY
===================================================================================================================

                ┌─────────────────────────────────────────────────────────────┐
                │                         Deployment                          │
                │     (Manages Declarative Upgrades, Rollbacks, Pauses)       │
                └──────────────────────────────┬──────────────────────────────┘
                                               │
                       ┌───────────────────────┴───────────────────────┐
                       ▼ (Active Revision)                             ▼ (Old Revision for Rollback)
         ┌───────────────────────────┐                   ┌───────────────────────────┐
         │     ReplicaSet (v2)       │                   │     ReplicaSet (v1)       │
         │  (Enforces Pod Count = 3) │                   │  (Scaled down to Replicas = 0)
         └─────────────┬─────────────┘                   └───────────────────────────┘
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │  Pod 1  │     │  Pod 2  │     │  Pod 3  │
  └─────────┘     └─────────┘     └─────────┘
===================================================================================================================
```

## 2. Deployments & RollingUpdate Mathematics

Deployments manage stateless web services and APIs. The Deployment controller does not create Pods directly; it creates and manages **ReplicaSets**, which in turn manage the Pods.

### 2.1 The Rolling Update Algorithm
During a rollout, the Deployment modifies the replica counts of the old and new ReplicaSets incrementally based on two critical parameters:
1. **`maxSurge`:** The maximum number of Pods that can be scheduled *above* the desired replica count.
2. **`maxUnavailable`:** The maximum number of Pods that can be unavailable during the update process.

```text
===================================================================================================================
                       ROLLING UPDATE STATE MACHINE (Replicas = 4, maxSurge=1, maxUnavailable=0)
===================================================================================================================

  T0 (Initial):       [Old-RS: 4 Pods Ready]           [New-RS: 0 Pods]        Available: 4/4 (100%)
                            │
                            ▼ (Create 1 New Pod via maxSurge=1)
  T1 (Surge):         [Old-RS: 4 Pods Ready]           [New-RS: 1 Pod Starting] Available: 4/4
                            │
                            ▼ (New Pod passes Readiness Probe)
  T2 (Ready):         [Old-RS: 4 Pods Ready]           [New-RS: 1 Pod READY]   Available: 5/4
                            │
                            ▼ (Terminate 1 Old Pod)
  T3 (Drain):         [Old-RS: 3 Pods Ready]           [New-RS: 1 Pod READY]   Available: 4/4
                            │
                            ▼ (Repeat cycle until Old-RS = 0, New-RS = 4)
  T_Final:            [Old-RS: 0 Pods]                 [New-RS: 4 Pods READY]  Available: 4/4
===================================================================================================================
```

### 2.2 Production Deployment Manifest
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: ecommerce
  labels:
    app.kubernetes.io/name: order-service
spec:
  replicas: 5
  revisionHistoryLimit: 10 # Retains last 10 ReplicaSets for instantaneous rollbacks
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # Allows up to 7 total pods during rollout
      maxUnavailable: 0      # Zero downtime guarantee: never drops below 5 ready pods
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
      - name: order-api
        image: enterprise/order-api:v2.1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "250m"
            memory: "512Mi"
          limits:
            cpu: "1000m"
            memory: "1Gi"
```

## 3. StatefulSets: Identity, Ordinals & Storage Topologies

Stateless deployments treat Pods as cattle: Pods have random names (`order-service-78f4b-abc12`), dynamic IPs, and share no sticky identity.

However, distributed stateful systems (e.g., **Kafka, Apache Cassandra, ZooKeeper, PostgreSQL Primary-Replica**) require:
1. **Stable Network Identifiers:** Each replica requires a predictable, immutable hostname.
2. **Dedicated Persistent Storage:** Replicas cannot share a single read-write volume; each node requires its own isolated disk that survives Pod restarts and rescheduling.
3. **Ordered Startup & Teardown:** Clustered nodes must boot in order ($0 \to 1 \to 2$) and terminate in reverse order ($2 \to 1 \to 0$).

```text
===================================================================================================================
                                      STATEFULSET ORDINAL TOPOLOGY
===================================================================================================================

  Headless Service: `kafka.datastore.svc.cluster.local` (ClusterIP: None)
         │
         ├────► kafka-0.kafka.datastore.svc.cluster.local ──► [PV 0: EBS-Volume-A]
         ├────► kafka-1.kafka.datastore.svc.cluster.local ──► [PV 1: EBS-Volume-B]
         └────► kafka-2.kafka.datastore.svc.cluster.local ──► [PV 2: EBS-Volume-C]

  Key Guarantees:
  • If Pod `kafka-1` crashes, it is recreated on ANY available node with the SAME name `kafka-1`.
  • It automatically re-attaches to [PV 1], preserving its committed logs and partition offsets!
===================================================================================================================
```

### 3.1 Production StatefulSet Manifest (Clustered PostgreSQL)
```yaml
apiVersion: v1
kind: Service
metadata:
  name: postgres-headless
  labels:
    app: postgres
spec:
  clusterIP: None # Headless service provides direct DNS A-records for each ordinal pod
  ports:
  - port: 5432
    name: postgres
  selector:
    app: postgres
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: "postgres-headless"
  replicas: 3
  podManagementPolicy: OrderedReady # Enforces sequential 0 -> 1 -> 2 initialization
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgresql
        image: postgres:16-alpine
        ports:
        - containerPort: 5432
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  # volumeClaimTemplates: Automatically provisions a unique PVC for each ordinal replica
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "gp3-sc"
      resources:
        requests:
          storage: 100Gi
```

## 4. DaemonSets: Node-Level Infrastructure Workloads

A **DaemonSet** guarantees that an exact copy of a Pod runs on **all (or selected) worker nodes**. As new nodes join the cluster, the DaemonSet controller automatically schedules the pod onto the new hardware.

### Canonical Use Cases:
1. **Cluster Storage Daemons:** Ceph OSD, GlusterFS, Portworx.
2. **Log Collection Daemons:** Fluentbit, Vector, Filebeat shipping local node `/var/log` files.
3. **Node Monitoring Daemons:** Prometheus Node Exporter, Datadog Agent.
4. **Networking & Security Daemons:** Cilium CNI agent, Calico `felix`, Falco runtime security.

===================================================================================================================
                                      DAEMONSET NODE COVERAGE
===================================================================================================================

## 5. Batch Workloads: Jobs & CronJobs

Not all enterprise workloads run continuously as daemon servers. Data pipelines, database migrations, and report generators require run-to-completion guarantees:

### 5.1 Jobs
A **Job** creates one or more Pods and ensures that a specified number of them successfully terminate with exit code `0`.
- **`completions`:** Total number of successful Pod terminations required.
- **`parallelism`:** Maximum number of Pods running concurrently.
- **`backoffLimit`:** Number of retries before marking the Job permanently failed.

### 5.2 CronJobs
Wraps a Job spec in a periodic cron scheduler (`schedule: "0 2 * * *"`).
- **`concurrencyPolicy`:**
  - `Allow` (Default): Concurrent execution of scheduled jobs.
  - `Forbid`: Skips the new run if the previous run has not yet finished (essential for non-reentrant financial batch jobs!).
  - `Replace`: Cancels the currently running job and starts a new instance.
