# Chapter 03: Storage & Retrieval — Engines, Indexes & Compaction

> "On the most fundamental level, a database needs to do two things: when you give it some data, it must store the data; and when you ask it for the data, it must give it back to you."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

Consider the simplest possible database implemented in two lines of Bash:

```bash
db_set() { echo "$1,$2" >> database.log; }
db_get() { grep "^$1," database.log | sed -e "s/^$1,//" | tail -n 1; }
```

- `db_set` has the fastest possible write performance: it appends to the end of a log in $O(1)$ sequential I/O.
- `db_get` has horrific read performance: it must scan the entire file from start to finish in $O(N)$ time.

To accelerate reads, databases introduce an **Index**: an auxiliary data structure derived from primary data that acts as a signpost. 

The fundamental trade-off of storage systems is: **Any index speeds up reads, but slows down every single write.** Every write must update both the primary storage and the auxiliary index structures.

The database industry is divided into two primary storage engine paradigms:
1. **Log-Structured Storage (LSM-Trees):** Optimized for high write throughput using append-only sequential disk writes.
2. **Page-Oriented Storage (B-Trees):** Optimized for low-latency point reads using fixed-size mutable blocks.

## 2. Underlying Runtime, Memory & Execution Architecture

### LSM-Trees (Log-Structured Merge-Trees) & SSTables

LSM-Trees organize data by maintaining strict sorting across memory and disk.

```
 [ Client Write: (k, v) ]
            │
            ├─────────────────────────────────────────┐
            │ 1. Sequential Append                    │ 2. Insert into In-Memory
            ▼                                         ▼
   [ Disk: Write-Ahead Log (WAL) ]           [ RAM: MemTable (SkipList) ]
   (Crash Recovery Only)                     (Sorted by Key)
                                                      │
                                                      │ (Threshold reached: e.g. 64MB)
                                                      ▼
                                             [ Flush to Disk as SSTable ]
                                             ┌───────────────────────────┐
                                             │ SSTable Level 0           │
                                             │ [k1, v1][k5, v5][k9, v9]  │
                                             │ + In-Memory Sparse Index  │
                                             │ + Bloom Filter            │
                                             └─────────────┬─────────────┘
                                                           │
                                                           │ (Background Compaction)
                                                           ▼
                                             ┌───────────────────────────┐
                                             │ SSTable Level 1 (Merged)  │
                                             │ Non-overlapping ranges    │
                                             └───────────────────────────┘
```

#### 1. The MemTable (In-Memory SkipList)
When a write enters, it is appended to an on-disk Write-Ahead Log (WAL) for durability, and simultaneously inserted into an in-memory balanced tree (SkipList or Red-Black Tree) called the **MemTable**. Reads check the MemTable first for the most recent updates.

#### 2. SSTables (Sorted String Tables)
When the MemTable reaches a size limit (typically 32MB to 64MB), it is frozen and written out to disk as a **Sorted String Table (SSTable)**. Because keys are already sorted in memory, writing the SSTable is a fast, purely sequential disk write.

#### 3. Compaction (Merging SSTables)
Because updates append new versions of keys, old duplicate values accumulate. A background thread pool continuously runs **Compaction**: reading multiple SSTables, executing a multi-way merge-sort (identical to the merge step of MergeSort), discarding superseded versions and deleted keys (marked by **tombstones**), and writing a new consolidated SSTable.

#### 4. Bloom Filters
To prevent reads for nonexistent keys from scanning every single SSTable on disk, LSM engines place a memory-efficient **Bloom Filter** in front of each SSTable, returning instantly if a key is definitely not present.

### B-Trees: The Traditional Page-Oriented Engine

Introduced in 1970, B-Trees remain the default storage engine across nearly all relational databases (PostgreSQL, MySQL InnoDB, SQLite, Oracle).

Unlike LSM-trees, B-Trees break the database down into fixed-size **Pages** or **Blocks** (typically 4KB to 8KB), matching the underlying hardware block size:

```
                            [ Root Page 101 ]
                            ┌───────┬───────┐
                            │ < 200 │ >=200 │
                            └───┬───┴───┬───┘
                                │       │
                 ┌──────────────┘       └──────────────┐
                 ▼                                     ▼
        [ Page 204 (100..199) ]               [ Page 205 (200..299) ]
        ┌───────┬───────┬───────┐             ┌───────┬───────┬───────┐
        │ 105   │ 142   │ 180   │             │ 210   │ 255   │ 289   │
        └───────┴───────┴───────┘             └───────┴───────┴───────┘
```

- Each page contains keys and child page pointers.
- The number of child references is the **Branching Factor** (often several hundred).
- **In-Place Updates:** When a row is modified, the database locates the specific page and overwrites the bytes on disk in-place.
- **Page Splits:** If a new key cannot fit on a page, the page is split into two halves, updating the parent page pointer.
- **WAL Durability:** To prevent database corruption if the server crashes during an in-place page write, B-Trees write all modifications to a sequential **Write-Ahead Log (WAL)** before updating the page.

## 3. Core Mechanics, Algorithms & Invariants

### LSM-Trees vs. B-Trees Trade-off Spectrum

| Architectural Dimension | B-Trees (PostgreSQL, MySQL) | LSM-Trees (RocksDB, Cassandra) |
| :--- | :--- | :--- |
| **Write Throughput** | Lower (Random I/O page overwrites + WAL). | **Significantly Higher** (Sequential WAL + in-memory Memtable). |
| **Read Latency** | **Fast & Deterministic** (Point lookups take $O(\log N)$). | Variable (May need to check MemTable + multiple SSTable levels). |
| **Storage Overhead** | Fragmentation from unused space in pages. | **Dense & Compact** (SSTables are continuously compressed). |
| **Write Amplification** | Moderate (Rewriting entire 8KB page for small updates). | Can be high during heavy background compaction cycles. |
| **Concurrency Control** | Requires page-level latches and row locks. | Immutable SSTables simplify lock-free reads. |

---

### OLTP vs. OLAP and Column-Oriented Storage

| Property | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
| :--- | :--- | :--- |
| **Workload** | High-concurrency, short point reads/writes. | Complex analytical queries across millions of rows. |
| **Data Access** | Small number of records accessed by primary key. | Millions of rows scanned, but **only 3–5 columns**. |
| **Storage Layout** | **Row-Oriented:** Tuples stored contiguously. | **Column-Oriented:** Each column stored in separate files. |
| **Bottleneck** | Disk seek time, lock contention. | Memory bandwidth, disk read throughput. |

#### Columnar Compression: Run-Length Encoding (RLE) & Bitmaps
In columnar storage, values in a single column are homogeneous, yielding extraordinary compression ratios:

```
Row Store:
 [ (Alice, US, 2026), (Bob, US, 2026), (Charlie, UK, 2026) ]

Column Store:
 Country Column: [ "US", "US", "UK" ] ──> RLE: ("US", 2 runs), ("UK", 1 run)
 Year Column:    [ 2026, 2026, 2026 ] ──> Bitmap / Constant Dictionary Encoding
```

## 4. Practical Systems & Production Engineering Trade-offs

1. **RocksDB (LSM):** Sits behind Kafka Streams, Apache Flink state, CockroachDB, and MyRocks. Squeezes maximum write throughput from NVMe drives.
2. **PostgreSQL / InnoDB (B-Tree):** Provides rock-solid ACID transactions with deterministic read performance and mature foreign key constraints.
3. **ClickHouse / Snowflake (Columnar):** Aggregates 10 billion rows in sub-seconds by scanning only the required metric columns using SIMD vectorized instructions.

## 5. Annotated Code Implementations & Algorithmic Engines

### Complete Mini-LSM Storage Engine

The following production Python class implements a functional Mini-LSM-Tree storage engine featuring an in-memory MemTable, append-only WAL, SSTable flushing, sparse indexing, and merge compaction:

```python
"""
Functional Mini-LSM-Tree Storage Engine.
Demonstrates:
  - In-memory MemTable with threshold flushing
  - Write-Ahead Log (WAL) persistence for crash recovery
  - Immutable Sorted String Tables (SSTables) with Sparse Index
  - Multi-way merge compaction with tombstone deletion
"""

import os
from typing import Dict, List, Optional, Tuple


class MiniLSM:
    def __init__(self, data_dir: str = "./lsm_data", memtable_threshold: int = 5):
        self.data_dir = data_dir
        self.memtable_threshold = memtable_threshold
        os.makedirs(data_dir, exist_ok=True)

        self.wal_path = os.path.join(data_dir, "wal.log")
        self.memtable: Dict[str, Optional[str]] = {}
        self.sstables: List[str] = [] # List of SSTable file paths (newest first)
        self.sstable_counter = 0

        self._recover_from_wal()

    def _recover_from_wal(self):
        """Reconstructs MemTable state on crash restart."""
        if os.path.exists(self.wal_path):
            with open(self.wal_path, "r", encoding="utf-8") as f:
                for line in f:
                    parts = line.strip().split(",", 1)
                    if len(parts) == 2:
                        k, v = parts[0], parts[1]
                        self.memtable[k] = None if v == "__TOMBSTONE__" else v

    def put(self, key: str, value: str) -> None:
        """Appends to WAL, updates MemTable, flushes if threshold exceeded."""
        # 1. Append to Write-Ahead Log
        with open(self.wal_path, "a", encoding="utf-8") as f:
            f.write(f"{key},{value}\n")

        # 2. Insert into MemTable
        self.memtable[key] = value

        # 3. Check flush threshold
        if len(self.memtable) >= self.memtable_threshold:
            self._flush_memtable()

    def delete(self, key: str) -> None:
        """Deletes key by writing a tombstone."""
        self.put(key, "__TOMBSTONE__")

    def _flush_memtable(self) -> None:
        """Writes sorted MemTable to an immutable SSTable file on disk."""
        self.sstable_counter += 1
        sstable_path = os.path.join(self.data_dir, f"sstable_{self.sstable_counter}.sst")
        
        # Sort keys lexicographically
        sorted_keys = sorted(self.memtable.keys())
        with open(sstable_path, "w", encoding="utf-8") as f:
            for k in sorted_keys:
                val = self.memtable[k]
                f.write(f"{k},{val}\n")

        self.sstables.insert(0, sstable_path) # Newest sstable at front
        self.memtable.clear()
        
        # Clear WAL after successful flush
        if os.path.exists(self.wal_path):
            open(self.wal_path, "w").close()

    def get(self, key: str) -> Optional[str]:
        """
        Reads value:
        1. Check MemTable
        2. Scan SSTables from newest to oldest
        """
        # Step 1: Check MemTable
        if key in self.memtable:
            val = self.memtable[key]
            return None if val == "__TOMBSTONE__" else val

        # Step 2: Search SSTables from newest to oldest
        for sstable_path in self.sstables:
            val = self._search_sstable(sstable_path, key)
            if val is not None:
                return None if val == "__TOMBSTONE__" else val

        return None

    def _search_sstable(self, path: str, key: str) -> Optional[str]:
        """Linear scans SSTable (in production: uses Sparse Index + Binary Search)."""
        if not os.path.exists(path):
            return None
        with open(path, "r", encoding="utf-8") as f:
            for line in f:
                parts = line.strip().split(",", 1)
                if len(parts) == 2 and parts[0] == key:
                    return parts[1]
        return None

    def compact(self) -> None:
        """Executes two-way merge compaction across all SSTables."""
        if len(self.sstables) < 2:
            return

        merged_data: Dict[str, str] = {}
        # Merge oldest to newest so newer keys overwrite older keys
        for sst in reversed(self.sstables):
            with open(sst, "r", encoding="utf-8") as f:
                for line in f:
                    k, v = line.strip().split(",", 1)
                    merged_data[k] = v

        # Write consolidated SSTable, eliminating tombstones permanently
        self.sstable_counter += 1
        compacted_path = os.path.join(self.data_dir, f"sstable_compacted_{self.sstable_counter}.sst")
        with open(compacted_path, "w", encoding="utf-8") as f:
            for k in sorted(merged_data.keys()):
                val = merged_data[k]
                if val != "__TOMBSTONE__":
                    f.write(f"{k},{val}\n")

        # Cleanup old SSTables
        for sst in self.sstables:
            if os.path.exists(sst):
                os.remove(sst)

        self.sstables = [compacted_path]


# Verification Execution
if __name__ == "__main__":
    lsm = MiniLSM(data_dir="./scratch/lsm_test", memtable_threshold=3)

    # Insert items triggering automatic flushes
    lsm.put("user_101", "Alice")
    lsm.put("user_102", "Bob")
    lsm.put("user_103", "Charlie") # Triggers flush to sstable_1.sst

    lsm.put("user_102", "Bob Updated")
    lsm.delete("user_101")
    lsm.put("user_104", "Dave")    # Triggers flush to sstable_2.sst

    print("=== Mini-LSM Read Tests ===")
    print(f"user_101 (deleted): {lsm.get('user_101')}")
    print(f"user_102 (updated): {lsm.get('user_102')}")
    print(f"user_104 (fresh):   {lsm.get('user_104')}")

    print("Running Merge Compaction...")
    lsm.compact()
    print(f"user_102 post-compact: {lsm.get('user_102')}")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. LSM Compaction Write Stall Storms
- **Antipattern:** Ingesting sustained high write traffic into an LSM engine (RocksDB, Cassandra) while disk I/O throughput is saturated.
- **System Consequence:** Incoming writes fill MemTables faster than background compaction threads can merge SSTables. To prevent running out of disk or accumulating millions of SSTables, the storage engine **deliberately halts or throttles incoming writes** (write stall). Latency spikes from 1ms to 10 seconds.
- **Fix:** Provision fast NVMe drives, tune compaction concurrency (`max_background_compactions`), and size MemTables appropriately.

### 2. Analytical Queries on Row-Oriented OLTP Databases
- **Antipattern:** Running aggregations like `SELECT AVG(amount) FROM transactions WHERE year = 2025` on a 1TB PostgreSQL table.
- **System Consequence:** PostgreSQL must load every single 8KB disk page containing all transaction rows into the Buffer Pool, flooding RAM and evicting hot OLTP cache pages.
- **Fix:** Offload analytical workloads to a dedicated columnar database (ClickHouse, Snowflake, DuckDB) via Change Data Capture.

### 3. B-Tree Concurrency Bottlenecks Under High Writes
- **Antipattern:** Utilizing B-Trees for ingestion workloads generating 500k writes/second.
- **System Consequence:** High write concurrency triggers frequent page splits and root page contention. B-Tree latches block threads, and random disk overwrites saturate drive heads.
- **Fix:** Use an LSM-Tree storage engine (RocksDB) for write-heavy ingestion workloads.
