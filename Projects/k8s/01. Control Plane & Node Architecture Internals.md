## 1. Executive Summary & Control Plane Topology

At its core, Kubernetes is a distributed state database (`etcd`) wrapped in an extensible HTTP/JSON REST API (`kube-apiserver`), governed by a set of asynchronous, independent reconciliation engines (`kube-controller-manager`, `kube-scheduler`), and executed on physical or virtual compute nodes via a local node agent (`kubelet`) and network proxy (`kube-proxy`).

## 2. Control Plane Components Deep Dive

### 2.1 `kube-apiserver`: The Gateway to the Cluster

The API server is the **only component that communicates directly with `etcd`**. Every other component—the controller manager, the scheduler, the kubelet, and end users—must interact through the API server. This strict architectural boundary guarantees:
1. **Total Access Mediation:** No client or node can bypass authentication, authorization, and validation rules.
2. **Optimistic Concurrency Control (OCC):** The API server prevents race conditions using `metadata.resourceVersion`. If two clients attempt to update the same resource concurrently, the client whose update arrives second receives an `HTTP 409 Conflict` error because its `resourceVersion` is stale:
   $$\text{Reject update if: } \text{Payload}.\text{resourceVersion} \ne \text{etcd}.\text{currentRevision}$$

#### The Watch API & Informer Mechanics
Polling a distributed database with tens of thousands of resources would cause immediate CPU and network exhaustion. Kubernetes uses an event-driven **HTTP/2 Streaming Watch Mechanism**:
- Clients open a long-lived GET request with `?watch=true&resourceVersion=X`.
- The API server streams all mutations (`ADDED`, `MODIFIED`, `DELETED`, `BOOKMARK`) that occurred after revision $X$.
- If connection drops, the client reconnects with its latest observed `resourceVersion`, resuming smoothly without missing events.

### 2.2 `etcd`: Distributed Consensus & Storage Internals

`etcd` is an open-source, strongly consistent, distributed key-value store implementing the **Raft consensus algorithm** (Ongaro & Ousterhout, 2014).

#### Key Storage Characteristics in Kubernetes:
- **Hierarchical Key Paths:** All Kubernetes objects are mapped into pseudo-filesystem paths:
  `/registry/<resource_plural>/<namespace>/<name>`  
  *(e.g., `/registry/pods/production/payment-service-7f89d4-abc12`)*
- **MVCC Architecture:** `etcd` does not overwrite keys in place. Every modification increments a global 64-bit counter called the `revision`. A key update creates a new revision record while preserving historical revisions until `etcd`'s background compactor purges them.
- **Quorum Calculations:** An `etcd` cluster of $N$ nodes requires a strict majority to commit writes:
  $$\text{Quorum Size} = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
  - $3$ nodes can tolerate $1$ failure ($\text{Quorum} = 2$).
  - $5$ nodes can tolerate $2$ failures ($\text{Quorum} = 3$).
  - Even node counts provide zero additional fault tolerance (a 4-node cluster still requires 3 nodes for quorum, tolerating only 1 failure while doubling communication overhead).

### 2.3 `kube-controller-manager`: The Brain of Declarative State

The Controller Manager is a single binary that packs dozens of distinct reconciliation loops into a single process. Each controller is conceptually an infinite loop:

```python
def reconciliation_loop():
    while True:
        desired_state = apiserver.get_spec()
        actual_state = apiserver.get_status()
        
        if desired_state != actual_state:
            delta = compute_divergence(desired_state, actual_state)
            execute_remedial_actions(delta)
            
        sleep(poll_or_wait_for_watch_event())
```

#### Key Built-In Controllers:
1. **Deployment Controller:** Watches Deployments and ReplicaSets. Scales ReplicaSets up/down during rolling updates.
2. **ReplicaSet Controller:** Ensures that exactly $N$ identical Pod replicas exist matching a given label selector.
3. **Node Lifecycle Controller:** Monitors node heartbeats (`/api/v1/nodes/<node>/status`). If a node stops sending lease renewals for `node-monitor-grace-period` (default: 40 seconds), it marks the node `NotReady` and evicts Pods after `pod-eviction-timeout`.
4. **EndpointSlice Controller:** Watches Services and Pods, mapping healthy Pod IPs and ports into `EndpointSlice` objects for `kube-proxy`.
5. **Namespace Controller:** Deletes all objects in a namespace when an HTTP DELETE is issued on the namespace.

## 3. Worker Node Architecture

### 3.1 `kubelet`: The Node Commander

The `kubelet` is the primary agent running on each worker node. It registers the node with the control plane and monitors the node's allocatable hardware resources.

#### The SyncLoop Engine
The kubelet runs an internal `syncLoop` driven by three event channels:
1. **Pod Updates Channel:** Receives desired PodSpecs from the API server watch stream (or local static pod manifests in `/etc/kubernetes/manifests/`).
2. **Timer Channel:** Evaluates periodic synchronization every `sync-frequency` (default: 10 seconds).
3. **PLEG (Pod Lifecycle Event Generator):** Periodically polls the container runtime to inspect actual container states, translating runtime events into high-level Kubernetes Pod status transitions.

### 3.2 `kube-proxy`: Service Routing & Virtual IP Engine

`kube-proxy` runs on every worker node and implements the **Service abstraction**. When a Pod accesses a Service's virtual `ClusterIP` (e.g., `10.96.0.10:80`), `kube-proxy` ensures traffic is routed to one of the backend Pod endpoints (e.g., `10.244.1.15:8080`).

#### The Three Operating Modes:
1. **User Space (Legacy):** Traffic enters kernel, is proxied out to userspace `kube-proxy` daemon, and back into kernel. Abysmal performance ($\approx 5,000$ packets/sec ceiling).
2. **iptables (Standard Default):** `kube-proxy` programs Linux Netfilter chains (`KUBE-SERVICES`, `KUBE-SVC-*`, `KUBE-SEP-*`). Performs DNAT (Destination NAT) with random probability weighting:
   ```bash
   -A KUBE-SVC-ABC -m statistic --mode random --probability 0.3333 -j KUBE-SEP-1
   -A KUBE-SVC-ABC -m statistic --mode random --probability 0.5000 -j KUBE-SEP-2
   -A KUBE-SVC-ABC -j KUBE-SEP-3
   ```
   *Limitation:* Sequential chain traversal causes $\mathcal{O}(N)$ lookup degradation at scale ($> 10,000$ services).
3. **IPVS (High Performance):** Uses the Linux kernel IP Virtual Server module. Stores service endpoints in indexed hash tables, achieving $\mathcal{O}(1)$ lookup speed and supporting advanced load balancing algorithms (Least Connection, Round Robin, Source Hashing).

## 4. Production Failure Modes & Troubleshooting

### Scenario 1: `etcd` Disk Fsync Latency Spike
- **Symptom:** `kube-apiserver` returns `HTTP 500 Internal Server Error`, leader election fails, heartbeat timeouts trigger false node evictions.
- **Root Cause:** `etcd` writes WAL commits using synchronous `fsync()`. If disk write latency exceeds $10\text{ms}$ (e.g., on shared spinning disks or throttled cloud volumes), the Raft leader times out, triggering endless leader elections.
- **Resolution:** Dedicate high-IOPS NVMe drives exclusively to `etcd`. Mount `etcd` storage with `noatime` and configure `etcd` process priority using `ionice -c2 -n0`.

### Scenario 2: Node OOM-Killer Kills `kubelet`
- **Symptom:** Node abruptly switches to `NotReady`, running workloads continue running but cannot be modified or monitored.
- **Root Cause:** Workload Pods without memory limits exhausted system RAM, forcing the kernel OOM-killer to terminate the `kubelet` process.
- **Resolution:** Configure explicit system reservations in `kubeletConfiguration`:
  ```yaml
  systemReserved:
    cpu: "500m"
    memory: "1Gi"
  kubeReserved:
    cpu: "500m"
    memory: "1Gi"
  evictionHard:
    memory.available: "500Mi"
    nodefs.available: "10%"
  ```
