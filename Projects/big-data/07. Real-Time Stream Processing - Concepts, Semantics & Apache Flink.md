# Chapter 07: Real-Time Stream Processing — Concepts, Semantics & Apache Flink

> "In the real world, data is not bounded. Data is generated as an infinite, continuous stream of events. Batch processing is simply an arbitrary, artificial slicing of unbounded data. To process reality as it occurs, one must embrace true event-driven stream processing."  
> — *Tyler Akidau et al., Streaming Systems*

---

## 🌊 1. The Stream Processing Paradigm: Micro-Batch vs. Native Streaming

How should a distributed system process an unbounded stream of data?

```text
===================================================================================================
                       MICRO-BATCHING VS. NATIVE EVENT-DRIVEN STREAMING
===================================================================================================

 [ 1. Micro-Batching (Apache Spark Streaming) ]
 Continuous Inbound Stream ──► Accumulates in buffer for 500ms ──► Dispatches Batch Spark Job!
 - Latency: Sub-second (100ms - 500ms).
 - High throughput; reuses existing Spark batch SQL/Catalyst engine.
 ⚠️ Artificial time boundaries: Events happening across micro-batch edges require complex state joins!

 [ 2. Native Event-Driven Streaming (Apache Flink / Kafka Streams) ]
 Event Arrival ──► Immediately processed through streaming DAG pipeline! (Latency < 5 milliseconds!)
 - True continuous processing: Processes events one by one or in micro-buffers as they arrive.
 - Native Event-Time processing and continuous stateful operators.
```

## ⏰ 2. The Three Time Domains & The Watermark Concept

A fundamental challenge of distributed streaming is that **the order in which events occur is not the order in which they arrive at your cluster**.

```text
===================================================================================================
                                       THE THREE TIME DOMAINS
===================================================================================================

  1. EVENT TIME:      The timestamp embedded inside the event by the client device/sensor.
                      (e.g., Mobile game tap at 14:02:01.450 UTC).
  2. INGESTION TIME:  The timestamp assigned when the event enters Kafka.
  3. PROCESSING TIME: The wall-clock time of the Flink TaskManager CPU processing the event.
```

```text
 Event Time:     14:00:01     14:00:02     14:00:03     14:00:04 (Traverses subway tunnel...)
                    │            │                         │
 Processing Time: 14:00:01    14:00:03                  14:00:04      14:00:15 (Arrives 11s late!)
```

### 2.1 Watermarks: Measuring Stream Completeness
How does a windowing operator computing a 1-minute window ($[14:00, 14:01)$) know when all events for that window have arrived?

A **Watermark** $W(t)$ is a control signal injected directly into the data stream carrying a timestamp $t$:
> *"A Watermark $W(t)$ asserts: We have observed all events up to Event Time $t$. No future events with timestamp $\le t$ will ever arrive."*

When Watermark $W(14:01:00)$ arrives at an operator, the operator safely **closes the window, computes the aggregation, and emits the result**!

## 🪟 3. Windowing Strategies

```text
===================================================================================================
                                      STREAM WINDOWING TYPES
===================================================================================================

 [ 1. Tumbling Window (Fixed, Non-Overlapping) ]
 [ 12:00 to 12:05 ] [ 12:05 to 12:10 ] [ 12:10 to 12:15 ]
 Ideal for: 5-minute sales summaries.

 [ 2. Sliding / Hopping Window (Fixed Length, Overlapping) ]
 [ 12:00 to 12:10 ]
        [ 12:05 to 12:15 ]
               [ 12:10 to 12:20 ]
 Ideal for: Moving averages ("Compute average CPU load over past 10 minutes, refreshed every 5 mins").

 [ 3. Session Window (Dynamic, Inactivity Gap Timeout) ]
 [ Events... ] [ Gap: 30 mins ] ──► Window Closes!
 Ideal for: Tracking user web browsing sessions.
```

## 🛡️ 4. Processing Delivery Semantics: Achieving Exactly-Once

1. **At-Most-Once:** Drops data on failure. Zero duplicates, but guarantees data loss. (Acceptable only for low-value metrics).
2. **At-Least-Once:** Retries on failure. Zero data loss, but introduces **duplicate records** when network acknowledgments drop.
3. **Exactly-Once Semantics (EOS):** The ultimate distributed goal. Guarantees that every event mutates the internal system state **precisely once**, even under arbitrary worker crashes!

## ⚡ 5. Apache Flink Architecture & The Chandy-Lamport Snapshot

Flink achieves high-throughput exactly-once state consistency using **Asynchronous Barrier Snapshotting (ABS)** (derived from the classic Chandy-Lamport distributed snapshot algorithm).

```text
===================================================================================================
                         ASYNCHRONOUS BARRIER SNAPSHOTTING IN FLINK
===================================================================================================

  Data Stream Flow: ──► [ Event ] [ Event ] [ BARRIER N ] [ Event ] [ Event ] ──►
                                                   │
                                                   ▼
                                         [ Operator TaskSlot ]
                                         - Emits Barrier N downstream
                                         - Asynchronously writes current state to S3!
                                         - CONTINUES PROCESSING EVENTS IMMEDIATELY!
                                         - Zero pipeline pausing!
```

### 5.1 How Checkpoint Barriers Guarantee Exactly-Once
1. The Flink JobManager periodically injects a **Checkpoint Barrier** into all source streams (Kafka topics).
2. The barrier flows naturally through the streaming DAG interleaved with regular records.
3. When an operator receives Barrier $N$, it snapshots its internal state (window aggregates, counts) asynchronously to persistent storage (AWS S3).
4. **On Node Crash:** Flink resets the streaming topology to Checkpoint $N$, rewinds Kafka partition offsets to Barrier $N$, and replays data. Because the internal state was saved precisely at Barrier $N$, **the recovered state is 100% mathematically identical to an uninterrupted run**!

## 🗄️ 6. Flink State Backends: Memory vs. RocksDB

| State Backend | Storage Mechanism | Maximum State Size | Latency Profile |
| :--- | :--- | :--- | :--- |
| **`HashMapStateBackend`** | Stores state as Java heap objects in TaskManager RAM. | Bounded by TaskManager JVM heap (tens of gigabytes). | Sub-microsecond reads and writes. Risk of JVM GC pauses. |
| **`EmbeddedRocksDBStateBackend`** | Stores state in an embedded **RocksDB LSM-Tree** in local SSD disk/off-heap memory. | Virtually unlimited (bounded only by local disk, terabytes per node). | Slightly higher latency (SSTable lookups), but completely immune to JVM GC stalls! |
