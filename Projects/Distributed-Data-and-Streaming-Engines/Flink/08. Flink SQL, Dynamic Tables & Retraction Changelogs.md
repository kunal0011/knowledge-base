# Chapter 08: Flink SQL, Dynamic Tables & Retraction Changelogs

> "Continuous queries on dynamic tables evaluate an infinite stream of mutations: every insert, update, and retraction produces a living query result that updates with mathematical precision."  
> — *Fabian Hueske & Vasiliki Kalavri, Stream Processing with Apache Flink*

---

## 1. Canonical Motivation & Theoretical Foundation

While the DataStream API provides low-level control over state and timers, developing and maintaining complex streaming pipelines in Java requires substantial boilerplate. Furthermore, data analysts, analytics engineers, and data scientists operate primarily in SQL.

However, executing ANSI SQL over unbounded data streams requires resolving a fundamental paradox:
- Standard SQL tables are static and bounded.
- Data streams are dynamic, continuous, and infinite.

Flink bridges this divide through the concept of **Dynamic Tables** and **Continuous Queries**:
1. **Dynamic Tables:** A table that evolves continuously over time as new events arrive.
2. **Continuous Queries:** A query that never terminates. As new records enter the dynamic input table, the continuous query continuously computes and emits updates to an output dynamic table.
3. **Changelog Materialization:** To project dynamic output tables into external storage systems (e.g. Kafka, Elasticsearch, JDBC), Flink converts table mutations into a stream of **Changelog Events** featuring insertions, updates, and retractions.

## 2. Underlying Runtime, Memory & Execution Architecture

### Dynamic Tables & Continuous Query Mechanics

```
               Continuous Event Stream
                          │
                          ▼ (Append)
               ┌───────────────────────┐
               │ Dynamic Input Table   │
               └──────────┬────────────┘
                          │
                          ▼ (Continuous Query: SELECT key, COUNT(*) GROUP BY key)
               ┌───────────────────────┐
               │ Dynamic Output Table  │
               └──────────┬────────────┘
                          │
                          ▼ (Changelog Encoding: Retractions / Updates)
        +I[K1, 1] ──> -U[K1, 1] ──> +U[K1, 2] ──> -D[K2, 1]
```

### The Retraction Mechanism: RowKind Encodings

When a continuous query aggregates data (e.g., `COUNT(*) GROUP BY userId`), a single incoming event modifies a previously emitted result. Flink represents these modifications using four distinct **RowKind** operations:

| RowKind | Symbol | Name | Description |
| :--- | :--- | :--- | :--- |
| **`INSERT`** | `+I` | Insert | A newly created row inserted into the dynamic table. |
| **`UPDATE_BEFORE`** | `-U` | Update Before | Retracts/cancels the previous version of a row before an update. |
| **`UPDATE_AFTER`** | `+U` | Update After | Emits the new state of the row following an update. |
| **`DELETE`** | `-D` | Delete | Retracts/removes a row permanently from the dynamic table. |

#### Changelog Modes Across Sinks
- **Append-Only Sinks:** Can only ingest `+I` events (e.g., standard Kafka topics, file systems). Attempting to send retraction streams (`-U`, `+U`, `-D`) to an append-only sink throws a `TableException`.
- **Upsert Sinks:** Ingest `+I`, `+U`, and `-D` events keyed by a primary key (e.g., `upsert-kafka`, Elasticsearch, JDBC tables with primary keys).
- **Retraction Sinks:** Native sinks that accept full changelog streams with explicit `-U` and `+U` pairs.

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Modern Window Table-Valued Functions (Window TVFs)

In modern Flink SQL (1.13+), legacy `GROUP BY TUMBLE(...)` syntax is replaced by standardized **Window Table-Valued Functions (Window TVFs)** based on SQL:2016 standards:
- `TUMBLE`: Non-overlapping tumbling windows.
- `HOP`: Sliding windows.
- `CUMULATE`: Cumulative windows (e.g. tracking hourly running totals across a day).

```sql
SELECT 
    window_start, 
    window_end, 
    customerId, 
    SUM(amount) AS total_spend
FROM TABLE(
    TUMBLE(TABLE Orders, DESCRIPTOR(order_time), INTERVAL '10' MINUTE)
)
GROUP BY window_start, window_end, customerId;
```

## 5. Annotated Code Implementations & Execution Traces

### End-to-End Flink SQL Pipeline: Kafka Ingestion, Window TVF Aggregation & Upsert-Kafka Sink

The following complete Java program configures a Flink `TableEnvironment`, defines source and sink DDLs with watermarks, and executes a continuous streaming aggregation:

```java
package com.knowledgebase.engines.flink;

import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.table.api.EnvironmentSettings;
import org.apache.flink.table.api.bridge.java.StreamTableEnvironment;

public class FlinkSqlWindowTvfJob {

    public static void main(String[] args) {
        // Step 1: Initialize Streaming Table Environment
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        EnvironmentSettings settings = EnvironmentSettings.newInstance().inStreamingMode().build();
        StreamTableEnvironment tableEnv = StreamTableEnvironment.create(env, settings);

        // Step 2: Set Idle State Retention (TTL for unbounded state joins/aggregations)
        tableEnv.getConfig().getConfiguration().setString("table.exec.state.ttl", "1 h");

        // Step 3: Define Source DDL (Kafka Ingestion with Event-Time Watermark)
        tableEnv.executeSql(
            "CREATE TABLE OrdersSource (" +
            "  order_id STRING," +
            "  customer_id STRING," +
            "  order_amount DECIMAL(10, 2)," +
            "  order_epoch_ms BIGINT," +
            "  order_time AS TO_TIMESTAMP_LTZ(order_epoch_ms, 3)," +
            "  WATERMARK FOR order_time AS order_time - INTERVAL '5' SECOND" +
            ") WITH (" +
            "  'connector' = 'kafka'," +
            "  'topic' = 'retail.orders.raw'," +
            "  'properties.bootstrap.servers' = 'broker1:9092,broker2:9092'," +
            "  'properties.group.id' = 'flink-sql-orders-consumer'," +
            "  'scan.startup.mode' = 'latest-offset'," +
            "  'format' = 'json'" +
            ")"
        );

        // Step 4: Define Sink DDL (Upsert Kafka Sink for Aggregated Results)
        tableEnv.executeSql(
            "CREATE TABLE WindowedCustomerSpendSink (" +
            "  customer_id STRING," +
            "  window_start TIMESTAMP(3)," +
            "  window_end TIMESTAMP(3)," +
            "  total_orders BIGINT," +
            "  total_amount DECIMAL(12, 2)," +
            "  PRIMARY KEY (customer_id, window_start, window_end) NOT ENFORCED" +
            ") WITH (" +
            "  'connector' = 'upsert-kafka'," +
            "  'topic' = 'retail.orders.windowed-spend'," +
            "  'properties.bootstrap.servers' = 'broker1:9092,broker2:9092'," +
            "  'key.format' = 'json'," +
            "  'value.format' = 'json'" +
            ")"
        );

        // Step 5: Execute Continuous Query using Modern Window Table-Valued Function (TUMBLE TVF)
        tableEnv.executeSql(
            "INSERT INTO WindowedCustomerSpendSink " +
            "SELECT " +
            "  customer_id," +
            "  window_start," +
            "  window_end," +
            "  COUNT(order_id) AS total_orders," +
            "  SUM(order_amount) AS total_amount " +
            "FROM TABLE(" +
            "  TUMBLE(TABLE OrdersSource, DESCRIPTOR(order_time), INTERVAL '5' MINUTE)" +
            ") " +
            "GROUP BY customer_id, window_start, window_end"
        );

        System.out.println("Continuous SQL Streaming Query submitted successfully.");
    }
}
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. The Append-Only Sink Retraction Crash
- **Antipattern:** Executing an aggregation query (e.g. `SELECT key, COUNT(*) FROM t GROUP BY key`) and directing the result into a standard `'connector' = 'kafka'` table.
- **System Consequence:** Standard Kafka connectors only support append streams. When the aggregation emits updates (`-U` / `+U`), Flink immediately throws a fatal runtime exception:  
  `TableException: AppendStreamTableSink doesn't support consuming update and delete changes`.
- **Fix:** Use `'connector' = 'upsert-kafka'` and define a primary key (`PRIMARY KEY (key) NOT ENFORCED`), or write to an upsert-compatible datastore (Elasticsearch, JDBC).

### 2. The Unset `table.exec.state.ttl` State Leak
- **Antipattern:** Running non-windowed aggregations or joins in Flink SQL without configuring state TTL.
- **System Consequence:** In queries like `SELECT customer_id, SUM(amount) FROM Orders GROUP BY customer_id`, Flink keeps state for *every customer ID forever*. Over months of operation, dead customer keys exhaust RocksDB disk storage.
- **Fix:** Always set state retention in configuration:
  ```java
  tableEnv.getConfig().getConfiguration().setString("table.exec.state.ttl", "24 h");
  ```

### 3. Missing `NOT ENFORCED` on DDL Primary Keys
- **Antipattern:** Defining primary keys in Flink DDL assuming Flink will validate constraints and reject duplicate inserts.
- **System Consequence:** Flink does not enforce primary key uniqueness on ingestion. The `PRIMARY KEY ... NOT ENFORCED` clause serves only as an informational hint to the query optimizer for retraction and upsert generation.
- **Fix:** Understand that primary key constraints in Flink DDL are declarative metadata for downstream upsert connectors, not transactional write constraints.
