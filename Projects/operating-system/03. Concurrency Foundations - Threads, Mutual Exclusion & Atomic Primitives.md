# Chapter 03: Concurrency Foundations — Threads, Mutual Exclusion & Atomic Primitives

> "A race condition occurs when the output of a program depends on the non-deterministic interleaving of threads executing concurrently. To prevent data corruption, we must enforce mutual exclusion over critical sections of code."  
> — *Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau, Operating Systems: Three Easy Pieces (OSTEP)*

## 🧵 1. The Thread Abstraction & Memory Topology

While a process is an isolated execution environment possessing its own private virtual memory space and file descriptor table, a **Thread** (Lightweight Process or LWP) represents an independent stream of instructions executing within the **same** address space.

```text
===================================================================================================
                               MULTI-THREADED MEMORY TOPOLOGY
===================================================================================================

                Single Process Virtual Address Space
  0xFFFFFFFFFFFFFFFF ┌─────────────────────────────────────────────────────────┐
                     │          Shared Heap (malloc / new allocations)         │
                     ├─────────────────────────────────────────────────────────┤
                     │          Shared Global & Static Variables (.data, .bss) │
                     ├─────────────────────────────────────────────────────────┤
                     │          Shared Code / Text Segment (.text)             │
                     ├─────────────────────────────────────────────────────────┤
                     │          Shared Open File Descriptors, Sockets, Pipes   │
                     ├─────────────────────────────────────────────────────────┤
                     │  Thread 1 Private Stack    Thread 2 Private Stack       │
                     │  (Local vars, ret addr)    (Local vars, ret addr)       │
                     │         │                            │                  │
                     │         ▼                            ▼                  │
  0x0000000000400000 └─────────────────────────────────────────────────────────┘
```

### 1.1 Thread Models: 1:1 Kernel Threads vs. M:N Green Threads
- **1:1 Model (Linux NPTL / POSIX `pthreads`):** Each user-space thread maps directly to a kernel `task_struct` created via the `clone()` system call with `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND`. The kernel scheduler preempts and distributes threads across all physical CPU cores natively.
- **M:N Model (Go Goroutines, Erlang Processes):** Many lightweight user-space green threads run on a smaller pool of kernel threads. Switching between green threads avoids kernel traps, enabling millions of concurrent routines with minimal RAM footprint ($2\text{ KB}$ initial stacks).

## 💥 2. The Anatomy of a Race Condition

Consider two concurrent threads executing a seemingly trivial statement: `counter++`. At the hardware architecture level, high-level code compiles into multiple machine instructions:

```nasm
; Assembly instructions for counter++
movl counter(%rip), %eax    ; 1. LOAD: Read counter from RAM into CPU register %eax
addl $1, %eax              ; 2. MODIFY: Increment register %eax
movl %eax, counter(%rip)    ; 3. STORE: Write %eax back to RAM
```

If Thread 1 is preempted by a timer interrupt between step 1 and step 3, an interleaving disaster occurs:

```text
===================================================================================================
                                RACE CONDITION INTERLEAVING TIMELINE
===================================================================================================

  Initial State: counter = 50
  
  Time   Thread 1                                Thread 2                           counter in RAM
   │
   1     movl counter, %eax (eax = 50)                                                    50
   2     addl $1, %eax      (eax = 51)                                                    50
   3     [ PREEMPTED BY TIMER INTERRUPT! ]
   4                                             movl counter, %eax (eax = 50)            50
   5                                             addl $1, %eax      (eax = 51)            50
   6                                             movl %eax, counter (writes 51)           51
   7     [ SCHEDULED BACK TO CPU ]
   8     movl %eax, counter (writes 51!)                                                  51!
   ▼
   Result: Two increments executed, but counter only increased by 1! (Lost Update Anomaly)
```

To prevent this, a piece of code that accesses shared state must be treated as a **Critical Section** and executed with **Mutual Exclusion**.

## 🔒 3. Criteria for Sound Mutual Exclusion

Any correct locking mechanism must satisfy three foundational computer science criteria:
1. **Mutual Exclusion:** At most one thread can execute inside the critical section at any instant.
2. **Progress (Liveness):** If no thread is in the critical section and some threads want to enter, only those threads not running in their remainder sections can participate in the selection, and the selection cannot be postponed indefinitely.
3. **Bounded Waiting (Starvation-Freedom):** There must be a bound on the number of times other threads can enter the critical section after a thread has requested entry before its request is granted.

## ⚙️ 4. Hardware Atomic Primitives

Software-only algorithms (like Peterson's Algorithm) fail on modern multi-core processors because modern CPUs and optimizing compilers execute instructions out-of-order and use speculative memory write buffers. True mutual exclusion requires **Hardware Atomic Instructions**.

### 4.1 Test-And-Set (`xchg`)
Atomically swaps the value of a memory address with a new value and returns the old value:
```c
int TestAndSet(int *ptr, int new) {
    int old = *ptr; // Atomic hardware bus transaction
    *ptr = new;
    return old;
}
```

### 4.2 Compare-And-Swap (CAS / `CMPXCHG`)
Tests if the value at address `ptr` equals `expected`. If true, it updates `ptr` to `new_val`. Regardless, it returns the actual value found:
```c
int CompareAndSwap(int *ptr, int expected, int new_val) {
    int original = *ptr;
    if (original == expected) {
        *ptr = new_val;
    }
    return original;
}
```

On x86 architectures, CAS is implemented via the `lock cmpxchg` assembly instruction. The `lock` prefix asserts a hardware lock signal on the CPU memory bus (or locks the specific cache line via the cache coherence protocol), guaranteeing that no other core can read or write that memory address concurrently.

## 🔄 5. Building Spinlocks & The Ticket Lock (Fairness)

### 5.1 Simple Spinlock Using CAS
```c
typedef struct {
    int flag;
} spinlock_t;

void spin_init(spinlock_t *lock) {
    lock->flag = 0;
}

void spin_lock(spinlock_t *lock) {
    // Spin-wait (busy-wait) until CAS successfully changes 0 -> 1
    while (__sync_val_compare_and_swap(&lock->flag, 0, 1) == 1) {
        #if defined(__x86_64__)
        __builtin_ia32_pause(); // Emits PAUSE instruction to prevent pipeline stalls
        #endif
    }
}

void spin_unlock(spinlock_t *lock) {
    __sync_synchronize(); // Full Memory Barrier
    lock->flag = 0;
}
```

### 5.2 The Fairness Problem & Ticket Locks
A simple spinlock does not guarantee bounded waiting; an unlucky thread can spin forever while other threads repeatedly acquire the lock. 

The **Ticket Lock** (invented by Mellor-Crummey and Scott) enforces absolute FIFO fairness using `FetchAndAdd`:

```c
typedef struct {
    int ticket;
    int turn;
} ticket_lock_t;

void ticket_init(ticket_lock_t *lock) {
    lock->ticket = 0;
    lock->turn = 0;
}

void ticket_acquire(ticket_lock_t *lock) {
    // Atomically draw a ticket number
    int my_turn = __sync_fetch_and_add(&lock->ticket, 1);
    while (lock->turn != my_turn) {
        #if defined(__x86_64__)
        __builtin_ia32_pause();
        #endif
    }
}

void ticket_release(ticket_lock_t *lock) {
    __sync_synchronize();
    lock->turn++; // Advance to the next ticket holder in line
}
```

## ⚡ 6. Cache Coherence & False Sharing

On modern symmetric multiprocessing (SMP) systems, every CPU core has its own private L1/L2 caches. Hardware implements the **MESI Protocol** (Modified, Exclusive, Shared, Invalid) to ensure a unified view of RAM.

```text
===================================================================================================
                                THE FALSE SHARING PITFALL
===================================================================================================

  CPU Core 1                                                      CPU Core 2
  ┌─────────────────────────────────┐                             ┌─────────────────────────────────┐
  │ Modifies thread1_counter (8 B)  │                             │ Modifies thread2_counter (8 B)  │
  └────────────────┬────────────────┘                             └────────────────┬────────────────┘
                   │                                                               │
                   ▼                                                               ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
  │                         SINGLE 64-BYTE HARDWARE CACHE LINE IN L1 CACHE                          │
  │  [ thread1_counter: 8 B ] [ thread2_counter: 8 B ] [ Unused Padding: 48 B                      │
  └─────────────────────────────────────────────────────────────────────────────────────────────────┘
                                                   │
  Every write by Core 1 invalidates Core 2's entire cache line via MESI bus traffic!
  The cores spend 95% of their time ping-ponging the cache line across the interconnect!
```

### Production Solution: Cache-Line Padding
```c
// Force variables onto distinct 64-byte hardware cache lines
struct alignas(64) thread_stat {
    uint64_t counter;
};
```
