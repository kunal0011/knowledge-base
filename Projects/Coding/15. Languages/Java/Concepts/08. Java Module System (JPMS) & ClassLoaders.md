# Java Concepts: Java Module System (JPMS) & ClassLoaders

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapter 12  
- *Project Jigsaw (JEP 200 & JEP 261)*  

---

## 1. Theoretical Motivation: Escaping "Classpath Hell"

Prior to Java 9, Java's modular boundary was the **JAR file**. However, JARs on the classpath suffered from three severe architectural flaws:
1. **No Strong Encapsulation:** Any class declared `public` inside a JAR was visible to every other class on the entire classpath, making it impossible to hide internal implementation libraries.
2. **Brittle Runtime Discovery:** Missing dependencies were not detected at JVM startup; they failed unpredictably at runtime with `NoClassDefFoundError` when code first attempted to execute the missing class.
3. **Monolithic JDK:** Every deployment, regardless of size, was forced to bundle the entire monolithic `rt.jar` runtime ($\approx 60\text{ MB}$).

Project Jigsaw (JPMS) introduced **Modules**—named, self-describing collections of code and data with explicit dependency boundaries.

## 2. Underlying Architecture: `module-info.java` Directives

A module is declared by placing a `module-info.java` file at the root of the source tree.

```
                              [ module com.finance.engine ]
                                            |
            +-------------------------------+-------------------------------+
            |                               |                               |
    requires com.common;           exports com.finance.api;        opens com.finance.model
 (Explicit Dependency Inward)     (Public API Exposed Outward)     (Reflection Access for ORMs)
```

### 2.1 The Master Directives Matrix:
| Directive | Syntax | Effect |
|:---|:---|:---|
| **`requires`** | `requires <mod>;` | Declares that this module depends on another module at compile and runtime. |
| **`requires transitive`**| `requires transitive <mod>;` | **Implied Readability:** Any module that reads this module automatically reads `<mod>`. |
| **`requires static`** | `requires static <mod>;` | Compile-time only dependency (e.g., compile-time code annotations). |
| **`exports`** | `exports <pkg>;` | Exposes public types in `<pkg>` to all modules. |
| **`exports to`** | `exports <pkg> to <m1>, <m2>;` | **Qualified Export:** Restricts visibility to specified friend modules. |
| **`opens`** | `opens <pkg>;` | Permits **deep reflection** (`setAccessible(true)`) on all classes/fields in package. |
| **`opens to`** | `opens <pkg> to <framework>;` | Permits reflection strictly for a specific framework (e.g., `to spring.core`). |
| **`uses`** | `uses <ServiceInter>;` | Declares consumer of a service loaded via `ServiceLoader`. |
| **`provides with`** | `provides <Svc> with <Impl>;` | Registers a concrete service provider implementation. |

```java
// Example: module-info.java
module com.enterprise.banking {
    requires transitive java.sql;      // Callers also get java.sql access
    requires static lombok;             // Only needed during compilation

    exports com.enterprise.banking.api; // Exposed public package
    opens com.enterprise.banking.model to org.hibernate.orm.core; // Safe reflection!

    uses com.enterprise.banking.spi.PaymentProvider; // Service consumer
}
```

## 3. The Three Types of Modules in JPMS

```
+-----------------------------------------------------------------------------------------+
|                                    MODULE CATEGORIES                                    |
+-----------------------+-----------------------+--------------------+--------------------+
| Module Category       | Location              | Has module-info?   | Module Name        |
+-----------------------+-----------------------+--------------------+--------------------+
| 1. Named Module       | Module-Path           | YES                | Declared in info   |
| 2. Automatic Module   | Module-Path           | NO (Legacy JAR)    | Derived from JAR   |
| 3. Unnamed Module     | Class-Path            | NO (Legacy JAR)    | Unnamed            |
+-----------------------+-----------------------+--------------------+--------------------+
```

### 3.1 Automatic Modules (Bridging the Migration):
When a legacy Java 8 JAR (without a `module-info.class`) is placed on the **module-path**:
- It becomes an **Automatic Module**.
- Its name is derived from the JAR filename (e.g., `guava-30.1.jar` becomes `guava`).
- It **exports all of its packages** and reads all other modules on the module-path.

## 4. ClassLoader Architecture & Parent-Delegation

Classes are loaded into HotSpot memory dynamically by the **ClassLoader Subsystem**:

```
                       [ Bootstrap ClassLoader ]
                      (Native C/C++ - Core java.base)
                                   ^
                                   | (Parent delegation)
                       [ Platform ClassLoader ]
                      (Formerly Extension ClassLoader)
                                   ^
                                   | (Parent delegation)
                      [ Application ClassLoader ]
                     (Loads user classpath / module-path)
                                   ^
                                   | (Parent delegation)
                      [ Custom ClassLoaders ]
                     (Tomcat, OSGi, Plugin Engines)
```

### 4.1 The Parent-Delegation Protocol
When a ClassLoader is requested to load a class:
1. It delegates the search to its parent ClassLoader **first**.
2. The parent delegates to its parent, cascading up to the Bootstrap ClassLoader.
3. If the parent cannot find the class, the child ClassLoader finally attempts to load it from its own repository via `findClass()`.

### Why This Invariant is Critical for Security:
Parent delegation prevents malicious user code from overriding core Java classes. If a rogue library contains a fraudulent `java.lang.SecurityManager`, the Application ClassLoader delegates up to the Bootstrap ClassLoader, which loads the genuine JVM runtime class and ignores the malicious replacement.

## 5. Authoritative Gotchas & Traps (OCP Standard)

### 5.1 The Split Package Disaster
```
Module A contains package: com.app.utils
Module B contains package: com.app.utils
```
**The Rule:** In JPMS, **no two modules are permitted to contain the same package**, even if the classes inside that package have completely different names! The Java compiler and runtime will reject this with:
`Error: package com.app.utils exists in another module: Module A`.

### 5.2 Cyclic Module Dependencies
Module A requires Module B, and Module B requires Module A:
```java
// module-info.java (Module A):
module A { requires B; }

// module-info.java (Module B):
module B { requires A; }
```
**Compilation Result:** `Error: cyclic dependence involving module A and module B`.
Unlike packages, cyclic dependencies between modules are **strictly forbidden**.

### 5.3 The `InaccessibleObjectException` Reflection Crash
In Java 9+, calling `field.setAccessible(true)` across module boundaries on a private field in an un-opened package triggers:
`java.lang.reflect.InaccessibleObjectException: Unable to make field accessible: module A does not "opens package" to module B`.  
**The Solution:** Add an `opens <package> to <framework>;` directive in the target module.

---

## 6. Actionable Summary Checklist

- [x] Use `requires transitive` when a module's public API returns types declared in an upstream dependency.
- [x] Use `opens` strictly for packages that require runtime deep reflection by frameworks (Spring, Hibernate, Jackson).
- [x] Never split packages across multiple modules; each package must belong uniquely to one module.
- [x] Understand that the ClassLoader **Parent-Delegation Model** protects JVM integrity by ensuring core classes (`java.lang.*`) are always loaded by the Bootstrap ClassLoader.
- [x] Place legacy JARs on the module-path to treat them as **Automatic Modules** during incremental JPMS migrations.
