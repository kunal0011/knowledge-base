## 🗣️ 1. Inter-Process Communication (IPC) Mechanisms

Because processes execute in strictly isolated virtual address spaces, the operating system must provide explicit communication channels:

```text
===================================================================================================
                                       IPC MECHANISM SPECTRUM
===================================================================================================

  Mechanism           Throughput   Kernel Crossings   Persistence   Topology
  ─────────────────────────────────────────────────────────────────────────────────────────────
  Anonymous Pipes     Medium       2 (write/read)     Process       Unidirectional (Parent/Child)
  Named Pipes (FIFO)  Medium       2 (write/read)     Filesystem    Unidirectional (Any process)
  Unix Domain Sockets High         2 (send/recv)      Filesystem    Bidirectional (Client/Server)
  POSIX Shared Memory Maximum      0 (Zero-Copy!)     Memory/Kernel Direct Memory Mapping
```

### 1.1 Unix Domain Sockets & File Descriptor Passing (`SCM_RIGHTS`)
Unlike TCP loopback (`127.0.0.1`), **Unix Domain Sockets (`AF_UNIX`)** bypass the entire TCP/IP network stack (checksumming, packetization, flow control), transferring raw memory buffers directly across processes.

Furthermore, Unix Domain Sockets possess a unique superpower: **Passing File Descriptors**. Using `sendmsg()` with `SCM_RIGHTS`, a parent or privileged process can hand an open file descriptor, database socket, or GPU handle directly to an unprivileged child process:

```text
===================================================================================================
                             PASSING FILE DESCRIPTORS VIA SCM_RIGHTS
===================================================================================================

  Process A (Privileged Root)                        Process B (Unprivileged Worker)
  ┌───────────────────────────────┐                  ┌───────────────────────────────┐
  │ 1. Opens /etc/shadow (fd = 3) │                  │ Waiting on Unix Socket...     │
  │ 2. Sends fd via SCM_RIGHTS    ├─[ AF_UNIX Sock ]─► Receives message:            │
  └───────────────────────────────┘                  │ Kernel clones struct file*    │
                                                     │ and installs it as new fd = 7!│
                                                     │ Can read /etc/shadow directly!│
                                                     └───────────────────────────────┘
```

## ⚡ 2. Unix Signals & Async-Signal Safety

A **Signal** is an asynchronous hardware or software interrupt delivered directly to a process by the kernel.

### 2.1 Critical Standard Signals
- **`SIGINT` (2):** Terminal interrupt (Ctrl+C). Default action: terminate.
- **`SIGKILL` (9):** Immediate, uncatchable, unignorable kernel termination.
- **`SIGSEGV` (11):** Invalid memory reference / segmentation violation.
- **`SIGTERM` (15):** Graceful termination request (can be trapped and handled).
- **`SIGCHLD` (17):** Sent to parent process when a child terminates or stops (prevents zombies).

### 2.2 The Trap of Async-Signal Safety
When a signal is delivered, the OS abruptly pauses the process's current instruction stream and immediately executes the registered signal handler. 

```text
===================================================================================================
                             THE SIGNAL HANDLER DEADLOCK DISASTER
===================================================================================================

  1. Main thread calls malloc()
     - malloc() acquires internal heap mutex lock: mutex_lock(&malloc_lock)
  2. Operating System delivers SIGINT!
     - Main thread pauses instruction stream INSIDE malloc()!
  3. Signal handler executes:
     - Buggy handler calls printf() or malloc()
     - printf() calls malloc() -> Attempts to acquire mutex_lock(&malloc_lock)!
  4. DEADLOCK!
     - Thread deadlocks with ITSELF! Process hangs forever!
```

> [!CAUTION]
> **Async-Signal-Safe Rule:** Inside a signal handler, you must **never** call non-reentrant functions (e.g., `printf`, `malloc`, `free`, `pthread_mutex_lock`). You may only modify variables of type `volatile sig_atomic_t` or invoke async-signal-safe syscalls (`write`, `_exit`).

## 🔄 3. The Evolution of I/O Multiplexing: `select` to `epoll`

When building servers that handle tens of thousands of concurrent connections (the **C10K Problem**), spawning one thread per connection exhausts memory. Servers must use **I/O Multiplexing**:

```text
===================================================================================================
                               I/O MULTIPLEXING COMPLEXITY EVOLUTION
===================================================================================================

  API        Data Structure          Algorithm Complexity   Max Connections
  ─────────────────────────────────────────────────────────────────────────────────────────────
  select()   Fixed-size Bitmask      O(N) linear scan       FD_SETSIZE (Default 1024)
  poll()     Array of pollfd         O(N) linear scan       Unlimited (Bounded by open files)
  epoll()    Red-Black Tree + List   O(1) event-driven!     Millions of sockets!
```

### 3.1 `epoll` Internals
`epoll` solves the $\mathcal{O}(N)$ bottleneck through two kernel data structures:
1. **Red-Black Tree:** Stores the set of file descriptors being monitored. Adding, modifying, or removing a descriptor takes $\mathcal{O}(\log N)$.
2. **Ready List (Doubly Linked List):** When a network packet arrives on a socket, the NIC hardware interrupt invokes the kernel socket callback, which places the socket directly onto `epoll`'s ready list.
3. When the application calls `epoll_wait()`, the kernel returns only the file descriptors in the ready list in $\mathcal{O}(1)$ time!

## 🚀 4. Linux `io_uring`: The Zero-Syscall Async I/O Revolution

Even with `epoll`, handling an I/O event requires two system calls per connection: `epoll_wait()` to get the event, followed by `read()` or `write()` to transfer data. At $2,000,000\text{ IOPS}$, system call traps (`sys_enter` / `sys_exit`) consume $> 30\%$ of total CPU time.

Created by Jens Axboe, **`io_uring`** eliminates system call overhead using **Shared Ring Buffers**:

```text
===================================================================================================
                                   io_uring SYSTEM ARCHITECTURE
===================================================================================================

  USER SPACE                                                KERNEL SPACE (Ring 0)
  ┌─────────────────────────────────┐                       ┌─────────────────────────────────┐
  │ 1. Writes I/O Request to SQE    │                       │ Kernel Worker / SQ Poller       │
  │    (Submission Queue Entry)     │                       │ Reads SQE directly from ring!   │
  │ 2. Increments SQ Tail pointer   │                       │ Submits read/write to NVMe/NIC  │
  └────────────────┬────────────────┘                       └────────────────┬────────────────┘
                   │                                                         │
                   ▼ (mmap Shared Memory)                                    ▼ (mmap Shared Memory)
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │                         LOCKLESS CIRCULAR RING BUFFERS IN SHARED RAM                        │
  │                                                                                             │
  │   [ Submission Queue (SQ) ]  ──► Tail updated by User, Head read by Kernel                  │
  │   [ Completion Queue (CQ) ]  ──► Tail updated by Kernel, Head read by User                  │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
                   ▲                                                         │
                   │ (mmap Shared Memory)                                    ▼ (mmap Shared Memory)
  ┌────────────────┴────────────────┐                       ┌────────────────┴────────────────┐
  │ 4. User reads completed result  │                       │ 3. Kernel places completion into│
  │    directly from CQ ring!       │                       │    CQE (Completion Queue Entry) │
  │    ZERO SYSCALLS EXECUTED!      │                       │    Increments CQ Tail pointer   │
  └─────────────────────────────────┘                       └─────────────────────────────────┘
```

### 4.1 Zero-Syscall Polling Mode (`IORING_SETUP_SQPOLL`)
When initialized with the `IORING_SETUP_SQPOLL` flag, the Linux kernel spawns a dedicated kernel thread that continuously polls the Submission Queue ring in memory. 
- The application simply writes I/O requests into the SQ buffer and advances the tail pointer.
- The kernel thread consumes them instantly and writes completions into the CQ buffer.
- The application can process **millions of concurrent read and write operations per second with literally ZERO system calls**, unlocking true line-rate performance for next-generation storage and network applications!
