# Chapter 04: Distributed Data — Database-per-Service & CQRS

> "The defining characteristic of a microservice is that it owns its data. If two services share the same database tables, they are not two microservices—they are two halves of the same monolith running in different processes."  
> — *Chris Richardson, Microservice Patterns*

---

## 1. Canonical Motivation & Theoretical Foundation

In a traditional monolithic architecture, all components share a single, massive relational database. While this enables foreign keys, multi-table joins (`JOIN`), and atomic ACID transactions, it introduces fatal architectural coupling:
1. **Lost Service Autonomy:** Changing a column name in the `orders` table breaks 4 different team codebases simultaneously.
2. **Database Resource Contention:** A long-running analytical reporting query takes a table lock that freezes high-frequency checkout transactions.
3. **Impedance to Polyglot Persistence:** A team building a geospatial search service is forced to use the relational database instead of an optimized spatial engine.

The foundational principle of microservices is **Database-per-Service**: every microservice has its own dedicated database that cannot be accessed by any other service directly. Communication occurs strictly through well-defined APIs or events.

---

## 2. Underlying Runtime, Memory & Execution Architecture

### The Distributed Query Dilemma

When each service owns its private database, how do you execute queries that span multiple services (e.g. *Find all orders placed by customers in Germany, along with their payment status*)?

```
─────────────────────────────────────────────────────────────────────────────
Approach 1: API Composition (In-Memory Join at Gateway / Aggregator)
 [ Client Query ] ──> [ Aggregator Service ]
                             ├── 1. GET /customers?country=DE ──> [ Customer Service DB ]
                             ├── 2. GET /orders?customer_id=... ──> [ Order Service DB    ]
                             └── 3. Aggregator joins rows in memory and returns to client.
 • Flaws: High network latency ($N+1$ queries), massive memory consumption on aggregator,
   and poor availability (if Order Service is down, the entire query fails).
─────────────────────────────────────────────────────────────────────────────
Approach 2: Command Query Responsibility Segregation (CQRS)
               [ Write Command ]                [ Read Query ]
                      │                               │
                      ▼                               ▼
            ┌───────────────────┐           ┌───────────────────┐
            │    Write Model    │           │    Read Model     │
            │  (Command Side)   │           │   (Query Side)    │
            │  PostgreSQL (3NF) │           │   Elasticsearch   │
            └─────────┬─────────┘           └─────────▲─────────┘
                      │                               │
                      ▼                               │ (Changelog Projection)
             [ Emit Domain Event ] ──> [ Kafka ] ─────┘
 • Writes are optimized for ACID domain invariants.
 • Reads are served instantly from denormalized, read-optimized views.
─────────────────────────────────────────────────────────────────────────────
```

## 3. Core Mechanics, Algorithms & Invariants

### CQRS and Eventual Consistency

Because the Read Model is updated asynchronously via an event stream (e.g. Kafka or Debezium CDC), the system is **Eventually Consistent**:
- When a user submits an update (`Command`), the Write Model updates instantly.
- A few milliseconds later ($10\text{ms} - 100\text{ms}$ replication lag), the projection consumer updates the Read Model.

#### Handling Read-Your-Own-Writes in CQRS:
If a user submits an order, receives confirmation, and is redirected to their dashboard, the Read Model might not have projected the new order yet:
1. **Client-Side Optimistic UI:** The frontend updates the local UI immediately using the Command response data without re-fetching the Read Model.
2. **Version Pinning:** The Command response returns the latest aggregate version (`v42`). The frontend polls the Read Model passing `min_version=42`. The Read Model waits until its projection catches up.

## 4. Practical Systems & Production Engineering Trade-offs

| Criterion | API Composition | CQRS (Command Query Responsibility Segregation) |
| :--- | :--- | :--- |
| **Operational Complexity** | Very Low (Just write an API endpoint). | High (Requires Kafka, projection workers, secondary datastores). |
| **Query Latency** | High ($N$ network round trips + memory join). | **Ultra-Low** (Pre-computed point lookups / indexed scans). |
| **Availability** | Fragile (Availability = $\prod A_{\text{backends}}$). | **High** (Read Model serves queries even if Write DB is down). |
| **Data Freshness** | 100% Real-Time (Strictly consistent). | Eventually Consistent (bounded by replication lag). |

## 5. Annotated Multi-Language Implementations

### Java, Go, and Python Implementations of CQRS Command, Projection & Query

#### Java (Spring Boot 3 / CQRS Command Handler Writing to SQL & Emitting Event)
```java
package com.knowledgebase.microservices.orders.command;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderCommandService {

    private final OrderRepository orderRepository;
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public OrderCommandService(OrderRepository orderRepository, KafkaTemplate<String, Object> kafkaTemplate) {
        this.orderRepository = orderRepository;
        this.kafkaTemplate = kafkaTemplate;
    }

    @Transactional
    public String createOrder(CreateOrderCommand cmd) {
        // 1. Enforce business invariants on Write Model
        OrderEntity order = new OrderEntity(cmd.customerId(), cmd.totalAmount(), "CREATED");
        orderRepository.save(order);

        // 2. Publish Domain Event to Kafka for CQRS Read Model projection
        OrderCreatedEvent event = new OrderCreatedEvent(order.getId(), order.getCustomerId(), order.getTotalAmount());
        kafkaTemplate.send("orders.domain.events", order.getId(), event);

        return order.getId();
    }
}
```

#### Go (CQRS Read-Model Projection Worker Consuming Events & Upserting Read Store)
```go
package main

import (
	"context"
	"encoding/json"
	"log"
	"github.com/segmentio/kafka-go"
	"github.com/redis/go-redis/v9"
)

type OrderCreatedEvent struct {
	OrderID    string  `json:"order_id"`
	CustomerID string  `json:"customer_id"`
	Amount     float64 `json:"amount"`
}

func main() {
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	r := kafka.NewReader(kafka.ReaderConfig{
		Brokers: []string{"localhost:9092"},
		Topic:   "orders.domain.events",
		GroupID: "order-read-model-projector",
	})

	log.Println("CQRS Projection Worker started, listening for events...")
	ctx := context.Background()

	for {
		m, err := r.ReadMessage(ctx)
		if err != nil {
			break
		}

		var event OrderCreatedEvent
		if err := json.Unmarshal(m.Value, &event); err != nil {
			log.Printf("Failed to unmarshal event: %v", err)
			continue
		}

		// Project denormalized materialized view directly into Redis in O(1) time
		readModelKey := "view:order:" + event.OrderID
		rdb.HSet(ctx, readModelKey, map[string]interface{}{
			"order_id":    event.OrderID,
			"customer_id": event.CustomerID,
			"amount":      event.Amount,
			"status":      "CREATED",
		})

		log.Printf("Successfully projected Read Model for Order [%s]", event.OrderID)
	}
}
```

#### Python (FastAPI High-Speed Query Handler Reading from Materialized Store)
```python
"""
CQRS Query Handler in FastAPI.
Reads directly from the pre-computed, denormalized read model in sub-milliseconds.
"""

from typing import Dict
from fastapi import FastAPI, HTTPException
import redis.asyncio as redis

app = FastAPI(title="Order Query Service (CQRS)")
rdb: redis.Redis = None


@app.on_event("startup")
async def startup():
    global rdb
    rdb = redis.Redis(host="localhost", port=6379, decode_responses=True)


@app.get("/api/v1/orders/view/{order_id}")
async def get_order_view(order_id: str) -> Dict[str, str]:
    """Serves high-throughput queries directly from read model without database joins!"""
    read_model_key = f"view:order:{order_id}"
    order_data = await rdb.hgetall(read_model_key)

    if not order_data:
        raise HTTPException(status_code=404, detail="Order not found in read model")

    return order_data
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Shared Database Anti-Pattern
- **Antipattern:** Giving multiple microservices direct JDBC/SQL connections to the same database tables.
- **System Consequence:** Tight coupling. If Service A adds a table lock during a batch migration, Service B experiences query timeouts. Autonomy is destroyed.
- **Fix:** Enforce strict **Database-per-Service**. Each service owns its data completely.

### 2. Dual-Write Divergence in Custom CQRS
- **Antipattern:** Committing the Write Model to PostgreSQL, and manually calling `redis.set()` in the same HTTP request without an event log.
- **System Consequence:** If the app crashes or network fails before updating Redis, the Write Model has committed, but the Read Model is stale forever.
- **Fix:** Update Read Models strictly via **Change Data Capture (CDC)** or the **Transactional Outbox Pattern**.

### 3. Out-of-Order Projection Updates
- **Antipattern:** Projecting events from a multi-partition Kafka topic where events for the same aggregate ID hash to different partitions.
- **System Consequence:** An `OrderCancelled` event is processed *before* the `OrderCreated` event. The read model overwrites the cancellation with the creation, leaving the order stuck in `CREATED` state.
- **Fix:** Always partition domain event topics by **Entity ID** (`order_id`) so all lifecycle events for an entity land in the same partition and preserve strict ordering.
