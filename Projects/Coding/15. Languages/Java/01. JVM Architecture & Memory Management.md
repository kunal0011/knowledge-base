# Java: JVM Architecture & Memory Management

**Target Audience:** Senior Software Engineers & Tech Candidates preparing for FAANG/Tier-1 Java Architecture & Systems Interviews  
**Topic:** JVM Subsystems, Runtime Data Areas, Object Header Layout, Generational GC, String Pool & The Java Memory Model (JMM)

---

## 1. High-Level JVM Architecture

The Java Virtual Machine (JVM) is an abstract computing machine that executes compiled Java bytecode (`.class` files). HotSpot is the reference and dominant JVM implementation.

```
+-------------------------------------------------------------------------+
|                         Class Loader Subsystem                          |
|   Loading (Bootstrap, Platform, App) -> Linking (Verify, Prepare,       |
|   Resolve) -> Initialization (<clinit>)                                 |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
|                           Runtime Data Areas                            |
|  +--------------------+  +--------------------+  +-------------------+  |
|  |     Metaspace      |  |     Java Heap      |  | JVM Thread Stacks |  |
|  | (Native Memory)    |  |  (Eden, S0/S1, Old)|  |  (Frames, LVT)    |  |
|  +--------------------+  +--------------------+  +-------------------+  |
|  | PC Registers       |  | Native Method Stack|                         |
|  +--------------------+  +--------------------+                         |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
|                            Execution Engine                             |
|  +--------------------+  +--------------------+  +-------------------+  |
|  |    Interpreter     |  |   JIT Compiler     |  | Garbage Collector |  |
|  |                    |  |   (C1/C2 Compilers)|  | (G1, ZGC, Parallel)|  |
|  +--------------------+  +--------------------+  +-------------------+  |
+-------------------------------------------------------------------------+
|                     Native Method Interface (JNI)                       |
+-------------------------------------------------------------------------+
```

### 1.1 ClassLoader Subsystem
1. **Loading:** Reads `.class` byte streams and creates `java.lang.Class` instances.
   - **Bootstrap ClassLoader:** Loads core Java runtime classes (`rt.jar` / `java.base`). Written in native C/C++.
   - **Platform (Extension) ClassLoader:** Loads platform extension classes.
   - **Application (System) ClassLoader:** Loads application classes on the classpath.
   - *Delegation Hierarchy:* Follows the **Parent-Delegation Model** (a classloader checks if its parent can load the class before attempting to load it itself to guarantee security and prevent core class spoofing).
2. **Linking:**
   - *Verification:* Verifies bytecode conforms to JVM specification and does not violate type safety.
   - *Preparation:* Allocates memory for static variables and initializes them to their default zero-values (`0`, `null`, `false`).
   - *Resolution:* Replaces symbolic references in the constant pool with direct memory pointers.
3. **Initialization:** Executes static initializers and static variable assignments (`<clinit>` bytecode method).

### 1.2 The Execution Engine: Interpreter vs JIT
HotSpot is a **Tiered-Compilation** runtime:
- **Interpreter:** Executes bytecode immediately line-by-line without warm-up latency.
- **C1 Compiler (Client JIT):** Compiles frequently executed methods ("hot spots") into machine code with lightweight profiling and basic optimizations.
- **C2 Compiler (Server JIT):** Performs aggressive optimizations on heavily warmed methods (inlining, loop unrolling, escape analysis, lock coarsening/elision).

## 2. JVM Runtime Data Areas

```
+---------------------------------------------------------------------------+
|                          Shared Across All Threads                        |
|                                                                           |
|   +-------------------------------------------------------------------+   |
|   |                            Heap                                   |   |
|   |   +------------------------------------+  +-------------------+   |   |
|   |   |        Young Generation            |  |  Old Generation   |   |   |
|   |   |  Eden (80%)  |  S0 (10%) | S1 (10%)|  |     (Tenured)     |   |   |
|   |   +------------------------------------+  +-------------------+   |   |
|   +-------------------------------------------------------------------+   |
|                                                                           |
|   +-------------------------------------------------------------------+   |
|   |                 Metaspace (Native Off-Heap Memory)                |   |
|   |   Class Metadata, Method Descriptors, Constant Pool, Bytecodes    |   |
|   +-------------------------------------------------------------------+   |
+---------------------------------------------------------------------------+
|                          Thread-Private Areas                             |
|                                                                           |
|   +--------------------------+  +-----------------+  +----------------+   |
|   |      Thread 1 Stack      |  | Thread 2 Stack  |  | Thread N Stack |   |
|   |  +--------------------+  |  +-----------------+  +----------------+   |
|   |  | Stack Frame 1      |  |                                            |
|   |  |  - Local Var Table |  |                                            |
|   |  |  - Operand Stack   |  |                                            |
|   |  |  - Frame Data      |  |                                            |
|   |  +--------------------+  |                                            |
|   +--------------------------+                                            |
|   | PC Register              |                                            |
+---------------------------------------------------------------------------+
```

### 2.1 Heap vs Stack
| Dimension | Java Heap | Thread Stack |
|:---|:---|:---|
| **Scope** | Shared across all threads | Private to each thread |
| **Contents** | All class objects, instances, arrays | Primitive local variables, reference pointers, call frames |
| **Lifetime** | Managed by Garbage Collector | Automatically reclaimed when method returns |
| **Error upon exhaustion** | `java.lang.OutOfMemoryError: Java heap space` | `java.lang.StackOverflowError` |
| **Allocation Speed** | Slower (requires pointer bump / TLAB) | Instantaneous (stack pointer adjustment) |

### 2.2 Metaspace (Java 8+)
Prior to Java 8, class metadata was stored in **PermGen** (Permanent Generation) inside the contiguous JVM heap, bounded by `-XX:MaxPermSize`, frequently resulting in `OutOfMemoryError: PermGen space`.
In Java 8+, PermGen was replaced by **Metaspace**, which resides in **native off-heap memory**. It grows automatically up to available OS memory unless constrained via `-XX:MaxMetaspaceSize`.

## 3. Object Memory Layout in HotSpot JVM

Every Java object on a 64-bit JVM consists of three distinct zones:

```
+-------------------------------------------------------------------+
|                           Object Header                           |
|  +-------------------------------------------------------------+  |
|  | Mark Word (64 bits / 8 bytes)                               |  |
|  | - HashCode, Age bits (4 bits), Lock state, Biased lock info |  |
|  +-------------------------------------------------------------+  |
|  | Klass Pointer (32 bits / 4 bytes with Compressed OOPs)      |  |
|  | - Pointer to Class Metadata in Metaspace                    |  |
|  +-------------------------------------------------------------+  |
|  | Array Length (32 bits / 4 bytes) [ARRAYS ONLY]              |  |
+-------------------------------------------------------------------+
|                           Instance Data                           |
|  Fields (int: 4B, long: 8B, reference: 4B with CompressedOOPs)    |
+-------------------------------------------------------------------+
|                        Alignment Padding                          |
|  Padded to make the entire object size a multiple of 8 bytes      |
+-------------------------------------------------------------------+
```

### 3.1 The Mark Word
The 64-bit Mark Word dynamically alters its bit layout depending on lock state:
- **Unlocked:** `[HashCode: 31 bits] [Age: 4 bits] [BiasedLock: 0] [Lock: 01]`
  - Note: The 4-bit Age field explains why the maximum tenuring threshold is **15** ($2^4 - 1$).
- **Biased Lock:** `[ThreadID: 54 bits] [Epoch: 2 bits] [Age: 4 bits] [BiasedLock: 1] [Lock: 01]`
- **Lightweight Lock:** `[Pointer to Lock Record on thread stack: 62 bits] [Lock: 00]`
- **Heavyweight Lock:** `[Pointer to ObjectMonitor mutex: 62 bits] [Lock: 10]`
- **Marked for GC:** `[Forwarding pointer: 62 bits] [Lock: 11]`

### 3.2 Compressed OOPs (Ordinary Object Pointers)
On 64-bit systems, memory addresses are 8 bytes. For heaps $< 32\text{ GB}$, HotSpot enables `-XX:+UseCompressedOops` by default:
- Because objects are aligned on 8-byte boundaries, the lowest 3 bits of every object pointer are always `000`.
- The JVM shifts the 32-bit integer right by 3 bits when storing, and shifts left by 3 bits upon dereferencing.
- This allows a 32-bit pointer to address up to $2^{32} \times 8\text{ bytes} = 32\text{ GB}$ of heap, reducing memory footprint by $\approx 30\%$.

## 4. Garbage Collection Mechanisms

### 4.1 The Weak Generational Hypothesis
1. Most allocated objects die shortly after creation (e.g., local variables within a method).
2. Objects that survive multiple collection cycles are likely to persist for a long time.

### 4.2 Young vs Old Generation Cycles
1. **Minor GC (Young Gen):**
   - New objects allocate in **Eden**.
   - When Eden fills, a Minor GC triggers. Live objects are evacuated to the empty survivor space (e.g., `S0`).
   - On subsequent Minor GCs, live objects from Eden and `S0` are copied to `S1`, incrementing their age counter.
   - When an object's age exceeds the tenuring threshold (default: 15, or dynamically calculated), it is **promoted** to the Old Generation.
2. **Major / Full GC:**
   - Cleans the Old Generation (and optionally Metaspace).
   - Involves longer Stop-The-World (STW) pauses.

### 4.3 Modern Production Garbage Collectors
- **Parallel GC (`-XX:+UseParallelGC`):** Throughput-oriented; multi-threaded STW for batch workloads.
- **G1 GC (`-XX:+UseG1GC`):** Default since Java 9. Divides the heap into thousands of equal-sized **regions** (1 MB to 32 MB). Prioritizes regions with the most garbage ("Garbage-First") to satisfy bounded pause-time targets (`-XX:MaxGCPauseMillis=200`).
- **ZGC (`-XX:+UseZGC`) & Shenandoah:** Ultra-low-latency collectors performing concurrent marking, evacuation, and reference updating. Pauses are consistently **$< 1\text{ ms}$**, independent of heap size (even for terabyte heaps).

## 5. Primitive vs Wrapper Types & The Integer Cache

```java
int primitiveVal = 42;             // 4 bytes directly on thread stack
Integer boxedVal = 42;             // Reference pointer (4B) -> Heap object (16B) = 20 bytes!
```

### The Integer Cache Trap
```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b);      // true (Cached reference!)

Integer c = 128;
Integer d = 128;
System.out.println(c == d);      // false (Different heap instances!)
System.out.println(c.equals(d)); // true (Value comparison)
```

### Why it Happens
Autoboxing calls `Integer.valueOf(int)`:
```java
// Simplified JDK java.lang.Integer implementation:
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}
```
The JVM pre-instantiates an array of `Integer` objects for values from **$-128$ to $127$**.
- Cache ranges for wrapper types:
  - `Byte`, `Short`, `Long`: $[-128, 127]$
  - `Character`: $[0, 127]$
  - `Boolean`: `Boolean.TRUE`, `Boolean.FALSE`

## 6. The String Pool & String Immutability

### 6.1 String Table Internals
The JVM maintains a native hash table called the **String Pool** (or `StringTable`):
```java
String s1 = "hello";              // Enters String Pool
String s2 = "hello";              // Reuses reference from String Pool
String s3 = new String("hello");  // Forces new instance on regular Heap!

System.out.println(s1 == s2);     // true
System.out.println(s1 == s3);     // false
System.out.println(s1 == s3.intern()); // true (intern() returns pool pointer)
```

```
Stack                     Heap Memory                          String Pool (Native Table)
+-----+                   +--------------------------+         +--------------------+
| s1  |------------------>|                          |-------->| "hello" instance   |
+-----+                   +--------------------------+         +--------------------+
| s2  |------------------------------------------------------->| (reused pointer)   |
+-----+                   +--------------------------+         +--------------------+
| s3  |------------------>| Distinct String instance |
+-----+                   +--------------------------+
```

### 6.2 Why `String` is Immutable in Java
1. **String Pool Optimization:** If strings were mutable, altering `s1` would silently corrupt `s2`.
2. **Security:** Strings represent network sockets, URLs, and database credentials. Immutability prevents Time-of-Check to Time-of-Use (TOCTOU) security tampering.
3. **Thread Safety:** Completely thread-safe across concurrent threads without synchronization.
4. **HashCode Caching:** `String` memoizes its `hash` in a 32-bit field. Since content is immutable, hash code is computed only once upon first invocation, making `HashMap<String, V>` lookups exceptionally fast.

### 6.3 Java 9 Compact Strings
Before Java 9, strings were stored as UTF-16 character arrays: `char[]` (2 bytes per character).
In Java 9+, strings are stored as `byte[]` accompanied by a `coder` flag byte:
- `LATIN1` (1 byte per char) for ISO-8859-1 strings (covers ASCII).
- `UTF16` (2 bytes per char) if non-Latin characters are present.
This reduces Java heap consumption by up to **$50\%$** for string-heavy enterprise applications.

## 7. Java Memory Model (JMM) & Concurrency Primitives

The Java Memory Model defines how threads interact through shared memory, establishing **Happens-Before** ordering guarantees.

### 7.1 The `volatile` Keyword
```java
private volatile boolean running = true;
```
`volatile` provides two critical guarantees:
1. **Visibility:** Writes to a volatile variable are immediately flushed to main memory; reads always bypass CPU L1/L2 caches and load directly from main memory.
2. **Instruction Reordering Prevention:** Emits CPU memory barriers (StoreStore, StoreLoad, LoadLoad, LoadStore) preventing JIT and CPU hardware from reordering statements across the volatile boundary.

> [!CAUTION]
> `volatile` guarantees **visibility**, but **NOT atomicity**!
> Operations like `count++` are composite: read, modify, write. Two concurrent threads reading simultaneously can both write the same incremented value. For atomicity, use `AtomicInteger` or `synchronized`.

### 7.2 CAS (Compare-And-Swap) & `AtomicInteger`
`java.util.concurrent.atomic` classes avoid heavyweight operating system mutexes using hardware CPU-level atomic instructions (`CMPXCHG` on x86):
```java
// Lock-free loop:
public final int incrementAndGet() {
    int current;
    int next;
    do {
        current = get();
        next = current + 1;
    } while (!compareAndSet(current, next));
    return next;
}
```
If another thread mutated the value in the interim, `compareAndSet` returns `false` and the thread spins. Under moderate contention, CAS is significantly faster than thread blocking and context-switching.
