# C++ Concepts: Classes, Inheritance & Object-Oriented Design

**Foundational Texts:**  
- *The C++ Programming Language (4th Ed.)* by Bjarne Stroustrup, Chapters 16–21  
- *Effective Modern C++* by Scott Meyers, Items 12 & 17  

---

## 1. Theoretical Motivation: Concrete Types vs. Class Hierarchies

Bjarne Stroustrup divided C++ user-defined types into two distinct architectural categories:
1. **Concrete Classes (Value Types):** Types like `std::complex`, `std::string`, and `std::vector`. They behave like built-in types, live directly on the stack, have no virtual table overhead, and are passed by value or `const&`.
2. **Abstract Classes & Hierarchies (Polymorphic Types):** Classes that define interfaces via `virtual` methods, manipulated exclusively via pointers or references (`Base*` or `Base&`), decoupling callers from concrete implementations.

## 2. Underlying Architecture: Virtual Tables (`vtable`) & `vptr`

How does dynamic dispatch actually execute at the CPU assembly level?

```
Polymorphic Object in Memory:
+-------------------------------------------------------------+
| vptr (8 bytes) ------------------------+                    |
| Derived member variables               |                    |
+----------------------------------------|--------------------+
                                         |
                                         v
Virtual Table (vtable in Read-Only Data Segment):
+-------------------------------------------------------------+
| &Derived::destructor()                                      |
| &Derived::draw()                                            |
| &Derived::area()                                            |
+-------------------------------------------------------------+
```

### 2.1 The Dynamic Dispatch Assembly Trace
When you execute `shape->draw()`:
1. The CPU reads `vptr` from offset `0` of the object: `mov rax, [rdi]`.
2. It fetches the function pointer at the fixed `draw()` slot index (e.g., slot 1): `mov rax, [rax + 8]`.
3. It issues an indirect call: `call rax`.

### Cost of Dynamic Dispatch:
- **Memory Overhead:** Adds an 8-byte `vptr` to every instance, plus one `vtable` per polymorphic class.
- **Cache Misses:** Two pointer indirections (object $\to$ vtable $\to$ code).
- **Inlining Prevention:** Compilers generally cannot inline indirect `call rax` instructions, losing massive optimization opportunities.

## 3. The Rule of 0 / 3 / 5

Managing object copy and move semantics requires strict adherence to standard lifecycle rules:

```
+-------------------------------------------------------------------------+
|                         THE RULE OF 0 / 3 / 5                           |
+-------------------+-----------------------------------------------------+
| Rule of Zero      | Use modern RAII member types (std::string, vector,  |
| (Preferred)       | unique_ptr). Declare NO custom destructors or copy/ |
|                   | move operations! The compiler handles all 5 cleanly.|
+-------------------+-----------------------------------------------------+
| Rule of Three     | If you manage raw resources and declare a custom:   |
| (C++98 Legacy)    | 1. Destructor, 2. Copy Constructor, or 3. Copy Assign|
|                   | ...you MUST explicitly implement all three!         |
+-------------------+-----------------------------------------------------+
| Rule of Five      | In modern C++, declaring any Rule of Three member   |
| (Modern C++11+)   | suppresses move operations. You must also implement: |
|                   | 4. Move Constructor and 5. Move Assignment Operator.|
+-------------------+-----------------------------------------------------+
```

### Meyers' Special Member Function Rules (Item 17):
- Declaring a **Copy Constructor** or **Copy Assignment** suppresses the automatic generation of Move operations.
- Declaring a **Move Constructor** or **Move Assignment** suppresses the automatic generation of Copy operations!

## 4. Modern Overriding Controls: `override` and `final`

Prior to C++11, subtle signature mismatches caused silent bugs:

```cpp
struct Base {
    virtual void render(float zoom) const;
};

// BUG: Missing 'const' or wrong parameter type created a NEW method instead of overriding!
struct Derived : Base {
    virtual void render(float zoom); // ACCIDENTAL SHADOWING! Base::render is NOT overridden!
};
```

### Scott Meyers' Item 12: Always Declare Overriding Functions `override`
```cpp
struct Derived : Base {
    void render(float zoom) const override; // COMPILE ERROR if signature doesn't match Base!
};
```

### The `final` Specifier & Devirtualization
Marking a method or class `final` informs the compiler that no further derivation is possible, enabling the optimizer to **devirtualize** calls and inline them directly:
```cpp
class FastRenderer final : public Base {
    void render(float zoom) const override final; // Inlined directly at call sites!
};
```

## 5. Multiple Inheritance & The Diamond Problem

When a class inherits from two base classes that both derive from a single root class:

```
Diamond Problem:
           [ Device ]
           /        \
      [ Printer ]   [ Scanner ]
           \        /
         [ Copier ]
```

Without special handling, `Copier` contains **two separate copies** of `Device`, causing ambiguous member access (`copier.Device::id`).

### The Virtual Base Class Solution:
```cpp
struct Device { int id; };

// Use virtual inheritance:
struct Printer : virtual public Device {};
struct Scanner : virtual public Device {};

struct Copier : public Printer, public Scanner {};
```
`Copier` now contains **only one shared instance** of `Device`. The compiler coordinates offsets using a runtime table pointer (`vbase_offset`).

## 6. Authoritative Gotchas & Traps (Stroustrup & Meyers)

### 6.1 Never Call Virtual Functions in Constructors or Destructors
```cpp
// DISASTROUS ANTI-PATTERN:
class Base {
public:
    Base() { log(); } // Calls Base::log(), NEVER Derived::log()!
    virtual void log() { std::cout << "Base initialized\n"; }
};

class Derived : public Base {
    std::string name;
public:
    Derived() : name("Widget") {}
    void log() override { std::cout << "Derived name: " << name << "\n"; }
};
```

#### Why it Breaks (Stroustrup):
During base class construction, the derived class fields have **not yet been allocated or constructed**. If C++ called `Derived::log()`, it would access uninitialized memory (`name`), causing instant crashes.
Therefore, during `Base` construction, the object's `vptr` points strictly to `Base`'s vtable!

### 6.2 The Missing Virtual Destructor Leak
```cpp
// FATAL MEMORY LEAK & UNDEFINED BEHAVIOR:
class Base {
    // Missing virtual destructor!
    ~Base() = default; 
};

class Derived : public Base {
    int* large_buffer = new int[1000000];
public:
    ~Derived() { delete[] large_buffer; }
};

Base* ptr = new Derived();
delete ptr; // FATAL: Calls Base::~Base(), NEVER Derived::~Derived()! Memory leaked!
```
**Stroustrup's Golden Rule:** Any class with at least one `virtual` function **MUST declare a `virtual` destructor**:
```cpp
virtual ~Base() = default;
```

## 7. Actionable Summary Checklist

- [x] Every polymorphic base class must declare a **`virtual` destructor** (`virtual ~Base() = default;`).
- [x] Always append **`override`** to derived virtual function declarations to catch signature mismatches at compile time (Effective Modern C++ Item 12).
- [x] Follow the **Rule of Zero** by encapsulating resources in smart pointers and standard containers.
- [x] **Never invoke virtual methods inside constructors or destructors**; dynamic dispatch is disabled during base construction.
- [x] Use `final` on classes or methods when inheritance is completed to enable compiler devirtualization.
