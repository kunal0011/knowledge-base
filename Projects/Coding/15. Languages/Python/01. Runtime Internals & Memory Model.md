# Python: Runtime Internals & Memory Model

**Target Audience:** Senior Software Engineers & Tech Candidates preparing for FAANG/Tier-1 Python Deep-Dive Interviews  
**Topic:** CPython Architecture, Object Model, Memory Allocators, Garbage Collection & The GIL

---

## 1. The CPython Object Model (`PyObject`)

In Python, **everything is an object**—including integers, functions, classes, modules, and booleans. At the C level (CPython), every object is represented by a C struct containing a common header defined by `PyObject`.

### 1.1 Anatomy of a `PyObject`
```c
// Simplified CPython definition from Include/object.h
typedef struct _object {
    _PyObject_HEAD_EXTRA // Doubly linked list pointers for GC tracking (debug builds)
    Py_ssize_t ob_refcnt;
    struct _typeobject *ob_type;
} PyObject;

// For variable-length objects (like lists, strings, tuples, dicts):
typedef struct {
    PyObject ob_base;
    Py_ssize_t ob_size; // Number of items in container
} PyVarObject;
```

Every Python object carries an overhead of at least 16 bytes on a 64-bit architecture:
- `ob_refcnt` (8 bytes): 64-bit integer tracking the active references.
- `ob_type` (8 bytes): Pointer to the type descriptor object (`PyTypeObject`), which defines methods (`__init__`, `__repr__`), operators (`__add__`), and memory sizing.

```
       +------------------------------------+
       |            PyObject                |
       +------------------------------------+
       |  ob_refcnt (8 bytes) = 1           |
       |  ob_type   (8 bytes) -> &PyLong_Type
       +------------------------------------+
       |  ob_digit  (digits payload)        |  <-- Specific to type (e.g. PyLongObject)
       +------------------------------------+
```

### 1.2 Mutable vs. Immutable Types
- **Immutable Types:** `int`, `float`, `complex`, `str`, `bytes`, `tuple`, `frozenset`, `bool`.
  - Their values cannot change after creation. Modifying an immutable object creates a new instance in memory.
  - Immutables can be hashable (if their constituent elements are also hashable) and can serve as dictionary keys.
- **Mutable Types:** `list`, `dict`, `set`, `bytearray`, custom user classes (by default).
  - Can change contents in-place without altering the underlying memory address (`id(obj)`).
  - Cannot be used as dictionary keys or stored in sets because in-place mutation would invalidate hash bucket placement.

## 2. Memory Allocation Hierarchy (`pymalloc`)

CPython does not make direct calls to the operating system's `malloc()` or `free()` for every small Python object. Doing so would lead to severe memory fragmentation and kernel context switch overhead. Instead, it uses a hierarchical allocator:

```
+-------------------------------------------------------------+
| Layer 3: Object-Specific Allocators (e.g., PyList, PyDict)  |
+-------------------------------------------------------------+
| Layer 2: Python Object Allocator (pymalloc for <= 512 bytes)|
+-------------------------------------------------------------+
| Layer 1: Python Core Memory Allocator (PyMem_RawMalloc)     |
+-------------------------------------------------------------+
| Layer 0: OS Allocator (malloc, calloc, mmap / brk)          |
+-------------------------------------------------------------+
```

### The Three Tiers of `pymalloc`:
1. **Arenas (256 KB):**
   - Allocated directly from the OS heap via `malloc()`.
   - Arenas are chunked into 64 Pools.
2. **Pools (4 KB - standard OS page size):**
   - Each pool manages memory blocks of a single uniform size class (e.g., 16 bytes, 32 bytes, ..., up to 512 bytes).
   - Pools maintain a singly linked list of free blocks.
3. **Blocks (8 to 512 bytes in multiples of 8):**
   - When Python needs 24 bytes (e.g., for a float or short string), it requests a block from a Pool of size-class 24.
   - For objects strictly $> 512$ bytes, CPython bypasses `pymalloc` and delegates directly to system `malloc`.

## 3. Small Integer Caching & String Interning

To optimize speed and memory, CPython pre-allocates and memoizes frequently used objects.

### 3.1 Small Integer Caching (`[-5, 256]`)
During interpreter startup, CPython creates a static array of `PyLongObject` instances representing integers from `-5` through `256` inclusive.

```python
a = 100
b = 100
print(a is b)  # True: Both reference the exact same global singleton

x = 257
y = 257
print(x is y)  # False (in REPL / separate code blocks): Distinct objects in memory
```

> [!NOTE]
> In a Python file or script, the bytecode compiler's constant folding table may optimize duplicate literals in the same code object, causing `x is y` to be `True` for 257. However, mathematically and semantically, only `[-5, 256]` are guaranteed singletons.

### 3.2 String Interning
CPython interns string literals that look like valid Python identifiers (ASCII alphanumeric characters and underscores):
- Interned strings are stored in an internal dictionary table.
- When comparing two interned strings for equality (`s1 == s2`), CPython skips character-by-character scanning and performs a simple $\mathcal{O}(1)$ pointer comparison: `s1 is s2`.
- You can manually intern arbitrary strings using `sys.intern(s)`.

## 4. Garbage Collection Architecture

Python employs a hybrid garbage collection system: **Reference Counting** (primary, immediate) combined with a **Generational Cyclic Garbage Collector** (secondary, periodic).

### 4.1 Primary Collector: Reference Counting
Every `PyObject` tracks how many places reference it (`ob_refcnt`):
- `ob_refcnt` increments when:
  - An object is assigned to a variable (`b = a`).
  - Passed as an argument to a function.
  - Stored in a container (list, dict, tuple).
- `ob_refcnt` decrements when:
  - Variable goes out of scope.
  - Variable is reassigned or deleted (`del a`).
  - Container holding the reference is deleted or cleared.
- **Immediate Reclaim:** As soon as `ob_refcnt == 0`, CPython immediately frees the object and invokes its deallocator.

```
Ref count = 2               Ref count = 1              Ref count = 0
[a = [1, 2]]  <--- b = a    [del b]                    [del a] -> Memory Freed Instantly!
```

### 4.2 The Weakness of Reference Counting: Reference Cycles
Reference counting alone **cannot** free circular dependencies:

```python
class Node:
    def __init__(self):
        self.neighbor = None

node1 = Node()
node2 = Node()
node1.neighbor = node2
node2.neighbor = node1

del node1
del node2
# Both objects now have ob_refcnt == 1 (referencing each other)!
# Neither can be freed by reference counting alone -> MEMORY LEAK!
```

### 4.3 Generational Cyclic GC (`gc` module)
To resolve cycles, CPython runs a cyclic garbage collector that inspects only **container objects** (lists, dicts, tuples, custom classes) capable of holding references:
- **Generations (0, 1, 2):**
  - **Generation 0:** Newly created container objects. Collected most frequently.
  - **Generation 1:** Objects that survived one collection of Gen 0.
  - **Generation 2:** Long-lived objects (survived Gen 1 collection). Collected least frequently.
- **Threshold Heuristic:**
  - `gc.get_threshold()` returns `(700, 10, 10)` by default.
  - When allocations minus deallocations exceed 700, Gen 0 collection triggers.
  - When Gen 0 has been collected 10 times, Gen 1 is collected alongside Gen 0.
  - When Gen 1 has been collected 10 times, a full GC (Gen 0, 1, 2) triggers.

### 4.4 How Cycle Detection Works (Trial Deletion Algorithm)
1. For every container object in the generation, the GC makes a copy of `ob_refcnt` called `gc_refs`.
2. The GC iterates over all objects and for each child object referenced, decrements `gc_refs` of the child:
   $$\text{gc\_refs} = \text{gc\_refs} - 1$$
3. Any object whose `gc_refs` reaches `0` had references originating **entirely from within the isolated cycle**.
4. Objects with `gc_refs > 0` are referenced from the outside and cannot be collected; their reachable children are also protected.
5. The unreachable objects are cleared and deallocated.

## 5. The Global Interpreter Lock (GIL)

### 5.1 What is the GIL?
The **Global Interpreter Lock (GIL)** is a mutex that protects access to Python objects, preventing multiple native threads from executing CPython bytecode simultaneously.

```
       +-------------------------------------------------+
       |                  The GIL Mutex                  |
       +-------------------------------------------------+
                 | Holds lock                | Blocked
                 v                           v
         [ Thread 1 (CPU) ]          [ Thread 2 (CPU) ]
         Executing bytecode          Waiting for GIL
```

### 5.2 Why does CPython have a GIL?
1. **Thread-Safe Memory Management:** The reference counting system is not thread-safe. Without the GIL, concurrent modifications to `ob_refcnt` would require fine-grained atomic operations or locks on every object access, severely hurting single-threaded performance.
2. **C Extension Integration:** It simplified integration of non-thread-safe C libraries without complex locking.

### 5.3 Concurrency Matrix: Threading vs. Multiprocessing vs. Asyncio

| Concurrency Model | CPU-Bound Task Speedup? | I/O-Bound Task Speedup? | Memory Sharing | Overhead |
|:---|:---:|:---:|:---|:---|
| **`threading`** | ❌ No (GIL contention slows it down) | ✅ Yes (releases GIL during socket/disk I/O) | Shared memory space | Low (threads) |
| **`multiprocessing`** | ✅ Yes (independent Python processes, each with its own GIL) | ✅ Yes | Separate memory (IPC / serialization via pickle) | High (process spawn) |
| **`asyncio`** | ❌ No (single thread cooperative concurrency) | ✅ Yes (event loop with non-blocking syscalls) | Single shared thread | Minimal (coroutines) |

### 5.4 Free-Threaded Python (PEP 703 / Python 3.13+)
Python 3.13 introduces an experimental build option (`--disable-gil` / free-threaded mode) replacing the GIL with:
- **Biased Reference Counting:** Fast, thread-local refcounting for objects accessed by only one thread.
- **Mimalloc integration:** Lock-free, thread-safe memory allocation.

## 6. Python Execution Engine (Source to Bytecode)

When you run `python main.py`:
1. **Parsing & Tokenization:** Source code string $\to$ Abstract Syntax Tree (AST).
2. **Bytecode Compilation:** AST $\to$ Bytecode instructions stored in `.pyc` files (`__pycache__`).
3. **Execution Loop (`_PyEval_EvalFrameDefault`):** A massive `switch-case` evaluation loop in C reading 16-bit bytecode instructions and manipulating a stack of `PyObject*` pointers.

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
```
Output:
```
  2           0 LOAD_FAST                0 (a)
              2 LOAD_FAST                1 (b)
              4 BINARY_OP                0 (+)
              8 RETURN_VALUE
```

## 7. High-Frequency Interview Questions & Gotchas

### Q1: Is Python Call-by-Value or Call-by-Reference?
**Answer:** Neither. Python uses **Call-by-Object-Reference** (or *Call-by-Sharing*):
- The parameter variable in the function receives a copy of the **pointer** (reference) to the object.
- If you mutate the object in-place (e.g. `lst.append(5)`), the caller sees the change.
- If you reassign the variable (e.g. `lst = [1, 2]`), you simply rebind the local pointer; the caller's reference remains unchanged.

### Q2: Why does `sys.getsizeof([])` return 56 or 64 bytes for an empty list?
**Answer:** A `PyListObject` contains:
- `PyObject_VAR_HEAD`: `ob_refcnt` (8 bytes) + `ob_type` (8 bytes) + `ob_size` (8 bytes) = 24 bytes.
- `ob_item` pointer (8 bytes): points to dynamically allocated array of item pointers.
- `allocated` capacity integer (8 bytes).
- GC tracking headers (16 bytes).
Total = 56–64 bytes of overhead even with 0 items!

### Q3: When should you manually call `gc.collect()`?
**Answer:** In memory-critical services after dropping references to very large, complex object graphs with known cyclic links (e.g., neural network models, parsed DOM trees), or when disabling cyclic GC during performance-critical request loops (`gc.disable()`) and manually running collection in background workers.
