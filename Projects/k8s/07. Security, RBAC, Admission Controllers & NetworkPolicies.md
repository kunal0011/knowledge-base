## 🛡️ 1. The Multi-Tiered Kubernetes Security Pipeline

Every single interaction with a Kubernetes cluster traverses an uncompromising, multi-stage security pipeline in the `kube-apiserver` before any state is written to `etcd`.

```text
===================================================================================================
                               API SERVER SECURITY LIFECYCLE
===================================================================================================

  kubectl / API Client Request
               │
               ▼
  ┌─────────────────────────┐
  │   1. Authentication     │  - Verifies identity: Who are you?
  │        (AuthN)          │  - X.509 Client Certs, OIDC (Okta/Dex), Projected ServiceAccount Tokens
  └────────────┬────────────┘
               │ (Authenticated: User "alice" or ServiceAccount "payment-svc")
               ▼
  ┌─────────────────────────┐
  │   2. Authorization      │  - Verifies permissions: Can you do this?
  │        (AuthZ)          │  - Role-Based Access Control (RBAC), Node Authorizer, ABAC
  └────────────┬────────────┘
               │ (Authorized: Can "create" "deployments" in "production")
               ▼
  ┌─────────────────────────┐
  │ 3. Mutating Admission   │  - Modifies request payload
  │       Webhooks          │  - Injects Istio sidecars, sets default security contexts, adds labels
  └────────────┬────────────┘
               │
               ▼
  ┌─────────────────────────┐
  │   4. Object Schema      │  - Validates OpenAPI schema compliance and field types
  │      Validation         │
  └────────────┬────────────┘
               │
               ▼
  ┌─────────────────────────┐
  │ 5. Validating Admission │  - Enforces cluster invariants & policies: Allowed to commit?
  │       Webhooks          │  - Pod Security Standards (PSS), OPA Gatekeeper, Kyverno
  └────────────┬────────────┘
               │ (Passed all policy gates)
               ▼
      Committed to etcd!
```

## 🔑 2. Authentication (AuthN) & Modern ServiceAccount Tokens

Kubernetes distinguishes between **Normal Users** (humans managed externally via IdPs) and **ServiceAccounts** (internal machine identities managed inside the cluster).

### 2.1 Bound ServiceAccount Token Projection (TokenRequest API)
In legacy Kubernetes, a ServiceAccount token was a static, non-expiring JWT stored in a Secret mounted indefinitely inside every container. If a container was compromised, the attacker held a permanent cluster credential.

Modern Kubernetes implements **Projected ServiceAccount Tokens**:
- Injected as ephemeral `tmpfs` volume mounts.
- Cryptographically bound to the specific Pod UID, namespace, and target audience (`aud`).
- Short-lived with automatic token rotation (default expiry 1 hour).
- If the Pod is terminated, the token is invalidated immediately by the API server.

```yaml
# Best Practice: Explicitly disable auto-mounting if Pod doesn't call API
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-processor
automountServiceAccountToken: false
```

## 📜 3. Role-Based Access Control (RBAC) Internals

RBAC regulates access to API resources based on four core primitives:
1. **`Role`:** Defines resource permissions within a **single namespace**.
2. **`ClusterRole`:** Defines permissions across the **entire cluster** or over non-namespaced resources (Nodes, PVs, CRDs).
3. **`RoleBinding`:** Grants permissions defined in a Role to a User, Group, or ServiceAccount within a namespace.
4. **`ClusterRoleBinding`:** Grants permissions defined in a ClusterRole across all namespaces in the cluster.

```text
===================================================================================================
                                      RBAC TOPOLOGY MATRIX
===================================================================================================

  [ Scoped to Single Namespace ]                  [ Cluster-Wide Scope ]
  
     ┌──────────────────────┐                        ┌──────────────────────┐
     │         Role         │                        │     ClusterRole      │
     │ namespace: payment   │                        │ (No namespace)       │
     │ resources: [pods]    │                        │ resources: [nodes]   │
     │ verbs: [get, list]   │                        │ verbs: [get, list]   │
     └──────────┬───────────┘                        └──────────┬───────────┘
                │                                               │
                ▼                                               ▼
     ┌──────────────────────┐                        ┌──────────────────────┐
     │     RoleBinding      │                        │  ClusterRoleBinding  │
     │ binds: payment-sa    │                        │ binds: cluster-admin │
     │ to: Role             │                        │ to: ClusterRole      │
     └──────────────────────┘                        └──────────────────────┘
```

### Production Principle of Least Privilege: Role Example
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: analytics
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get"]
```

## 👮 4. Pod Security Standards (PSS) & Admission Enforcement

Pod Security Policies (PSP) were deprecated and removed in Kubernetes v1.25. The modern standard is **Pod Security Standards (PSS)**, integrated natively into the API server admission phase via namespace labels.

### 4.1 The Three Security Levels
1. **`Privileged`:** Completely unrestricted. Allows host root, host namespaces, privileged containers (used only for CNI/CSI system daemons).
2. **`Baseline`:** Minimally restrictive. Prevents known privilege escalations; allows default container settings.
3. **`Restricted`:** Hardened production posture. Enforces rootless execution, drops all Linux capabilities except `NET_BIND_SERVICE`, enforces read-only root filesystems, forbids host access.

### 4.2 Namespace Enforcement Configuration
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: secure-prod
  labels:
    # Hard rejection of non-compliant pods
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    # Generates audit log warning
    pod-security.kubernetes.io/audit: restricted
    # Returns visible warning banner to kubectl user
    pod-security.kubernetes.io/warn: restricted
```

### 4.3 Hardened Restricted Container Spec
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hardened-microservice
  namespace: secure-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: cgr.dev/chainguard/static:latest
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
          volumeMounts:
            - name: tmp-dir
              mountPath: /tmp
      volumes:
        - name: tmp-dir
          emptyDir: {}
```

## 🕸️ 5. Zero-Trust NetworkPolicies

By default, Kubernetes networking is completely open: any Pod can initiate TCP connections to any other Pod across any namespace. **NetworkPolicies** configure the CNI plugin (Calico, Cilium) to enforce stateful packet filtering via Linux netfilter or eBPF.

### 5.1 Default-Deny-All Baseline (Golden Production Rule)
Every production namespace must start with an explicit default-deny policy for both ingress and egress:
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {} # Selects all pods in namespace
  policyTypes:
    - Ingress
    - Egress
```

### 5.2 Microservice Whitelist Policy
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-payment-api
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: payment-api
  policyTypes:
    - Ingress
    - Egress
  ingress:
    # Allow incoming traffic ONLY from Ingress Gateway in gateway-infra namespace on port 8080
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: gateway-infra
          podSelector:
            matchLabels:
              app: envoy-gateway
      ports:
        - protocol: TCP
          port: 8080
  egress:
    # Allow outgoing TCP traffic ONLY to Postgres in db namespace on port 5432
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: database
          podSelector:
            matchLabels:
              app: postgres
      ports:
        - protocol: TCP
          port: 5432
    # CRITICAL: Whitelist DNS resolution (CoreDNS on UDP 53)
    - to:
        - namespaceSelector: {}
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
```
