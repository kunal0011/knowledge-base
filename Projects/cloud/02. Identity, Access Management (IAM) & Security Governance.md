> "Identity is the new perimeter. In the legacy enterprise, security was anchored to physical network firewalls and private IP boundaries. ## 🛡️ 1. Core Fundamentals: Authentication, Authorization & Principals

At the core of all cloud security governance lies the distinction between verifying identity and granting permission:

```text
===================================================================================================
                         AUTHENTICATION (AuthN) VS. AUTHORIZATION (AuthZ)
===================================================================================================

  [ 1. AUTHENTICATION (AuthN) ]                   [ 2. AUTHORIZATION (AuthZ) ]
  "Who are you?"                                  "What actions are you permitted to execute?"
  
  ┌─────────────────────────────────────┐         ┌─────────────────────────────────────┐
  │ Cryptographic Verification:         │         │ Policy Evaluation Engine:           │
  │ - OIDC / SAML 2.0 Identity Token    │   ───►  │ - Identity Policies (RBAC/ABAC)     │
  │ - X.509 Mutual TLS (mTLS)           │         │ - Resource Policies (Bucket/Key ACL)│
  │ - Ephemeral STS Session Tokens      │         │ - Organizational Guardrails (SCPs)  │
  └─────────────────────────────────────┘         └──────────────────┬──────────────────┘
                                                                     │
                                                    ┌────────────────┴────────────────┐
                                                    ▼                                 ▼
                                              [ 200 OK: ALLOW ]              [ 403 FORBIDDEN: DENY ]
```

### 1.1 Types of Cloud Principals
1. **Human Identities:** Developers, operators, and business users. In enterprise environments, human users are almost never created natively in individual cloud consoles; they are federated from central Identity Providers (IdPs) such as Okta, Ping Identity, or Microsoft Entra ID via SAML 2.0 or OpenID Connect (OIDC).
2. **Workload / Machine Identities:** Compute instances, container pods, serverless functions, and CI/CD pipelines.
   - **The Antipattern:** Generating long-lived static API access keys (e.g., AWS `AKIA...` keys or GCP JSON service account private keys) and baking them into environment variables or disk images.
   - **The Cloud-Native Standard:** Ephemeral, dynamically minted, short-lived security tokens managed directly by hypervisor metadata services without stored passwords.

### 2.1 Amazon Web Services (AWS) IAM & STS
- **AWS IAM Roles:** An IAM role is an identity with specific permissions that is not associated with a single person or static credential. Instead, it is assumed dynamically by trusted entities.
- **Instance Profiles:** A container that passes an IAM role to an Amazon EC2 instance.
- **AWS Security Token Service (STS):** The cryptographic engine that mints temporary credentials via APIs:
  - `AssumeRole`: Exchanges caller credentials for temporary access keys with a configurable expiration (15 minutes to 12 hours).
  - `AssumeRoleWithWebIdentity`: Exchanges an external OIDC token (from GitHub Actions, Kubernetes, or Google) for AWS credentials.
- **Policy Evaluation Logic:** AWS processes six distinct policy layers. The evaluation algorithm is strictly deterministic:

```text
===================================================================================================
                             AWS IAM POLICY EVALUATION DECISION TREE
===================================================================================================

                                 [ Incoming API Request ]
                                            │
                                            ▼
                           Is there an EXPLICIT DENY in ANY policy?
                           (Identity, Resource, SCP, Boundary, Session)
                                   ├─── YES ───► [ ❌ DENY ACCESS ]
                                   │
                                   └─── NO
                                        │
                                        ▼
                           Does an applicable SCP ALLOW the action?
                                   ├─── NO  ───► [ ❌ DENY ACCESS ]
                                   │
                                   └─── YES
                                        │
                                        ▼
                      Is there a RESOURCE-BASED POLICY allowing the action?
                                   ├─── YES ───► [ ✅ ALLOW ACCESS ]
                                   │
                                   └─── NO
                                        │
                                        ▼
                      Does an IDENTITY-BASED POLICY allow the action?
                                   ├─── NO  ───► [ ❌ DENY ACCESS ]
                                   │
                                   └─── YES
                                        │
                                        ▼
                      Is there a PERMISSIONS BOUNDARY allowing the action?
                                   ├─── NO  ───► [ ❌ DENY ACCESS ]
                                   │
                                   └─── YES ───► [ ✅ ALLOW ACCESS ]
```

### 2.2 Microsoft Azure: Entra ID & Azure RBAC
Azure splits identity and authorization across two distinct subsystems:
1. **Microsoft Entra ID (formerly Azure Active Directory):** Manages identity (AuthN).
   - **Service Principal:** The local representation of an application object within a specific Entra ID tenant.
   - **Managed Identities:** Eliminates credential management for developers by provisioning an identity in Entra ID automatically:
     - *System-Assigned:* Tied directly to the lifecycle of a single Azure resource (VM, Function, App Service). If the VM is deleted, the identity is purged.
     - *User-Assigned:* Standalone Azure resource that can be shared across multiple VM instances.
2. **Azure Role-Based Access Control (Azure RBAC):** Manages authorization (AuthZ) over Azure Resource Manager (ARM) resources.
   - **Role Definition:** A JSON document specifying allowed `Actions`, disallowed `NotActions`, data actions (`DataActions`), and assignable scopes (`AssignableScopes`).
   - **Role Assignment:** Links three elements together:
     $$\text{Role Assignment} = \langle \text{Principal (User/Group/SPN)}, \text{Role Definition}, \text{Scope (MgmtGroup/Sub/RG/Resource)} \rangle$$

---

### 2.3 Google Cloud Platform (GCP) Cloud IAM
- **Cloud IAM Member Types:** `user:email`, `group:email`, `serviceAccount:email`, `domain:domain.com`.
- **Service Accounts:** Represent machine identities formatted as:
  $$\text{service-account-name}@\text{project-id}.\text{iam.gserviceaccount.com}$$
- **Role Categories:**
  - *Primitive Roles:* `roles/owner`, `roles/editor`, `roles/viewer` (Coarse-grained; strictly prohibited in production).
  - *Predefined Roles:* Fine-grained roles curated by Google (e.g., `roles/storage.objectViewer`, `roles/pubsub.publisher`).
  - *Custom Roles:* User-defined collections of specific permissions (e.g., `compute.instances.start`).
- **Workload Identity Federation:** Allows external workloads (running in AWS, Azure, on-premises Kubernetes, or GitHub Actions) to impersonate a GCP Service Account by exchanging their native OpenID Connect (OIDC) tokens via Google's Security Token Service—**completely eliminating static JSON service account keys!**

## 🔑 4. Zero-Trust Keyless CI/CD Federation: GitHub Actions to Cloud

Static cloud credentials stored in GitHub Secrets represent one of the most common attack vectors in enterprise breaches. Below is the modern keyless OpenID Connect architecture:

```text
===================================================================================================
                   KEYLESS CI/CD AUTHENTICATION VIA OPENID CONNECT (OIDC)
===================================================================================================

  [ GitHub Actions Pipeline ]                 [ Cloud STS / Token Exchange ]        [ Target Resource ]
              │                                             │                                │
  1. Job starts; requests OIDC token                       │                                │
     from GitHub Token Service                             │                                │
              │                                             │                                │
  2. GitHub returns signed JWT                              │                                │
     (Issuer: token.actions.githubusercontent.com)          │                                │
              │                                             │                                │
  3. POST JWT token to Cloud STS ──────────────────────────►│                                │
     (AWS STS / Azure Entra / GCP WIF)                      │                                │
                                                            │                                │
                                                 4. Validates:                               │
                                                    - JWT Signature against JWKS             │
                                                    - Audience (Aud)                         │
                                                    - Subject (repo:org/repo:ref)            │
                                                            │                                │
  5. Returns Short-Lived Ephemeral Cloud Token ◄────────────┘                                │
     (AWS AccessKey/Secret/Token or OAuth2 Bearer)                                           │
              │                                                                              │
  6. Execute deployment commands with temporary credentials ────────────────────────────────►│
```

## 💥 5. Real-World Security Post-Mortem: SSRF & IMDS Exploitation

### The Attack: The Capital One Breach (2019)
The most notorious cloud identity exploitation in history occurred through a Server-Side Request Forgery (SSRF) flaw on an AWS EC2 instance running a ModSecurity WAF.

```text
===================================================================================================
                         IMDSv1 SSRF VULNERABILITY VS. IMDSv2 DEFENSE
===================================================================================================

 [ The IMDSv1 Vulnerability (Exploited in Capital One) ]
 Attacker sends malicious HTTP request to misconfigured WAF/Reverse Proxy:
   GET /proxy?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/WAF-Role
 
 1. WAF server forwards request blindly to link-local address: 169.254.169.254.
 2. AWS IMDSv1 responds with:
    { "AccessKeyId": "ASIA...", "SecretAccessKey": "...", "Token": "..." }
 3. Attacker extracts AWS credentials and exfiltrates 700 S3 buckets containing 100M+ credit records!

 [ The IMDSv2 Session Token Defense ]
 IMDSv2 requires a stateful session-oriented token exchange:
 
 Step 1: PUT request with custom header to acquire session token:
   PUT http://169.254.169.254/latest/api/token
   Header: "X-aws-ec2-metadata-token-ttl-seconds: 21600"
 
 Step 2: Use token in subsequent GET request:
   GET http://169.254.169.254/latest/meta-data/iam/security-credentials/WAF-Role
   Header: "X-aws-ec2-metadata-token: <session_token>"

 🌟 Why IMDSv2 Neutralizes SSRF:
 - Standard SSRF injection flaws cannot forge arbitrary HTTP methods (`PUT`) or custom headers.
 - AWS limits IP packet Time-To-Live (TTL = 1 hop) on IMDSv2 responses, preventing container proxies!
```

### Azure and GCP Equivalents
- **Azure IMDS:** Always requires a mandatory HTTP header: `Metadata: true`. Any request lacking this header is rejected immediately with HTTP 400 Bad Request.
- **GCP Compute Metadata:** Requires the HTTP header: `Metadata-Flavor: Google`. Requests without this header are dropped by the hypervisor network filter.

## 🛠️ 6. Production Security Manifests

### 6.1 AWS IAM Policy with Strict Contextual Constraints
Enforces TLS 1.2+ encryption in transit and restricts bucket access strictly to principals originating from within the corporate AWS Organization:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceTLSRequestsOnly",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::enterprise-data-lake-prod",
        "arn:aws:s3:::enterprise-data-lake-prod/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    },
    {
      "Sid": "RestrictToOrganizationPrincipals",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::enterprise-data-lake-prod",
        "arn:aws:s3:::enterprise-data-lake-prod/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalOrgID": "o-a1b2c3d4e5"
        }
      }
    }
  ]
}
```

### 6.2 GCP Cloud IAM Binding with CEL Condition
Grants storage viewer access exclusively during standard business hours and restricted to corporate IP ranges using Common Expression Language (CEL):

```yaml
bindings:
  - role: roles/storage.objectViewer
    members:
      - "group:analytics-engineers@enterprise.com"
    condition:
      title: "BusinessHoursAndCorporateIP"
      description: "Allow data access only during work hours from trusted egress IP"
      expression: >
        request.time.getHours('America/New_York') >= 9 &&
        request.time.getHours('America/New_York') <= 18 &&
        request.time.getDayOfWeek('America/New_York') >= 1 &&
        request.time.getDayOfWeek('America/New_York') <= 5 &&
        ip_in_range(request.ip, '198.51.100.0/24')
```

## 🎯 7. Architectural Takeaways & Security Checklist

1. **Purge Long-Lived API Keys:** Mandate AWS IAM Roles, Azure Managed Identities, and GCP Workload Identity Federation. Disallow IAM user access keys across all production subscriptions and projects.
2. **Enforce IMDSv2 Universally:** Configure launch templates to require `HttpTokens = required` and set `HttpPutResponseHopLimit = 1` to block container escape SSRF attacks.
3. **Least Privilege Boundaries:** Combine identity policies with **AWS Permissions Boundaries**, **Azure Policy Deny**, or **GCP IAM Deny Policies** to prevent development teams from escalating their own privileges.
