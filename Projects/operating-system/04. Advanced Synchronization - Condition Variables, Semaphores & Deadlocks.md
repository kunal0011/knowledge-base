## 💤 1. From Spinning to Sleeping: The Linux `futex` Architecture

While spinlocks are ideal for short, low-latency critical sections in kernel interrupt handlers, using a spinlock in user space is catastrophic: if the thread holding the lock is preempted by the OS scheduler, all other threads will spin, burning $100\%$ CPU cycles doing zero useful work.

To solve this, modern operating systems implement **Sleeping Locks** powered by the Linux **`futex` (Fast Userspace Mutex)** system call:

```text
===================================================================================================
                                  LINUX FUTEX TWO-TIERED ARCHITECTURE
===================================================================================================

  Thread requests Lock:
           │
           ▼
  [ Fast Path: Zero Kernel Traps! ]
  Execute atomic Compare-And-Swap (CAS) in User Space (0 -> 1)
           │
           ├─► SUCCESS: Lock acquired! Cost = ~10 nanoseconds.
           │
           ▼ FAILURE (Lock is already held)
  [ Slow Path: Fallback to Kernel ]
  Invoke syscall: futex(addr, FUTEX_WAIT, expected_val, NULL)
           │
           ▼
  Kernel puts thread state to TASK_INTERRUPTIBLE
  Places thread on hash-bucket wait queue associated with physical address
  Invokes schedule() to immediately yield CPU to another process!
```

When the holding thread releases the lock:
1. If no threads are waiting, it resets the integer in user space via atomic swap ($0$ syscalls).
2. If waiting threads exist, it invokes `futex(addr, FUTEX_WAKE, 1)`, prompting the kernel to wake the sleeping thread and transition it back to the `READY` runqueue.

## ⏳ 2. Condition Variables & The Mesa Semantics Invariant

A **Condition Variable** provides synchronization based on data state rather than lock ownership. It supports two primary operations:
- `wait(cond, mutex)`: Atomically releases the mutex and suspends the calling thread on the condition queue. When awakened, it re-acquires the mutex before returning.
- `signal(cond)`: Awakens one thread waiting on the condition queue.

### 2.1 Mesa vs. Hoare Semantics: Why `while`, Never `if`
In theoretical literature (**Hoare Semantics**), signaling a thread transfers the lock and CPU execution directly to the awakened thread immediately. 

In real-world operating systems (**Mesa Semantics**, used in Linux, POSIX `pthreads`, Java, and Go):
- Signaling a thread merely moves it from the condition wait queue to the lock ready queue.
- By the time the awakened thread actually runs, **another thread may have sneaked in, acquired the lock, and modified the state again**.
- Additionally, POSIX permits **Spurious Wakeups** (threads waking without any explicit signal due to OS signal interruptions).

```text
===================================================================================================
                                THE FATAL "IF" RACE CONDITION
===================================================================================================

  Thread A (Consumer)            Thread B (Producer)            Thread C (Sneaky Consumer)
  ───────────────────            ───────────────────            ──────────────────────────
  Buffer is EMPTY
  Calls wait(&cv, &mutex)
  [ Goes to Sleep ]
                                 Produces item into buffer
                                 Calls signal(&cv)
                                 Wakes Thread A
                                                                Acquires lock FIRST!
                                                                Consumes the item!
                                                                Buffer is now EMPTY!
                                                                Releases lock
  Thread A finally runs...
  If it used "if", it attempts
  to consume from EMPTY buffer!
  ==> CRASH / SEGFAULT!
```

> [!CAUTION]
> **The Golden Law of Condition Variables:** Always evaluate the condition inside a **`while` loop**, never an `if` statement:
> ```c
> pthread_mutex_lock(&mutex);
> while (ready == 0) {
>     pthread_cond_wait(&cond, &mutex);
> }
> // Safe to proceed: state is guaranteed true under lock
> pthread_mutex_unlock(&mutex);
> ```

## 🏭 3. The Producer-Consumer (Bounded Buffer) Solution

```c
#include <pthread.h>
#define BUFFER_SIZE 16

int buffer[BUFFER_SIZE];
int fill_ptr = 0;
int use_ptr  = 0;
int count    = 0;

pthread_mutex_t lock  = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t  fill  = PTHREAD_COND_INITIALIZER;

void put(int val) {
    buffer[fill_ptr] = val;
    fill_ptr = (fill_ptr + 1) % BUFFER_SIZE;
    count++;
}

int get() {
    int val = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % BUFFER_SIZE;
    count--;
    return val;
}

void *producer(void *arg) {
    for (int i = 0; i < 1000; i++) {
        pthread_mutex_lock(&lock);
        while (count == BUFFER_SIZE) {          // While buffer is FULL
            pthread_cond_wait(&empty, &lock);   // Sleep waiting for empty slot
        }
        put(i);
        pthread_cond_signal(&fill);             // Signal consumers that an item is ready
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 1000; i++) {
        pthread_mutex_lock(&lock);
        while (count == 0) {                    // While buffer is EMPTY
            pthread_cond_wait(&fill, &lock);    // Sleep waiting for an item
        }
        int item = get();
        pthread_cond_signal(&empty);            // Signal producers that a slot is freed
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
```

## 🚦 4. Dijkstra's Semaphores

Invented by Edsger Dijkstra, a **Semaphore** is an integer variable with two atomic operations:
1. `sem_wait(s)` (or $P$): Decrements $s$. If $s < 0$, suspends the calling thread.
2. `sem_post(s)` (or $V$): Increments $s$. If threads are waiting, wakes one up.

### 4.1 Throttling & Rate-Limiting with Counting Semaphores
```c
sem_t db_pool_limiter;

void init_pool() {
    // Initialize semaphore to 5: allow at most 5 concurrent DB connections
    sem_init(&db_pool_limiter, 0, 5);
}

void execute_query() {
    sem_wait(&db_pool_limiter); // Blocks if 5 queries are already running
    // ... execute heavy SQL query ...
    sem_post(&db_pool_limiter); // Releases slot for waiting queries
}
```

## 💀 5. Deadlocks & The Coffman Conditions

A **Deadlock** occurs when a set of concurrent processes are permanently blocked because each process holds a resource that another process needs while waiting for a resource held by that other process.

```text
===================================================================================================
                               CIRCULAR DEADLOCK VISUALIZATION
===================================================================================================

                    ┌──────────────┐
                    │   Mutex L1   │◄──────────────┐
                    └──────┬───────┘               │
             Held by       │                       │ Wanted by
                           ▼                       │
                    ┌──────────────┐        ┌──────┴───────┐
                    │   Thread 1   │        │   Thread 2   │
                    └──────┬───────┘        └──────────────┘
                           │                       ▲
                 Wanted by │                       │ Held by
                           ▼                       │
                    ┌──────────────┐               │
                    │   Mutex L2   ├───────────────┘
                    └──────────────┘
```

### 5.1 The Four Coffman Conditions (All 4 Required!)
A system can deadlock if and only if **all four** conditions hold simultaneously:
1. **Mutual Exclusion:** Resources cannot be shared; only one thread can hold a resource at a time.
2. **Hold and Wait:** A thread holds at least one resource while waiting to acquire additional resources held by others.
3. **No Preemption:** Resources cannot be forcibly revoked from a thread; they can only be released voluntarily.
4. **Circular Wait:** There exists a closed chain of threads $\{T_1, T_2, \dots, T_n\}$ such that $T_1$ waits for a resource held by $T_2$, and $T_n$ waits for a resource held by $T_1$.

### 5.2 Deadlock Prevention: Total Resource Ordering
The most practical engineering solution to deadlocks is breaking the **Circular Wait** condition by establishing a **Global Lock Ordering Rule**:
> If any thread needs both Lock $A$ and Lock $B$, every thread across the entire codebase must acquire Lock $A$ before Lock $B$.

## 🚀 6. Priority Inversion & The Mars Pathfinder Anomaly

In 1997, the NASA Mars Pathfinder spacecraft experienced repeated total system resets on Mars. 

### The Root Cause: Unbounded Priority Inversion
Three tasks shared CPU time under a preemptive priority scheduler:
- **Task High ($T_H$):** Mission-critical attitude control thread.
- **Task Medium ($T_M$):** Long-running, low-importance communications thread.
- **Task Low ($T_L$):** Meteorological sensor thread.

```text
1. Task Low (TL) acquires shared Mutex M.
2. High-priority Task High (TH) wakes up and needs Mutex M.
   - TH blocks waiting for TL to release Mutex M.
3. Medium-priority Task Medium (TM) wakes up.
   - TM has higher priority than TL, so the OS scheduler preempts TL!
4. TM runs for a long time.
   - TL never gets to run, so TL can never release Mutex M!
   - TH (the most critical task) is starved indefinitely by TM!
5. Watchdog timer triggers, assuming system is frozen -> Reboots spacecraft!
```

### The Fix: Priority Inheritance Protocol
When a high-priority task ($T_H$) blocks waiting for a lock held by a low-priority task ($T_L$), the OS **temporarily elevates $T_L$'s priority to match $T_H$**. $T_L$ runs immediately, finishes its critical section, releases the lock, and drops back to its original priority—allowing $T_H$ to acquire the lock with zero delay!
