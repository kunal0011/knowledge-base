## 1. Theoretical Motivation: Characters vs. Bytes

In *Fluent Python*, Luciano Ramalho highlights the defining breakthrough of Python 3: **the absolute separation between human text and raw binary data**.

```
              HUMAN TEXT                                     MACHINE BYTES
      Sequence of Unicode Code Points                   Sequence of 8-bit Integers
           Type: str (Text)                                Type: bytes / bytearray
                  |                                                  ^
                  |                .encode('utf-8')                  |
                  +--------------------------------------------------+
                  |                                                  |
                  |                .decode('utf-8')                  |
                  v                                                  |
                  +--------------------------------------------------+
```

- **A Character is a Unicode Code Point:** An abstract mathematical integer between `U+0000` and `U+10FFFF` (represented as `\uXXXX` or `\UXXXXXXXX`).
- **Bytes are Raw Octets:** Physical 8-bit integers ($0$ to $255$) stored on disk or transmitted across network sockets.
- **An Encoding is a Translation Protocol:** Algorithms like UTF-8, UTF-16, and ASCII map code points to byte sequences.

## 2. Underlying Architecture: PEP 393 Flexible String Representation

Prior to Python 3.3, Python compiled strings either with 2-byte UCS-2 or 4-byte UCS-4 buffers. This was disastrous: a pure ASCII string in a UCS-4 build wasted **75% of RAM** storing zeros.

In Python 3.3+, **PEP 393** introduced a dynamic, flexible string architecture:

```
CPython PyCompactUnicodeObject Layout:
+-------------------------------------------------------------------------+
| PyObject Header (ob_refcnt, ob_type)                                    |
| length (number of characters)                                           |
| hash memoization field                                                  |
| state flags: interned, kind (1, 2, or 4 bytes per char), compact, ascii |
+-------------------------------------------------------------------------+
| Character Payload: Sized strictly according to maximum code point!      |
+-------------------------------------------------------------------------+
```

### The Three Internal Storage Kinds:
1. **1 Byte per Character (Latin-1 / ASCII):** If all code points in the string are $< 256$ (`U+0000` to `U+00FF`), CPython uses an 8-bit `uint8_t` array.
2. **2 Bytes per Character (UCS-2):** If the maximum code point is $< 65536$ (`U+0100` to `U+FFFF`), CPython uses a 16-bit `uint16_t` array.
3. **4 Bytes per Character (UCS-4):** If even a single character exceeds `U+FFFF` (e.g., an emoji like `\U0001F600` 😀), the entire string is promoted to a 32-bit `uint32_t` array.

```python
import sys

s1 = "hello world"      # All ASCII
s2 = "café"            # Max codepoint: é (U+00E9 = 233 < 256) -> 1 byte per char
s3 = "привет"          # Max codepoint: Cyrillic (U+043F = 1087) -> 2 bytes per char
s4 = "hello 😀"         # Max codepoint: Emoji (U+1F600) -> 4 bytes per char!

print(sys.getsizeof(s1)) # 60 bytes
print(sys.getsizeof(s4)) # 104 bytes (Promoted to 4 bytes per char!)
```

## 3. The "Unicode Sandwich" Architectural Model

In production systems handling web APIs, database records, and file systems, Ramalho recommends the **Unicode Sandwich** pattern:

```
               [ Input Boundary: File / Socket / DB ]
                                  |
                                  v
                       DECODE BYTES TO STR EARLY
                                  |
                                  v
               +-------------------------------------+
               |         CORE BUSINESS LOGIC         |
               |       Strictly 100% Unicode         |
               |        (No raw bytes allowed)       |
               +-------------------------------------+
                                  |
                                  v
                       ENCODE STR TO BYTES LATE
                                  |
                                  v
               [ Output Boundary: File / Socket / HTTP ]
```

## 4. Unicode Normalization: The String Comparison Trap

In Unicode, visually identical glyphs can be represented by completely different byte sequences and code points:

```python
# The word "café" represented in two distinct Unicode formats:
s1 = 'café'            # 4 code points: 'c', 'a', 'f', '\u00e9' (é as single precomposed char)
s2 = 'cafe\u0301'      # 5 code points: 'c', 'a', 'f', 'e', '\u0301' (e + combining acute accent)

print(s1 == s2)        # FALSE!
print(len(s1), len(s2))# 4 5
```

### The Solution: `unicodedata.normalize`
Unicode defines four standard normalization forms:
- **NFC (Normalization Form C):** Composes characters into shortest equivalent precomposed characters (Standard for web and storage).
- **NFD (Normalization Form D):** Decomposes precomposed characters into base characters and separate combining marks.
- **NFKC / NFKD (Compatibility forms):** Normalizes formatting differences (e.g., converts ligature `ﬁ` into `fi`, or exponent `²` into `2`).

```python
import unicodedata

# Normalize both strings to NFC before comparing:
norm_s1 = unicodedata.normalize('NFC', s1)
norm_s2 = unicodedata.normalize('NFC', s2)

print(norm_s1 == norm_s2)  # TRUE!
```

### Case Folding for Case-Insensitive Matching
Never use `.lower()` for robust case-insensitive comparisons across international text. Use `.casefold()`:
```python
# German lowercase sharp s:
s = "straße"
print(s.lower())     # 'straße'
print(s.casefold())  # 'strasse' (Matches 'STRASSE'!)
```

## 5. Binary Data Parsing with `struct`

For parsing binary network packet headers, C structs, and file formats without manual bit shifting:

```python
import struct

# Format string:
# > : Big-endian (network byte order)
# H : 2-byte unsigned short (Header ID)
# I : 4-byte unsigned int (Sequence number)
# f : 4-byte float (Payload sensor reading)
packet_fmt = '>HIf'

# Packing binary bytes:
binary_data = struct.pack(packet_fmt, 101, 2048, 98.6)
print(len(binary_data))  # Exactly 10 bytes!
print(binary_data)       # b'\x00e\x00\x00\x08\x00Bp\xcc\xcd'

# Unpacking bytes back into Python primitives:
header_id, seq, reading = struct.unpack(packet_fmt, binary_data)
print(header_id, seq, f"{reading:.1f}")  # 101 2048 98.6
```

## 6. Authoritative Gotchas & Traps (Ramalho & Lutz)

### 6.1 The Encoding Blindness Trap: Never Rely on Default Encoding
```python
# DISASTROUS ANTI-PATTERN:
with open('data.txt', 'w') as f:
    f.write('café')
```
**Why it fails:** If `encoding` is omitted, Python uses `locale.getpreferredencoding()`. On Linux/macOS, this is typically `utf-8`. On Windows, it is frequently `cp1252` or `gbk`. Code that runs perfectly on macOS will crash with `UnicodeEncodeError` on Windows!  
**The Golden Rule:** **ALWAYS** specify `encoding='utf-8'` explicitly when opening text files.

### 6.2 Encoding Error Handlers
```python
city = 'São Paulo'

# 1. 'strict' (Default): Raises exception on unrecognized characters
try:
    city.encode('ascii')
except UnicodeEncodeError as e:
    print("Strict blocked:", e)

# 2. 'replace': Replaces invalid bytes with '?' or \ufffd
print(city.encode('ascii', errors='replace')) # b'S?o Paulo'

# 3. 'ignore': Silently drops unencodable characters (DANGEROUS DATA LOSS!)
print(city.encode('ascii', errors='ignore'))  # b'So Paulo' (Corrupted!)
```

## 7. Actionable Summary Checklist

- [x] Text is `str` (Unicode code points); binary is `bytes` (8-bit integers). Keep them strictly separated.
- [x] Follow the **Unicode Sandwich**: decode bytes immediately upon input; process strictly as `str`; encode back to `bytes` only at the output boundary.
- [x] Always pass `encoding='utf-8'` to `open()` to prevent cross-platform locale encoding crashes.
- [x] Normalize strings using `unicodedata.normalize('NFC', s)` before comparing user-supplied Unicode text.
- [x] Use `s.casefold()` instead of `s.lower()` for international case-insensitive comparisons.
- [x] Use the `struct` module for parsing binary protocols and packed C structs directly.
