# Chapter 10: Modern Data Lakehouse & Table Formats — Iceberg, Delta Lake & Hudi

> "For over a decade, Data Lakes were plagued by the lack of transactions, corrupted partial writes, and agonizing directory listings. Open Table Formats like Apache Iceberg and Delta Lake brought true ACID guarantees, schema evolution, and time travel to cloud object storage, unifying the data warehouse and the data lake into the Modern Lakehouse."  
> — *Ryan Blue & Dan Weeks, Apache Iceberg: The Definitive Guide*

---

## 🚫 1. The Death of Data Lake 1.0 (The Hive Metastore Flaw)

In the original Hadoop/Hive paradigm, a "table" was simply a folder of files on HDFS or S3:
`s3://company-lake/orders/country=US/year=2026/month=09/part-0001.parquet`

This directory-based model suffered from four critical production failures:

```text
===================================================================================================
                               DATA LAKE 1.0 ARCHITECTURAL TRAPS
===================================================================================================

  ⚠️ 1. LACK OF ATOMICITY (Corrupted Partial Writes)
     If a Spark job writing 1,000 files to S3 crashes at file 750, the table is left in a corrupted,
     half-written state. Downstream BI queries read incomplete, invalid data!

  ⚠️ 2. ZERO CONCURRENCY (Dirty Reads & Race Conditions)
     If a reader queries a table while a writer is modifying it, the reader observes a mix of
     old files and new files, yielding non-deterministic, phantom numbers.

  ⚠️ 3. THE S3 OBJECT LISTING BOTTLENECK
     To execute a query, the query engine had to invoke S3 LIST operations recursively over millions
     of objects. S3 LIST requests took 15 to 30 minutes just to determine which files existed!

  ⚠️ 4. RIGID PHYSICAL PARTITIONING
     If an engineer partitioned by `date` and later wanted to query by `month`, the query engine
     could not optimize it without rewriting petabytes of data into new directory trees!
```

## 🧊 2. Apache Iceberg: The Hierarchical Metadata Tree

Created by Ryan Blue and Dan Weeks at Netflix, **Apache Iceberg** solved this by tracking a table not as a folder of files, but as an **immutable tree of snapshot metadata**:

```text
===================================================================================================
                                  APACHE ICEBERG METADATA TREE
===================================================================================================

  [ Iceberg Catalog (AWS Glue / REST / Nessie) ] ──► Points to Current Version: v3.metadata.json
                                                              │
                                                              ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ METADATA FILE: v3.metadata.json                                                             │
  │ - Table Schema (Tracks fields via permanent integer IDs, NOT names!)                        │
  │ - Partition Specifications & Snapshot History Log                                           │
  │ - Current Snapshot ID: 1048201                                                              │
  └──────────────────────────────────────────────┬──────────────────────────────────────────────┘
                                                 │
                                                 ▼
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ MANIFEST LIST: snap-1048201.avro                                                            │
  │ - List of all active Manifest Files participating in Snapshot 1048201                       │
  │ - Manifest Summary & Partition Range Bounds                                                 │
  └──────────────────────┬──────────────────────────────────────────────┬───────────────────────┘
                         │                                              │
                         ▼                                              ▼
  ┌──────────────────────────────────────────┐  ┌──────────────────────────────────────────┐
  │ MANIFEST FILE: manifest-A.avro           │  │ MANIFEST FILE: manifest-B.avro           │
  │ - File Path: s3://.../data-01.parquet    │  │ - File Path: s3://.../data-03.parquet    │
  │ - Min/Max Stats for EVERY Column         │  │ - Min/Max Stats for EVERY Column         │
  └──────────────────────┬───────────────────┘  └──────────────────────────────────────────┘
                         │
                         ▼
  ┌──────────────────────────────────────────┐
  │ DATA FILE: data-01.parquet               │
  │ Raw Columnar Data Blocks                 │
  └──────────────────────────────────────────┘
```

## ⚡ 3. ACID Transactions via Optimistic Concurrency Control (OCC)

Iceberg achieves full ACID transactional guarantees over standard object storage (AWS S3, GCS, ADLS):

1. **Snapshot Isolation:** Readers always read from a stable, immutable snapshot. They are completely decoupled from concurrent writers!
2. **Atomic Commits:** When a writer finishes writing new Parquet data files, it writes a new Manifest List and a new Metadata File (`v4.metadata.json`).
3. **Commit via CAS (Compare-And-Swap):** The writer attempts an atomic update on the central Catalog:
   $$\text{Catalog.swap}(\text{old} = \text{v3.metadata.json},\ \text{new} = \text{v4.metadata.json})$$
   - If successful: The transaction becomes globally active in a **single atomic swap**!
   - If another writer committed first: Conflict detected! The engine checks if the changes overlap. If non-conflicting, it automatically re-bases and commits. Otherwise, it safely rolls back!

## 🕰️ 4. Time Travel & Instant Disaster Recovery

Because previous snapshot metadata trees are retained, querying historical versions of tables requires zero backup restores:

```sql
-- Query table exactly as it existed on September 1st, 2026!
SELECT * 
FROM analytics.orders 
FOR SYSTEM_TIME AS OF '2026-09-01 00:00:00 UTC';

-- Query table using a specific Snapshot ID:
SELECT * 
FROM analytics.orders 
FOR SYSTEM_VERSION AS OF 1048201;
```

If a rogue script or buggy ETL pipeline accidentally deletes or corrupts millions of records, an engineer rolls back the table to the prior valid snapshot in **under 100 milliseconds**:
```sql
CALL iceberg.system.rollback_to_snapshot('analytics.orders', 1048201);
```

## ⚖️ 5. The Big Three Open Table Formats: Iceberg vs. Delta vs. Hudi

| Dimension | Apache Iceberg | Delta Lake (Databricks) | Apache Hudi (Uber) |
| :--- | :--- | :--- | :--- |
| **Origin & Focus** | Netflix (Universal open standard, general analytics) | Databricks (Deep Spark integration, unified batch/streaming) | Uber (Real-time CDC, high-frequency streaming upserts) |
| **Metadata Mechanism** | **Hierarchical Snapshot Tree** (`.json` $\to$ Manifest Lists $\to$ Manifests) | **Linear Transaction Log** (`_delta_log/` JSON commits + Parquet checkpoints) | **Timeline & Log** (Timeline files + `.deltacommit`) |
| **Partitioning** | **Hidden Partitioning** (Translates time transforms without user query modifications) | Hive-style physical directory paths | Hive-style or virtual key partitioning |
| **Mutation Models** | Copy-on-Write & Merge-on-Read (Equality & Position Delete Files) | Copy-on-Write (Deletion Vectors in Delta 3.0+) | **Merge-on-Read (MoR)** with specialized Avro row log files |
| **Engine Agnosticism** | 100% engine agnostic (First-class in Trino, Snowflake, Spark, DuckDB) | Highly optimized for Spark; expanding to Trino/Presto | Primarily Spark and Flink |
