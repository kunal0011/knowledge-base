# Chapter 02: Memory Virtualization — Paging, Segmentation, TLB & Virtual Memory

> "The abstraction of an address space allows the operating system to create the illusion that each process has its own large, private physical memory. With memory virtualization, the OS and hardware coordinate to translate every memory access into a physical location on the RAM chips."  
> — *Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau, Operating Systems: Three Easy Pieces (OSTEP)*

---

## 🧠 1. The Virtual Address Space Abstraction

When a C program prints the memory address of a pointer (`printf("%p", &x)`), the address printed is not physical RAM; it is a **Virtual Address**. Memory virtualization achieves three core imperatives:
1. **Transparency:** The program executes as though it owns all physical memory contiguously.
2. **Efficiency:** Virtualization must incur negligible time overhead (leveraging hardware MMUs and TLBs) and minimal space overhead (avoiding bloated mapping tables).
3. **Protection & Isolation:** No process can read, write, or corrupt the private memory space or kernel data structures of another process.

---

## 📑 2. Paging Foundations & Multi-Level Page Tables

Early systems used **Segmentation** (carving memory into variable-sized chunks for Code, Heap, and Stack). Segmentation inevitably caused **External Fragmentation** (free physical memory was chopped into tiny unusable slivers between active allocations).

Paging solves external fragmentation by dividing memory into fixed-size chunks:
- **Virtual Page (VP):** Fixed-size block of virtual memory (typically $4\text{ KB}$).
- **Physical Frame (PFN / Page Frame Number):** Fixed-size slot in physical RAM.

### 2.1 The Memory Explosion of Linear Page Tables
On a 32-bit system with $4\text{ KB}$ ($2^{12}\text{ bytes}$) pages:
- Virtual address space $= 2^{32} = 4\text{ GB}$.
- Number of pages $= \frac{2^{32}}{2^{12}} = 2^{20} \approx 1,000,000\text{ pages}$.
- If each Page Table Entry (PTE) is $4\text{ bytes}$, a linear page table consumes **$4\text{ MB}$ of contiguous RAM per process**. With 500 processes, $2\text{ GB}$ of RAM is squandered purely on page tables!
- On 64-bit systems, a linear page table would consume millions of gigabytes per process—making linear tables mathematically impossible.

---

### 2.2 Four-Level Paging Architecture (x86_64)

Modern 64-bit architectures use **Multi-Level Page Tables** arranged as a tree. If an entire branch of an address space is unmapped (e.g., the unused void between the heap and the stack), **none of the lower-level page tables are allocated**.

In x86_64, a 48-bit canonical virtual address is split into five fields:
$$\text{48-Bit Virtual Address} = \underbrace{\text{PGD (9 bits)}}_{\text{Level 4}} + \underbrace{\text{PUD (9 bits)}}_{\text{Level 3}} + \underbrace{\text{PMD (9 bits)}}_{\text{Level 2}} + \underbrace{\text{PTE (9 bits)}}_{\text{Level 1}} + \underbrace{\text{Offset (12 bits)}}_{\text{In-Page Offset}}$$

```text
===================================================================================================
                     x86_64 4-LEVEL HIERARCHICAL PAGE TABLE WALK
===================================================================================================

 Virtual Address: [ PGD: 9b ] [ PUD: 9b ] [ PMD: 9b ] [ PTE: 9b ] [ Offset: 12b ]
                        │           │           │           │             │
  %cr3 Register         │           │           │           │             │
       │                │           │           │           │             │
       ▼                ▼           ▼           ▼           ▼             │
  ┌──────────┐     ┌──────────┐┌──────────┐┌──────────┐┌──────────┐       │
  │   PGD    ├────►│   PUD    ├┼─►  PMD   ├┼─►  PTE   ├┼─► Physical       │
  │ (Level 4)│     │ (Level 3)││ (Level 2)││ (Level 1)││ Page Frame      │
  └──────────┘     └──────────┘└──────────┘└──────────┘└────┬─────┘       │
   (512 entries)   (512 entries) (512 entries)(512 entries) │             │
                                                            ▼             ▼
                                             Physical Address: [ PFN ] [ Offset ]
```

Every page table at every level occupies exactly $4096\text{ bytes}$ ($512\text{ entries} \times 8\text{ bytes per entry}$).

## ⚡ 3. Translation Lookaside Buffer (TLB) & Fast Hardware Walks

A 4-level page table walk requires **five physical memory accesses** to read a single integer from memory (4 for the page table traversal $+ 1$ for the actual memory reference). To prevent memory operations from slowing down by $500\%$, hardware CPUs incorporate an on-chip, ultra-fast associative cache: the **Translation Lookaside Buffer (TLB)**.

```text
===================================================================================================
                                      TLB HARDWARE LOOKUP FLOW
===================================================================================================

                                 Virtual Address Generated by CPU
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │ Extract VPN & Offset  │
                                    └───────────┬───────────┘
                                                │
                                                ▼
                                    ┌───────────────────────┐
                                    │     Check MMU TLB     │
                                    └───────────┬───────────┘
                                                │
                         ┌──────────────────────┴──────────────────────┐
                         ▼ HIT                                         ▼ MISS
             ┌───────────────────────┐                     ┌───────────────────────┐
             │ Fast Path (1 Cycle)   │                     │ Slow Path (MMU Walk)  │
             │ Retrieve PFN directly │                     │ Walk PGD -> PUD ->    │
             │ from on-chip TLB SRAM │                     │ PMD -> PTE in memory  │
             └───────────┬───────────┘                     └───────────┬───────────┘
                         │                                             │
                         │                                             ▼
                         │                                 Install translation in TLB
                         │                                             │
                         └──────────────────────┬──────────────────────┘
                                                │
                                                ▼

```

### 3.1 Context Switches & Process Context Identifiers (PCID)
Historically, whenever the OS executed a context switch, it had to flush the entire TLB (`INVLPG` or reloading `%cr3`) because virtual address `0x00400000` in Process $A$ mapped to a completely different physical frame than in Process $B$. This resulted in catastrophic cache misses following every context switch.

Modern processors use **PCID (Process Context Identifiers)** (or **ASID** on ARM). Each TLB entry is tagged with a 12-bit ID indicating which process owns the translation. On a context switch, the OS changes the active PCID without wiping the TLB entries, allowing Process $A$'s translations to remain cached when it gets rescheduled!

## 💥 4. Page Faults & Demand Paging

A **Page Fault** is not necessarily a bug; it is an architectural interrupt (x86 Interrupt Vector 14, `#PF`) raised by the Memory Management Unit (MMU) when an address translation cannot be completed.

```text
===================================================================================================
                                  PAGE FAULT RESOLUTION PATH
===================================================================================================

  CPU attempts memory access ──► MMU checks PTE Present Bit
                                           │
                        ┌──────────────────┴──────────────────┐
                        ▼ Present Bit = 1                     ▼ Present Bit = 0
                Hardware executes access                      Hardware raises #PF Trap
                                                              CPU saves faulting address in %cr2
                                                                       │
                                                                       ▼
                                                       Kernel do_page_fault() Handler
                                                                       │
        ┌──────────────────────────────────────────────────────────────┼─────────────────────────────────────────┐
        ▼                                                              ▼                                         ▼
 [ Case 1: Segmentation Fault ]                             [ Case 2: Demand Paging ]                  [ Case 3: Copy-on-Write (CoW) ]
 Address outside any vm_area_struct                         Valid anonymous/file memory                 Shared page marked Read-Only
 (e.g., NULL pointer dereference)                           Allocate physical RAM frame                 Kernel allocates fresh RAM frame
 Kernel sends SIGSEGV to process                            Load from disk/swap into RAM                Copies 4KB data from shared page
 Process terminated!                                        Update PTE Present=1                        Marks new PTE Read-Write
                                                            Restart faulting instruction!               Restart faulting instruction!
```

## 👥 5. Copy-on-Write (CoW) Mechanics in `fork()`

When a parent process calls `fork()`, duplicating its entire multi-gigabyte memory space would be prohibitively slow and waste RAM. Modern operating systems leverage **Copy-on-Write (CoW)**:
1. The kernel duplicates the page tables of the parent into the child, but **does not copy physical memory frames**.
2. Both parent and child PTEs are modified to point to the exact same physical frames.
3. The kernel clears the **Write Bit** (`W=0`) on every single shared page table entry and increments the reference count on the physical page frame (`struct page->_refcount`).
4. Both processes can read shared pages concurrently with zero performance penalty.
5. If either process attempts to write to a page, the MMU triggers a `#PF` trap because `W=0`.
6. The kernel page fault handler checks the page reference count:
   - If reference count $> 1$, it allocates a new physical frame, copies the $4\text{ KB}$ content, updates the faulting process's PTE to point to the new frame with `W=1`, and decrements the old frame's reference count.

## 🔄 6. Swapping & Page Replacement Algorithms

When physical memory is exhausted, the OS must evict pages to disk (Swap space) to make room for incoming allocations.

### 6.1 The Clock (Second-Chance) Algorithm
While True LRU (Least Recently Used) is theoretically ideal, maintaining a linked list of pages in timestamp order on every single memory access is impossible without paralyzing the CPU. The OS approximates LRU using the hardware-supported **Reference (Accessed) Bit**:

```text
===================================================================================================
                                  CLOCK REPLACEMENT ALGORITHM
===================================================================================================

                         Page 0 [Ref=1]
                        /              \
            Page 7 [Ref=0]            Page 1 [Ref=0]  ◄── Clock Hand Pointer
                  │                         │
            Page 6 [Ref=1]            Page 2 [Ref=1]
                        \              /
                         Page 4 [Ref=0]

 Algorithm Steps:
 1. Examine page pointed to by Clock Hand.
 2. If Reference Bit == 1:
    - Clear Reference Bit to 0.
    - Advance Clock Hand to next page.
 3. If Reference Bit == 0:
    - THIS IS OUR VICTIM PAGE!
    - If Dirty Bit == 1, write page out to swap disk.
    - Evict page and allocate frame to new request.
    - Advance Clock Hand.
```
