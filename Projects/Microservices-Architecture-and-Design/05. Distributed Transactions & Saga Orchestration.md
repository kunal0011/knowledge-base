# Chapter 05: Distributed Transactions & Saga Orchestration

> "In a distributed system, you cannot use traditional Two-Phase Commit: locking database rows across asynchronous network boundaries invites deadlocks and downtime. Instead, we use Sagas—breaking distributed transactions into sequences of local transactions with compensating rollbacks."  
> — *Chris Richardson, Microservice Patterns*

---

## 1. Canonical Motivation & Theoretical Foundation

In a monolithic database, transferring funds between two accounts or checking out an e-commerce cart is wrapped in an atomic SQL block:
```sql
BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```
If anything fails, the database rolls back changes automatically.

In a microservices architecture with **Database-per-Service**, an e-commerce checkout spans three separate physical databases:
- **Order Service Database** (PostgreSQL)
- **Payment Service Database** (MySQL)
- **Inventory Service Database** (MongoDB)

### Why Two-Phase Commit (2PC / XA) is Dead in Microservices
Historically, distributed systems used **Two-Phase Commit (2PC)**. In microservices, 2PC is universally regarded as an anti-pattern:
1. **Blocking Row Locks:** 2PC holds physical database row locks across all participating services for the entire duration of the network handshake. If one service experiences a GC pause or network lag, all other services stall.
2. **Availability Collapse:** According to the CAP theorem, 2PC requires $100\%$ availability of all participants. If any single service or network link fails, all transactions abort.
3. **Coordinator SPoF:** If the coordinator crashes mid-commit, database rows remain locked indefinitely (**in-doubt transactions**).

## 2. Underlying Runtime, Memory & Execution Architecture

### The Saga Pattern

Formulated by Hector Garcia-Molina and Kenneth Salem in 1987, a **Saga** is a sequence of local transactions:

$$T_1, \; T_2, \; T_3, \; \dots, \; T_n$$

- Each local transaction $T_i$ updates state in a single service and **commits immediately**, releasing database locks.
- If a step $T_k$ fails (e.g. Insufficient Credit), the Saga executes a sequence of **Compensating Transactions** ($C$) in reverse order to semantically undo previous writes:

$$C_{k-1}, \; C_{k-2}, \; \dots, \; C_1$$

```
 Successful Saga Execution Flow:
 [ Create Order (T1) ] ──> [ Authorize Payment (T2) ] ──> [ Reserve Inventory (T3) ] ──> [ SUCCESS ]

 Failed Saga Execution with Compensations:
 [ Create Order (T1) ] ──> [ Authorize Payment (T2) ] ──> [ Reserve Inventory (T3: Fails!) ]
                                                                   │
                                                                   ▼ (Rollback Triggered)
 [ Reject Order (C1) ] <── [ Refund Payment (C2) ] <───────────────┘
```

---

### Saga Execution Topologies: Choreography vs. Orchestration

```
─────────────────────────────────────────────────────────────────────────────
1. Choreography-Based Saga (Decentralized / Event-Driven)
 [ Order Service ] ──(OrderCreated Event)──> [ Payment Service ]
        ▲                                           │
        │                                           ▼ (PaymentAuthorized Event)
        └──────(InventoryFailed Event)─────── [ Inventory Service ]
 • Services listen to peer events and execute next steps autonomously.
 • Best for: Simple workflows (2–3 services).
 • Vulnerability: Hard to visualize; risk of cyclic event storms.
─────────────────────────────────────────────────────────────────────────────
2. Orchestration-Based Saga (Centralized State Machine)
                               ┌───────────────────────────┐
                               │     Saga Orchestrator     │
                               │  (Explicit State Machine) │
                               └─────────────┬─────────────┘
                     ┌───────────────────────┼───────────────────────┐
                     │ 1. Reserve Credit     │ 2. Deduct Stock       │ 3. Confirm
                     ▼                       ▼                       ▼
            [ Payment Service ]     [ Inventory Service ]    [ Order Service ]
 • A centralized coordinator instructs participants via commands and listens for replies.
 • Best for: Complex business workflows (4+ steps).
 • Advantage: Clear visibility; centralized timeout and compensation logic.
─────────────────────────────────────────────────────────────────────────────
```

## 3. Core Mechanics, Algorithms & Invariants

### Transaction Classifications within a Saga

1. **Compensable Transactions:** Steps that can potentially be undone if downstream steps fail (e.g. creating an order in `PENDING` state, holding inventory).
2. **The Pivot Transaction:** The **point of no return**. If the pivot transaction commits, the Saga is guaranteed to proceed to completion. It is neither compensable nor retriable (e.g. charging a credit card).
3. **Retriable Transactions:** Steps following the pivot transaction that are guaranteed to succeed eventually via retries and idempotent execution (e.g. sending a confirmation email, generating a shipping label).

---

### The Lack of Isolation Anomaly (ACD without I)

Sagas satisfy Atomicity, Consistency, and Durability, but **lack true Isolation**:
- Because local transactions commit immediately, writes made by an in-flight Saga are **visible to other concurrent transactions** before the Saga finishes!

#### Countermeasures for Lack of Isolation:
- **Semantic Lock:** Place an explicit status flag on records (`status = PENDING_APPROVAL`) preventing other transactions from modifying them until the Saga resolves.
- **Commutative Updates:** Design operations so they can be applied in any order (e.g. debiting and crediting balances).
- **Optimistic Concurrency Control:** Attach version numbers to domain entities to detect concurrent modifications.

---

## 4. Practical Systems & Production Engineering Trade-offs

1. **Temporal.io / Cadence:** The industry gold standard for durable, code-as-configuration Saga orchestration with automated state persistence, retries, and compensation.
2. **Camunda Zeebe / Axon:** BPMN-based workflow engines for visual Saga coordination.
3. **Idempotency Invariant:** Every compensating transaction ($C_i$) **must be strictly idempotent**. If a compensation network call times out, the orchestrator must retry safely without double-refunding.

## 5. Annotated Multi-Language Implementations

### Java, Go, and Python Implementations of Saga Orchestration & Compensation

#### Java (Spring Boot 3 / Centralized Saga Orchestrator State Machine)
```java
package com.knowledgebase.microservices.saga;

import org.springframework.stereotype.Service;

@Service
public class OrderSagaOrchestrator {

    private final PaymentClient paymentClient;
    private final InventoryClient inventoryClient;
    private final OrderRepository orderRepository;

    public OrderSagaOrchestrator(PaymentClient paymentClient, InventoryClient inventoryClient, OrderRepository orderRepository) {
        this.paymentClient = paymentClient;
        this.inventoryClient = inventoryClient;
        this.orderRepository = orderRepository;
    }

    public boolean executeOrderSaga(String orderId, String customerId, double amount, String productSku) {
        // Step 1: Compensable Transaction (Create Order in PENDING state)
        orderRepository.updateStatus(orderId, "PENDING");

        // Step 2: Compensable Transaction (Reserve Inventory)
        boolean inventoryReserved = inventoryClient.reserve(productSku, 1);
        if (!inventoryReserved) {
            // Rollback Step 1
            orderRepository.updateStatus(orderId, "REJECTED_OUT_OF_STOCK");
            return false;
        }

        // Step 3: Pivot Transaction (Authorize Payment)
        boolean paymentSuccess = paymentClient.processPayment(customerId, amount);
        if (!paymentSuccess) {
            // Rollback Step 2: Compensate Inventory!
            inventoryClient.release(productSku, 1);
            // Rollback Step 1: Mark Order Rejected
            orderRepository.updateStatus(orderId, "REJECTED_PAYMENT_FAILED");
            return false;
        }

        // Step 4: Retriable Transaction (Confirm Order)
        orderRepository.updateStatus(orderId, "CONFIRMED");
        return true;
    }
}
```

#### Go (Idempotent Choreography Event Consumer with Compensation Handling)
```go
package main

import (
	"context"
	"encoding/json"
	"log"
	"github.com/segmentio/kafka-go"
)

type InventoryEvent struct {
	OrderID    string `json:"order_id"`
	ProductSKU string `json:"product_sku"`
	Quantity   int    `json:"quantity"`
	Action     string `json:"action"` // "RESERVE" or "COMPENSATE_RELEASE"
}

type InventoryService struct {
	// Database connection pool
}

func (s *InventoryService) HandleEvent(ctx context.Context, evt InventoryEvent) error {
	if evt.Action == "RESERVE" {
		log.Printf("[Inventory] Reserving %d units of SKU %s for Order %s", evt.Quantity, evt.ProductSKU, evt.OrderID)
		// Local SQL: UPDATE inventory SET stock = stock - quantity WHERE sku = ...
		return nil
	} else if evt.Action == "COMPENSATE_RELEASE" {
		// Idempotent Compensation Handler!
		log.Printf("[COMPENSATION] Releasing %d units of SKU %s for failed Order %s", evt.Quantity, evt.ProductSKU, evt.OrderID)
		// Local SQL: UPDATE inventory SET stock = stock + quantity WHERE sku = ...
		return nil
	}
	return nil
}
```

#### Python (Async Saga Runner with Automatic Rollback Cascade)
```python
"""
Async Saga Execution Runner in Python.
Demonstrates sequential step execution with automatic reverse compensation.
"""

import asyncio
from typing import Callable, List, Tuple


class SagaStep:
    def __init__(self, name: str, action: Callable, compensate: Callable):
        self.name = name
        self.action = action          # Forward transaction
        self.compensate = compensate  # Compensating rollback action


class AsyncSagaCoordinator:
    def __init__(self, steps: List[SagaStep]):
        self.steps = steps
        self.executed_steps: List[SagaStep] = []

    async def execute(self) -> bool:
        """Executes forward transactions; triggers reverse rollbacks upon failure."""
        for step in self.steps:
            print(f"[Saga] Executing forward step: {step.name}")
            try:
                success = await step.action()
                if not success:
                    raise RuntimeError(f"Step '{step.name}' returned business failure")
                self.executed_steps.append(step)
            except Exception as e:
                print(f"[Saga Alert] Failure in '{step.name}': {e}. Initiating compensation cascade...")
                await self._rollback()
                return False

        print("[Saga Complete] All steps committed successfully.")
        return True

    async def _rollback(self):
        """Executes compensating actions in strict reverse order of execution."""
        for step in reversed(self.executed_steps):
            print(f" -> [Compensating] Undoing step: {step.name}")
            try:
                await step.compensate()
            except Exception as e:
                print(f"CRITICAL: Compensation failed for {step.name}: {e}")


# Verification Execution
if __name__ == "__main__":
    async def create_order(): return True
    async def undo_order(): print("    Order marked CANCELLED")

    async def reserve_stock(): return True
    async def undo_stock(): print("    Stock replenished in inventory")

    async def charge_card(): 
        # Simulate payment failure
        return False
    async def refund_card(): print("    Card refunded")

    saga = AsyncSagaCoordinator([
        SagaStep("CreateOrder", create_order, undo_order),
        SagaStep("ReserveStock", reserve_stock, undo_stock),
        SagaStep("ChargePayment", charge_card, refund_card),
    ])

    asyncio.run(saga.execute())
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Non-Idempotent Compensation Disaster
- **Antipattern:** Writing compensating transactions that execute relative math without idempotency checks (`UPDATE balance SET bal = bal + 100`).
- **System Consequence:** If the network hiccups and the orchestrator retries the compensating transaction, the customer is refunded twice ($200 instead of $100).
- **Fix:** Enforce **Idempotency Keys** on all compensating endpoints.

### 2. Attempting to Compensate Past the Pivot Transaction
- **Antipattern:** Designing a Saga where steps following physical irreversible actions (e.g. shipping a package with FedEx) can fail and attempt to roll back.
- **System Consequence:** You cannot "un-ship" a box once it is on the delivery truck.
- **Fix:** Once the Pivot Transaction commits, all subsequent steps **must be retriable until success**.

### 3. Saga Deadlocks Across Distributed Services
- **Antipattern:** Saga 1 reserves Inventory then Credit; concurrent Saga 2 reserves Credit then Inventory.
- **System Consequence:** Both Sagas grab one resource and wait on the other, creating a distributed deadlock.
- **Fix:** Enforce a **global resource acquisition order** across all Saga definitions.
