# Chapter 07: Transactions — ACID, Isolation Levels & Anomalies

> "Transactions were created with a single purpose: to simplify the programming model for applications accessing a database. By using transactions, the application is free to ignore certain software and hardware problems, because the database takes care of them."  
> — *Martin Kleppmann, Designing Data-Intensive Applications*

---

## 1. Canonical Motivation & Theoretical Foundation

In real-world data systems, many things can go wrong simultaneously:
- Database software or hardware can crash in the middle of a multi-step operation.
- Network partitions can interrupt communication halfway through updating several tables.
- Multiple clients can read and write concurrently, overwriting each other's data and causing race conditions.

A **Transaction** is an abstraction that groups multiple reads and writes into a single logical execution unit: **either the entire transaction succeeds (commits), or it fails completely and rolls back (aborts)**.

### The Real Meaning of ACID

The acronym **ACID** (Atomicity, Consistency, Isolation, Durability) was coined in 1983, but has been heavily distorted by database marketing. Kleppmann unpacks their true technical definitions:

1. **Atomicity (Abortability):** It does **not** mean concurrency! It means if an operation cannot complete due to a fault, the database can **abort** the transaction and discard all writes made up to that point, leaving the database state pristine.
2. **Consistency (Invariants):** The application’s notion of state correctness (e.g. debits must equal credits). The database cannot enforce business consistency alone; consistency is fundamentally the **application’s responsibility**.
3. **Isolation (Concurrency Control):** Concurrently executing transactions cannot step on each other’s toes. Historically defined as **Serializability**: the net result is mathematically equivalent to transactions running serially one after another.
4. **Durability (Persistence):** Once committed, data will not be lost even in the event of a crash, guaranteed via Write-Ahead Logs (WAL) and replication.

## 2. Underlying Runtime, Memory & Execution Architecture

### Weak (Non-Serializable) Isolation Levels & Concurrency Anomalies

Running all transactions with true serializability imposes severe performance costs. Consequently, databases implement **Weak Isolation Levels**:

```
 ┌───────────────────────────┬─────────────────────────────────────────────────────────────┐
 │     Isolation Level       │ Anomalies Prevented                                         │
 ├───────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ Read Uncommitted          │ None (Permits Dirty Reads & Dirty Writes)                   │
 │ Read Committed            │ Dirty Reads, Dirty Writes                                   │
 │ Snapshot Isolation (MVCC) │ Dirty Reads, Dirty Writes, Non-Repeatable Reads (Read Skew) │
 │ Serializable              │ All Anomalies (including Lost Updates, Write Skew, Phantoms)│
 └───────────────────────────┴─────────────────────────────────────────────────────────────┘
```

---

### Multi-Version Concurrency Control (MVCC) & Tuple Headers

Snapshot Isolation is implemented using **Multi-Version Concurrency Control (MVCC)**. 

The core architectural principle of MVCC is:  
**Readers never block Writers, and Writers never block Readers.**

In engines like PostgreSQL, every table tuple maintains internal metadata in its header:
- **`xmin`:** The Transaction ID (`txid`) that inserted this tuple.
- **`xmax`:** The Transaction ID (`txid`) that deleted or superseded this tuple (initially 0).

```
 Tuple on Disk:
 ┌──────────────────────┬─────────┬─────────┬───────────────────────────────────────────┐
 │ Row ID               │ xmin    │ xmax    │ Data Attributes                           │
 ├──────────────────────┼─────────┼─────────┼───────────────────────────────────────────┤
 │ user_42 (v1)         │ 100     │ 105     │ {"name": "Alice", "balance": 100}         │
 │ user_42 (v2)         │ 105     │ 0       │ {"name": "Alice", "balance": 150}         │
 └──────────────────────┴─────────┴─────────┴───────────────────────────────────────────┘
```

#### Snapshot Read Visibility Rules:
When Transaction 102 starts, it receives a **Snapshot** of the database. When reading a row:
1. Ignore any tuple whose `xmin` is greater than 102 (created in the future).
2. Ignore any tuple whose `xmin` belongs to an uncommitted or aborted transaction.
3. If `xmax` is 0 or belongs to an uncommitted transaction, the tuple is **visible**.
4. If `xmax` is committed and less than 102, the tuple was deleted *before* this snapshot, so it is **invisible**.

## 3. Core Mechanics, Algorithms & Invariants

### Advanced Concurrency Anomalies

#### 1. Lost Updates
Occurs during concurrent **read-modify-write** cycles (e.g. two users incrementing an account balance simultaneously):
- Tx 1 reads balance ($100$).
- Tx 2 reads balance ($100$).
- Tx 1 writes $100 + 10 = 110$.
- Tx 2 writes $100 + 20 = 120$ (overwriting Tx 1's write!).
- *Fix:* Use atomic SQL updates (`UPDATE acc SET bal = bal + 10`) or explicit pessimistic locks (`SELECT ... FOR UPDATE`).

#### 2. Write Skew and Phantoms
**Write Skew** is the most subtle and dangerous concurrency anomaly. It occurs when two transactions read the same objects, make an application decision based on those reads, and then modify **different** records, violating a global business invariant.

```
 Case Study: The Doctors on Call Invariant
 Rule: At least ONE doctor must remain on call at all times.
 Currently on call: Alice and Bob (Total = 2).

   Transaction 1 (Alice):                      Transaction 2 (Bob):
   1. SELECT COUNT(*) FROM on_call; (Returns 2) 1. SELECT COUNT(*) FROM on_call; (Returns 2)
   2. "Since 2 >= 2, I can go off call!"        2. "Since 2 >= 2, I can go off call!"
   3. UPDATE doctors SET on_call = FALSE        3. UPDATE doctors SET on_call = FALSE
      WHERE name = 'Alice';                        WHERE name = 'Bob';
   4. COMMIT;                                   4. COMMIT;

 Result: BOTH transactions commit successfully under Snapshot Isolation!
 Final state: ZERO doctors on call! The invariant is violated!
```

- Why did row locks fail? Because Alice locked Alice's row, and Bob locked Bob's row. Neither transaction locked the other's row!
- An anomaly where a write in one transaction changes the search result of another transaction is called a **Phantom**.

### True Serializability: The Three Approaches

| Mechanism | Architecture & Concurrency | Major Systems | Performance Characteristics |
| :--- | :--- | :--- | :--- |
| **Actual Serial Execution** | Single-threaded execution in RAM. Zero lock overhead. | Redis, VoltDB, Datomic | Ultra-fast ($< 1\text{ms}$), but limited to single CPU core throughput. |
| **Two-Phase Locking (2PL)** | Shared read locks and Exclusive write locks. | MySQL InnoDB, SQL Server | High contention; readers block writers; prone to deadlocks. |
| **Serializable Snapshot Isolation (SSI)**| Optimistic MVCC; tracks anti-dependency conflicts ($rw$-cycles); aborts on collision. | PostgreSQL (since 9.1), CockroachDB | Non-blocking reads; aborts transactions only when true serializability conflict occurs. |

---

## 4. Practical Systems & Production Engineering Trade-offs

1. **PostgreSQL SSI:** Provides true serializability with near-Snapshot-Isolation throughput by tracking read-write anti-dependencies using lock-free `SIREAD` memory locks.
2. **PostgreSQL Vacuuming Overhead:** Because MVCC retains deleted and updated rows on disk, PostgreSQL requires a background `VACUUM` process to reclaim dead tuples. Long-running transactions prevent vacuuming, causing table bloat.
3. **Database Vendor Naming Lies:** Oracle calls its Snapshot Isolation level "Serializable"! An engineer deploying code to Oracle assuming Write Skew is prevented will suffer production data corruption.

## 5. Annotated Code Implementations & Algorithmic Engines

### In-Memory MVCC Storage Engine with Snapshot Read Isolation

The following production Python class implements an MVCC storage engine with transaction identifiers, tuple versioning (`xmin`, `xmax`), and snapshot read isolation:

```python
"""
Multi-Version Concurrency Control (MVCC) Storage Engine.
Demonstrates:
  - Transaction ID allocation and active transaction tracking
  - Tuple versioning with xmin (creator) and xmax (deleter/updater)
  - Snapshot read visibility rules preventing dirty reads and read skew
  - Atomic commit and abort mechanics
"""

from typing import Dict, List, Optional, Set, Tuple


class TupleVersion:
    def __init__(self, key: str, value: str, xmin: int):
        self.key = key
        self.value = value
        self.xmin = xmin # Transaction ID that inserted this version
        self.xmax = 0    # Transaction ID that deleted/superseded this version (0 = active)


class MVCCDatabase:
    def __init__(self):
        self.global_tx_counter = 100
        self.active_transactions: Set[int] = set()
        self.committed_transactions: Set[int] = set()
        # Storage: key -> list of version tuples
        self.table: Dict[str, List[TupleVersion]] = {}

    def begin_transaction(self) -> int:
        """Starts a transaction and takes a snapshot of active transactions."""
        self.global_tx_counter += 1
        txid = self.global_tx_counter
        self.active_transactions.add(txid)
        return txid

    def commit(self, txid: int) -> None:
        """Commits transaction."""
        self.active_transactions.remove(txid)
        self.committed_transactions.add(txid)

    def abort(self, txid: int) -> None:
        """Aborts transaction and cleans uncommitted tuples."""
        self.active_transactions.remove(txid)
        # Purge tuples created by aborted transaction
        for versions in self.table.values():
            for v in versions:
                if v.xmin == txid:
                    v.xmin = -1 # Invalidate
                if v.xmax == txid:
                    v.xmax = 0  # Revert delete

    def put(self, txid: int, key: str, value: str) -> None:
        """Inserts or updates a key under transaction txid."""
        if key not in self.table:
            self.table[key] = []

        # If key already exists, mark latest version as deleted by this txid
        for v in self.table[key]:
            if v.xmax == 0 and v.xmin in self.committed_transactions:
                v.xmax = txid

        # Append new version
        new_version = TupleVersion(key, value, xmin=txid)
        self.table[key].append(new_version)

    def get(self, txid: int, key: str) -> Optional[str]:
        """Reads key according to Snapshot Isolation visibility rules."""
        if key not in self.table:
            return None

        # Snapshot rule: Transaction sees committed writes made BEFORE its start,
        # plus its own in-flight writes.
        for v in reversed(self.table[key]):
            # 1. Was it created by our own transaction?
            created_by_us = (v.xmin == txid)
            # 2. Was it created by a committed transaction before we started?
            created_by_committed = (v.xmin in self.committed_transactions and v.xmin < txid)

            if not (created_by_us or created_by_committed):
                continue # Invisible (created in future or uncommitted)

            # Check if deleted
            if v.xmax != 0:
                deleted_by_us = (v.xmax == txid)
                deleted_by_committed = (v.xmax in self.committed_transactions and v.xmax < txid)
                if deleted_by_us or deleted_by_committed:
                    continue # Invisible (deleted)

            return v.value

        return None


# Verification Execution
if __name__ == "__main__":
    db = MVCCDatabase()

    # Step 1: Initial state committed by Tx 101
    tx101 = db.begin_transaction()
    db.put(tx101, "account_balance", "$100")
    db.commit(tx101)

    # Step 2: Tx 102 begins (Snapshot taken: balance is $100)
    tx102 = db.begin_transaction()

    # Step 3: Concurrent Tx 103 updates balance to $500 and commits
    tx103 = db.begin_transaction()
    db.put(tx103, "account_balance", "$500")
    db.commit(tx103)

    # Step 4: Tx 102 reads balance. MUST see $100 (Snapshot Isolation), NOT $500!
    val_tx102 = db.get(tx102, "account_balance")
    print("=== MVCC Snapshot Isolation Verification ===")
    print(f"Tx 102 read value: {val_tx102} (Expected: $100)")
    assert val_tx102 == "$100", "Snapshot isolation violated! Dirty read / read skew detected!"

    # Step 5: Tx 104 begins after Tx 103 committed. MUST see $500!
    tx104 = db.begin_transaction()
    val_tx104 = db.get(tx104, "account_balance")
    print(f"Tx 104 read value: {val_tx104} (Expected: $500)")
    assert val_tx104 == "$500", "New transaction failed to observe committed state!"

    print("MVCC Tuple visibility rules mathematically verified.")
```

## 6. Authoritative Gotchas, Pitfalls, Concurrency Anomaly Edge Cases & Triage

### 1. The Write Skew Financial Overdraft Disaster
- **Antipattern:** Relying on Snapshot Isolation (`REPEATABLE READ`) to prevent negative balances across multiple accounts (e.g., Alice has Checking: $80, Savings: $50. Invariant: Checking + Savings $\ge 0$).
- **System Consequence:** Two concurrent transactions withdraw $100$ simultaneously: Tx 1 withdraws from Checking, Tx 2 withdraws from Savings. Both verify Checking + Savings = $130 \ge 100$. Both commit. Final balance: $-70$.
- **Fix:** Enforce true **Serializable Isolation**, or materialize conflicts explicitly using `SELECT ... FOR UPDATE`.

### 2. Long-Running Transaction Table Bloat (PostgreSQL Freeze)
- **Antipattern:** An analytics query or developer's open `psql` console leaving a transaction open for 14 hours.
- **System Consequence:** The database cannot delete any row updated or deleted *after* that transaction's `xmin`. The `VACUUM` daemon is paralyzed. Disk usage balloons by hundreds of gigabytes, eventually triggering transaction ID wraparound failure.
- **Fix:** Configure `idle_in_transaction_session_timeout` (e.g. 5 minutes) to automatically terminate stale transactions.

### 3. Read Skew on Inconsistent Backups
- **Antipattern:** Taking database backups by running `pg_dump` or `mysqldump` without a snapshot transaction.
- **System Consequence:** If the dump takes 2 hours, the first table represents 10:00 AM state, while the last table represents 12:00 PM state. Restoring from this backup corrupts foreign key references.
- **Fix:** Always execute backups under explicit Snapshot Isolation (`--single-transaction` in `mysqldump`).
