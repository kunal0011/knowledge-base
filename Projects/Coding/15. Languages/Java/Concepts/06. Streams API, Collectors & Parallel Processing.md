# Java Concepts: Streams API, Collectors & Parallel Processing

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapter 10  
- *Effective Java (3rd Ed.)* by Joshua Bloch, Items 45–48 (The Streams Masterclass)  

---

## 1. Theoretical Motivation: Declarative Pipelines vs. Imperative Loops

In *Effective Java*, Joshua Bloch explains the architectural intent of the Streams API: to transform imperative iteration into **declarative computation pipelines**.

```
Imperative Loop (Tells the computer HOW to do it):
- Manual loop counters, index bounds, mutable accumulator lists, and state checks.
- Serial execution tied strictly to one thread.

Declarative Stream Pipeline (Tells the computer WHAT to achieve):
- Expresses filtering, mapping, grouping, and reduction as composable functions.
- Decouples pipeline description from physical execution strategy (enabling parallelization).
```

A Stream is **not a data structure**—it does not store elements. It is an on-demand view of a data source (collection, array, I/O channel) evaluated via functional transformations.

---

## 2. Underlying Architecture: The Stream Pipeline Lifecycle

A Stream pipeline consists of three distinct phases:

```
[ Data Source ] ===> [ Intermediate Operations (0 or more) ] ===> [ Terminal Operation (1) ]
  List, Set,            filter(), map(), sorted(),                  collect(), reduce(),
  Array, I/O            distinct(), flatMap()                       count(), forEach()
```

### 2.1 Lazy Evaluation & Operation Fusion
Intermediate operations are strictly **lazy**. Calling `.filter()` or `.map()` executes zero processing; it simply constructs a new `ReferencePipeline` stage object.
Processing only begins when a **Terminal Operation** is invoked.

```
Source: [ 1, 2, 3, 4, 5, 6 ]
Pipeline: .filter(x -> x % 2 == 0).map(x -> x * 10).findFirst()

Execution trace (Fused Single Pass):
Element 1: filter(1) -> false (Discarded immediately!)
Element 2: filter(2) -> true  -> map(2) = 20 -> findFirst() MATCH!
Terminates immediately! Elements 3, 4, 5, 6 are NEVER evaluated.
```
HotSpot fuses intermediate operations together, avoiding the allocation of intermediate collections.

## 3. Master Matrix of Stream Operations

| Operation | Type | Statefulness | Short-Circuiting? | Description |
|:---|:---|:---|:---:|:---|
| **`filter(Predicate)`** | Intermediate | Stateless | No | Keeps elements satisfying predicate |
| **`map(Function)`** | Intermediate | Stateless | No | 1-to-1 transform of elements |
| **`flatMap(Function)`**| Intermediate | Stateless | No | 1-to-many transform; flattens streams |
| **`sorted(Comparator)`**| Intermediate | **Stateful** | No | Requires buffering all elements in RAM! |
| **`distinct()`** | Intermediate | **Stateful** | No | Tracks seen elements via internal `HashSet` |
| **`limit(n)`** | Intermediate | Stateful | **Yes** | Binds output stream to size $n$ |
| **`takeWhile(Predicate)`**| Intermediate| Stateless | **Yes** | Emits until predicate fails (Java 9+) |
| **`collect(Collector)`**| Terminal | Stateful | No | Accumulates into target data structure |
| **`reduce(BinaryOp)`** | Terminal | Stateful | No | Folds elements into a single value |
| **`anyMatch(Predicate)`**| Terminal | Stateless | **Yes** | Returns true immediately upon match |

## 4. Advanced Collectors Deep-Dive

`java.util.stream.Collectors` provides functional building blocks for data aggregation:

### 4.1 Multi-Level Grouping
```java
public record Transaction(String category, String currency, double amount) {}

List<Transaction> txns = getTransactions();

// Group by Category -> then group by Currency -> sum total amount:
Map<String, Map<String, Double>> summary = txns.stream()
    .collect(Collectors.groupingBy(
        Transaction::category,
        Collectors.groupingBy(
            Transaction::currency,
            Collectors.summingDouble(Transaction::amount)
        )
    ));
```

### 4.2 Handling Duplicate Keys in `toMap`
```java
// ANTI-PATTERN: Crashes with IllegalStateException if duplicate names exist!
// map = users.stream().collect(Collectors.toMap(User::name, User::id));

// CORRECT: Provide merge function to handle duplicate keys:
Map<String, Long> userMap = users.stream().collect(
    Collectors.toMap(
        User::name,
        User::id,
        (existingId, newId) -> existingId // Keep original on collision
    )
);
```

## 5. Parallel Streams & The `ForkJoinPool`

When you invoke `.parallelStream()`, the stream uses the JVM-wide **`ForkJoinPool.commonPool()`**:

```
                       [ Input Collection ]
                                |
                   Spliterator splits range (Divide)
                                |
             +------------------+------------------+
             |                                     |
      [ Sub-range 1 ]                       [ Sub-range 2 ]
      Worker Thread 1                       Worker Thread 2
             \                                     /
              \                                   /
               +----------------+----------------+
                                |
                      Combiner merges results
```

### Joshua Bloch's Rule of Parallel Streams (Item 48):
Parallel streams do **not** automatically speed up code. Under the wrong conditions, they run drastically slower than serial execution!

### When to Parallelize:
1. **Source Splittability:** Arrays, `ArrayList`, and `IntStream.range` split with $\mathcal{O}(1)$ cost. In contrast, `LinkedList` or `Stream.iterate()` cannot be split cleanly, destroying parallel gains.
2. **Data Locality:** Contiguous memory arrays maximize CPU cache utilization; object pointer graphs cause cache miss stalls.
3. **Computation Density ($N \times Q$ Rule):** $N$ (number of elements) $\times$ $Q$ (operations per element) must be $\ge 100,000$ to overcome thread dispatch and synchronization overhead.

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 Joshua Bloch's Item 46: Purity & Side Effects in Streams
```java
// DISASTROUS ANTI-PATTERN: Mutating state inside stream operations
List<String> results = new ArrayList<>();
words.stream()
     .filter(w -> w.length() > 5)
     .forEach(results::add); // DANGEROUS! Race condition if stream is made parallel!
```
**Why it fails:** Mutating shared external state inside `.forEach()` violates functional purity. If converted to `.parallelStream()`, multiple threads invoke `ArrayList.add()` concurrently, corrupting internal array bounds and throwing `ArrayIndexOutOfBoundsException`.  
**The Pure Idiom:**
```java
List<String> results = words.stream()
     .filter(w -> w.length() > 5)
     .toList(); // Side-effect free! Safe for serial and parallel!
```

### 6.2 The Single-Use Stream Trap
```java
Stream<String> stream = List.of("A", "B", "C").stream();
stream.forEach(System.out::println);

// Calling another terminal operation:
long count = stream.count(); // Crashes with IllegalStateException!
```
Streams are **single-use pipelines**. Once a terminal operation is executed, the stream is closed and cannot be re-operated upon.

## 7. Actionable Summary Checklist

- [x] Use streams judiciously (Effective Java Item 45); if an imperative loop is shorter and clearer, favor the loop.
- [x] Keep stream functions strictly **side-effect-free** (Effective Java Item 46); use `collect()` rather than mutating external lists inside `forEach()`.
- [x] Always supply a collision merge function when using `Collectors.toMap()` to prevent `IllegalStateException` crashes.
- [x] Exercise extreme caution when parallelizing streams (Effective Java Item 48); verify that $N \times Q$ is large and the source splits efficiently.
- [x] Use primitive stream specializations (`IntStream`, `LongStream`) to eliminate boxing overhead during numeric reductions.
