## 🎲 1. Randomness & Cryptographically Secure PRNGs (CSPRNG)

All cryptography depends on unpredictability. If a key generation algorithm draws numbers from an insecure random number generator (such as standard C `rand()` or Python `random`), an attacker can reconstruct the seed and regenerate all private keys retrospectively.

### 1.1 The Dual_EC_DRBG Backdoor (NIST SP 800-90A)
In 2006, NIST standardized **Dual_EC_DRBG**, an elliptic curve random number generator actively promoted by RSA Security (which received $\$10\text{ million}$ from the NSA).

#### The Trapdoor:
Dual_EC_DRBG generated random numbers by multiplying points on an elliptic curve using two fixed public points, $P$ and $Q$. The NSA secretly selected $P$ and $Q$ such that:
$$P = e \cdot Q$$
where $e$ was a secret private scalar known only to the NSA! By observing just 32 bytes of "random" output from a Dual_EC_DRBG instance, anyone holding the secret $e$ could instantly compute the internal state of the generator, predicting all past and future keys!

## ⏱️ 2. Side-Channel Attacks: Timing Leaks & Constant-Time Code

A **Side-Channel Attack** does not attack the mathematical cipher; it measures physical properties of the running computer (execution time, power consumption, electromagnetic emissions) to deduce the key.

### 2.1 The Deadly Variable-Time String Compare
Consider a developer verifying an HMAC authentication tag using standard library `memcmp()`:

```c
// VULNERABLE CODE: Variable-Time Comparison
int verify_mac_insecure(const uint8_t *expected, const uint8_t *received, size_t len) {
    for (size_t i = 0; i < len; i++) {
        if (expected[i] != received[i]) {
            return 0; // LEAKS TIMING! Exits immediately on the first mismatch!
        }
    }
    return 1;
}
```

#### How the Attacker Exploits This:
1. Attacker sends candidate tag beginning with `0x00`. Server compares byte 0: mismatch! Server returns error in **$2.10\ \mu\text{s}$**.
2. Attacker tests `0x01`, `0x02` ... until testing `0x4A`.
3. When byte 0 matches, the loop proceeds to byte 1! The comparison takes slightly longer: **$2.25\ \mu\text{s}$**!
4. By measuring microsecond latency differences across API calls, the attacker recovers byte 0, then byte 1, cracking a 32-byte HMAC tag in $256 \times 32 = 8,192$ requests!

---

### 2.2 The Solution: Constant-Time Programming
Cryptographic comparisons must execute in **identical clock cycles**, regardless of whether the match succeeds or fails:

```c
// SECURE CODE: Constant-Time Comparison
int constant_time_memcmp(const uint8_t *a, const uint8_t *b, size_t len) {
    uint8_t diff = 0;
    for (size_t i = 0; i < len; i++) {
        diff |= (a[i] ^ b[i]); // Accumulates XOR differences without branching!
    }
    // Returns 1 if identical (diff == 0), 0 otherwise
    return (1 & ((diff - 1) >> 8));
}
```

### 3.1 The Bellcore Fault Attack on CRT-RSA
In Chapter 05, we demonstrated that RSA private-key signatures use the Chinese Remainder Theorem (CRT) for $4\times$ speedup:
$$s_1 = m^{d \bmod (p-1)} \bmod p, \quad s_2 = m^{d \bmod (q-1)} \bmod q$$
Combined via CRT: $s = \text{CRT}(s_1, s_2)$.

Suppose an attacker hits the CPU with a tiny laser pulse or voltage glitch during computation, inducing **a single bit-flip error in $s_1$**, producing a corrupted $s'_1$, while $s_2$ computes correctly:
- The corrupted signature is $s'$.
- Notice: $(s')^e \not\equiv m \pmod p$, but $(s')^e \equiv m \pmod q$!
- Therefore, $q$ divides the difference $((s')^e - m)$, but $p$ does not!

The attacker simply computes:
$$q = \gcd((s')^e - m,\ n)$$
In less than **1 millisecond of Euclidean division**, the 2048-bit modulus is factored, completely exposing the private key!

**Production Defense:** Always verify the signature mathematically ($(s)^e \equiv m \pmod n$) in software before transmitting it out of the device!

## 📋 4. Cryptographic Engineering Best Practices Checklist

1. **Never Implement Your Own Primitives:** Always use vetted, audited libraries (**libsodium**, **OpenSSL 3.0**, **BoringSSL**, **RustCrypto**).
2. **Mandate Authenticated Encryption (AEAD):** Never use unauthenticated modes (ECB, raw CBC, raw CTR). Use **AES-256-GCM** or **ChaCha20-Poly1305**.
3. **Never Reuse Nonces:** In AES-GCM and ChaCha20, nonce reuse shatters authenticity. Use random 96-bit nonces or synthetic deterministic nonces.
4. **Enforce Constant-Time Execution:** Guarantee that no secret data governs branch conditions (`if`, `switch`) or memory array lookup indices.
5. **Memory Sanitation:** Overwrite sensitive key buffers immediately after use with `explicit_bzero()` (preventing compiler dead-code elimination) and lock buffers into RAM with `mlock()` to prevent swapping keys to disk.
6. **Embrace Post-Quantum Preparedness:** Transition new key exchange architectures to **Hybrid X25519 + ML-KEM-768**.
