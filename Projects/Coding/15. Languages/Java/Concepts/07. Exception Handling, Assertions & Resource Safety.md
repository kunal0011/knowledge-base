# Java Concepts: Exception Handling, Assertions & Resource Safety

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapter 11  
- *Effective Java (3rd Ed.)* by Joshua Bloch, Items 69–77 & Item 9  

---

## 1. Theoretical Motivation: The `Throwable` Hierarchy

Java uniquely divides error handling into distinct categories within its class hierarchy:

```
                            java.lang.Throwable
                               /           \
                              /             \
                   java.lang.Error      java.lang.Exception
                 (Fatal JVM Failures)      /           \
                 - OutOfMemoryError       /             \
                 - StackOverflowError    /       RuntimeException
                                        /       (Unchecked Exceptions)
                               Checked Exceptions - NullPointerException
                               - IOException     - IllegalArgumentException
                               - SQLException    - IndexOutOfBoundsException
```

### 1.1 Checked vs. Unchecked Exceptions (Bloch Item 70)
- **Checked Exceptions (Direct Subclasses of `Exception`):** Represent **recoverable conditions**. The compiler enforces that callers must either catch them in a `try-catch` block or declare them in the method signature (`throws IOException`).
- **Unchecked Exceptions (`RuntimeException`):** Represent **programming errors** (precondition violations, illegal arguments, indexing bugs). The compiler does not require explicit handling.
- **Errors (`Error`):** Reserved for fatal JVM conditions from which standard application code cannot reasonably recover. Should never be caught.

## 2. Underlying Architecture: `try-with-resources` & Suppressed Exceptions

In *Effective Java* Item 9, Joshua Bloch declares: **"Prefer `try-with-resources` to `try-finally`"**.

### 2.1 The `AutoCloseable` Contract
Any class implementing `java.lang.AutoCloseable` (which defines `void close() throws Exception`) can be managed within a `try-with-resources` statement:

```java
try (var in = new FileInputStream("input.txt");
     var out = new FileOutputStream("output.txt")) {
    in.transferTo(out);
}
```

```
Execution Invariants:
1. Resource Declaration: Resources are initialized from left to right.
2. Resource Teardown: Resources are closed in REVERSE order of declaration!
   (out is closed first, then in is closed).
3. Scope Limitation: Resource variables are implicitly final and exist only within the try block.
```

### 2.2 Suppressed Exceptions Architecture
In legacy `try-finally` blocks, if the `try` block threw an exception and the `finally` block also threw an exception while closing, **the second exception completely masked the first exception**, erasing the original root cause!

With `try-with-resources`, HotSpot preserves the primary exception from the `try` block, and attaches any subsequent closing exceptions as **Suppressed Exceptions**:

```java
try (var res = new FaultyResource()) {
    throw new IllegalStateException("Primary computation failed!");
} catch (Exception e) {
    System.err.println("Main Exception: " + e.getMessage());
    for (Throwable t : e.getSuppressed()) {
        System.err.println("Suppressed Exception: " + t.getMessage());
    }
}
```

## 3. Multi-Catch & Exception Subclassing Rules

Java 7 introduced the multi-catch statement to eliminate redundant catch blocks:

```java
try {
    executeDatabaseCall();
} catch (SQLException | IOException e) {
    log.error("I/O or Database Failure", e);
    // CRITICAL OCP RULE: The catch variable 'e' in a multi-catch is IMPLICITLY FINAL!
    // e = new SQLException(); // COMPILE ERROR!
}
```

> [!WARNING]
> **Subclass Disallowed in Multi-Catch:**
> `catch (FileNotFoundException | IOException e)` will **refuse to compile**. Because `FileNotFoundException` is a subclass of `IOException`, listing both creates dead code.

## 4. Assertions for Internal Invariants

Assertions verify internal assumptions that should **never** fail if the software is bug-free:

```java
assert speed >= 0 : "Speed cannot be negative: " + speed;
```

### OCP Rules on Assertions:
1. **Disabled by Default:** Assertions are disabled in production JVMs unless explicitly enabled using the `-ea` (`-enableassertions`) command-line flag.
2. **Never for Public Parameter Validation:** Never use assertions to check arguments to public methods (Effective Java Item 49). Use `Objects.requireNonNull()` or `IllegalArgumentException`, which execute unconditionally.
3. **Never Include Side Effects:** `assert list.remove(obj);` is an anti-pattern because the element will only be removed if assertions are enabled!

## 5. Joshua Bloch's Core Exception Guidelines

### Item 69: Use Exceptions Only for Exceptional Conditions
```java
// DISASTROUS ANTI-PATTERN: Using exceptions for loop termination!
try {
    int i = 0;
    while (true) array[i++].process();
} catch (ArrayIndexOutOfBoundsException e) {
    // Loop terminated
}
```
**Why this is toxic:** The JVM optimizes standard for-loops aggressively. Exception construction captures the entire stack trace, running **$100\times$ slower** than a standard boundary check. Furthermore, it conceals genuine array bugs inside `process()`.

### Item 76: Strive for Failure Atomicity
A failed method call should leave the object in the exact state it was in before the call.
- Check parameters for validity **before** modifying mutable internal state.
- Order operations so that failure points occur before state changes.
- Perform work on a temporary copy, and swap pointers only after success.

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 The Swallowed Exception Trap in `finally`
```java
// FATAL ANTI-PATTERN: Returning or throwing from inside a finally block
public static int calculate() {
    try {
        throw new RuntimeException("Original Fatal Error!");
    } finally {
        return 42; // CATASTROPHIC! The RuntimeException is completely discarded!
    }
}

System.out.println(calculate()); // Prints 42! No exception raised!
```
**Rule:** Never write a `return` or throw a new exception inside a `finally` block; it completely overwrites any active exception thrown by the `try` block.

### 6.2 The Swallowed `InterruptedException` Trap
```java
// DANGEROUS:
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // Empty catch! Swallows the interrupt signal!
}
```
When `InterruptedException` is caught, the thread's interrupted status is **cleared**. Upstream executors or cancelation tokens will never know the thread was requested to stop!  
**The Fix:**
```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // Restore interrupted status!
}
```

## 7. Actionable Summary Checklist

- [x] Use checked exceptions for recoverable conditions and unchecked exceptions for programming errors (Effective Java Item 70).
- [x] Always prefer **`try-with-resources`** over manual `try-finally` to ensure deterministic cleanup and access suppressed exceptions (Effective Java Item 9).
- [x] Resources in `try-with-resources` close in **reverse order** of declaration.
- [x] Never use exceptions for normal control flow (Effective Java Item 69).
- [x] Never return or throw from inside a `finally` block, as it obliterates in-flight exceptions.
- [x] Always restore the thread interrupt flag (`Thread.currentThread().interrupt()`) when catching `InterruptedException`.
