# Chapter 05: Kubernetes Storage Architecture — PVs, PVCs, StorageClasses & CSI

> "Decoupling storage configuration from storage consumption is one of the most powerful design abstractions in Kubernetes. StorageClasses define *how* storage is provisioned, PersistentVolumes represent *what* is available, and PersistentVolumeClaims express *what* an application needs."  
> — *Michael Hausenblas & Stefan Schimanski, Programming Kubernetes*

## 💾 1. Storage Abstraction Hierarchy: The Volume Decoupling Model

Containers have ephemeral filesystems; when a container crashes, its root filesystem is destroyed and replaced with a fresh image layer. Kubernetes solves this through a layered storage abstraction model that separates administrative infrastructure provisioning from developer workload requests.

```text
===================================================================================================
                             KUBERNETES STORAGE DECOUPLING MODEL
===================================================================================================

 [ Infrastructure Admin Domain ]                [ Application Developer Domain ]
 
   ┌───────────────────────────┐
   │       StorageClass        │
   │ - CSI Driver: ebs.csi.aws │
   │ - Type: gp3, IOPS: 3000   │
   │ - volumeBindingMode:      │
   │   WaitForFirstConsumer    │
   └─────────────┬─────────────┘
                 │
                 ▼ (Dynamic Provisioning)
   ┌───────────────────────────┐                 ┌───────────────────────────┐
   │     PersistentVolume      │◄──(Bound to)───┤   PersistentVolumeClaim   │
   │ - Capacity: 100Gi         │                 │ - StorageClass: gp3       │
   │ - AccessMode: RWO         │                 │ - Request: 100Gi          │
   │ - VolumeID: vol-012345678 │                 │ - AccessMode: RWO         │
   └─────────────┬─────────────┘                 └─────────────┬─────────────┘
                 │                                             │
                 │                                             ▼
                 │                               ┌───────────────────────────┐
                 └──────────────────────────────►│         Pod Spec          │
                                                 │  volumes:                 │
                                                 │  - name: data             │
                                                 │    persistentVolumeClaim: │
                                                 │      claimName: data-pvc  │
                                                 └───────────────────────────┘
```

## 🏗️ 2. Volume Lifecycle & Binding Modes

### 2.1 Static vs. Dynamic Provisioning
- **Static Provisioning:** Cluster administrator manually provisions physical SAN/EBS volumes and creates `PersistentVolume` manifests. PVCs match existing PVs by storage capacity and access modes.
- **Dynamic Provisioning:** Administrator creates a `StorageClass`. When a developer deploys a `PersistentVolumeClaim`, the cluster automatically invokes the CSI storage driver to provision the underlying disk on-demand.

### 2.2 Reclaim Policies
When a user deletes a `PersistentVolumeClaim`, the reclaim policy on the PV dictates what happens to the underlying storage:
- **`Delete` (Default for dynamic):** Automatically purges the PV object in Kubernetes and deallocates the underlying cloud block device (e.g., deletes AWS EBS volume).
- **`Retain`:** Retains the PV object and physical block storage intact. The PV enters `Released` status. No other claim can bind to it until an admin manually salvages the data and resets `pv.spec.claimRef`.
- **`Recycle` (Deprecated):** Performed basic scrubbing (`rm -rf /thevolume/*`). Replaced by dynamic provisioning.

### 2.3 Access Modes Matrix

| Access Mode | CLI Abbrev | Description | Typical Backends |
| :--- | :--- | :--- | :--- |
| **ReadWriteOnce** | `RWO` | Volume can be mounted as read-write by a **single node**. | AWS EBS, GCP Persistent Disk, Azure Managed Disk. |
| **ReadOnlyMany** | `ROX` | Volume can be mounted as read-only by **many nodes** simultaneously. | NFS, AWS EFS, CephFS, Read-only block storage. |
| **ReadWriteMany** | `RWX` | Volume can be mounted as read-write by **many nodes** simultaneously. | NFS, CephFS, GlusterFS, AWS EFS, Azure Files. |
| **ReadWriteOncePod** | `RWOP` | Volume can be mounted as read-write by a **single Pod** across the entire cluster (v1.27+ GA). | High-performance single-writer databases (prevents split-brain). |

## ⚡ 3. The `volumeBindingMode` Trap: Immediate vs. `WaitForFirstConsumer`

One of the most critical production failure modes in multi-AZ clusters is configuring `volumeBindingMode: Immediate`.

```text
[ Scenario: Multi-AZ Cluster (us-east-1a, us-east-1b) ]

  If volumeBindingMode: Immediate
  1. PVC is created.
  2. CSI driver immediately provisions EBS volume in us-east-1a.
  3. Pod is created requesting PVC.
  4. kube-scheduler runs: us-east-1a nodes are at 100% CPU/Memory!
  5. Only available nodes are in us-east-1b.
  6. SCHEDULING DEADLOCK!
     Pod cannot run in us-east-1b (EBS volume is locked to AZ us-east-1a).
     Pod enters perpetual Pending state: "1 node(s) had volume node affinity conflict".

  Solution: volumeBindingMode: WaitForFirstConsumer
  1. PVC remains Pending until Pod is submitted.
  2. Scheduler first picks an optimal worker node with available CPU/Memory.
  3. CSI driver is instructed to provision the EBS volume in the EXACT AZ where the Pod was scheduled!
```

### Production StorageClass Manifest
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ebs-gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
parameters:
  type: gp3
  iops: "5000"
  throughput: "250"
  encrypted: "true"
```

## 🔌 4. Container Storage Interface (CSI) Architecture

Before CSI, storage plugins were "in-tree" (compiled directly inside the `kubelet` and `kube-controller-manager` binaries). CSI provides an out-of-tree, gRPC-based standard.

### 4.1 CSI Architecture Components
1. **Controller Plugin (Deployment):** Runs as a cluster-level singleton or replica.
   - Watches PVC objects.
   - Interacts with Cloud APIs (e.g., AWS EC2 API to create/attach volumes).
2. **Node Plugin (DaemonSet):** Runs on every worker node.
   - Interacts with the host Linux kernel (formatting filesystems, mounting directories).

```text
===================================================================================================
                                CSI ATTACH & MOUNT RPC FLOW
===================================================================================================

  API Server / Controller Manager                    Node (kubelet / csi-node-driver)
 ────────────────────────────────                   ───────────────────────────────────
                │                                                     │
 1. PVC created │                                                     │
 ───────────────► [ csi-provisioner ]                                 │
                │         │                                           │
                │         ▼ gRPC                                      │
                │  CreateVolume()                                     │
                │  (Cloud allocates EBS disk)                         │
                │                                                     │
 2. Pod scheduled on Node 1                                           │
 ───────────────► [ csi-attacher ]                                    │
                │         │                                           │
                │         ▼ gRPC                                      │
                │  ControllerPublishVolume()                          │
                │  (AWS attaches /dev/xvdf to Node 1)                 │
                │                                                     │
 3. Disk attached to Node 1                                           │
 ─────────────────────────────────────────────────────────────────────► kubelet triggers CSI Node
                                                                      │         │
                                                                      │         ▼ gRPC
                                                                      │  NodeStageVolume()
                                                                      │  - Formats disk (mkfs.ext4)
                                                                      │  - Mounts to staging path:
                                                                      │    /var/lib/kubelet/plugins/
                                                                      │    kubernetes.io/csi/...
                                                                      │         │
                                                                      │         ▼ gRPC
                                                                      │  NodePublishVolume()
                                                                      │  - Bind mounts staging path
                                                                      │    into Pod rootfs:
                                                                      │    /var/lib/kubelet/pods/<uid>/
                                                                      │    volumes/kubernetes.io~csi/...
                                                                      ▼
                                                          Container launches with mounted storage!
```

## 📈 5. Online Volume Expansion & Snapshots

### 5.1 Expanding a PersistentVolumeClaim
With `allowVolumeExpansion: true` on the StorageClass, expanding storage requires simply updating the PVC spec:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 200Gi  # Increased from 100Gi
```
**Kernel Execution Flow:**
1. CSI Controller calls `ControllerExpandVolume` (cloud resizes underlying EBS block device to 200Gi).
2. `kubelet` notices device size change and CSI Node calls `NodeExpandVolume`.
3. Node executes filesystem resize utility online without unmounting (`resize2fs` for ext4 or `xfs_growfs` for XFS).

## 🚨 6. Production Troubleshooting: The Multi-Attach Error

### The Bug Scenario
A worker node crashes or loses network connectivity. Kubernetes initiates Pod eviction and schedules a new replica on a healthy node. However, the new Pod remains stuck in `ContainerCreating`:
```text
Warning  FailedAttachVolume  2m   attachdetach-controller  
Multi-Attach error for volume "pvc-abc-123" Volume is already exclusively 
attached to one node and cannot be attached to another.
```

### Root Cause & Resolution Flow
```text
 Node A (Unresponsive / Network Partitioned)        Node B (Target Node for Rescheduled Pod)
 ┌────────────────────────────────────────┐         ┌────────────────────────────────────────┐
 │ Pod 1 (Terminating)                    │         │ Pod 1-new (ContainerCreating)          │
 │                                        │         │                                        │
 │ Underlying EBS Volume attached to      │         │ Waiting for EBS volume attachment      │
 │ /dev/xvdf on Node A                    │         │                                        │
 └───────────────────┬────────────────────┘         └───────────────────┬────────────────────┘
                     │                                                  │
                     ▼                                                  ▼
   AWS API rejects attach request: Volume vol-123 is already attached to instance i-NodeA!

 Resolution Runbook:
 1. Check volume attachments:
    kubectl get volumeattachment | grep <pvc-uid>
 2. Verify if old node is truly dead or partitioned:
    kubectl describe node node-a
 3. Force-delete volumeattachment ONLY if node is confirmed shut down / dead:
    kubectl delete volumeattachment csi-volume-attachment-uuid
 4. Alternatively, use ReadWriteOncePod (RWOP) to strictly regulate single-consumer locking.
```
