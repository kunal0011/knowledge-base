# Chapter 08: Linux Kernel Subsystems — eBPF, Cgroups, Namespaces & Containerization

> "There is no such physical thing as a 'container' inside the Linux kernel. A container is simply an ordinary Linux process wrapped in three fundamental kernel mechanisms: Namespaces for isolation, Control Groups (cgroups) for resource restriction, and pivot_root for filesystem containment."  
> — *Robert Love, Linux Kernel Development*

---

## 📦 1. Demystifying Containers: The Three Kernel Pillars

In Docker or Kubernetes, developers interact with high-level container abstractions. At the Linux kernel layer, every container is fundamentally a standard `task_struct` process initialized with specific isolation flags.

```text
===================================================================================================
                               WHAT IS A CONTAINER IN LINUX?
===================================================================================================

                        ┌────────────────────────────────────────┐
                        │      Standard Linux Process (PID)      │
                        └───────────────────┬────────────────────┘
                                            │
         ┌──────────────────────────────────┼──────────────────────────────────┐
         ▼                                  ▼                                  ▼
  [ Linux Namespaces ]             [ Control Groups (cgroups) ]        [ chroot / pivot_root ]
  "What can I SEE?"                "How much can I USE?"               "Where is my ROOT?"
  - Isolated PIDs (PID 1)          - Limits CPU time (quota/period)    - Jails process inside
  - Isolated Network stack         - Limits Memory (OOM triggers)      - container image rootfs
  - Isolated Mount points          - Limits Disk I/O & IOPS            - Hides host filesystem
  - Isolated UIDs/GIDs             - Limits Process count (pids.max)
```

## 🌐 2. The Eight Linux Namespaces

A **Namespace** wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they possess their own isolated instance of that resource.

| Namespace | Flag | Isolated Resource | Real-World Container Behavior |
| :--- | :--- | :--- | :--- |
| **`PID`** | `CLONE_NEWPID` | Process IDs | The container's main process becomes PID 1 inside the namespace, while having a normal PID (e.g., 28412) on the host. |
| **`NET`** | `CLONE_NEWNET` | Network devices, IP routing, firewall | Container gets its own private `eth0`, loopback, routing table, and independent port range (e.g., port 80). |
| **`MNT`** | `CLONE_NEWNS` | Filesystem mount points | Mounts and unmounts inside the container do not alter host mount tables. |
| **`IPC`** | `CLONE_NEWIPC` | System V IPC & POSIX message queues | Prevents processes in different containers from communicating via shared memory segments. |
| **`UTS`** | `CLONE_NEWUTS` | Hostname and NIS domain | Container can set its own independent hostname (`web-01`). |
| **`USER`** | `CLONE_NEWUSER` | User and Group IDs | UID 0 (`root`) inside the container maps to unprivileged UID 10001 on the host, preventing root breakout exploits! |
| **`CGROUP`**| `CLONE_NEWCGROUP`| Control group view | Container only observes its own cgroup hierarchy under `/sys/fs/cgroup`. |
| **`TIME`** | `CLONE_NEWTIME` | System monotonic/boot clocks | Container can offset system clock without altering the physical host time. |

### 2.1 The Namespace System Call Trio
1. **`clone(..., flags)`:** Creates a child process directly inside newly allocated namespaces.
2. **`unshare(flags)`:** Detaches the calling process from its current namespaces and moves it into new ones.
3. **`setns(fd, nstype)`:** Attaches the calling process to an existing namespace (e.g., `docker exec` or `nsenter`).

## 📊 3. Control Groups: cgroups v1 vs. cgroups v2

While namespaces control **visibility**, **Control Groups (cgroups)** enforce **resource limitations, prioritization, and accounting**.

```text
===================================================================================================
                             cgroups v1 VS. cgroups v2 ARCHITECTURE
===================================================================================================

 [ cgroups v1: Fragmented Multi-Hierarchy ]
 /sys/fs/cgroup/
 ├── cpu/            ──► Hierarchy A (Process 100 in Group X)
 ├── memory/         ──► Hierarchy B (Process 100 in Group Y)  <-- Race conditions! Memory controller
 └── blkio/          ──► Hierarchy C                           cannot coordinate with block I/O!

 [ cgroups v2: Unified Single-Hierarchy Tree ]
 /sys/fs/cgroup/
 └── production/
     ├── cgroup.controllers: "cpu memory io pids"
     ├── cpu.max: "200000 100000" (2 vCPUs)
     ├── memory.max: "2147483648"  (2 GB hard limit)
     ├── memory.high: "1825361100" (Throttling / Reclaim threshold)
     └── web_app/ (Leaf group holding PIDs)
```

### 3.1 Kernel Enforcement: Memory Limits & OOM Killer
Under cgroups v2:
- **`memory.high`:** A soft throttle boundary. When breached, the kernel slows down the process and executes aggressive asynchronous page cache reclamation.
- **`memory.max`:** The absolute hard limit. If anonymous memory exceeds this limit and no pages can be reclaimed:
  1. The kernel pauses the allocating thread.
  2. Invokes the **Memcg OOM Killer**.
  3. Selects the process with the highest `oom_score` within that specific cgroup and terminates it with `SIGKILL`.
  4. The rest of the host operating system remains completely unaffected!

## ⚡ 4. Extended Berkeley Packet Filter (eBPF)

**eBPF** is a revolutionary kernel subsystem that allows engineers to execute custom, sandboxed bytecode directly inside the Linux kernel at runtime without compiling kernel modules or modifying kernel source code.

```text
===================================================================================================
                                      eBPF SYSTEM ARCHITECTURE
===================================================================================================

  User Space
  ┌────────────────────────────────────────────────────────┐
  │ C / Rust Source Code ──► LLVM / Clang ──► eBPF Bytecode │
  └───────────────────────────┬────────────────────────────┘
                              │
                              ▼ Syscall: bpf(BPF_PROG_LOAD)
  Kernel Space (Ring 0)
  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │  1. In-Kernel Verifier                                                                      │
  │     - Proves mathematically that program halts (no infinite loops)                          │
  │     - Validates memory safety (no out-of-bounds pointer dereferences)                       │
  │     - Ensures program cannot crash the kernel or corrupt kernel memory                      │
  │                                                                                             │
  │  2. JIT (Just-In-Time) Compiler                                                             │
  │     - Compiles safe eBPF bytecode into native x86_64 / ARM machine code                     │
  │                                                                                             │
  │  3. Attach to Kernel Hook:                                                                  │
  │     - XDP / tc: Process raw network packets at wire-speed before TCP stack                  │
  │     - kprobes / tracepoints: Intercept any Linux kernel function call (sys_execve)          │
  │     - sock_ops: Intercept socket operations (replaces kube-proxy iptables)                  │
  │                                                                                             │
  │  4. BPF Maps (Shared State with User Space):                                                │
  │     - Hash tables, Ring buffers, Arrays accessible by both Kernel and User Space            │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Minimal eBPF Tracing Program in C
```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

// Hook onto the sys_enter_execve tracepoint
SEC("tracepoint/syscalls/sys_enter_execve")
int trace_execve(struct trace_event_raw_sys_enter *ctx) {
    char comm[16];
    bpf_get_current_comm(&comm, sizeof(comm));
    
    // Prints message directly to /sys/kernel/debug/tracing/trace_pipe
    bpf_printk("Process spawned: %s\n", comm);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

### 4.2 Why eBPF is Transforming Systems Engineering
1. **Zero-Overhead Networking (Cilium):** Replaces 10,000 slow `iptables` linear netfilter rules with $\mathcal{O}(1)$ BPF hash maps, enabling sub-microsecond service load-balancing.
2. **Kernel Security (Tetragon / Falco):** Detects privilege escalations, unauthorized root shell spawns, and namespace breakouts directly at the system call gate before the syscall completes.
3. **Observability (bcc / bpftrace):** Measures disk I/O latency distributions, scheduler queue run-delays, and memory allocation bottlenecks in production without impacting application latency.
