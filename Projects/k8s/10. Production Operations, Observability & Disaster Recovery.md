## 🚨 2. The Golden Signals for Production Cluster Health

| Component | Metric Name | Warning Threshold | Operational Meaning |
| :--- | :--- | :--- | :--- |
| **API Server** | `apiserver_request_duration_seconds` | $> 1.0\text{s}$ for `LIST` requests | API server saturated; etcd slow; controllers thrashing. |
| **etcd** | `etcd_disk_backend_commit_duration_seconds` | $> 25\text{ms}$ (99th percentile) | Disk I/O too slow for Raft heartbeats; risk of leader loss! |
| **Kubelet** | `container_cpu_cfs_throttled_periods_total` | $> 20\%$ of total periods | CPU limits set too low; latency spikes in request threads. |
| **Pods** | `kube_pod_container_status_restarts_total` | Rate $> 0.1 / \text{min}$ | CrashLoopBackOff; memory leaks; failing readiness probes. |
| **Storage** | `kubelet_volume_stats_used_bytes / capacity` | $> 85\%$ capacity | PersistentVolume filling up; risk of read-only disk lock. |

## 💾 3. etcd Disaster Recovery: Backup & Restore Runbook

`etcd` is the single source of truth for the entire cluster. If `etcd` loses quorum or suffers disk corruption, all cluster state is lost.

```text
===================================================================================================
                                   etcd DISASTER RECOVERY FLOW
===================================================================================================

  1. Active Control Plane            2. Take Atomic Snapshot              3. Disaster: Quorum Lost
  ┌─────────────────────┐            ┌─────────────────────┐              ┌─────────────────────┐
  │   kube-apiserver    │            │ etcdctl snapshot    │              │  etcd database      │
  │   (Active writes)   │            │ save /backup.db     │              │  corrupted / wiped  │
  └──────────┬──────────┘            └──────────┬──────────┘              └──────────┬──────────┘
             │                                  │                                    │
             ▼                                  ▼                                    ▼
  ┌─────────────────────┐            ┌─────────────────────┐              ┌─────────────────────┐
  │     etcd Leader     │            │ Verified Snapshot   │              │ Stop all Apiservers │
  │   (Port 2379 mTLS)  │            │ (sha256 checked)    │              │ Restore from Backup │
  └─────────────────────┘            └─────────────────────┘              └─────────────────────┘
```

### Production Backup Command
```bash
# Automated cron job on control plane
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/backups/etcd/etcd-snapshot-$(date +%Y%m%d_%H%M%S).db

# Verify snapshot integrity immediately
ETCDCTL_API=3 etcdctl snapshot status /var/backups/etcd/etcd-snapshot-latest.db -w table
```

### Restore Runbook (Restoring Quorum on Control Plane)
1. **Stop all `kube-apiserver` instances** (move `/etc/kubernetes/manifests/kube-apiserver.yaml` out of the directory so kubelet stops the static pod).
2. **Stop running `etcd` instance**.
3. **Execute Restore:**
```bash
ETCDCTL_API=3 etcdctl snapshot restore /var/backups/etcd/etcd-snapshot-latest.db \
  --data-dir=/var/lib/etcd-restored \
  --name=master-01 \
  --initial-cluster=master-01=https://192.168.1.10:2380 \
  --initial-cluster-token=etcd-cluster-restore \
  --initial-advertise-peer-urls=https://192.168.1.10:2380
```
4. Update `/etc/kubernetes/manifests/etcd.yaml` volume mount hostPath to point to `/var/lib/etcd-restored`.
5. Restart `kube-apiserver`. Verify cluster health with `kubectl get nodes`.

## 🔄 4. The GitOps Operating Model: ArgoCD & Reconciliation

Manual cluster modifications via `kubectl apply` lead to configuration drift and tribal knowledge. Under the **GitOps** model:
- **Git** is the sole Source of Truth (SSOT).
- Changes enter via Pull Requests and automated CI checks.
- A cluster-internal controller (ArgoCD or Flux) continuously reconciles cluster state against Git.

```text
===================================================================================================
                                      GITOPS CONTROL LOOP
===================================================================================================

  Developer ──► git push ──► Git Repository (SSOT)
                                    │
                                    │ (Continuous Polling / Webhook)
                                    ▼
                         ┌────────────────────┐
                         │   ArgoCD Engine    │
                         └─────────┬──────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
   Calculates Diff: Git vs. etcd            Auto-Sync & Self-Healing
   - Git: replicas = 5                      - Applies diff via dynamic client
   - Cluster: replicas = 3                  - Corrects manual out-of-band edits!
```

## ⬆️ 5. Zero-Downtime Node Draining & Cluster Upgrades

When upgrading Kubernetes versions or replacing worker instances for AMI updates, you must execute a controlled eviction cycle:

```bash
# Step 1: Cordon node (mark Unschedulable)
kubectl cordon worker-node-04

# Step 2: Gracefully drain pods while respecting PodDisruptionBudgets (PDBs)
kubectl drain worker-node-04 \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --force \
  --grace-period=60 \
  --timeout=5m

# Step 3: Upgrade kubeadm, kubelet, and containerd on the node
apt-get update && apt-get install -y kubeadm=1.31.0-00 kubelet=1.31.0-00
systemctl daemon-reload && systemctl restart kubelet

# Step 4: Uncordon node to re-enable scheduling
kubectl uncordon worker-node-04
```
