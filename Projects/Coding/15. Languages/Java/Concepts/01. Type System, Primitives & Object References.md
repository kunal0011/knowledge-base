# Java Concepts: Type System, Primitives & Object References

**Foundational Texts:**  
- *OCP Oracle Certified Professional Java SE 17 Developer Study Guide* by Jeanne Boyarsky & Scott Selikoff, Chapter 1  
- *Effective Java (3rd Ed.)* by Joshua Bloch, Item 61: Prefer primitive types to boxed primitives

## 1. Theoretical Motivation: The Dual Type System

Java features a hybrid type system consisting of two distinct categories:
1. **Primitive Types:** Eight foundational building blocks that store raw values directly on the thread execution stack without object overhead.
2. **Reference Types:** Class instances, arrays, and interfaces allocated on the JVM heap, accessed via 32-bit or 64-bit reference pointers.

```
+----------------------------------------------------------------------------------+
|                               JAVA TYPE HIERARCHY                                |
+----------------------------------------+-----------------------------------------+
| Primitive Types (Stack Allocated)      | Reference Types (Heap Allocated)        |
+-------------------+--------------------+--------------------+--------------------+
| Type              | Size / Range       | Type               | Description        |
+-------------------+--------------------+--------------------+--------------------+
| boolean           | JVM dependent (1B) | Object             | Root class         |
| byte              | 8 bits (-128..127) | Arrays (int[], etc)| Contiguous heap    |
| short             | 16 bits (-32k..32k)| Classes (String)   | User/Standard types|
| char              | 16 bits (Unicode)  | Records            | Immutable data     |
| int               | 32 bits (2's comp) | Interfaces         | Contract types     |
| long              | 64 bits            | Enums              | Type-safe constants|
| float             | 32 bits (IEEE 754) |                    |                    |
| double            | 64 bits (IEEE 754) |                    |                    |
+-------------------+--------------------+--------------------+--------------------+
```

## 2. Underlying Architecture: Memory Footprint & Bytecode

### 2.1 Stack Allocation vs. Heap Object Overhead
When you declare an `int`, it consumes exactly 4 bytes of memory inside the thread's Local Variable Table (LVT). In contrast, an `Integer` object introduces substantial HotSpot overhead:

```
Primitive int x = 42 (4 bytes):
+-------------------------------+
| 0x0000002A (Raw 32-bit value) |
+-------------------------------+

Boxed Integer obj = 42 (16 to 24 bytes):
Thread Stack Frame:
+-------------------------------+
| Pointer (4 bytes / 8 bytes)   |---------+
+-------------------------------+         |
                                          v
Heap Memory:
+---------------------------------------------------------------+
| Mark Word (64-bit / 8 bytes): Lock flags, age, hash code      |
| Klass Pointer (32-bit / 4 bytes with Compressed OOPs)         |
| int value field (4 bytes): 42                                 |
| Padding (4 bytes): Aligns object to 8-byte boundary           |
+---------------------------------------------------------------+
Total: 20-24 bytes on the heap + 4 bytes pointer = ~24 bytes (6x memory bloat!)
```

### 2.2 Bytecode Generation for Autoboxing
Autoboxing is syntactic sugar introduced in Java 5. The compiler inserts explicit calls to `.valueOf()` and `.intValue()`:
```java
// Source:
Integer a = 100;
int b = a;

// Compiled Bytecode:
0: bipush        100
2: invokestatic  #7 // Method java/lang/Integer.valueOf:(I)Ljava/lang/Integer;
5: astore_1
6: aload_1
7: invokevirtual #13 // Method java/lang/Integer.intValue:()I
10: istore_2
```

## 3. The Wrapper Cache Architecture

To alleviate the heap allocation penalty of frequent boxing, the JVM caches instances of wrapper types during startup:

```
IntegerCache Architecture (java.lang.Integer):
Range: [-128, 127]
Array: static final Integer cache[] = new Integer[-(-128) + 127 + 1]; // 256 instances
```

```java
Integer x = 127;
Integer y = 127;
System.out.println(x == y); // true (Points to identical pre-allocated instance in cache!)

Integer a = 128;
Integer b = 128;
System.out.println(a == b); // false (Separate heap allocations!)
System.out.println(a.equals(b)); // true (Value comparison)
```

| Wrapper Type | Cached Range | Configurable? |
|:---|:---|:---|
| **`Integer`** | `-128` to `127` | Yes via `-XX:AutoBoxCacheMax=<size>` |
| **`Byte`, `Short`, `Long`** | `-128` to `127` | Fixed |
| **`Character`** | `0` to `127` (`\u0000` to `\u007F`) | Fixed |
| **`Boolean`** | `Boolean.TRUE`, `Boolean.FALSE` | Fixed |

## 4. Modern Java: Type Inference & Pattern Matching

### 4.1 Local Variable Type Inference with `var` (Java 10+)
`var` allows the compiler to infer the static type of a local variable from its initializer expression:

```java
// Reduces boilerplate without sacrificing static type safety:
var map = new HashMap<String, List<Integer>>();
var list = List.of("apple", "banana");

// Legal: For-loop index and try-with-resources:
for (var item : list) { ... }
try (var in = new FileInputStream("file.txt")) { ... }
```

**Where `var` CANNOT Be Used (OCP Exam Rules):**
1. Class instance or static fields: `private var x = 10;` (ILLEGAL!)
2. Method parameters or return types: `public var process(var x) { ... }` (ILLEGAL!)
3. Variable declarations without initializers: `var count;` (ILLEGAL!)
4. Initialized to `null`: `var obj = null;` (ILLEGAL! Cannot infer type)

### 4.2 Pattern Matching for `instanceof` (Java 16+)
Eliminates redundant casting boilerplate:
```java
// Pre-Java 16:
if (obj instanceof String) {
    String s = (String) obj; // Redundant cast
    System.out.println(s.toLowerCase());
}

// Java 16+ Pattern Matching:
if (obj instanceof String s && !s.isEmpty()) {
    System.out.println(s.toLowerCase()); // 's' in scope automatically!
}
```

### 4.3 Pattern Matching for `switch` (Java 17/21)
```java
static String formatValue(Object obj) {
    return switch (obj) {
        case Integer i -> String.format("Integer: %d", i);
        case Long l    -> String.format("Long: %d", l);
        case Double d  -> String.format("Double: %.2f", d);
        case String s when s.length() > 5 -> "Long string: " + s;
        case String s  -> "Short string: " + s;
        case null      -> "Null reference!";
        default        -> obj.toString();
    };
}
```

## 5. Authoritative Gotchas & Traps (Bloch & OCP)

### 5.1 Joshua Bloch's Item 61: The Unintentional Boxing Storm
```java
// DISASTROUS ANTI-PATTERN:
Long sum = 0L; // Notice 'Long' (Boxed Object) instead of 'long' (Primitive)!
for (long i = 0; i <= Integer.MAX_VALUE; i++) {
    sum += i; // Constructs 2.14 BILLION Long instances on the heap!
}
```
**The Consequence:** Because `sum` is an object, `sum += i` unboxes `sum`, adds `i`, and boxes the result back into a newly allocated `Long` on every iteration. This runs **$6\times \text{ to } 10\times$ slower** and triggers intense Garbage Collection pause storms.  
**Rule:** Always declare loop accumulators as primitive types (`long`, `int`).

### 5.2 The `NullPointerException` Unboxing Trap
```java
Integer count = null;
// ... later in code ...
if (count == 0) { // Throws java.lang.NullPointerException!
    ...
}
```
**Why it happens:** When comparing an object wrapper with a primitive, Java automatically unboxes the wrapper by calling `count.intValue()`. Calling a method on a `null` reference results in an immediate NPE.

### 5.3 Widening vs. Autoboxing Precedence (OCP Trap)
The compiler prefers **widening** over **boxing**, and **boxing** over **varargs**:
```java
static void test(long x)    { System.out.println("Widened to long"); }
static void test(Integer x) { System.out.println("Boxed to Integer"); }

int val = 5;
test(val); // Prints: "Widened to long"! (Widening beats Autoboxing)
```
> [!WARNING]
> Java **will not perform widening and then boxing simultaneously** (e.g., an `int` will not automatically box into a `Long`).

## 6. Actionable Summary Checklist

- [x] Prefer primitive types (`int`, `long`, `double`) to boxed wrappers (`Integer`, `Long`) in all algorithmic and compute-heavy code (Effective Java Item 61).
- [x] Always use `.equals()` to compare wrapper objects; `==` only works reliably within the cached range `[-128, 127]`.
- [x] Guard against unboxing `null` wrapper instances to prevent silent `NullPointerException` crashes.
- [x] Use `var` for local variables with obvious RHS types to improve readability without compromising compile-time safety.
- [x] Utilize pattern matching for `instanceof` and `switch` (Java 17/21) to eliminate boilerplate casting.
