# Chapter 01: Databricks Architecture, Control Plane & Data Plane

> "Enterprise data architecture must satisfy a fundamental security paradox: users demand centralized, collaborative SaaS software, but enterprise infosec demands that raw data never leave the customer's private virtual network. Databricks resolves this through the decoupled Control Plane and Customer Data Plane model."

## 1. Canonical Motivation & Theoretical Foundation

### The Origins of Databricks
In 2013, the creators of Apache Spark at UC Berkeley's AMPLab (Matei Zaharia, Ali Ghodsi, Reynold Xin, Patrick Wendell, Ion Stoica, Scott Shenker, and Andy Konwinski) founded **Databricks**. 

Their primary objective was to overcome the severe operational friction of enterprise big data:
- Managing on-premises Hadoop/YARN clusters required dedicated systems operations teams.
- Deploying Spark in the cloud involved manual EC2 cluster provisioning, fragile driver-worker networking, slow initialization, and fragmented governance.
- Data teams were siloed: data engineers used Spark on CLI, analysts used SQL warehouses, and data scientists trained models in local Python environments.

**The Solution:** A unified cloud-native platform providing managed Spark runtimes, ACID storage (Delta Lake), centralized governance (Unity Catalog), and high-performance vectorized query execution (Photon).

### Classic Compute vs. Serverless Compute Architecture

```
┌────────────────────────────────────────────────────────────────────────────────┐

│    • Virtual machines (e.g. AWS EC2, Azure VMs) run in the customer's VPC.     │
│    • Startup time: 3 to 7 minutes (Cloud VM provisioning + DBR initialization).│
│    • Customer pays cloud provider for VMs + Databricks DBUs.                   │
├────────────────────────────────────────────────────────────────────────────────┤
│ 2. Serverless Compute (Databricks-Managed Hardened Data Plane)                 │
│    • Compute instances run in a secure, containerized Databricks environment.  │
│    • Warm Instant Pool Startup: < 5 seconds!                                   │
│    • Zero idle cluster costs: Scales to 0 instantly when queries complete.    │
│    • Connects back to customer storage via Cloud Private Link / VPC Peering.   │
└────────────────────────────────────────────────────────────────────────────────┘
```

### Cluster Topologies: All-Purpose vs. Job vs. SQL Warehouses

| Cluster Type | Lifecycle Model | Workload Focus | Relative Cost (DBUs) |
| :--- | :--- | :--- | :--- |
| **All-Purpose Cluster** | Long-running, multi-user, manual termination | Ad-hoc data science, interactive notebooks | **High (Standard DBU rate)** |
| **Job Cluster** | Ephemeral: Spun up for task, terminated on finish | Scheduled production ETL, automated pipelines| **Low (~50% cheaper than All-Purpose)**|
| **SQL Warehouse** | Serverless / Pro: Instant multi-cluster scaling| BI dashboards, SQL analytics, Trino-style OLAP| **Tuned for SQL throughput** |

### The Photon Execution Engine Architecture
Traditionally, Apache Spark executes SQL and DataFrame queries via the **Tungsten Engine**, compiling query expressions into Java bytecode via Whole-Stage Code Generation (WSCG). 

**Photon** replaces Tungsten's physical execution tier with a **100% native C++ vectorized execution engine**:

```
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │ PHOTON C++ VECTORIZED CORE                                                  │
 │                                                                             │
 │  Spark Catalyst Logical Plan ──► Physical Plan ──► Photon Native Operators  │
 │                                                                             │
 │  • Vectorized Batch Processing: Processes batches of 2,048 tuples in        │
 │    continuous CPU cache (L1/L2), utilizing modern SIMD registers (AVX-512). │
 │  • Native Memory Management: Direct off-heap allocation with zero JVM       │
 │    Garbage Collection pauses.                                               │
 │  • Seamless Fallback: Non-supported operations (e.g. legacy Python UDFs)    │
 │    gracefully fall back to JVM Tungsten without failing the query.          │
 └─────────────────────────────────────────────────────────────────────────────┘
```

## 3. Core API Mechanics & Modern Idiomatic Patterns

### Cluster Sizing & Autoscaling Mechanics
Databricks implements **Optimized Autoscaling**:
- Analyzes Spark shuffle file metrics and task queue backlog rather than raw CPU utilization.
- Scales up aggressively when tasks queue up.
- Scales down conservatively: avoids terminating nodes holding active shuffle files, preventing task re-computation.

## 4. Practical Systems & Production Engineering Trade-offs

### The All-Purpose vs. Job Cluster Anti-Pattern
- **The Anti-Pattern:** Scheduling automated production ETL jobs to run on persistent All-Purpose clusters.
- **Financial Consequence:** All-Purpose compute carries a **$2\times - 3\times$ markup in Databricks Unit (DBU) pricing** compared to Job compute. Leaving an All-Purpose cluster idle or running nightly jobs wastes tens of thousands of dollars annually.
- **Invariant:** Production workflows must **always run on ephemeral Job Clusters or Serverless Jobs**.

## 5. Annotated Production Implementations

### 1. Terraform: Provisioning Databricks Workspace & Production Photon Job Cluster
Demonstrates provisioning a production-grade Databricks job cluster with Photon enabled, spot instances, and auto-termination guardrails.

```hcl
# databricks_cluster.tf
terraform {
  required_providers {
    databricks = {
      source  = "databricks/databricks"
      version = "~> 1.30.0"
    }
  }
}

# Fetch latest Long-Term Support (LTS) Databricks Runtime with Photon
data "databricks_spark_version" "latest_lts_photon" {
  long_term_support = true
  photon            = true
}

# Fetch optimal memory-optimized AWS instance type
data "databricks_node_type" "worker_node" {
  min_memory_gb = 32
  min_cores     = 8
  category      = "Memory Optimized"
}

# Production Job Cluster Definition
resource "databricks_cluster" "production_etl_cluster" {
  cluster_name           = "prod-photon-etl-worker"
  spark_version          = data.databricks_spark_version.latest_lts_photon.id
  node_type_id           = data.databricks_node_type.worker_node.id
  driver_node_type_id    = data.databricks_node_type.worker_node.id
  runtime_engine         = "PHOTON"

  # Cost Optimization: Use AWS Spot instances for workers, On-Demand for driver
  aws_attributes {
    first_on_demand    = 1
    availability       = "SPOT_WITH_FALLBACK"
    spot_bid_price_percent = 100
  }

  # Dynamic Autoscaling: 2 to 10 nodes
  autoscale {
    min_workers = 2
    max_workers = 10
  }

  # Safety Guardrail: Auto-terminate after 20 minutes of inactivity
  autotermination_minutes = 20

  spark_conf = {
    "spark.databricks.delta.preview.enabled" = "true"
    "spark.sql.shuffle.partitions"          = "auto"
  }
}
```

### 2. Python: Interacting Programmatically with Databricks SDK
Demonstrates programmatic cluster inspection, trigger execution, and monitoring using the official `databricks-sdk`.

```python
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import compute

# Initialize client using environment variables (DATABRICKS_HOST, DATABRICKS_TOKEN)
w = WorkspaceClient()

# List all active clusters and inspect runtime engines
print("Querying active Databricks clusters...")
for cluster in w.clusters.list():
    state = cluster.state.value
    photon_status = "ENABLED" if cluster.runtime_engine == compute.RuntimeEngine.PHOTON else "DISABLED"
    print(f"Cluster: {cluster.cluster_name} | ID: {cluster.cluster_id} | State: {state} | Photon: {photon_status}")

# Trigger an on-demand Serverless Job
def trigger_serverless_pipeline(job_id: int):
    print(f"Triggering Serverless Job ID: {job_id}...")
    run = w.jobs.run_now(job_id=job_id)
    print(f"Job launched successfully. Run ID: {run.run_id}")
    return run.run_id

if __name__ == "__main__":
    # Example cluster inspection
    pass
```

## 6. Authoritative Gotchas, Pitfalls & Performance Anti-Patterns

### 1. Driver Out-of-Memory (OOM) on `.collect()`
- **The Pitfall:** Calling `df.collect()` or `df.toPandas()` in a notebook on a 20-million-row DataFrame.
- **Failure Mode:** While worker nodes process partitions in parallel, `.collect()` pulls all distributed partitions across the network into the **single Driver node's JVM heap memory**. The driver runs out of memory, throwing `java.lang.OutOfMemoryError: Java heap space`, crashing the entire cluster and terminating all concurrent users' work.
- **Rule:** Never call `.collect()` or `.toPandas()` on unbounded datasets. Use `.take(100)`, `.limit(100).toPandas()`, or write directly to Delta tables via `.write.saveAsTable()`.

### 2. Single-Node Cluster Anti-Pattern in Production
- **The Pitfall:** Selecting "Single Node" cluster mode for an ETL job to save costs.
- **Failure Mode:** Single-node clusters disable distributed execution; all Spark executors run within the single driver VM. If data volume surges from 5GB to 50GB, the job stalls with disk spilling or crashes, defeating the purpose of distributed computing.
- **Rule:** Use Single-Node clusters exclusively for small Python development; use multi-node autoscaling clusters for all data processing.

### 3. Outage Triage: The "Spot Node Eviction Storm"
- **Symptom:** Long-running Spark jobs fail with `SparkException: Job aborted due to stage failure: ShuffleMapStage failed`.
- **Root Cause:** A batch cluster was configured with $100\%$ Spot instances. AWS/Azure reclaimed the spot instances simultaneously during peak cloud demand, killing multiple workers and destroying intermediate shuffle blocks.
- **Resolution:** Configure `availability = "SPOT_WITH_FALLBACK"` and ensure the **Driver Node is always an On-Demand instance** (`first_on_demand = 1`).
