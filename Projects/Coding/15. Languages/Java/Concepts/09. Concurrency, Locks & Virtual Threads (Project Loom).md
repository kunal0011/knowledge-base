## 1. Theoretical Motivation: Platform Threads vs. Virtual Threads

Historically, every Java `Thread` was a thin 1-to-1 wrapper around an **Operating System (OS) kernel platform thread**.

```
Platform Thread Model (1-to-1):
Java Thread 1 --------> OS Platform Thread 1 (Kernel scheduled)
Java Thread 2 --------> OS Platform Thread 2 (Consumes ~1 MB RAM Stack!)
...
Java Thread 5000 -----> OS Thread Exhaustion! OutOfMemoryError / Thrashing.
```

### The Platform Thread Bottleneck:
- **Memory Footprint:** Each platform thread reserves $1\text{ MB}$ of memory for its thread stack, capping JVM capacity at a few thousand threads.
- **Context-Switch Latency:** Switching between OS threads requires kernel privilege context-switching and CPU cache invalidations ($1\text{ to }10\ \mu\text{s}$).
- **Thread-Per-Request Limits:** High-concurrency servers (handling $100,000$ concurrent WebSockets or HTTP connections) were forced into complex reactive frameworks (Netty, WebFlux) because threads were too expensive to block.

## 2. Project Loom: Virtual Threads (Java 21 JEP 444)

Java 21 introduces **Virtual Threads**—lightweight user-mode threads managed directly by the JVM runtime rather than the operating system.

```
Virtual Thread Architecture (M-to-N Scheduling):
[ Virtual Thread 1 ] [ Virtual Thread 2 ] ... [ Virtual Thread 1,000,000 ]
         \                  |                  /
          v                 v                 v
           [ Carrier Thread Pool: ForkJoinPool (N CPU Cores) ]
                                |
                                v
               [ OS Kernel Platform Threads (Few) ]
```

### 2.1 The Continuation & Unmounting Mechanism
When a Virtual Thread executes a blocking operation (e.g., `Socket.read()`, `Thread.sleep()`, database query):
1. The JVM **unmounts** the virtual thread from its underlying OS Carrier Thread.
2. The virtual thread's stack frames are saved as a lightweight `Continuation` object on the JVM heap ($\approx 200\text{ to }400\text{ bytes}$).
3. The Carrier Thread is immediately free to execute other runnable virtual threads!
4. When the I/O event completes, the JVM re-mounts the virtual thread onto an available carrier thread to resume execution seamlessly.

### 2.2 Writing Million-Thread Code:
```java
// Spawn 100,000 concurrent threads with zero thread pool configuration!
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i -> {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // Unmounts carrier thread!
            return i;
        });
    });
} // Executor automatically waits for all 100,000 tasks to complete!
```

## 3. Explicit Synchronization: `ReentrantLock` & Condition Variables

While `synchronized` provides basic monitor locks, `java.util.concurrent.locks.ReentrantLock` offers advanced capabilities:
1. Timed lock acquisition (`tryLock(timeout, unit)`).
2. Interruptible lock acquisition (`lockInterruptibly()`).
3. Multiple condition variables (`Condition`).
4. Fairness policies.

```java
public class BoundedBuffer<T> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    private final Object[] items = new Object[100];
    private int putptr, takeptr, count;

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await(); // Releases lock and suspends thread
            }
            items[putptr] = x;
            if (++putptr == items.length) putptr = 0;
            count++;
            notEmpty.signal(); // Wakes up a waiting consumer
        } finally {
            lock.unlock(); // Always unlock in finally!
        }
    }
}
```

## 4. Lock-Free Concurrency & Atomics

To eliminate lock contention completely, Java provides atomic variables using CPU-level **Compare-And-Swap (CAS)** instructions (`CMPXCHG`):

```java
// Lock-free accumulator using CAS:
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet(); // CPU atomic instruction
```

### High-Throughput Contention: `LongAdder`
Under extreme concurrent write contention (e.g., thousands of threads incrementing a metrics counter), `AtomicLong` spins heavily on CAS retries.
`java.util.concurrent.atomic.LongAdder` divides the counter into **striped cells across CPU cache lines**:
```java
LongAdder adder = new LongAdder();
adder.increment(); // Distributes writes across cells, eliminating cache line contention!
long total = adder.sum(); // Gathers sum across all cells
```

## 5. Thread Coordination Primitives Matrix

| Coordination Class | Mechanism | Primary Systems Use Case |
|:---|:---|:---|
| **`CountDownLatch`** | One-way gate that trips when count reaches 0 | Waiting for $N$ worker threads to finish initialization |
| **`CyclicBarrier`** | Reusable rendezvous point where $N$ threads wait | Multi-phase parallel simulation / matrix multiplication |
| **`Semaphore`** | Manages a fixed set of permits | Rate limiting access to physical hardware or connection pools |
| **`StampedLock`** | Read/write lock supporting **optimistic reads** | High-read caches with zero lock acquisition overhead |

## 6. Authoritative Gotchas & Traps (Bloch & OCP)

### 6.1 Virtual Thread Pinning (The JEP 444 Trap)
A Virtual Thread is **pinned** to its OS carrier thread if it blocks while inside:
1. A **`synchronized`** block or method.
2. A native method call (JNI).

When pinned, the carrier thread is blocked and cannot execute other virtual threads, collapsing scalability!  
**The Fix:** Replace `synchronized` blocks in I/O-heavy paths with **`ReentrantLock`**, which supports proper unmounting.

### 6.2 Joshua Bloch's Item 78: Visibility vs. Atomicity
```java
// BROKEN: Stop request is never seen by worker thread!
public class StopThread {
    private static boolean stopRequested; // Not volatile!

    public static void main(String[] args) throws InterruptedException {
        Thread background = new Thread(() -> {
            int i = 0;
            while (!stopRequested) i++; // JIT hoists: if (!stopRequested) while(true) i++;
        });
        background.start();
        Thread.sleep(1000);
        stopRequested = true; // Worker thread NEVER stops!
    }
}
```
**Why it fails:** Without `volatile` or synchronization, the JIT compiler is legally permitted to hoist the loop condition into an infinite loop, reading stale CPU register cache values.  
**Rule:** Declare `private static volatile boolean stopRequested;`.

## 7. Actionable Summary Checklist

- [x] Use **Virtual Threads** (`Executors.newVirtualThreadPerTaskExecutor()`) in Java 21 for I/O-bound server workloads to handle millions of concurrent tasks.
- [x] Avoid using `synchronized` inside virtual thread tasks to prevent **carrier thread pinning**; use `ReentrantLock` instead.
- [x] Always unlock `ReentrantLock` inside a **`finally` block** immediately following `lock()`.
- [x] Use `LongAdder` instead of `AtomicLong` for high-concurrency metric counters to eliminate CAS cache-line contention.
- [x] Ensure that shared mutable variables are either `volatile`, protected by atomic classes, or guarded by locks to guarantee JMM visibility (Effective Java Item 78).
